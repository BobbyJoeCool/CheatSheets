Swarm Mode

Swarm mode is Docker's built-in orchestrator: it joins several Docker hosts into one cluster and keeps services at the state you declare, rescheduling containers when a node fails. Managers store cluster state with the Raft consensus algorithm and schedule work; workers just run tasks. It ships with Docker Engine, so there's nothing extra to install.

Ports to Open Between Nodes

  • 2377/tcp — cluster management (managers)
  • 7946/tcp+udp — node discovery (gossip)
  • 4789/udp — overlay network traffic (VXLAN)
  • Managers are also workers unless drained

Building a Cluster

# On the first manager
docker swarm init --advertise-addr 10.0.0.10
docker swarm join-token worker          # print the worker join command
docker swarm join-token manager         # …and the manager one

# On each other node (command printed by join-token)
docker swarm join --token SWMTKN-1-<token> 10.0.0.10:2377

# Back on a manager
docker node ls                          # * = the node you're on
docker node promote node2 node3         # 3 managers for HA
docker node update --availability drain node4   # move tasks off
docker node update --availability active node4
docker node update --label-add zone=east node4
docker node inspect node4 --pretty
docker swarm join-token --rotate worker # invalidate leaked tokens
docker swarm leave                      # on a worker; then `node rm` it

Code Explained

--advertise-addr — IP other nodes use to reach this one
drain — no new tasks; existing ones move elsewhere (maintenance)
pause — keep running tasks, schedule nothing new
Node labels drive placement constraints (Sheet 26)
swarm leave --force on the last manager destroys the swarm

⚠ Common Mistakes

  • Running 2 managers — losing either one loses quorum; use an odd number
  • Firewalls blocking 4789/udp or 7946 — services deploy but containers on different nodes can't talk
  • Treating the join token like a config value — anyone with it can join; rotate it if it leaks
  • Taking a node down without draining — tasks restart elsewhere only after it's marked down

✓ Tips & Best Practices

  • Keep managers small and dedicated in production: drain them so they only manage
  • Spread managers across failure zones (racks, availability zones)
  • Back up /var/lib/docker/swarm on a manager to restore the cluster state
  • Need autoscaling, a big ecosystem or managed cloud offerings? Use Kubernetes instead

Quick Summary

  • swarm init / join — create and grow a cluster
  • node promote/demote — manager vs worker
  • node update --availability drain — maintenance
  • odd managers — (N−1)/2 failures tolerated
