Beyond Auto-Generated Migrations

Data migrations change rows rather than schema, for example filling a new column from existing data. Create an empty migration and add RunPython (or RunSQL) with a forward and reverse function. Inside, always load models with apps.get_model() so you get the historical version matching that point in time. Over time, squashmigrations folds long histories into one file.

Notes

  • Historical models have fields but no custom methods
  • Give a reverse function, or RunPython.noop, so rollbacks work
  • Two developers adding 0005_* creates a conflict; fix with --merge
  • atomic = False lets big data migrations commit in batches
  • run_before forces ordering against another app

A Data Migration

# python manage.py makemigrations blog --empty --name fill_slugs
from django.db import migrations
from django.utils.text import slugify

def fill_slugs(apps, schema_editor):
    Post = apps.get_model("blog", "Post")      # historical model
    for post in Post.objects.filter(slug="").iterator():
        post.slug = slugify(post.title)
        post.save(update_fields=["slug"])

def clear_slugs(apps, schema_editor):
    apps.get_model("blog", "Post").objects.update(slug="")

class Migration(migrations.Migration):
    dependencies = [("blog", "0004_post_slug")]
    operations = [
        migrations.RunPython(fill_slugs, clear_slugs),
        migrations.RunSQL("UPDATE blog_post SET status = 'D' WHERE status = '';",
                          reverse_sql=migrations.RunSQL.noop),
    ]

Housekeeping

python manage.py makemigrations --merge        # resolve 0005 conflict
python manage.py squashmigrations blog 0001 0020

Code Explained

apps.get_model() returns the model as of this migration
.iterator() streams rows instead of loading them all
The second function makes the migration reversible
RunSQL runs raw SQL with an optional reverse_sql
Set atomic = False for SQL that can't run in a transaction

⚠ Common Mistakes

  • Importing models directly (from blog.models import Post) in a migration; it breaks once the model changes
  • Calling custom model methods in RunPython; historical models don't have them
  • No reverse function, so migrate blog 0003 fails with IrreversibleError

✓ Tips & Best Practices

  • Process large tables in batches with iterator(chunk_size=2000)
  • Test migrations both ways: migrate then migrate app <previous>
  • Use RunPython.noop when the reverse truly has nothing to undo

Quick Summary

  • --empty: start a data migration
  • RunPython(forward, reverse): data change
  • apps.get_model(): historical model
  • squashmigrations / --merge: housekeeping
