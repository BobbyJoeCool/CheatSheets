Django's Test Runner

Django's test framework builds on unittest. manage.py test finds files named test*.py, creates a separate test database, runs each test inside a transaction and rolls it back afterwards, so tests don't affect each other. Use TestCase for anything touching the database and SimpleTestCase for tests that don't.

Notes

  • Test DB is named test_<name> and destroyed after the run
  • setUpTestData() runs once per class: fast shared fixtures
  • setUp() runs before every test method
  • Use --keepdb to reuse the test database between runs
  • pytest-django is a popular alternative runner

blog/tests.py

from django.test import TestCase, SimpleTestCase
from django.urls import reverse
from .models import Post

class PostModelTests(TestCase):
    @classmethod
    def setUpTestData(cls):                   # once for the class
        cls.post = Post.objects.create(title="Hello World", status="P")

    def test_str(self):
        self.assertEqual(str(self.post), "Hello World")

    def test_published_manager(self):
        Post.objects.create(title="Draft", status="D")
        self.assertQuerySetEqual(Post.objects.published(), [self.post])

    def test_list_view(self):
        resp = self.client.get(reverse("blog:list"))
        self.assertEqual(resp.status_code, 200)
        self.assertContains(resp, "Hello World")
        self.assertTemplateUsed(resp, "blog/post_list.html")

class SlugTests(SimpleTestCase):              # no database
    def test_slugify(self): self.assertEqual(slugify("Hi!"), "hi")

Running

python manage.py test                         # everything
python manage.py test blog.tests.PostModelTests.test_str --keepdb -v 2
coverage run manage.py test && coverage report

⚠ Common Mistakes

  • Creating data in setUp() for every test when setUpTestData would do it once
  • Tests that depend on run order or on each other's data
  • Hitting real external APIs in tests; mock them with unittest.mock.patch

✓ Tips & Best Practices

  • Use factory_boy or model_bakery to create test data quickly
  • Guard performance with assertNumQueries on list views
  • Run tests in CI on every push, with --parallel for speed
