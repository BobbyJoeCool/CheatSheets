ForeignKey Relationships

ForeignKey · on_delete · CASCADE · PROTECT · SET_NULL · related_name · _set reverse access

Many-to-One Links

A ForeignKey creates a many-to-one relationship: many comments belong to one post. The column stores the related row's primary key (post_id). on_delete is required and decides what happens to comments when their post is deleted. Django adds a reverse accessor on the other model, named comment_set by default or whatever related_name says.

Notes

  • Access the object with c.post; the raw id with c.post_id (no query)
  • Refer to models by string ("auth.User") to avoid circular imports
  • Use settings.AUTH_USER_MODEL for links to users
  • An index is created on every ForeignKey column automatically
  • 6.1: DB_CASCADE and friends let the database handle deletes

Defining and Following a ForeignKey

from django.conf import settings
from django.db import models

class Post(models.Model):
    title = models.CharField(max_length=200)

class Comment(models.Model):
    post = models.ForeignKey(Post, on_delete=models.CASCADE,
                             related_name="comments")
    author = models.ForeignKey(settings.AUTH_USER_MODEL,
                               on_delete=models.SET_NULL, null=True)
    category = models.ForeignKey("Category", on_delete=models.PROTECT)
    text = models.TextField()

c = Comment.objects.get(pk=1)
c.post                       # <Post: Hello>   (1 query)
c.post_id                    # 3               (no query)
post = Post.objects.get(pk=3)
post.comments.all()          # reverse: every comment on the post
post.comments.create(text="Nice!", category=cat)
post.delete()                # CASCADE deletes its comments too

Code Explained

related_name="comments" replaces the default comment_set
SET_NULL requires null=True on the field
PROTECT raises ProtectedError if a category is still in use
filter(post__title=...) follows the FK in a lookup (a JOIN)
post.comments.create() sets post for you

⚠ Common Mistakes

  • SET_NULL without null=True: system check error
  • Two FKs to the same model without related_name: reverse accessor clash
  • Looping for c in comments: c.post.title without select_related, which is N+1 queries

✓ Tips & Best Practices

  • Default to PROTECT for lookup tables, CASCADE for owned children
  • Use c.post_id when you only need the id
  • Pick plural related_names that read well: post.comments, user.orders
