Middleware

MIDDLEWARE order · __init__(get_response) · __call__() · process_view() · process_exception() · async middleware

Hooks Around Every Request

Middleware is a chain of callables that wrap every request and response. Requests flow down the MIDDLEWARE list to the view, and responses flow back up in reverse order. Each middleware can inspect or change the request, short-circuit with its own response, or modify the response. Built-in middleware handles security headers, sessions, CSRF, auth and messages.

Notes

  • Order matters: sessions before auth, auth before anything using request.user
  • Returning a response early skips the rest of the chain and the view
  • __init__ runs once at startup, not per request
  • Raise MiddlewareNotUsed in __init__ to disable conditionally
  • Mark sync/async support with sync_capable / async_capable

Writing Middleware

import time, logging
log = logging.getLogger(__name__)

class TimingMiddleware:
    def __init__(self, get_response):          # once, at startup
        self.get_response = get_response

    def __call__(self, request):               # every request
        start = time.perf_counter()
        response = self.get_response(request)  # call next layer / view
        ms = (time.perf_counter() - start) * 1000
        response["Server-Timing"] = f"app;dur={ms:.1f}"
        return response

    def process_view(self, request, view_func, view_args, view_kwargs):
        request.view_name = view_func.__name__ # None = continue

    def process_exception(self, request, exception):
        log.exception("Unhandled error on %s", request.path)
        return None                            # let Django handle it

# settings.py
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    # ... sessions, common, csrf, auth, messages, clickjacking
    "core.middleware.TimingMiddleware",            # yours, last
]

Code Explained

Code before get_response runs on the way in
Code after it runs on the way out
process_view runs just before the view is called
process_exception runs only when the view raises
Returning None from hooks means "carry on"

⚠ Common Mistakes

  • Custom middleware using request.user placed above AuthenticationMiddleware
  • Heavy work in __call__ (DB queries) that slows every single request
  • Storing per-request data on self; one instance is shared by all requests

✓ Tips & Best Practices

  • Attach data to request (request.tenant = ...) for views to use
  • Use a function-based middleware for tiny wrappers
  • Check order with the debug toolbar or by logging in each layer

Quick Summary

  • MIDDLEWARE: ordered list
  • __call__: wrap get_response(request)
  • process_view / process_exception: hooks
  • Down for requests, up for responses
