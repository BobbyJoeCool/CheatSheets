View Mixins & Decorators

LoginRequiredMixin · PermissionRequiredMixin · UserPassesTestMixin · method_decorator · MRO order

Reusing View Behavior

Mixins add behavior to class-based views through multiple inheritance, and decorators wrap function views. Auth mixins check access in dispatch() before the handler runs. Because Python resolves methods left to right (the MRO), access mixins must come before the view class. method_decorator lets you apply any function decorator to a CBV.

Notes

  • Order: class V(LoginRequiredMixin, PermissionRequiredMixin, UpdateView)
  • Anonymous users are redirected to LOGIN_URL with ?next=
  • Logged-in users without permission get a 403
  • Django 5.1+: LoginRequiredMiddleware + @login_not_required makes login the default
  • Write your own mixin when several views share the same override

Mixins and Decorators

from django.contrib.auth.decorators import login_required, permission_required
from django.contrib.auth.mixins import (LoginRequiredMixin,
    PermissionRequiredMixin, UserPassesTestMixin)
from django.utils.decorators import method_decorator
from django.views.decorators.cache import cache_page

class ReportView(LoginRequiredMixin, PermissionRequiredMixin, ListView):
    permission_required = "reports.view_report"
    raise_exception = True                     # 403 instead of redirect

class PostEditView(UserPassesTestMixin, UpdateView):
    model = Post
    def test_func(self):
        return self.get_object().author == self.request.user

@method_decorator(cache_page(60 * 15), name="dispatch")
class HomeView(TemplateView):
    template_name = "home.html"

class OwnerQuerysetMixin:                      # custom mixin
    def get_queryset(self):
        return super().get_queryset().filter(owner=self.request.user)

@login_required
@permission_required("reports.view_report", raise_exception=True)
def report(request): ...

Code Explained

permission_required is "app_label.codename"
raise_exception = True returns 403 even for anonymous users
test_func() returns True to allow access
method_decorator(dec, name="dispatch") covers every method
Custom mixins call super() so they chain with the view

⚠ Common Mistakes

  • Putting LoginRequiredMixin after the view class; the view's dispatch runs first
  • test_func calling get_object() on a CreateView, where there is no object yet
  • Decorating a CBV class directly with @login_required; use method_decorator

✓ Tips & Best Practices

  • Combine mixins into one base class (StaffOnlyMixin) to keep views short
  • Prefer permission checks over is_staff checks for fine-grained access
  • Use LoginRequiredMiddleware for sites where nearly every page needs login

Quick Summary

  • Mixins go left of the view class
  • LoginRequiredMixin: auth gate
  • UserPassesTestMixin.test_func(): custom rule
  • method_decorator: FBV decorator on a CBV
