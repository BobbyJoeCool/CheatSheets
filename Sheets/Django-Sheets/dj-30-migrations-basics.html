Migrations — Basics

makemigrations · migrate · showmigrations · sqlmigrate · migrate app zero · --fake

Version Control for the Schema

Migrations are Python files that record changes to your models so the database schema can follow along. makemigrations compares models to the last migration state and writes a new file; migrate applies unapplied migrations in dependency order and records them in the django_migrations table. Commit migration files to git with the code that needs them.

Notes

  • Each app has its own migrations/ folder, numbered 0001_initial.py, 0002_...
  • Renames are detected interactively ("Did you rename...?")
  • Adding a non-null field to existing rows needs a default
  • Migrations run inside a transaction on PostgreSQL and SQLite
  • Never edit a migration that's already applied elsewhere

Everyday Workflow

python manage.py makemigrations                 # all apps
python manage.py makemigrations blog --name add_status
python manage.py makemigrations --check --dry-run   # CI: fail if missing
python manage.py migrate                        # apply everything
python manage.py migrate blog 0003              # go to a specific state
python manage.py migrate blog zero              # unapply all of blog
python manage.py showmigrations blog            # [X] applied, [ ] not
python manage.py sqlmigrate blog 0004           # print the SQL
python manage.py migrate blog 0004 --fake       # mark applied, no SQL

A Generated Migration

class Migration(migrations.Migration):
    dependencies = [("blog", "0003_post_slug")]
    operations = [
        migrations.AddField(model_name="post", name="status",
            field=models.CharField(default="D", max_length=1)),
    ]

Code Explained

--name gives the file a readable name
--check exits non-zero if models and migrations differ
Migrating to an earlier number runs reverse operations
sqlmigrate is great for reviewing risky changes
--fake only updates django_migrations; use with care

⚠ Common Mistakes

  • Not committing migration files, so teammates generate different ones
  • Deleting migrations to "start fresh" on a database that already applied them
  • Running --fake to silence an error, leaving the schema and history out of sync

✓ Tips & Best Practices

  • Run makemigrations --check in CI to catch forgotten migrations
  • Review sqlmigrate output before deploying changes to large tables
  • Keep schema changes and data changes in separate migrations

Quick Summary

  • makemigrations: models → migration file
  • migrate: file → database
  • showmigrations / sqlmigrate: inspect
  • migrate app zero: roll back an app
