Sheet 61

Caching

CACHES · cache.get() / set() · @cache_page · {% cache %} · per-site cache · Redis backend

Caching at Every Level

Caching stores expensive results so later requests reuse them. Configure a backend in CACHES (Redis and Memcached for production, local memory for development). Then cache at the right granularity: whole views with @cache_page, template fragments with {% cache %}, or any value with the low-level cache API. The per-site cache wraps everything via middleware.

Notes

  • LocMemCache is per-process; it isn't shared between workers
  • Redis backend is built in (4.0+): django.core.cache.backends.redis.RedisCache
  • Timeouts are seconds; None means forever, 0 means don't cache
  • Cache keys vary by URL; use vary_on_cookie for per-user pages
  • Async API: await cache.aget() / aset()

Configuration and APIs

CACHES = {"default": {
    "BACKEND": "django.core.cache.backends.redis.RedisCache",
    "LOCATION": "redis://127.0.0.1:6379/1",
    "TIMEOUT": 300,                                  # default 5 min
}}

from django.core.cache import cache
cache.set("stats", compute_stats(), timeout=600)
cache.get("stats")                                   # value or None
cache.get_or_set("top", lambda: Post.objects.top()[:10], 3600)
cache.add("lock:job", 1, 60)                         # only if missing
cache.incr("hits")                                   # atomic +1
cache.delete("stats"); cache.delete_many(["a", "b"])

from django.views.decorators.cache import cache_page
from django.views.decorators.vary import vary_on_cookie
@cache_page(60 * 15)                                  # whole response
@vary_on_cookie
def dashboard(request): ...
path("about/", cache_page(3600)(TemplateView.as_view(template_name="about.html")))

Template Fragment

{% load cache %}
{% cache 600 sidebar request.user.pk %} ...expensive sidebar... {% endcache %}

Code Explained

get_or_set computes and stores only on a miss
add is a simple lock: fails if the key exists
@cache_page keys on the full URL
vary_on_cookie separates logged-in users
Fragment cache keys include the extra args (user.pk)

⚠ Common Mistakes

  • @cache_page on views that show per-user data without vary_on_cookie
  • Caching a lazy QuerySet object; cache list(qs) or values instead
  • Never invalidating; stale data persists until timeout, delete keys on save

✓ Tips & Best Practices

  • Delete related keys in post_save signals or model save()
  • Prefix keys with a version (KEY_PREFIX, VERSION) to bust everything on deploy
  • Measure first; the slowest thing is often a missing select_related
