Big O Notation

O / Ω / Θ · upper bound · drop constants · dominant term · best / average / worst case · input size n

Measuring How Code Scales

Big O describes how an algorithm's running time (or memory) grows as the input size n grows. It ignores constant factors and small terms, and keeps only the dominant term, because for large n that term is all that matters. It's the shared language for comparing solutions before you write them.

Ground Rules

  • n = input size (array length, node count, string length)
  • Big O is usually quoted for the worst case
  • Drop constants: O(3n) → O(n)
  • Keep the biggest term: O(n² + n) → O(n²)

Counting Steps

function first(arr)                 // O(1): same work for any n
    return arr[0]

function contains(arr, x)           // O(n): may look at every item
    for each v in arr
        if v = x return true
    return false

function hasDuplicate(arr)          // O(n²): checks every pair
    n ← length(arr)
    for i ← 0 to n - 1
        for j ← i + 1 to n - 1
            if arr[i] = arr[j] return true
    return false

// Exact count:  T(n) = 3n² + 5n + 20
// Drop constants and lower terms  →  O(n²)

Code Explained

O(1) — constant: independent of n
O(n) — linear: one pass
O(n²) — quadratic: all pairs, about n²/2 checks
early return helps the best case, not the worst
the growth rate matters, not the exact count

⚠ Common Mistakes

  • Saying O(n) is "fast": with n = 10⁹ and a heavy loop body it's still seconds
  • Merging different inputs: O(n + m) is not O(n) unless m ≤ n is guaranteed
  • Confusing best case with Big O: "O(1) if the first item matches" isn't the bound

✓ Tips & Best Practices

  • State complexity in terms of named inputs: O(rows × cols), O(V + E)
  • Quote time and space in every interview answer
  • Mention average vs worst when they differ (hashing, quicksort)

Quick Summary

  • O — upper bound on growth
  • Drop constants and lower-order terms
  • Θ — tight bound
  • Worst case unless stated otherwise
