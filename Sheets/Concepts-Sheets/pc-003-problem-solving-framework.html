Problem-Solving Framework

UMPIRE · clarify inputs · brute force first · optimize · state the tradeoffs · write test cases · talk through the plan

A Repeatable Process

Most failed interview answers come from coding too soon. A fixed process keeps you from solving the wrong problem. UMPIRE (Understand, Match, Plan, Implement, Review, Evaluate) is a common checklist: clarify first, name a pattern, plan in pseudocode, then code and test.

Ground Rules

  • Say a brute-force answer out loud first, with its complexity
  • Read the constraints; they hint at the target Big O (Sheet 026)
  • Plan in pseudocode or comments before writing real code
  • Test with a small example by hand, not just by running

The Process as Pseudocode

function solve(problem)
    // U — Understand
    restate the problem in your own words
    ask: input size? sorted? duplicates? negatives? empty?
    write 2–3 examples, including an edge case
    // M — Match
    pattern ← recognizeSignals(problem)      // Sheet 103
    // P — Plan
    write brute force + its Big O
    improve: which work is repeated? can a structure remove it?
    outline the steps in pseudocode
    // I — Implement
    code the plan, one helper at a time
    // R — Review
    trace your example through the code (Sheet 004)
    // E — Evaluate
    state final time · space and any tradeoffs

Code Explained

Understand — clarify inputs, outputs, and limits
Match — map signals to a known pattern
Plan — brute force first, then optimize
Implement — small functions, clear names
Review — dry-run before you hit Run
Evaluate — Big O and what you'd do with more time

⚠ Common Mistakes

  • Starting to code before confirming the output format: you solve a different problem
  • Skipping brute force: you lose an easy partial answer and a baseline to optimize
  • Optimizing silently: interviewers grade your reasoning, so narrate tradeoffs

✓ Tips & Best Practices

  • Write the examples as test cases you can run at the end
  • If stuck for two minutes, list the data structures you know and ask which one removes the slow step
  • End by naming what you'd improve with more time

Quick Summary

  • Understand — clarify before coding
  • Match — signals → pattern
  • Plan — brute force, then better
  • Review — dry-run, then state Big O
