Lifetimes — Basics

'a syntax · why lifetimes exist · E0106 / E0597 · functions returning references · 'static · lifetimes describe, they don't extend

Naming How Long Borrows Live

A lifetime is the region of code where a reference is valid. The compiler infers most of them, but when a function returns a reference derived from its inputs, you sometimes have to say which input it borrows from with a lifetime parameter like 'a. Lifetimes are checked at compile time and never change how long a value lives.

Key Points

  • 'a reads "lifetime a"
  • fn f<'a>(x: &'a str) -> &'a str: result lives as long as x
  • 'static = valid for the whole program (literals, leaked data)
  • Lifetime errors mean a reference might dangle

Lifetime Annotations

// fn longest(a: &str, b: &str) -> &str  // E0106: missing lifetime specifier
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

let s1 = String::from("long string");
let result;
{
    let s2 = String::from("xyz");
    result = longest(&s1, &s2);
    println!("{result}");                   // OK: s2 still alive here
}
// println!("{result}");            // E0597: `s2` does not live long enough

fn first<'a>(a: &'a str, _b: &str) -> &'a str { a }   // only tied to a

let kept;
{
    let temp = String::from("temp");
    kept = first(&s1, &temp);
}
println!("{kept}");                         // fine: depends only on s1

let lit: &'static str = "lives forever";    // in the binary
fn get_name() -> &'static str { "Ferris" }  // returning a literal is OK

// fn make() -> &String {                    // E0106
//     let s = String::from("x"); &s         // would dangle
// }
fn make() -> String { String::from("x") }   // return owned data instead

Code Explained

'a says the result borrows from both a and b
The result cannot be used after the shorter input dies
first ties the result only to a, so temp can die
A reference to a local cannot be returned; return the owned value

Coming From…

  • C++ returning a string_view to a temporary compiles and dangles
  • Go / Java / Python the GC keeps referenced data alive
  • C no checks; dangling pointers are undefined behavior

The Rust Way

  • adding 'static to silence errors → return owned data
  • <'a> on every function → let elision handle simple cases

Errors

CodeMeaning
E0106Missing lifetime specifier
E0597Value does not live long enough
E0515Returns reference to local
E0716Temporary dropped while borrowed

⚠ Common Mistakes

  • Thinking 'a makes a value live longer
  • Using 'static bounds when owned types would do
  • Returning references to locals or temporaries

✓ Tips & Best Practices

  • Return owned values (String, Vec) when unsure
  • Read the error's "borrowed value does not live long enough" arrow diagram
  • Most code needs no explicit lifetimes

Quick Summary

  • 'a — names a borrow region
  • ties output to inputs
  • 'static — whole program
  • describe, never extend
