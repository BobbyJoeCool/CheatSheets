Borrowed Data in Structs

A struct that holds a reference needs a lifetime parameter, which guarantees the struct cannot outlive the data it borrows. Elision rules let you skip annotations in common function signatures, and '_ marks an inferred lifetime. In practice, most structs should own their data; borrowing structs suit short-lived views like parsers.

Key Points

  • struct Parser<'a> { input: &'a str }
  • Impl blocks repeat the parameter: impl<'a> Parser<'a>
  • Elision: a &self method returns refs tied to self
  • '_ shows a borrow without naming it

Structs with References

struct Parser<'a> {
    input: &'a str,                         // borrows, never owns
    pos: usize,
}

impl<'a> Parser<'a> {
    fn new(input: &'a str) -> Self { Parser { input, pos: 0 } }

    fn next_word(&mut self) -> Option<&'a str> {   // tied to input, not self
        let rest = self.input[self.pos..].trim_start();
        if rest.is_empty() { return None; }
        let start = self.input.len() - rest.len();
        let end = rest.find(' ').map_or(self.input.len(), |i| start + i);
        self.pos = end;
        Some(&self.input[start..end])
    }
}

let text = String::from("parse these words");
let mut p = Parser::new(&text);
while let Some(w) = p.next_word() {
    print!("[{w}] ");                       // [parse] [these] [words]
}

// Elision: these two signatures are the same
fn first_word(s: &str) -> &str { s.split(' ').next().unwrap_or("") }
fn first_word2<'a>(s: &'a str) -> &'a str { s.split(' ').next().unwrap_or("") }

impl Parser<'_> {                           // '_ when the name isn't needed
    fn remaining(&self) -> &str { &self.input[self.pos..] }   // tied to self
}

struct Holder<'a, T: 'a> { item: &'a T }   // T must outlive 'a

struct Config { name: String }              // usually better: own the data

Code Explained

Parser<'a> cannot outlive the string it reads
next_word returns &'a str, so words outlive the &mut self borrow
Elision fills in lifetimes for one-input functions
impl Parser<'_> skips naming an unused lifetime

Coming From…

  • C++ a struct holding a string_view can outlive its buffer
  • Java / Go objects hold references; the GC prevents dangling
  • Python same as Java; no concept of borrowed fields

The Rust Way

  • struct User<'a> { name: &'a str } in long-lived data → name: String
  • naming lifetimes the compiler can elide → let elision work

Elision Rules

RuleEffect
1Each input ref gets its own lifetime
2One input lifetime → output gets it
3&self / &mut self → output gets self's
OtherwiseAnnotate (E0106)

When to Borrow in Structs

SituationChoice
Parser / iterator over inputBorrow &'a
Config, models, entitiesOwn (String, Vec)
Shared across threadsArc<T>
Sometimes ownedCow<'a, T>

⚠ Common Mistakes

  • Adding lifetimes to every struct and spreading them through the codebase
  • Returning &str tied to &mut self when it should be tied to 'a
  • Self-referential structs (not expressible safely)

✓ Tips & Best Practices

  • Start with owned fields; add borrowing only for performance
  • Use '_ to keep signatures short
  • Read rule 3 when a method's returned reference keeps self borrowed

Quick Summary

  • struct Foo<'a> { r: &'a T }
  • impl<'a> repeats it
  • three elision rules
  • prefer owned fields
