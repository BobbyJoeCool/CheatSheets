Sheet 13

Cookies & Sessions

Set-Cookie · HttpOnly · Secure · SameSite · Domain / Path · Max-Age · session IDs · CSRF tokens

State on Top of a Stateless Protocol

The server sets a cookie with Set-Cookie; the browser sends it back in Cookie on every matching request. A session cookie holds a random ID that points to data on the server (or an encrypted, signed blob of the data itself). Because browsers attach cookies automatically, even on requests another site triggers, cookie-based auth needs CSRF protection: SameSite plus a token the attacker's page can't read.

Notes

  • No Max-Age / Expires = session cookie, gone when the browser closes
  • Max-Age=0 deletes a cookie
  • Each cookie ~4 KB max; keep data on the server, the ID in the cookie
  • Mobile apps and server-to-server calls usually use tokens, not cookies

Security Check

  • HttpOnly stops script (XSS) from reading the session cookie
  • Name it __Host-sid (any __Host- name) to force Secure, Path=/ and no Domain
  • Issue a new session ID at login and logout (session fixation)

Login, Then Use the Session

POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

email=ada%40example.com&password=...

HTTP/1.1 303 See Other
Location: /dashboard
Set-Cookie: __Host-sid=8f2c; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=1209600
Set-Cookie: csrftoken=Qx9; Path=/; Secure; SameSite=Lax

GET /dashboard HTTP/1.1
Cookie: __Host-sid=8f2c; csrftoken=Qx9

POST /transfer HTTP/1.1
Cookie: __Host-sid=8f2c; csrftoken=Qx9
X-CSRF-Token: Qx9
Content-Type: application/json

{"to":"acct_7","amount":50}

Code Explained

Session cookie lasts 14 days; script can't read it
The CSRF cookie is readable on purpose so your JS can copy it
Server checks the header matches the cookie (double-submit)
Another site can make the browser send cookies, but can't set the header

In Your Stack

  • Express — express-session; res.cookie(name, v, { httpOnly: true, secure: true, sameSite: 'lax' })
  • Django — Sessions built in; SESSION_COOKIE_SECURE = True; {% csrf_token %} / CsrfViewMiddleware
  • Spring — Spring Security sessions; CSRF on by default; server.servlet.session.cookie.same-site=lax
  • Rails — session[:user_id] (encrypted cookie store); protect_from_forgery; cookies.encrypted
  • ASP.NET — AddAuthentication().AddCookie(); CookieOptions { HttpOnly = true, Secure = true }; antiforgery
  • Go — http.SetCookie(w, &http.Cookie{Name: "session", HttpOnly: true, Secure: true, SameSite: http.SameSiteLaxMode})

Debug It

  • DevTools → Application → Cookies shows every flag; a yellow warning says why one was blocked
  • Cookie not sent: Secure on http://, SameSite=None without Secure, or Domain / Path mismatch
  • Cross-origin fetch needs credentials: 'include' and CORS credentials (sheet 18)

⚠ Common Mistakes

  • Storing the user's role or price in a plain cookie; clients can edit it
  • Turning off CSRF protection because "it's an API" while still using cookies
  • SameSite=None everywhere to make a cross-site setup work

✓ Tips & Best Practices

  • Same-site SPA + API (app. and api. on one domain): cookies with SameSite=Lax are simplest
  • Expire idle sessions server-side; don't rely on the cookie lifetime
  • Store sessions in Redis or the DB so any server can read them

Quick Summary

  • Set-Cookie / Cookie — server sets, browser returns
  • HttpOnly · Secure · SameSite — always set all three
  • session ID — random, server-side data
  • CSRF token — required with cookie auth
