Sheet 09

4xx Client Errors

400 · 401 vs 403 · 404 vs 410 · 405 · 409 · 412 · 415 · 422 · 429

The Client Needs to Change Something

A 4xx code says the request itself is the problem, so sending it again unchanged won't help (except 408 and 429). The most-confused pair is 401 ("who are you?": missing or bad credentials) versus 403 ("I know who you are, and no"). Use 400 for requests you can't parse, 422 for well-formed requests that fail validation, and 409 when the request clashes with the current state.

Notes

  • 401 must send WWW-Authenticate saying how to authenticate
  • 405 must send Allow listing the methods that do work
  • 429 should send Retry-After (sheet 23)
  • RFC 9110 renamed 422 to Unprocessable Content and 413 to Content Too Large

Security Check

  • Return 404 instead of 403 when even revealing that a resource exists is a leak
  • Login failures: one generic message; don't say whether the email exists
  • Rate-limit 401s per account and per IP to slow credential stuffing

Common 4xx Responses

GET /reports HTTP/1.1

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api"

DELETE /reports/7 HTTP/1.1
Authorization: Bearer eyJhbGciOi...

HTTP/1.1 403 Forbidden
Content-Type: application/problem+json

{"title":"Only owners can delete reports","status":403}

PUT /users/42 HTTP/1.1
If-Match: "v41"

HTTP/1.1 412 Precondition Failed

POST /users HTTP/1.1
Content-Type: application/json

{"email":"ada@example.com"}

HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{"title":"Email already registered","status":409}

Code Explained

No credentials sent → 401 + a challenge
Valid token, wrong role → 403
If-Match lost a race with another edit → 412 (sheet 12)
Duplicate unique value → 409; bad email format would be 422

In Your Stack

  • Express — res.status(404).json(...); validation with express-validator or zod
  • Django — DRF raises NotFound · PermissionDenied · ValidationError (400 by default)
  • Spring — throw new ResponseStatusException(HttpStatus.NOT_FOUND); @Valid failures → 400
  • Rails — RecordNotFound → 404 automatically; render json: e, status: :unprocessable_entity
  • ASP.NET — Results.NotFound() · Results.Forbid() · Results.ValidationProblem(errors)
  • Go — http.NotFound(w, r) · http.Error(w, msg, http.StatusConflict)

Debug It

  • 401 while sending a token: check exp and aud; the WWW-Authenticate error text often says which
  • 403 on POST in Django, Rails or Spring: usually a missing CSRF token (sheet 13)
  • 413 before your code runs: the proxy's body limit (client_max_body_size in nginx)

⚠ Common Mistakes

  • Using 401 for "not allowed": clients will log the user out and retry login
  • Returning 500 for bad input because validation threw an unhandled exception
  • Mixing 400 and 422 at random; pick a rule and use it everywhere

✓ Tips & Best Practices

  • Return every validation error at once, not just the first (sheet 10)
  • Send Allow with 405 and Retry-After with 429; clients use them
  • Map your framework's not-found and validation exceptions to codes in one place

Quick Summary

  • 401 — who are you? · 403 — not you
  • 400 — can't parse · 422 — invalid values
  • 404 · 409 · 412 — missing · conflict · stale
  • 429 — slow down, see Retry-After
