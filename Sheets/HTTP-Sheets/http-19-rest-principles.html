REST Principles

Model Things, Not Function Calls

REST is an architectural style, not a standard: you expose resources (orders, customers) at URLs, and clients act on them with the standard HTTP methods, exchanging representations (usually JSON). The uniform interface means every resource behaves the same way, so clients, caches and tools understand your API without custom rules. Most "REST APIs" stop at level 2 of the Richardson model: resources plus correct methods and status codes.

Notes

  • A resource is a noun; a representation is one format of it (JSON, CSV)
  • Stateless: no server-side conversation between requests
  • HATEOAS: responses carry links to what the client can do next
  • RPC (POST /createOrder) is fine internally; gRPC is RPC done well

A Resource with Links

GET /orders/9001 HTTP/1.1
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
ETag: "o9001-v3"

{
  "id": 9001,
  "status": "pending",
  "total": {"amount": 4998, "currency": "USD"},
  "customer": {"id": 42, "href": "/customers/42"},
  "_links": {
    "self":    {"href": "/orders/9001"},
    "items":   {"href": "/orders/9001/items"},
    "cancel":  {"href": "/orders/9001/cancellation", "method": "POST"},
    "payment": {"href": "/orders/9001/payment"}
  }
}

Code Explained

One canonical URL per order; ETag makes it cacheable and safely editable
Money as integer cents plus currency avoids float errors
_links (HAL style) shows actions allowed in this state
When the order ships, cancel simply disappears

In Your Stack

  • Express — express.Router() per resource: router.route('/:id').get(show).patch(update)
  • Django — DRF DefaultRouter().register('orders', OrderViewSet) → list + detail routes
  • Spring — @RestController + @RequestMapping("/orders"); Spring HATEOAS EntityModel + linkTo()
  • Rails — resources :orders → the seven RESTful routes; check with bin/rails routes
  • ASP.NET — var orders = app.MapGroup("/orders") then orders.MapGet("/{id}", ...)
  • Go — One pattern per method + path: "GET /orders/{id}", "PATCH /orders/{id}"

⚠ Common Mistakes

  • Verbs in URLs (/getOrders, /updateUser) on an API you call REST
  • Tunnelling everything through POST and returning 200 with error flags
  • Exposing database tables one-to-one as resources instead of what clients need

✓ Tips & Best Practices

  • Design from client use cases, then pick resources
  • Level 2 is the practical target; add links where they save clients logic
  • Be consistent: one style for naming, errors, paging across the whole API

Quick Summary

  • resource — a noun at a URL
  • representation — JSON (or other) view of it
  • uniform interface — standard methods + codes
  • HATEOAS — links to next actions
