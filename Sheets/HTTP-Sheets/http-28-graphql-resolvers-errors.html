GraphQL Resolvers, Errors & Performance

resolver (parent · args · context) · N+1 + DataLoader · errors array · connections · depth / cost limits

Running Queries Safely and Fast

Every field has a resolver: a function that gets the parent object, the field's arguments and a per-request context (current user, DataLoaders, DB). Resolving a list then a field on each item causes the N+1 problem; a DataLoader batches those lookups into one query per request. Failures don't change the HTTP status: the field becomes null and an entry is added to the top-level errors array, with a path to the failed field.

Notes

  • Put the authenticated user in context; check access in resolvers
  • Create DataLoaders per request so caches don't leak between users
  • Lists use connections: edges { cursor node } + pageInfo
  • extensions.code (e.g. FORBIDDEN) lets clients branch on error type

Security Check

  • Limit query depth and cost (fields × list sizes) and set a timeout
  • Authorize per field/object; one forgotten resolver leaks data
  • Rate-limit by query cost; aliases can pack 100 login attempts into one request

An N+1 Query

query {
  orders(first: 50) {
    edges {
      cursor
      node { id customer { name } }   # 50 customer lookups
    }
    pageInfo { hasNextPage endCursor }
  }
}

Partial Success Response

{
  "data": { "order": { "id": "9001", "invoice": null } },
  "errors": [{
    "message": "Not authorized to view invoice",
    "path": ["order", "invoice"],
    "locations": [{ "line": 3, "column": 5 }],
    "extensions": { "code": "FORBIDDEN" }
  }]
}

Code Explained

Without batching: 1 orders query + 50 customer queries
DataLoader collects the 50 IDs → WHERE id IN (...), once
invoice failed, the rest of order still came back
path says exactly which field failed

In Your Stack

  • Express — dataloader: new DataLoader(ids => getCustomers(ids)) created per request
  • Django — Strawberry DataLoader(load_fn=load_customers) in the context
  • Spring — @BatchMapping on a controller method batches automatically
  • Rails — GraphQL::Dataloader: dataloader.with(Sources::Record, Customer).load(id)
  • ASP.NET — BatchDataLoader<int, Customer> or the [DataLoader] source generator
  • Go — vikstrous/dataloadgen or graph-gophers/dataloader

Debug It

  • 200 OK but the UI shows nothing: read the errors array in the response
  • Count DB queries per request; 50 identical queries = an N+1
  • Turn on resolver tracing (Apollo / OpenTelemetry) to find the slow field

⚠ Common Mistakes

  • A DataLoader shared across requests, leaking one user's data to another
  • Throwing raw database errors into errors[].message
  • Checking auth only at the top-level query while nested fields expose more

✓ Tips & Best Practices

  • Batch every field that loads by ID; make it the default pattern
  • Return domain errors in payloads, unexpected ones in errors[]
  • Log operation name, cost and duration for every request

Quick Summary

  • resolver(parent, args, context) — one per field
  • DataLoader — batch + cache per request
  • errors[] + path — partial failures
  • Limit depth, cost, page size and time
