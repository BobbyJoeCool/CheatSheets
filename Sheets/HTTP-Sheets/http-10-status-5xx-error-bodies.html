Sheet 10

5xx Server Errors & Error Bodies

500 · 502 vs 504 · 503 + Retry-After · application/problem+json · type · title · status · detail

Our Fault, Said Clearly

A 5xx code means the server failed at a request that may well have been fine. 500 is the catch-all for bugs; 502 and 504 come from a proxy or gateway that couldn't get a good answer from the app behind it; 503 means "down on purpose or overloaded, try later". Whatever the code, give errors one consistent body shape. Problem Details (RFC 9457, application/problem+json) is the standard one.

Notes

  • type is a URI naming the error kind; about:blank means "just the status"
  • Add your own fields (errors, traceId) next to the standard ones
  • 503 + Retry-After is the right answer during maintenance
  • Same shape for 4xx and 5xx, so clients parse errors one way

Security Check

  • Never return stack traces, SQL or file paths: turn debug mode off in production
  • Log details server-side with a request ID and return only the ID
  • Don't echo raw user input in detail; it can carry script or log-injection text

Problem Details Bodies

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/validation",
  "title": "Your request has invalid fields",
  "status": 422,
  "detail": "2 fields failed validation",
  "instance": "/orders",
  "errors": [
    {"pointer": "/email", "detail": "must be a valid email"},
    {"pointer": "/quantity", "detail": "must be at least 1"}
  ]
}

HTTP/1.1 500 Internal Server Error
Content-Type: application/problem+json

{"type":"about:blank","title":"Internal Server Error",
 "status":500,"traceId":"7f3a9c21e4b0"}

HTTP/1.1 503 Service Unavailable
Retry-After: 120

Code Explained

title is short and stable; detail is specific to this request
errors is an extension: one entry per bad field, as JSON Pointers
The 500 body gives a traceId to quote to support, nothing else
Retry-After: 120 = try again in two minutes

In Your Stack

  • Express — No built-in; a last error middleware (err, req, res, next) that writes the problem body
  • Django — DRF EXCEPTION_HANDLER setting reshapes errors; DEBUG = False in production
  • Spring — ProblemDetail + spring.mvc.problemdetails.enabled=true; @ControllerAdvice for custom types
  • Rails — rescue_from in ApplicationController; consider_all_requests_local = false in production
  • ASP.NET — builder.Services.AddProblemDetails() + app.UseExceptionHandler()
  • Go — Recovery middleware + w.Header().Set("Content-Type", "application/problem+json")

Debug It

  • 502: the proxy reached nothing useful; the app crashed, isn't listening, or closed the connection
  • 504: the app is up but slower than the proxy's timeout; find the slow query
  • Match the traceId / X-Request-Id in proxy and app logs to follow one request

⚠ Common Mistakes

  • Returning HTML error pages from a JSON API: clients choke on <!DOCTYPE
  • Using 500 for validation failures; clients and alerts can't tell bugs from bad input
  • A different error shape per endpoint, so clients need custom parsing for each

✓ Tips & Best Practices

  • Point type at a docs page that explains how to fix the problem
  • Return a request ID header on every response, not just errors
  • Alert on 5xx rate; don't alert on 4xx spikes alone

Quick Summary

  • 500 — our bug · 503 — try later
  • 502 / 504 — proxy got bad / no answer
  • application/problem+json — standard error body
  • traceId — link the client's error to your logs
