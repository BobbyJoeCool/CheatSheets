Sheet 22

Versioning & Evolving APIs

/v1 path · version header · media type · breaking vs non-breaking · additive fields · Deprecation · Sunset

Change the API Without Breaking Clients

Most changes don't need a new version: adding endpoints, optional parameters or response fields is non-breaking as long as clients ignore fields they don't know. A breaking change (removing or renaming a field, changing a type, tightening validation) needs a new version that runs alongside the old one for a while. Choose one versioning scheme and announce retirement with the Deprecation and Sunset headers.

Notes

  • Tolerant reader: clients ignore unknown fields and enum values
  • Path versions (/v1) are the most visible and easiest to route
  • Date-based versions (2026-11-01, Stripe style) pin each client
  • Version the whole API, not each endpoint separately

Three Ways to Ask for a Version

GET /v1/orders/9001 HTTP/1.1

GET /orders/9001 HTTP/1.1
API-Version: 2026-11-01

GET /orders/9001 HTTP/1.1
Accept: application/vnd.example.v2+json

HTTP/1.1 200 OK
Content-Type: application/json
Deprecation: @1798675200
Sunset: Wed, 30 Jun 2027 23:59:59 GMT
Link: <https://api.example.com/docs/migrate-to-v2>; rel="deprecation"

Code Explained

Path, custom header, or vendor media type; pick one
Deprecation (RFC 9745): deprecated since 31 Dec 2026, as a Unix time
Sunset (RFC 8594): the date it stops working
Link rel="deprecation" points to migration docs

In Your Stack

  • Express — Mount routers: app.use('/v1', v1) · app.use('/v2', v2)
  • Django — DRF URLPathVersioning or AcceptHeaderVersioning; read request.version
  • Spring — @RequestMapping("/v1/orders"); Spring Framework 7 adds @GetMapping(version = "2")
  • Rails — namespace :v1 do resources :orders end → V1::OrdersController
  • ASP.NET — Asp.Versioning.Http: app.NewApiVersionSet() + .HasApiVersion(2.0)
  • Go — mux.Handle("/v1/", http.StripPrefix("/v1", v1))

⚠ Common Mistakes

  • Shipping a breaking change in place because "only one client uses that field"
  • Bumping the major version for additive changes, multiplying versions to maintain
  • Sunsetting without measuring who still calls the old version

✓ Tips & Best Practices

  • Log the version and client ID on every request so you know who to contact
  • Keep a public changelog with dates; link it from the docs
  • Add Sunset headers months ahead; email owners of active API keys

Quick Summary

  • Additive = safe; remove / rename = new version
  • Pick one scheme: path, header or media type
  • Deprecation + Sunset — announce the end
  • Tolerant readers ignore what they don't know
