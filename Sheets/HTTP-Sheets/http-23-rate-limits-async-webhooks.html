Rate Limits, Async Jobs & Webhooks

429 + Retry-After · RateLimit headers · backoff + jitter · 202 + polling · webhooks · HMAC signatures

Slow Down, Come Back Later, We'll Call You

Rate limits protect the API: over the budget, answer 429 with Retry-After, and tell clients their remaining budget in headers. Work that takes longer than a few seconds should return 202 Accepted with a status URL the client polls. Better still, push the result with a webhook: an HTTP POST from your server to a URL the client registered, signed so the receiver can trust it.

Notes

  • Many APIs use X-RateLimit-Limit / -Remaining / -Reset; RateLimit is the IETF draft
  • Limit per API key or user, not just per IP
  • Webhooks are at-least-once: receivers must handle duplicates
  • Receivers should answer 2xx fast and process in the background

Security Check

  • Verify the HMAC over the raw body with a constant-time compare
  • Reject timestamps older than ~5 minutes to stop replays; dedupe by message ID
  • Senders: block private IPs and internal hosts as webhook targets (SSRF)

429, a Job, and a Signed Webhook

HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Policy: "default";q=100;w=60
RateLimit: "default";r=0;t=30

POST /exports HTTP/1.1

HTTP/1.1 202 Accepted
Location: /exports/jobs/77

GET /exports/jobs/77 HTTP/1.1

HTTP/1.1 200 OK
Retry-After: 5

{"status":"running","progress":0.4}

POST /hooks/payments HTTP/1.1
Content-Type: application/json
Webhook-Id: msg_2b1x
Webhook-Timestamp: 1793631600
Webhook-Signature: v1,K5oZfzN95Z9UVu1EsfQmfVNQhnkZ2pj9o9NDN/H/pI4=

{"type":"payment.succeeded","data":{"id":"pay_77"}}

Code Explained

100 requests per 60 s; none left; resets in 30 s
Poll the job; Retry-After hints how often
When done the job returns a 303 to the file, or a result link
Signature = HMAC-SHA256 of id.timestamp.body (Standard Webhooks)

In Your Stack

  • Express — express-rate-limit; keep the raw body for signatures: express.raw({ type: 'application/json' })
  • Django — DRF throttle_classes (UserRateThrottle); Celery jobs; verify request.body
  • Spring — Bucket4j or a gateway; job queue + status table; read the body as byte[] to verify
  • Rails — rate_limit to: 100, within: 1.minute (7.2+); Active Job; verify request.raw_post
  • ASP.NET — AddRateLimiter() + .RequireRateLimiting("fixed"); BackgroundService / Hangfire
  • Go — x/time/rate limiter middleware; io.ReadAll(r.Body), then hmac.Equal

Debug It

  • Watch RateLimit / X-RateLimit-Remaining across calls to see the budget drain
  • Signature mismatch: you verified re-serialized JSON, not the exact bytes received
  • Receive webhooks locally with a tunnel (ngrok, stripe listen, cloudflared)

Webhook Checklist

SideDo
SenderSign, include ID + timestamp, retry with backoff for ~3 days
SenderEvent types + a way to replay missed events
ReceiverVerify signature and timestamp first
ReceiverReturn 2xx in < 5 s; queue the work
ReceiverDedupe by Webhook-Id

⚠ Common Mistakes

  • Retrying in a tight loop on 429, which keeps you rate-limited
  • Doing slow work inside the webhook request, so the sender times out and retries
  • Trusting webhook payloads without a signature check

✓ Tips & Best Practices

  • Add jitter to every retry so clients don't stampede together
  • Webhook payloads can be thin ({type, id}); the receiver fetches fresh data
  • Give each client its own signing secret and support rotating it

Quick Summary

  • 429 + Retry-After — wait, then retry
  • 202 + Location — poll the job
  • Webhook — signed POST to the client
  • Backoff + jitter for every retry
