Sheet 24

Documenting with OpenAPI

OpenAPI 3.1 · paths & operations · parameters · requestBody · components/schemas · $ref · securitySchemes

One Spec, Many Tools

An OpenAPI document describes every path, operation, parameter, body and response in YAML or JSON. From it you get interactive docs (Swagger UI, Redoc, Scalar), generated clients and servers, mock servers, request validation and contract tests. Write it design-first (spec, then code) or generate it code-first from annotations; either way, treat it as part of the API and review changes to it. Version 3.1 uses standard JSON Schema.

Notes

  • operationId becomes the method name in generated clients
  • $ref reuses schemas, parameters and responses from components
  • 3.1 allows type: [string, "null"] instead of nullable
  • Lint specs in CI (Spectral) and diff them for breaking changes

A Minimal OpenAPI 3.1 Spec

openapi: 3.1.0
info: { title: Orders API, version: 1.4.0 }
servers: [{ url: https://api.example.com/v1 }]
paths:
  /orders/{id}:
    get:
      operationId: getOrder
      parameters:
        - { name: id, in: path, required: true, schema: { type: integer } }
      responses:
        '200':
          description: The order
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Order' }
        '404': { description: No such order }
      security: [{ bearerAuth: [] }]
components:
  schemas:
    Order:
      type: object
      required: [id, status]
      properties:
        id: { type: integer }
        status: { type: string, enum: [pending, paid, shipped] }
  securitySchemes:
    bearerAuth: { type: http, scheme: bearer, bearerFormat: JWT }

Code Explained

paths → URL → method → operation
Path params must be required: true
Responses are keyed by status code, quoted
security on an operation names a scheme from securitySchemes

In Your Stack

  • Express — swagger-ui-express serves a spec; zod-to-openapi or tsoa generate one
  • Django — drf-spectacular: SpectacularAPIView + SpectacularSwaggerView
  • Spring — springdoc-openapi: /v3/api-docs and /swagger-ui.html out of the box
  • Rails — rswag (specs → OpenAPI) or oas_rails
  • ASP.NET — AddOpenApi() + MapOpenApi() (.NET 9+); Scalar or Swagger UI to view it
  • Go — swaggo/swag from comments, or spec-first with oapi-codegen

⚠ Common Mistakes

  • Docs that drift from the code because nobody checks the spec in CI
  • Documenting only 200 and leaving out error responses
  • Inline schemas everywhere instead of $ref, so generated clients get dozens of duplicate types

✓ Tips & Best Practices

  • Fail CI on spec lint errors and on breaking diffs against main
  • Add examples to schemas; docs and mocks get much better
  • Publish the raw spec URL so clients can generate their own SDKs
