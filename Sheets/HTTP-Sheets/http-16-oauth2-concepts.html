OAuth 2.0 Concepts

resource owner · client · authorization server · resource server · scopes · access / refresh tokens · grants

Delegated Access Without Sharing Passwords

OAuth 2.0 lets an app (the client) get limited access to an API (the resource server) on behalf of a user (the resource owner), without ever seeing the user's password. An authorization server checks who the user is, asks for consent, and issues an access token limited by scopes. A grant type is the recipe for getting that token; machines with no user use client credentials.

Notes

  • OAuth is authorization; for login use OpenID Connect on top (sheet 17)
  • Confidential clients (servers) can keep a secret; public clients (SPAs, mobile) can't
  • Access tokens: short-lived. Refresh tokens: long-lived, used to get new access tokens
  • Discovery: /.well-known/openid-configuration lists every endpoint

Security Check

  • Never put a client secret in an SPA or mobile app; use PKCE instead (sheet 17)
  • Request the smallest scopes; register exact redirect URIs, no wildcards
  • Rotate refresh tokens on every use and revoke the family if one is reused

Client Credentials (Machine to Machine)

curl -u "$CLIENT_ID:$CLIENT_SECRET" \
     -d grant_type=client_credentials \
     -d scope="reports:read" \
     https://auth.example.com/oauth/token

curl -H "Authorization: Bearer $ACCESS_TOKEN" \
     https://api.example.com/reports

curl -d grant_type=refresh_token \
     -d refresh_token="$REFRESH_TOKEN" \
     -d client_id="$CLIENT_ID" \
     https://auth.example.com/oauth/token

Token Response

{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 900,
  "scope": "reports:read"
}

Code Explained

The client authenticates itself with Basic auth at the token endpoint
expires_in: 900 → get a new token after 15 minutes
The API only sees the access token and checks its scopes
Refresh tokens come from user flows, not client credentials

In Your Stack

  • Express — Client: openid-client; API: express-oauth2-jwt-bearer or jose
  • Django — Server: django-oauth-toolkit; client: authlib
  • Spring — spring-boot-starter-oauth2-client / -resource-server; Spring Authorization Server
  • Rails — Client: omniauth-oauth2; server: doorkeeper
  • ASP.NET — AddOpenIdConnect() client · AddJwtBearer() API · OpenIddict / Duende server
  • Go — golang.org/x/oauth2 and oauth2/clientcredentials: cfg.Token(ctx)

⚠ Common Mistakes

  • Using OAuth access tokens as proof of login ("OAuth for authentication")
  • Asking for every scope up front; users decline and admins block the app
  • Caching a token past expires_in and retrying with it forever

✓ Tips & Best Practices

  • Refresh a little before expiry, not after a 401
  • Name scopes resource:action (orders:read) and check them in the API
  • Use a hosted identity provider unless running one is your product

Quick Summary

  • client gets a token for a resource server
  • scope — what the token may do
  • access (short) vs refresh (long) tokens
  • client_credentials — no user involved
