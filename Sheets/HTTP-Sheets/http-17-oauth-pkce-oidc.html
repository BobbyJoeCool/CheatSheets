Sheet 17

OAuth Flows: Authorization Code + PKCE & OpenID Connect

/authorize · state · code_verifier / code_challenge · /token · refresh rotation · id_token · userinfo

The One Flow Every App Should Use

In the authorization code flow the app sends the browser to the authorization server, the user logs in there, and the server redirects back with a one-time code that the app swaps for tokens over a back channel. PKCE binds the two halves: the app sends a hash of a random verifier first and proves it holds the verifier at the swap, so a stolen code is useless. Add the openid scope and you get OpenID Connect: an ID token (a JWT about the user) that makes this a login.

Notes

  • Codes are single-use and expire in about a minute
  • state ties the callback to the browser that started the flow
  • ID token is for the app (who logged in); access token is for the API
  • Implicit flow is gone: SPAs use code + PKCE or a backend-for-frontend

Security Check

  • Register exact redirect URIs; never accept one from the request without matching
  • Validate the ID token: signature, iss, aud = your client ID, exp, nonce
  • SPAs: a backend-for-frontend (BFF) keeps tokens server-side in an HttpOnly session

Authorization Code + PKCE, Step by Step

# 1. App makes a random verifier and its SHA-256 challenge
VERIFIER=$(openssl rand -base64 48 | tr -d '=+/' | cut -c1-64)
CHALLENGE=$(printf %s "$VERIFIER" | openssl dgst -sha256 -binary \
            | base64 | tr '+/' '-_' | tr -d '=')

# 2. Browser is sent to the authorization server
https://auth.example.com/authorize?response_type=code
  &client_id=photo-app&redirect_uri=https://app.example.com/callback
  &scope=openid%20profile%20photos:read&state=af0ifjsldkj&nonce=n-0S6
  &code_challenge=$CHALLENGE&code_challenge_method=S256

# 3. User logs in and consents; browser comes back with a code
https://app.example.com/callback?code=SplxlOBeZQQYbYS6&state=af0ifjsldkj

# 4. App swaps code + verifier for tokens (back channel)
curl -d grant_type=authorization_code -d code=SplxlOBeZQQYbYS6 \
     -d redirect_uri=https://app.example.com/callback \
     -d client_id=photo-app -d code_verifier="$VERIFIER" \
     https://auth.example.com/oauth/token
# {"access_token":"...","id_token":"eyJ...","refresh_token":"...","expires_in":900}

Code Explained

Only the challenge travels through the browser; the verifier stays in the app
The app checks state on the callback matches what it sent
Confidential clients also send their secret in step 4
nonce is copied into the ID token; compare it to stop replay

In Your Stack

  • Express — openid-client: buildAuthorizationUrl(), then authorizationCodeGrant() with the verifier
  • Django — authlib: oauth.register(...) · authorize_redirect() · authorize_access_token()
  • Spring — .oauth2Login() + spring.security.oauth2.client.registration.* (PKCE automatic)
  • Rails — omniauth_openid_connect with pkce: true
  • ASP.NET — AddOpenIdConnect(o => { o.ResponseType = "code"; o.UsePkce = true; })
  • Go — oauth2.GenerateVerifier() · AuthCodeURL(state, oauth2.S256ChallengeOption(v)) · Exchange(ctx, code, oauth2.VerifierOption(v))

Debug It

  • redirect_uri_mismatch: must match the registered URI exactly, trailing slash included
  • invalid_grant: code already used or expired, or the verifier doesn't match the challenge
  • Errors come back on the callback as ?error=...&error_description=...; read the Network tab

⚠ Common Mistakes

  • Sending the ID token to your API as an access token; its aud is the client, not the API
  • Skipping state / nonce checks because "PKCE covers it"
  • Embedded web views for login on mobile: users can't trust them and providers block them

✓ Tips & Best Practices

  • Use a certified OIDC client library; the flow has many small checks
  • Rotate refresh tokens and store them only on a server or in OS secure storage
  • Read endpoints from discovery instead of hard-coding them

Quick Summary

  • /authorize → code → /token
  • PKCE — verifier + S256 challenge
  • state · nonce — tie callback and token to this login
  • id_token — who logged in (OIDC)
