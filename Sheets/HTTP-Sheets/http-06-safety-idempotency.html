Safe, Idempotent & Cacheable Methods

safe · idempotent · cacheable · retries · Idempotency-Key · POST vs PUT for create · double-submit

Which Requests Are Safe to Repeat

A safe method doesn't change state (GET, HEAD, OPTIONS). An idempotent method has the same effect whether it runs once or ten times (all safe methods plus PUT and DELETE). This matters because networks fail: a client that times out can't know if the server acted, and only idempotent requests are safe to retry blindly. For POST, an Idempotency-Key header lets the server spot a retry and replay the first result.

Notes

  • Idempotent is about server state, not the response: a second DELETE may return 404
  • Idempotency-Key is an IETF draft, used by Stripe, Adyen and others
  • Cacheable by default: GET and HEAD; POST only with explicit freshness headers
  • Browsers and proxies may retry idempotent requests on their own

Retrying a Payment Safely

KEY=$(uuidgen)                     # one key per logical operation

curl --json '{"amount":2500,"currency":"usd"}' \
     -H "Idempotency-Key: $KEY" https://api.example.com/payments
# 201 Created ... but the client timed out and never saw it

curl --json '{"amount":2500,"currency":"usd"}' \
     -H "Idempotency-Key: $KEY" https://api.example.com/payments
# 201 Created, same body: server replayed the stored result

curl --json '{"amount":9999,"currency":"usd"}' \
     -H "Idempotency-Key: $KEY" https://api.example.com/payments
# 422: same key, different payload is rejected

# PUT is idempotent by design: two calls, one final state
curl -X PUT --json '{"name":"Ada"}' https://api.example.com/users/42
curl -X PUT --json '{"name":"Ada"}' https://api.example.com/users/42

Code Explained

The client makes the key once and reuses it for every retry
Server stores key → (payload hash, response) for a day or so
Same key + same payload = replay; different payload = error
PUT needs no key: replaying it can't create a duplicate

In Your Stack

  • Express — No built-in; middleware that stores key → response in Redis
  • Django — No built-in; unique idempotency_key column + transaction.atomic()
  • Spring — No built-in; a HandlerInterceptor or filter + unique DB constraint
  • Rails — No built-in; create_or_find_by!(key:) on a unique index
  • ASP.NET — No built-in; endpoint filter + IDistributedCache
  • Go — Middleware wrapping the handler; key table with a UNIQUE index

When to Retry

SituationRetry?
Network error on GET / PUT / DELETEYes, with backoff
Network error on POSTOnly with an Idempotency-Key
429 · 503Yes, after Retry-After
408 · 502 · 504Yes, with backoff
Other 4xxNo: fix the request
500Maybe once; it may repeat

⚠ Common Mistakes

  • Retrying POST automatically (client libraries, queues): duplicate orders and double charges
  • Making a GET increment a counter or send an email: prefetchers and retries will repeat it
  • Generating a new idempotency key on each retry, which defeats the point

✓ Tips & Best Practices

  • Disable a submit button after click and send an idempotency key; do both
  • Use PUT with a client-chosen ID (PUT /orders/{uuid}) to make creates naturally idempotent
  • Expire stored keys after 24 hours or so; long enough for any retry window

Quick Summary

  • safe — read-only (GET, HEAD, OPTIONS)
  • idempotent — same effect on repeat (+ PUT, DELETE)
  • Idempotency-Key — makes POST retry-safe
  • Retry 429/503 after Retry-After
