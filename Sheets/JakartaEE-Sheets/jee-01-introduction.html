Jakarta EE 11

Introduction & the Platform

specifications · profiles · compatible runtimes · jakarta.* · MicroProfile

Description

Jakarta EE is a set of specifications for server-side Java: CDI, Servlet, REST, Persistence, Security and more. A spec defines the API (jakarta.* interfaces and annotations); a compatible implementation (WildFly, Payara, Open Liberty, GlassFish) provides the code. You write against the API and deploy to any compatible runtime. The Eclipse Foundation runs it; it was Java EE under Oracle until 2017.

Notes

  • Targets Jakarta EE 11 (Java 17+, Java 21 for virtual threads)
  • Three profiles: Core ⊂ Web ⊂ Platform
  • Spring Boot runs on the same jakarta.* APIs (Servlet, JPA, Validation)

A Complete Jakarta REST + CDI App

@ApplicationPath("/api")                    // turns on Jakarta REST
public class App extends Application { }
@ApplicationScoped                          // CDI bean, one per app
public class GreetingService {
    public String greet(String name) { return "Hello, " + name; }
}

@Path("/hello")                             // GET /api/hello/Bob
public class HelloResource {
    @Inject GreetingService service;        // container injects it

    @GET @Path("{name}")
    @Produces(MediaType.TEXT_PLAIN)
    public String hello(@PathParam("name") String name) {
        return service.greet(name);         // Hello, Bob
    }
}

Code Explained

@ApplicationPath — base URI for every REST resource in the war
@ApplicationScoped — one shared instance, created lazily by CDI
@Inject — the container supplies the bean; no new
No main() — the server owns the lifecycle and the threads

Spring Equivalent

  • Jakarta REST @Path → @RestController + @RequestMapping
  • CDI @ApplicationScoped → singleton @Service
  • Spring uses Jakarta Servlet, JPA, Validation directly · See Spring 01

Prefer / Avoid

  • javax.ws.rs.* imports → jakarta.ws.rs.* (EE 9+)
  • fat war bundling the API → jakartaee-api as provided
  • picking a spec per tutorial → check the EE 11 spec list (sheet 40)

⚠ Common Mistakes

  • Mixing javax.* and jakarta.* jars — classes don't match and injection silently fails
  • Treating the spec as a product — features beyond the spec are vendor extensions and don't port
  • Choosing Platform when Web is enough — bigger server, slower start, more to secure

✓ Tips & Best Practices

  • Start from start.jakarta.ee to get a working war for your runtime
  • Read the spec's own docs at jakarta.ee/specifications for exact rules
  • Keep vendor-specific config in one place so switching runtimes stays cheap

Quick Summary

  • spec — API contract; runtime supplies the code
  • Core / Web / Platform — nested profiles
  • jakarta.* — namespace since EE 9
  • EE 11 — Java 17+, Data 1.0, Concurrency 3.1
