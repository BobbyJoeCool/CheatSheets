Persistence 3.2

JPQL, Criteria & Fetching

createQuery · named parameters · @NamedQuery · JOIN FETCH · entity graphs · Criteria API · pagination

Description

JPQL queries entities and fields, not tables and columns; the provider translates it to SQL. Use named parameters for values, **JOIN FETCH or entity graphs to load relationships in one query, and the Criteria API** when a query is built dynamically. Persistence 3.2 adds union, ||, cast and left/right to JPQL.

Notes

  • TypedQuery<T> avoids casts
  • getSingleResult() throws if 0 or 2+ rows
  • Native SQL: createNativeQuery(sql, Product.class)

Under the Container

  • JPQL is translated to SQL for your database's dialect at runtime
  • Lazy associations in a loop cause N+1: one query, then one per row
  • JOIN FETCH and entity graphs change the generated SQL to load it all at once

Queries

List<Order> recent = em.createQuery(
        "SELECT o FROM PurchaseOrder o JOIN FETCH o.lines " +
        "WHERE o.customer.email = :email ORDER BY o.placed DESC",
        PurchaseOrder.class)
    .setParameter("email", email)
    .setFirstResult(0).setMaxResults(20)        // page 1, size 20
    .getResultList();

@NamedQuery(name = "Product.bySku",
            query = "SELECT p FROM Product p WHERE p.sku = :sku")

EntityGraph<?> g = em.getEntityGraph("Order.withLines");
em.find(PurchaseOrder.class, id,
        Map.of("jakarta.persistence.fetchgraph", g));

CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Product> q = cb.createQuery(Product.class);
Root<Product> p = q.from(Product.class);
q.where(cb.lt(p.get("price"), max), cb.like(p.get("sku"), "MUG%"));
List<Product> cheap = em.createQuery(q).getResultList();

Code Explained

:email — named parameter, never string-concatenate
setFirstResult/setMaxResults — offset pagination
fetchgraph — load exactly the graph's attributes
Criteria — type-safe with the generated metamodel (Product_.price)

Spring Equivalent

  • JPQL in @Query on Spring Data repositories (Spring 40)
  • @EntityGraph on repository methods; Specification ≈ Criteria (Spring 43–44)

Prefer / Avoid

  • string concatenation into JPQL → named parameters
  • JOIN FETCH + pagination on collections → two queries or entity graph
  • p.get("price") strings → metamodel Product_.price

⚠ Common Mistakes

  • JOIN FETCH a collection with setMaxResults — the provider paginates in memory (and warns)
  • Using table/column names in JPQL — it uses entity and field names
  • Bulk UPDATE/DELETE then reading managed entities — the context still holds old values; clear()

✓ Tips & Best Practices

  • Enable SQL logging and count queries per request to catch N+1
  • Use DTO projections for read-only lists
  • Validate named queries at deploy: errors surface early

Quick Summary

  • JPQL — entity-level queries
  • JOIN FETCH — eager load per query
  • EntityGraph — reusable fetch plan
  • Criteria — dynamic queries
