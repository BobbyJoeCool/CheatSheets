Persistence 3.2

EntityManager & Entity Lifecycle

@PersistenceContext · persist · find · merge · remove · managed / detached · flush · @PrePersist

Description

The **EntityManager is the gateway to the persistence context: the set of managed entities for the current transaction. Changes to managed entities are written automatically at flush (dirty checking**). Entities move between four states: new, managed, detached and removed.

Notes

  • Inject with @PersistenceContext (or @Inject with a producer)
  • find() returns null; getReference() returns a lazy proxy
  • merge() returns a new managed copy

Under the Container

  • The persistence context is a first-level cache: find() twice → one SELECT
  • Dirty checking at flush writes changed fields — no update() call needed
  • Flush happens before queries and at commit; transaction-scoped context ends at commit

State Transitions

@ApplicationScoped @Transactional
public class ProductService {
    @PersistenceContext EntityManager em;

    public Long create(String sku) {
        Product p = new Product(sku);          // NEW
        em.persist(p);                         // → MANAGED
        return p.getId();                      // id after flush/IDENTITY
    }
    public void reprice(Long id, BigDecimal price) {
        Product p = em.find(Product.class, id);   // MANAGED (or null)
        p.setPrice(price);                     // UPDATE at commit
    }
    public Product save(Product detached) {    // from REST, DETACHED
        return em.merge(detached);             // returns managed copy
    }
    public void delete(Long id) {
        em.remove(em.getReference(Product.class, id));  // → REMOVED
    }
}
@Entity @EntityListeners(Audit.class) class Product {
    @PrePersist void onCreate() { createdAt = Instant.now(); }
}

Code Explained

persist — new → managed; INSERT at flush
setPrice on a managed entity — no save call needed
merge — copies state onto a managed instance; keep using the return value
@PrePersist — lifecycle callback before INSERT

Spring Equivalent

  • em.persist/merge → repository.save() (Spring 38)
  • Dirty checking works the same inside @Transactional

Prefer / Avoid

  • em.merge() on managed entities → just modify them
  • calling flush() everywhere → let commit flush
  • keeping entities across requests → reload by id

⚠ Common Mistakes

  • Ignoring merge()'s return value — further changes go to the detached object and are lost
  • Calling persist() on a detached entity — EntityExistsException
  • Using EntityManager outside a transaction for writes — TransactionRequiredException

✓ Tips & Best Practices

  • Use getReference() to set a FK without loading the row
  • em.detach(e) or clear() in batch jobs to keep memory flat
  • Batch inserts: flush + clear every N rows

Quick Summary

  • persist — new → managed
  • find — load by id
  • merge — reattach copy
  • flush — write pending changes
