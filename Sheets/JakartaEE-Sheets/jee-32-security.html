Security 4.0

Security

@RolesAllowed · SecurityContext · identity stores · @BasicAuthenticationMechanismDefinition · OpenID Connect

Description

Jakarta Security lets an app define authentication mechanisms (Basic, Form, OpenID Connect) and identity stores (database, LDAP, custom) in code, without server-specific config. **@RolesAllowed protects CDI beans, EJBs and REST resources; SecurityContext** answers who the caller is.

Notes

  • Security 4.0 (EE 11) supports multiple mechanisms with qualifiers
  • Roles must be declared (@DeclareRoles) or mapped
  • @PermitAll / @DenyAll override class-level rules

Basic Auth + DB Identity Store

@BasicAuthenticationMechanismDefinition(realmName = "shop")
@DatabaseIdentityStoreDefinition(
    dataSourceLookup = "java:app/jdbc/shop",
    callerQuery = "SELECT password FROM users WHERE email = ?",
    groupsQuery = "SELECT role FROM user_roles WHERE email = ?",
    hashAlgorithm = Pbkdf2PasswordHash.class)
@DeclareRoles({"admin", "customer"})
@ApplicationScoped public class SecurityConfig { }

@Path("/admin") @RolesAllowed("admin")
public class AdminResource {
    @Inject SecurityContext security;

    @GET public String me() {
        return security.getCallerPrincipal().getName();   // bob@shop.app
    }
    @GET @Path("public") @PermitAll public String ping() { return "ok"; }
}

@OpenIdAuthenticationMechanismDefinition(
    providerURI = "https://login.example.com",
    clientId = "shop", clientSecret = "${oidc.secret}",
    redirectURI = "${baseURL}/callback")

Code Explained

Mechanism + identity store = complete login with no web.xml
Pbkdf2PasswordHash — salted hashing for stored passwords
isCallerInRole("admin") — programmatic check
OIDC mechanism handles the redirect/callback flow

Spring Equivalent

  • Spring Security SecurityFilterChain replaces mechanisms/stores (Spring 45–46)
  • @RolesAllowed works with @EnableMethodSecurity(jsr250Enabled = true)

Prefer / Avoid

  • <security-constraint> in web.xml → @RolesAllowed
  • plain-text passwords → Pbkdf2PasswordHash
  • server-specific realms → @…IdentityStoreDefinition

⚠ Common Mistakes

  • @RolesAllowed on a class nobody intercepts (plain new object) — no check happens
  • Basic auth over HTTP — credentials are only Base64; always TLS
  • Mixing REST's jakarta.ws.rs.core.SecurityContext and Jakarta Security's — different APIs

✓ Tips & Best Practices

  • Implement IdentityStore for custom user sources
  • Use HttpAuthenticationMechanism for token/JWT auth (or MicroProfile JWT)
  • Test with @RunAs or runtime test utilities

Quick Summary

  • IdentityStore — validates them
  • @RolesAllowed — authorization
