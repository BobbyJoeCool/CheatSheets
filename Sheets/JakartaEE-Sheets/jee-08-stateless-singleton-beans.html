Stateless & Singleton Session Beans

@Stateless · @Singleton · @Startup · @Lock · @ConcurrencyManagement · @Local

Description

Session beans are EJB components the container pools, secures and wraps in transactions. A **@Stateless bean holds no per-client state, so any pooled instance can serve any call. A @Singleton** has exactly one instance per app, with container-managed locking. Both get a container transaction on every public method by default.

Notes

  • No-interface view: inject the class itself; @Local only for interfaces
  • @Startup creates a singleton eagerly at deploy
  • Singleton default lock is WRITE — one caller at a time
  • Inject with @Inject (CDI) rather than @EJB

Under the Container

  • Stateless instances are pooled; never keep caller data in fields
  • Every business method runs in a container transaction (REQUIRED) unless told otherwise
  • this.other() skips the proxy — no new transaction, no security check

Stateless Service + Singleton Cache

@Stateless                                   // pooled, transactional
public class OrderService {
    @PersistenceContext EntityManager em;
    public void place(Order o) { em.persist(o); }   // tx per call
}

@Singleton @Startup                          // one instance, eager
@ConcurrencyManagement(ConcurrencyManagementType.CONTAINER)
public class RateCache {
    private Map<String, BigDecimal> rates = new HashMap<>();

    @PostConstruct void load() { rates = fetchRates(); }

    @Lock(LockType.READ)                     // many readers at once
    public BigDecimal rate(String ccy) { return rates.get(ccy); }

    @Lock(LockType.WRITE)                    // exclusive
    public void refresh() { rates = fetchRates(); }
}

Code Explained

@Stateless — container picks a free instance per call
@Startup — runs @PostConstruct during deployment
@Lock(READ) — concurrent callers; WRITE blocks everyone
BEAN concurrency → you use synchronized yourself

Spring Equivalent

  • @Stateless → @Service + @Transactional (Spring beans aren't pooled)
  • @Singleton @Startup → @Component + ApplicationReadyEvent · See Spring 42

Prefer / Avoid

  • @Stateless only for transactions → @ApplicationScoped + @Transactional
  • @EJB field injection → @Inject
  • WRITE lock on read methods → @Lock(READ)

⚠ Common Mistakes

  • Storing request data in a stateless field — the next caller may get the same instance and see it
  • Long work under a WRITE lock — every other call to the singleton waits or times out
  • Calling a REQUIRES_NEW method on this — the annotation is ignored

✓ Tips & Best Practices

  • Use @AccessTimeout to fail fast instead of piling up on a lock
  • Inject SessionContext and call getBusinessObject() to self-call through the proxy
  • For new code, try a CDI bean first (sheet 10)

Quick Summary

  • @Stateless — pooled, no state
  • @Singleton — one, container-locked
  • @Lock(READ/WRITE) — concurrency
  • @Startup — eager init
