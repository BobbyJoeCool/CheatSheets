Sheet 10
EJB 4.0 · CDI 4.1

Enterprise Beans vs CDI Beans

pooling · timers · MDBs · @Lock · @Transactional · CDI-first · legacy EJB

Description

Since Java EE 7, most EJB services are available to plain CDI beans: @Transactional, @RolesAllowed, interceptors and managed executors. The platform's direction is CDI-first; EE 12 continues moving EJB features into CDI-based specs. Keep EJB where it still adds something unique, and write new services as CDI beans.

Notes

  • Core and Web Profiles include only EJB Lite or none
  • EJB Lite: session beans, no MDBs, no remote, no timers in Core
  • A class can't be both @Stateless and @ApplicationScoped
  • Converting is usually just swapping the annotation

Code Explained

Pick CDI by default; it's lighter and works in every profile
Keep EJB for MDBs, persistent timers and pooled throttling
Mixed apps are normal — CDI can inject EJBs and vice versa

Spring Equivalent

  • Spring never had EJBs; every Spring bean is CDI-style
  • Spring @Transactional = CDI @Transactional semantics · See Spring 42

Prefer / Avoid

  • new @Stateless service → @ApplicationScoped + @Transactional
  • EJB @Asynchronous → Concurrency @Asynchronous
  • @Remote EJB → REST resource

⚠ Common Mistakes

  • Assuming CDI @ApplicationScoped is pooled — it's one shared instance, so fields need thread safety
  • Swapping to CDI but forgetting @Transactional — writes now run without a transaction
  • Converting MDBs to CDI — there's no CDI message listener; keep the MDB

✓ Tips & Best Practices

  • Migrate one bean at a time and run integration tests between steps
  • Grep for @TransactionAttribute to find tx settings that must move to @Transactional
  • Watch EE 12 milestones for further EJB-to-CDI moves

Quick Summary

  • CDI-first — default for new beans
  • @Transactional — CDI transactions
  • EJB — MDBs, timers, pools
  • EJB Lite — Web Profile subset
