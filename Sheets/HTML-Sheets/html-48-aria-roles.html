Roles and the First Rule of ARIA

ARIA (Accessible Rich Internet Applications) attributes change what the accessibility tree reports. A role tells assistive tech what an element is: button, tab, dialog, alert. Native elements already have implicit roles (<button> → button, <nav> → navigation). The first rule of ARIA: if a native element does the job, use it instead. ARIA changes semantics only, never behavior.

Notes

  • role="button" doesn't make an element focusable or keyboard-operable
  • Abstract roles (widget, landmark) are never used in markup
  • role="presentation" / "none" removes an element's semantics
  • Widget roles (tabs, menus, trees) require specific keyboard behavior (WAI-ARIA APG)

♿ Accessibility

  • No ARIA beats bad ARIA: WebAIM's surveys find more errors on pages that use more ARIA
  • Don't override native roles: <h2 role="tab"> loses the heading
  • Every interactive role needs a name, focusability and keyboard support

Pairing with CSS

  • [role="tab"][aria-selected="true"]: style from ARIA state so looks and semantics stay in sync
  • [role="alert"]: give alert messages one consistent style
  • Prefer native selectors where they exist: button over [role="button"]

Code Explained

role="button" on a div: still needs tabindex="0" and Enter/Space handlers
tablist / tab / tabpanel: the APG Tabs pattern
tabindex="-1" on inactive tabs: arrow keys move between them
role="alert": an assertive live region (sheet 49)
presentation: the table is read as plain content

Native First, ARIA When Needed

<!-- ✖ role on a div: no focus, no keys -->
<div role="button" onclick="save()">Save</div>

<!-- ✔ native element -->
<button type="button" onclick="save()">Save</button>

<!-- ✔ ARIA fills a gap: tabs (needs arrow-key JS) -->
<div role="tablist" aria-label="Trail info">
  <button role="tab" id="t-map" aria-selected="true"
          aria-controls="p-map">Map</button>
  <button role="tab" id="t-rev" aria-selected="false"
          aria-controls="p-rev" tabindex="-1">
    Reviews</button>
</div>
<div role="tabpanel" id="p-map" aria-labelledby="t-map">
  …map…
</div>
<div role="tabpanel" id="p-rev" aria-labelledby="t-rev"
     hidden>…reviews…</div>

<!-- ✔ alert: announced immediately -->
<p role="alert">Payment failed. Check your card.</p>

<!-- ✔ strip semantics from a layout table -->
<table role="presentation">…</table>

<!-- ✖ overriding a native role -->
<h2 role="button">Details</h2>

⚠ Common Mistakes

  • Adding role="button" to a <div> and stopping there: keyboard users can't reach or press it
  • Using role="menu" for site navigation: screen readers expect app-style arrow keys
  • Repeating native roles (<nav role="navigation">): harmless noise that validators flag

✓ Tips & Best Practices

  • Copy widget patterns from the WAI-ARIA Authoring Practices Guide (APG)
  • Check computed roles in DevTools' Accessibility pane
  • Remove any ARIA you can't explain; it often does more harm than good

Quick Summary

  • first rule: use native HTML
  • role: what an element is
  • implicit roles: built into elements
  • ARIA adds no behavior: write the keyboard JS
