Projects & Performance

projects config · pool threads / forks · isolate · --shard · maxWorkers · --changed in CI · slow-test reporting

One Repo, Several Test Setups, Fast Runs

Projects run different test setups in one Vitest command: unit tests in node, component tests in jsdom, browser tests in Chromium, or one project per package in a monorepo. Speed comes from parallel workers (pool), skipping per-file isolation when tests are safe, sharding across CI machines, and running only tests affected by a change.

Notes

  • projects replaced the old vitest.workspace file
  • Default pool is forks (child processes); threads can be faster
  • isolate: false reuses module state between files: only for pure tests
  • Slow tests are marked in the default reporter (over slowTestThreshold)

Under the Hood

  • Each worker runs test files one at a time; files spread across workers
  • forks uses child processes (most compatible); threads uses worker threads (less overhead)
  • --shard=1/3 splits the file list into thirds; each CI job runs one

Projects and Speed Settings

// vitest.config.ts
export default defineConfig({
  test: {
    projects: [
      { extends: true, test: { name: 'unit', environment: 'node',
          include: ['src/**/*.test.ts'] } },
      { extends: true, test: { name: 'dom', environment: 'happy-dom',
          include: ['src/**/*.test.tsx'] } },
      'packages/*',                     // each package's own config
    ],
    pool: 'threads',
    maxWorkers: 4,
    slowTestThreshold: 300,
  },
})

// $ npx vitest --project unit
// CI: shard across 3 jobs, then merge
// $ npx vitest run --shard=1/3 --reporter=blob
// $ npx vitest run --shard=2/3 --reporter=blob
// $ npx vitest --merge-reports --reporter=junit

Code Explained

extends: true makes a project inherit the root config (plugins, aliases)
A glob like packages/* picks up each package's own Vitest config
--reporter=blob saves partial results that --merge-reports combines
--project runs one project locally

Jest ↔ Vitest

  • Jest: projects: [...] in jest.config with separate configs per project
  • Jest: --shard=1/3, --maxWorkers; workers are child processes
  • Jest has no isolate: false equivalent

TypeScript

  • Give type tests their own project with typecheck: { enabled: true }
  • Monorepo packages can each extend a shared base config

Prefer / Avoid

  • one config forcing jsdom on every file → node and dom projects
  • one long CI job → --shard across jobs
  • vitest.workspace.ts → test.projects

Pool Options

OptionEffect
pool: "forks"Child processes (default, most compatible)
pool: "threads"Worker threads (faster, some native modules break)
maxWorkersParallel worker cap
isolate: falseReuse modules across files (faster, riskier)

⚠ Common Mistakes

  • isolate: false with tests that change globals, causing order-dependent failures
  • threads with native modules that aren't thread-safe
  • Projects without extends: true that lose the root plugins and aliases

✓ Tips & Best Practices

  • Start with defaults; profile before tuning pools
  • Use --changed in PR builds and a full run on main
  • Put browser-mode tests in their own project

Quick Summary

  • projects — several setups in one run
  • pool — forks (default) / threads
  • --shard + blob — split across CI jobs
  • isolate: false — faster, only for pure tests
