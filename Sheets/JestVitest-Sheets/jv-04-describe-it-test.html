Sheet 04

describe, it & test

describe · it vs test · nesting · test names · import { test, expect } from 'vitest' · file naming *.test.ts

Structure That Reads Like a Spec

describe(name, fn) groups related tests and can nest; it(name, fn) and test(name, fn) are the same function and define one test. Names combine into a sentence in the report: total > applies a discount. Tests run in the order written within a file; files run in parallel workers.

Notes

  • A test passes if its function returns (or its promise resolves) without throwing
  • An async test can await anything (sheet 10)
  • Third argument: timeout in ms or options { timeout, retry }
  • Empty describe blocks are allowed but report nothing

Grouping Tests

import { describe, it, test, expect } from 'vitest'
import { Cart } from './cart'

describe('Cart', () => {
  describe('add', () => {
    it('adds a new item', () => {
      const cart = new Cart()
      cart.add('apple', 2)
      expect(cart.count('apple')).toBe(2)
    })

    it('increases the quantity of an existing item', () => {
      const cart = new Cart()
      cart.add('apple', 2)
      cart.add('apple', 1)
      expect(cart.count('apple')).toBe(3)
    })
  })

  test('total is 0 when empty', () => {
    expect(new Cart().total()).toBe(0)
  })

  it('loads remote prices', async () => {
    await expect(new Cart().loadPrices()).resolves.toBeUndefined()
  }, 10_000)                           // per-test timeout
})

Code Explained

Report names join with >: Cart > add > adds a new item
Each test builds its own Cart, so tests stay independent
it and test are aliases; pick one style per project
The last argument sets a timeout for slow tests

Jest ↔ Vitest

  • Identical in Jest: describe, it, test (as globals)
  • Jest timeout: same third argument, or jest.setTimeout(ms)
  • Vitest also accepts an options object: it(name, { retry: 2 }, fn)

TypeScript

  • Annotate test data with satisfies to catch shape mistakes: const item = {…} satisfies Item
  • Files can be .test.ts or .test.tsx; both run directly

Prefer / Avoid

  • it("works") → names describing behavior: it("rejects a negative discount")
  • shared let cart mutated by every test → build it in beforeEach or each test
  • deep nesting of describe → two levels is usually enough

Test API

Naming Styles

StyleExample
Behaviorit("rejects a negative discount")
Given / when / thenit("given an empty cart, total is 0")
Method + casedescribe("add") → it("increases quantity")

⚠ Common Mistakes

  • Putting setup code directly in describe bodies; it runs at collection time, before any hooks
  • Tests that depend on the previous test's side effects
  • Async tests without await or return, which pass before the work finishes

✓ Tips & Best Practices

  • Read the report as a spec; if the names don't make sense together, rename them
  • Keep one behavior per test
  • Use test.todo("…") to list cases you still need to write

Quick Summary

  • describe — group
  • it / test — one test
  • names join into a sentence
  • third arg — timeout or options
