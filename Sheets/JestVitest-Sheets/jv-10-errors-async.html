Testing Throws and Promises

To test that code throws, wrap the call in a function: expect(() => fn()).toThrow(...). For promises, make the test async and await expect(promise).resolves or .rejects. Forgetting the await is the classic bug: the test finishes before the promise settles and passes no matter what.

Notes

  • toThrow accepts a string (substring), regex, class or error object
  • Always await (or return) .resolves / .rejects
  • expect.assertions(n) fails if fewer assertions ran, catching skipped catch blocks
  • Unhandled rejections during a test fail the run

Under the Hood

  • An async test returns a promise; the runner waits for it
  • A .rejects chain without await creates a promise nobody waits for, so the test ends first
  • Vitest reports such dangling promises as errors when they reject later

Throws and Promises

test('rejects a bad discount', () => {
  expect(() => total([10], 2)).toThrow(RangeError)
  expect(() => total([10], 2)).toThrow('discount 0..1')
  expect(() => total([10], 2)).toThrow(/0\.\.1/)
})

test('loads a user', async () => {
  await expect(fetchUser(1)).resolves.toMatchObject({ id: 1 })
})

test('fails for a missing user', async () => {
  await expect(fetchUser(999)).rejects.toThrow(NotFoundError)
})

test('plain await style', async () => {
  const user = await fetchUser(1)
  expect(user.name).toBe('Ann')
})

test('catch block runs', async () => {
  expect.assertions(1)
  try {
    await fetchUser(999)
  } catch (e) {
    expect(e).toBeInstanceOf(NotFoundError)
  }
})

Code Explained

expect(total(...)) without the arrow function throws before expect runs
.rejects.toThrow(Class) checks the rejection reason's type
Plain await + assertions is often the clearest async style
expect.assertions(1) fails the test if fetchUser unexpectedly resolves

Jest ↔ Vitest

  • Same in Jest, except Jest 30 removed the toThrowError alias; use toThrow
  • Jest still allows done callbacks; Vitest doesn't (use promises)

TypeScript

  • In catch (e), e is unknown; narrow with toBeInstanceOf or if (e instanceof …)
  • await expect(p).resolves keeps p's resolved type for chained matchers

Prefer / Avoid

  • expect(p).rejects… without await → await expect(p).rejects…
  • try/catch without expect.assertions → .rejects or add expect.assertions(n)
  • done callbacks → async / await

⚠ Common Mistakes

  • expect(fn()).toThrow() instead of expect(() => fn()).toThrow()
  • Missing await on .resolves / .rejects
  • Using toThrowError after upgrading to Jest 30

✓ Tips & Best Practices

  • Use toThrow(ErrorClass) plus a message regex for precise checks
  • Turn on the @typescript-eslint/no-floating-promises lint rule to catch missing awaits
  • Prefer .rejects over try/catch in tests

Quick Summary

  • expect(() => fn()).toThrow() — sync errors
  • await expect(p).resolves / .rejects — promises
  • async tests — await anything
  • expect.assertions(n) — guard paths
