DOM Environments

environment: 'jsdom' vs 'happy-dom' · per-file @vitest-environment comment · document / window in tests · what's missing vs a browser

A Fake Browser in Node

Tests run in Node, which has no document or window. A DOM environment adds them: jsdom (most complete, slower) or happy-dom (faster, a little less complete). Set it globally in config or per file with a comment, so pure logic tests stay on the faster node environment. Neither does layout or real rendering; for that, use browser mode (sheet 19) or Playwright.

Notes

  • Install the one you use: npm i -D jsdom or happy-dom
  • Per-file comment must be the first comment in the file
  • Missing APIs (matchMedia, IntersectionObserver, ResizeObserver) need small stubs
  • getBoundingClientRect() returns zeros: there's no layout

Under the Hood

  • jsdom and happy-dom are JavaScript re-implementations of the DOM standards, not browsers
  • They parse HTML and run events, but compute no CSS layout and paint nothing
  • Anything that depends on sizes, scrolling or visibility needs a real browser

Choosing an Environment

// vitest.config.ts — default for all tests
test: { environment: 'node' }

// Button.test.tsx — this file only
// @vitest-environment jsdom
import { test, expect } from 'vitest'

test('adds a class on click', () => {
  document.body.innerHTML = '<button id="b">Save</button>'
  const btn = document.getElementById('b')!
  attachToggle(btn)
  btn.click()
  expect(btn.classList.contains('active')).toBe(true)
})

// vitest.setup.ts — stub what jsdom lacks
Object.defineProperty(window, 'matchMedia', {
  value: (query: string) => ({
    matches: false, media: query,
    addEventListener() {}, removeEventListener() {},
  }),
})

// projects: node for logic, jsdom for components (sheet 21)

Code Explained

node is the default and the fastest; only DOM tests need jsdom
The @vitest-environment comment overrides config for one file
matchMedia is missing in jsdom; many UI libraries call it on import
Projects (sheet 21) can assign environments by folder instead of comments

Jest ↔ Vitest

  • Jest: testEnvironment: "jsdom" needs the jest-environment-jsdom package (Jest 28+); Jest 30 ships jsdom 26
  • Per file: /** @jest-environment jsdom */

TypeScript

  • Add "lib": ["dom"] and DOM types in the test tsconfig
  • Non-null assertions (!) are common for getElementById; Testing Library queries avoid them

Prefer / Avoid

  • jsdom for every test file → node default + jsdom per file or project
  • testing layout / scroll in jsdom → browser mode or Playwright
  • hand-written innerHTML + querySelector → Testing Library (sheet 18)

⚠ Common Mistakes

  • Running every test in jsdom and wondering why the suite is slow
  • Asserting element sizes or visibility based on CSS in jsdom
  • Placing the environment comment after imports, where it's ignored

✓ Tips & Best Practices

  • Try happy-dom first; switch to jsdom when something is missing
  • Keep a shared setup file with the standard stubs
  • Move layout-dependent tests to browser mode

Quick Summary

  • jsdom / happy-dom — DOM in Node
  • // @vitest-environment jsdom — per file
  • no layout — sizes are zero
  • stub missing APIs in setup
