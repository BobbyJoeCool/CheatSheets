Shared Examples Become Tests

Behavior-Driven Development starts with conversations about concrete examples of how the system should behave, written in plain language everyone can read. Gherkin is the common format: a Feature with Scenarios of Given / When / Then steps. Step definitions map each step to code. The value is the shared understanding; the automation is a bonus. Tools: Cucumber (JVM, JS), behave and pytest-bdd (Python), playwright-bdd.

Notes

  • Write scenarios with product and QA before coding ("three amigos")
  • Describe behavior, not UI clicks: "When she checks out", not "When she clicks #btn-3"
  • Scenario Outlines + Examples tables parameterize scenarios
  • Gherkin adds a layer; skip it if nobody outside engineering reads the specs

A Feature File and Steps

Feature: Coupons at checkout

  Scenario: A valid coupon reduces the total
    Given a cart with items worth $50.00
    When the shopper applies coupon "SAVE10"
    Then the total is $45.00

  Scenario Outline: Coupons that are not accepted
    Given a cart with items worth $50.00
    When the shopper applies coupon "<code>"
    Then they see the message "<message>"
    Examples:
      | code     | message           |
      | OLD2024  | Coupon expired    |
      | NOPE     | Unknown coupon    |

# step definitions (pseudocode)
given "a cart with items worth ${amount}":  ctx.cart = make_cart(total=amount)
when  "the shopper applies coupon {code}":  ctx.result = apply_coupon(ctx.cart, code)
then  "the total is ${amount}":             assert ctx.cart.total == amount

Code Explained

Anyone on the team can read and challenge the scenarios
The Examples table runs the outline once per row
Steps are reusable phrases backed by code
Steps can drive a domain API, an HTTP API or a browser

Smell Check

  • You see scenarios full of CSS selectors and clicks → it means UI scripts, not behavior → do write steps in domain language
  • You see feature files nobody outside engineering reads → it means overhead without the benefit → do use plain tests with GWT names

⚠ Common Mistakes

  • Writing Gherkin alone, after the code, as a reporting format
  • Huge step libraries with near-duplicate phrases
  • One scenario testing a whole user journey with 30 steps

✓ Tips & Best Practices

  • Keep scenarios to a handful of steps
  • Run example-mapping sessions before writing scenarios
  • Use BDD where business rules are rich and stakeholders care

Quick Summary

  • BDD — shared concrete examples
  • Gherkin — Feature / Scenario / Given-When-Then
  • step definitions — phrases → code
  • domain language, not UI clicks
