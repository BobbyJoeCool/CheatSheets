Sheet 12

Designing for Testability

seams · dependency injection · injecting a clock · injecting randomness · pure functions · functional core, imperative shell

Code That Is Easy to Test Is Easy to Change

Code is hard to test when it reaches out for its dependencies: calls now(), random(), new HttpClient() or a global. A seam is a place where a test can substitute something. The simplest seam is dependency injection: pass collaborators in (constructor or parameter). Even better, keep decisions in pure functions (same input, same output) and push I/O to a thin outer layer: functional core, imperative shell.

Notes

  • Time, randomness, IDs, env vars and I/O are the usual hidden dependencies
  • Constructor injection works without a framework
  • Pure functions need no doubles at all
  • If a test needs heavy patching, the design is asking for a seam

Hidden Dependencies → Injected

# ✗ hard to test: reaches for time, randomness and the network
function create_invite(email):
    token  = random_hex(16)
    expires = now() + days(7)
    http_post("https://mail.example/send", { to: email, token })
    return Invite(email, token, expires)

# ✓ functional core: pure, no doubles needed
function build_invite(email, token, today) -> Invite:
    return Invite(email, token, expires=today + days(7))

# ✓ imperative shell: dependencies passed in
function create_invite(email, clock, tokens, mailer):
    invite = build_invite(email, tokens.next(), clock.today())
    mailer.send(email, invite.token)
    return invite

test "invite expires in 7 days":
    invite = build_invite("a@x.com", "t1", today="2026-11-04")
    assert invite.expires == "2026-11-11"

Code Explained

The pure build_invite is tested with plain values
The shell takes a clock, token source and mailer, so tests pass fakes
Production wiring passes the real clock and mailer once, at start-up
Most logic moves into the easy-to-test core

Smell Check

  • You see tests patching 5 modules to run one function → it means hidden dependencies → do inject them
  • You see static / global singletons used everywhere → it means no seams → do pass instances in

⚠ Common Mistakes

  • Making everything an interface "for testing" even when there's one implementation and no I/O
  • Injecting the clock but still calling now() deep inside
  • Refactoring for testability without tests to protect the refactor (see sheet 35)

✓ Tips & Best Practices

  • Pass a clock wherever business rules depend on time
  • Extract decisions into pure functions first; it's the cheapest win
  • Wire real dependencies in one place (main, the DI container)
