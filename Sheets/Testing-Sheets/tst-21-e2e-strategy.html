Sheet 21

End-to-End Test Strategy

critical user journeys · stable selectors · auth & test data setup · environments · keeping the suite small

Few, Valuable, Reliable

E2E tests are the most expensive tests you have, so spend them on critical user journeys: sign up, log in, search, buy, the flows that lose money or users when broken. Make each test independent: set up data and auth through APIs rather than clicking through the UI, use stable selectors (roles, test IDs), and rely on auto-waiting instead of sleeps. Run them against a known environment.

Notes

  • Reuse a logged-in session (storage state) instead of logging in every test
  • Create test data via API or seed scripts; clean up or use unique names
  • Run a small smoke subset on every deploy, the full set before release
  • Record traces / videos on failure (sheet 31)

A Journey Test With API Setup

suite setup:
    api.login_as("ann") → save session to "ann.json"      # once

test "returning customer reorders a past purchase" [tag: critical]:
    use session "ann.json"                                  # skip the login UI
    order = api.create_order(customer="ann", sku="A1")     # fast setup via API
    open_page("/orders")
    click(by_role("row", name=order.reference) → by_role("button", name="Reorder"))
    click(by_role("button", name="Checkout"))
    expect(by_role("heading", name="Order confirmed")).visible

# ✗ avoid
sleep(3)                                  # use waiting assertions
click("#app > div:nth-child(4) > button")  # use roles / test IDs
test 2 depends on data from test 1        # each test sets up its own

Code Explained

Logging in once and reusing the session removes minutes from a suite
API setup makes the test about the journey, not the setup screens
Waiting assertions retry until the page is ready, so no sleeps
Tagging lets CI run critical journeys on every deploy

Smell Check

  • You see an E2E suite that takes an hour → it means too many tests or UI setup → do cut to critical journeys and set up via API
  • You see sleep calls in E2E tests → it means timing guesses → do use auto-waiting assertions

⚠ Common Mistakes

  • Logging in through the UI in every test
  • Tests that share and mutate the same records
  • Running the full E2E suite against production

✓ Tips & Best Practices

  • Keep a short list of critical journeys and review it each quarter
  • Give every test unique data (timestamped names)
  • Fail fast in CI with a smoke subset first

Quick Summary

  • critical journeys only
  • auth and data via API, not the UI
  • roles / test IDs + auto-waiting
  • independent tests, known environment
