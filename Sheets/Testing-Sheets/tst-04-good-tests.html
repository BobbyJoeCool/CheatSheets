Sheet 04

What Makes a Good Test

FIRST (fast, isolated, repeatable, self-validating, timely) · deterministic · readable · behavior over implementation · one reason to fail

Fast, Trustworthy, Readable, Behavior-Focused

A good test is fast, isolated from other tests, repeatable (same result every run), self-validating (pass or fail, no reading logs), and written timely, close to the code: the FIRST acronym. It tests behavior (what the code promises) rather than implementation details (how it does it today), so refactoring doesn't break it. And it fails for one reason you can read from its name.

Notes

  • A test that sometimes fails is worse than no test: people learn to ignore red
  • Test the public API of a unit, not its private helpers
  • Readable beats clever: a test is read far more often than written
  • "Would this test survive a refactor that keeps behavior?"

Interview Angle

  • Q: "What makes a good unit test?" Walk through FIRST
  • Add *behavior, not implementation* with an example (testing output vs asserting private calls)
  • Mention determinism: no real clock, network or randomness

Implementation-Coupled vs Behavior-Focused

# ✗ coupled to implementation: breaks on any refactor
test "total calls _sum_lines then _apply_tax":
    cart = Cart()
    spy(cart, "_sum_lines"); spy(cart, "_apply_tax")
    cart.total()
    assert cart._sum_lines.called_once
    assert cart._apply_tax.called_after(cart._sum_lines)

# ✓ tests the promise: survives refactors
test "total includes 7% tax":
    cart = Cart(tax_rate=0.07)
    cart.add(price=100.00)
    assert cart.total() == 107.00

# ✗ not repeatable: depends on today's date
test "trial is active":   assert Trial(start=today()).active()
# ✓ repeatable: fixed clock (sheet 12)
test "trial is active on day 13":
    clock = FixedClock("2026-11-13")
    assert Trial(start="2026-11-01", clock=clock).active()

Code Explained

The first test fails if you merge the two helpers, even though nothing a user sees changed
The second test pins down the observable result
Real dates make tests pass today and fail next month
Injecting a clock makes time a test input like any other

In Your Stack

  • pytest plain functions + fixtures; monkeypatch the clock ↗13

Smell Check

  • You see tests that break on every refactor → it means they test implementation → do assert on outputs and public behavior
  • You see "rerun and it passes" → it means non-determinism → do remove real time, randomness and shared state

Behavior vs Implementation

Test thisNot this
Return valuesPrivate methods
State changes others can seeInternal call order
Calls across boundaries (email sent)Calls between your own classes
Errors raised for bad inputWhich helper raised them

⚠ Common Mistakes

  • Making private methods public just to test them
  • Asserting on log messages instead of results
  • Tests that pass alone but fail in the full suite

✓ Tips & Best Practices

  • If a test is hard to write, the design may need a seam (sheet 12)
  • Run tests in random order to catch hidden dependencies
  • Name tests so a failure reads like a broken requirement

Quick Summary

  • FIRST — fast, isolated, repeatable, self-validating, timely
  • deterministic — no real clock / network / randomness
  • behavior over implementation
  • one reason to fail
