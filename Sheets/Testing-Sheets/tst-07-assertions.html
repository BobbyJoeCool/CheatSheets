Sheet 07

Writing Useful Assertions

exact vs loose assertions · assertion messages · approximate equality · collections & order · assertion roulette · custom matchers

Assertions Decide What a Test Proves

An assertion should be exact enough to catch the bug you care about and loose enough to ignore details that don't matter (generated IDs, timestamps, order of a set). Compare whole values for a single readable diff, use tolerance for floats, and name what you check. Many unlabeled asserts in one test, where you can't tell which failed, is called assertion roulette.

Notes

  • assert result (truthy) proves very little
  • Order matters for lists, not for sets: use the right comparison
  • Floats need a tolerance; money is better as integer cents or decimals
  • Custom matchers give domain-specific failure messages

Precise, Readable Checks

# ✗ too loose — passes for almost anything
assert response
assert len(orders) > 0

# ✓ exact on what matters, flexible on the rest
assert response.status == 201
assert response.body == {
    id:        any(String),          # generated — don't pin it
    createdAt: any(Date),
    status:    "NEW",
    total:     45.00,
}

assert approx(order.tax, 3.15, abs=0.005)       # floats
assert sorted(tags) == ["gift", "rush"]          # order doesn't matter
assert lines == [("A1", 2), ("B2", 1)]           # order matters

# ✗ roulette: which one failed?
assert a; assert b; assert c; assert d
# ✓ grouped with labels, all reported
assert_all("address", street == "1 Main", city == "Tripoli")

Code Explained

Comparing the whole body gives one diff showing every wrong field
any(String) keeps the test stable without ignoring the field entirely
Sort or use a set comparison when order isn't part of the contract
Grouped assertions report every failure, not just the first

Smell Check

  • You see assertTrue(x.equals(y)) → it means the failure will say only "expected true" → do use an equality assertion that prints both values
  • You see tests asserting on a timestamp → it means flaky by design → do freeze time or use a matcher

⚠ Common Mistakes

  • Asserting only that no exception was thrown
  • Copying the implementation into the test to compute the expected value
  • Ignoring whole fields to make a flaky test pass

✓ Tips & Best Practices

  • Write the expected value as a literal the reader can check by eye
  • Mutation testing (sheet 25) shows which assertions are too weak
  • Add a custom matcher when the same complex check appears in many tests

Quick Summary

  • exact on what matters, loose on the rest
  • whole-value equality for one diff
  • approx for floats
  • avoid assertion roulette
