Tests Buy the Freedom to Change Code

An automated test runs a piece of code with known inputs and checks the result, every time, in seconds. The real payoff isn't finding today's bug; it's confidence: you can refactor, upgrade a library or add a feature and know within minutes whether something that used to work broke (a regression). Good tests also document behavior: they show how code is meant to be used, and they stay correct because they run.

Notes

  • A bug found while coding costs minutes; the same bug in production can cost days
  • Tests don't prove code correct; they reduce risk where you point them
  • Manual testing still matters for exploring; automate what you check repeatedly
  • This set uses pseudocode; In Your Stack links to real syntax

Anatomy of a Test (house style, sheet 05)

test "cart total applies a 25% discount":
    # Arrange — build the situation
    cart = Cart()
    cart.add(item="apple", price=10.00, qty=2)

    # Act — do the one thing under test
    total = cart.total(discount=0.25)

    # Assert — check the outcome
    assert total == 15.00

# A test runner finds tests, runs each in isolation,
# and reports: 1 passed, 0 failed (0.01 s)

Code Explained

The name states the behavior, so a failure reads as a broken promise
Arrange-Act-Assert keeps setup, action and check visibly separate
One clear outcome per test makes failures easy to diagnose
Runs in milliseconds, so it can run on every save and every push

In Your Stack

  • pytest def test_…(): + plain assert ↗01
  • Vitest it("…", () => expect(x).toBe(y)) ↗01
  • JUnit @Test void …() + assertEquals ↗01
  • Playwright test("…", async ({ page }) => …) for the browser ↗01

Smell Check

  • You see a suite nobody runs before merging → it means tests aren't trusted or are too slow → do make them fast and required in CI
  • You see tests added only after bugs → it means no safety net while building → do test as you write the feature

What Tests Give You

⚠ Common Mistakes

  • Treating a passing suite as proof the software is correct
  • Writing tests only to hit a coverage number
  • Skipping tests "to go faster" and paying for it in debugging time later

✓ Tips & Best Practices

  • Start with the code that would hurt most if it broke
  • Keep tests fast enough to run constantly
  • Read a test as documentation: could a newcomer learn the behavior from it?
