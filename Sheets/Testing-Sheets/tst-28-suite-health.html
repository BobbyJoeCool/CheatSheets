Test Suite Health

suite speed · flake rate · pyramid shape · dead tests · reviewing tests in PRs · test ownership

Keep the Safety Net Strong

A test suite is a product the team depends on, and it decays without care. Track a few health signals: speed (how long until feedback), flake rate, pyramid shape (are slow tests multiplying?), and failures that are ignored or skipped. Review tests in PRs as carefully as code, give suites owners, and delete tests that no longer earn their keep.

Notes

  • A suite people avoid running is already failing
  • Most CI systems report slowest and flakiest tests
  • Skipped tests rot; review them regularly
  • Deleting a useless test is a valid improvement

A Suite Health Report

suite health — week 45
  total tests:          3,412   (+58)
  median CI time:       9m 40s  (target < 10m)
  slowest 10 tests:     4m 12s  combined   ← push down or parallelize
  flaky (retried):      7 tests (0.2%)    ← owners assigned
  skipped / disabled:   23                ← 6 older than 90 days
  layer mix:            unit 81% · integration 16% · e2e 3%
  coverage on changed:  87%               (floor 80%)

PR review checklist for tests:
  [ ] does each new test fail if the feature breaks?
  [ ] names describe behavior
  [ ] no sleeps, no real network, no shared state
  [ ] the cheapest layer that catches the bug

Code Explained

Trends matter more than single numbers
The slowest few tests often dominate suite time
Old skipped tests are either fixed or deleted
A short checklist keeps PR review of tests consistent

Smell Check

  • You see CI time creeping up every month → it means nobody owns speed → do set a time budget and fix the slowest tests
  • You see dozens of skipped tests from last year → it means dead tests → do fix or delete them

Unreadable testsFactories, better names, smaller tests

⚠ Common Mistakes

  • Measuring only test count
  • Letting "known failures" stay red in CI
  • Nobody responsible for the suite as a whole

✓ Tips & Best Practices

  • Review test-health numbers in a regular team meeting
  • Give the slowest-test list an owner
  • Make deleting bad tests normal
