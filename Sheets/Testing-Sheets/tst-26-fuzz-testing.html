Fuzz Testing

random vs coverage-guided fuzzing · corpus · crashes as bugs · Atheris · Jazzer · go test -fuzz

Throw Unexpected Input Until Something Breaks

Fuzzing feeds huge numbers of malformed or random inputs to code that parses or handles untrusted data, looking for crashes, hangs, memory errors and unexpected exceptions. Coverage-guided fuzzers (libFuzzer, AFL, Jazzer, Atheris, Go's native fuzzing) watch which code paths each input reaches and mutate the inputs that find new paths. A saved corpus of interesting inputs makes later runs smarter.

Notes

  • Best targets: parsers, decoders, file formats, protocol handlers
  • Every crash found becomes a regression test
  • Run continuously (OSS-Fuzz, CI nightly) rather than once
  • Related to property-based testing; fuzzers focus on crashes and security

A Fuzz Target

fuzz_target(data: bytes):
    try:
        doc = parse_invoice(data)
    except InvoiceParseError:
        return                      # expected: bad input rejected cleanly
    # anything else (crash, other exception, hang) is a bug
    assert doc.total >= 0

# run
fuzz parse_invoice --corpus corpus/invoices --max-time 10m
# found: IndexError with input b"INV\x00\x00;;"
# → saved to crashes/crash-3f2a…
# → add as a regression test:
test "parser rejects truncated header":
    raises InvoiceParseError: parse_invoice(b"INV\x00\x00;;")

Code Explained

The target defines what "acceptable" failure looks like
Any other exception is reported with the input that caused it
The corpus starts with real sample files and grows with interesting inputs
Each finding becomes a normal example test

In Your Stack

  • pytest Atheris (coverage-guided) or Hypothesis for structured fuzzing ↗22
  • Vitest Jazzer.js; fast-check for structured input ↗06
  • JUnit Jazzer with @FuzzTest on JUnit ↗14
  • Playwright not a fuzzer; API tests can send malformed payloads

Smell Check

  • You see a parser of untrusted files with only happy-path tests → it means security bugs waiting → do add a fuzz target and run it nightly
  • You see fuzz crashes triaged once and forgotten → it means regressions return → do turn each crash into a test

⚠ Common Mistakes

  • Fuzzing code that has no clear failure condition
  • Running a fuzzer once for a minute and calling it done
  • Not saving the corpus between runs

✓ Tips & Best Practices

  • Seed the corpus with real sample inputs
  • Run fuzzers nightly with a time limit
  • Fuzz anything that parses data from users or the network

Quick Summary

  • fuzzing — massive unexpected input
  • coverage-guided — mutate inputs that find new paths
  • corpus — remembered interesting inputs
  • crash → regression test
