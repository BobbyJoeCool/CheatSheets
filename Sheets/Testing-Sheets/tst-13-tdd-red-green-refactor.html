TDD: Red, Green, Refactor

write a failing test · simplest pass · refactor on green · baby steps · triangulation · test list

Let a Failing Test Drive the Next Line of Code

Test-Driven Development is a short loop: write a small test that fails (red), write the simplest code that passes (green), then refactor with the test as a safety net. Repeat in minutes. Keep a test list of cases to cover, take baby steps, and use triangulation (a second example) to force real logic instead of a hard-coded answer.

Notes

  • Seeing red first proves the test can fail
  • "Simplest" can be a hard-coded return; the next test forces generality
  • Refactor only on green, test and code both
  • TDD is a design technique as much as a testing one

Interview Angle

  • Q: "Do you practice TDD?" Describe red-green-refactor and a real case where it helped
  • Be honest about where you don't (spikes, UI layout) — interviewers value judgment
  • Mention that writing the test first shapes a cleaner API

Three Turns of the Loop

# Test list: 0 items · 1 item · many items · discount · invalid discount

# RED
test "empty cart totals 0":       assert Cart().total() == 0
# GREEN — simplest thing
class Cart: total() -> return 0

# RED
test "one item totals its price":
    cart = Cart(); cart.add(price=5.00)
    assert cart.total() == 5.00
# GREEN — triangulation forces a real implementation
class Cart:
    items = []
    add(price) -> items.append(price)
    total()    -> return sum(items)

# REFACTOR — tests stay green
class Cart:
    lines = []
    add(price, qty=1) -> lines.append(Line(price, qty))
    total()           -> return sum(l.price * l.qty for l in lines)

Code Explained

The first green is a constant; the second test makes the constant wrong
Each step is small enough that a failure points straight at the change
Refactoring renames and reshapes while the tests prove behavior is unchanged
The test list keeps you from forgetting cases while staying in small steps

Smell Check

  • You see tests written after all the code, then adjusted until green → it means tests confirm code, not requirements → do see each test fail first
  • You see huge steps between greens → it means debugging instead of TDD → do shrink the next test

The Loop

StepGoalRule
RedA failing test for one small behaviorMust fail for the right reason
GreenPass as fast as possibleSimplest code; no extra features
RefactorClean up code and testsOnly on green; behavior unchanged

Techniques

TechniqueUse

⚠ Common Mistakes

  • Writing several tests before any code
  • Skipping the refactor step, so code piles up
  • Testing private details because the design came first

✓ Tips & Best Practices

  • Keep the loop under a few minutes
  • Commit on green so you can always step back
  • Start a bug fix with a failing regression test

Quick Summary
