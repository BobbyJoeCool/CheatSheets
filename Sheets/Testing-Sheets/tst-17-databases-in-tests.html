Databases in Tests

transaction rollback per test · Testcontainers · running migrations · seeding · cleanup strategies · parallel-safe data

Real Databases Without Slow, Shared Mess

Test against the same engine and version as production, started in a container. Apply the real migrations once, so tests also prove migrations work. Each test then gets a clean slate by rolling back a transaction, truncating tables, or using unique data. Seed only shared reference data; each test creates the rest itself.

Notes

  • Container start-up costs seconds; do it once per run
  • Rollback can't test code that commits or uses multiple connections
  • Parallel workers need separate databases or schemas
  • Never point tests at a shared dev or staging database

Interview Angle

  • Q: "How do you test code that uses a database?" Real engine in a container, migrations once, isolation per test
  • Compare with in-memory fakes: faster, but miss SQL dialect bugs
  • Mention parallel safety (database per worker or unique data)

Database Test Lifecycle

once per run:
    pg = PostgresContainer("postgres:17").start()
    run_migrations(pg.url)                  # the real migration files
    seed(pg, reference_data="countries, plans")

per worker (parallel runs):
    schema = "test_" + worker_id            # or one database per worker

per test:
    tx = pg.begin()
    yield                                   # test runs inside tx
    tx.rollback()

test "monthly report counts only paid orders":
    make_order(status="PAID", month="2026-10")
    make_order(status="NEW",  month="2026-10")
    assert monthly_report("2026-10").order_count == 1

Code Explained

Running migrations in tests catches broken migrations before deploy
Reference data is seeded once; scenario data is created per test
A schema per worker keeps parallel tests from colliding
Factories (sheet 08) create rows with valid defaults

Smell Check

  • You see tests that fail when run twice → it means data left behind → do roll back or clean up per test
  • You see a 2 GB fixture dump loaded before tests → it means mystery guests everywhere → do seed minimal reference data, build the rest per test

⚠ Common Mistakes

  • Using a shared staging database for automated tests
  • Skipping migrations and creating schema from ORM models, so migrations go untested
  • Huge shared fixture files that every test depends on

✓ Tips & Best Practices

  • Pin the database image version to production's
  • Use a container reuse option locally to avoid restart cost
  • Assert with SQL when you need to prove what was actually stored

Quick Summary

  • real engine in a container
  • migrations once per run
  • rollback / truncate / unique data per test
  • database per worker for parallel runs
