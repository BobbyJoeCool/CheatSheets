Accessibility Testing

automated checks (axe) · what automation misses · keyboard-only pass · screen reader spot checks · WCAG levels

Can Everyone Use It?

Accessibility testing checks that people using keyboards, screen readers, magnification or other assistive technology can use the product, against the WCAG guidelines (level AA is the usual target). Automated tools like axe catch missing labels, low contrast and invalid ARIA, roughly a third of issues. The rest needs manual checks: keyboard-only navigation, focus order, and screen reader spot checks.

Notes

  • Run automated checks in component and E2E tests
  • Querying by role / label in tests is a free accessibility check
  • Keyboard: every action reachable with Tab, Enter, Space, Esc, arrows
  • The HTML, CSS and SwiftUI sets have Accessibility boxes on every sheet

Automated and Manual Checks

# automated: run axe on each key page / component state
test "checkout page has no a11y violations":
    open_page("/checkout")
    results = axe.analyze(tags=["wcag2a", "wcag2aa"])
    assert results.violations == []

test "error state of login form is accessible":
    render(LoginForm, error="Wrong password")
    assert axe(container).violations == []
    expect(by_role("alert")).has_text("Wrong password")    # announced

# manual pass (per release, ~15 min per flow)
keyboard only:   Tab through checkout — order logical? focus visible?
                 open/close the dialog with Enter / Esc — focus returns?
screen reader:   VoiceOver / NVDA on the form — labels read? errors announced?
zoom 200%:       nothing cut off, no horizontal scrolling

Code Explained

axe runs dozens of rules in milliseconds
Error states are tested too, not just the default page
Manual checks cover what tools can't judge: order, meaning, usability
Fix violations in components so every page using them benefits

Smell Check

  • You see a passing axe scan treated as "accessible" → it means two-thirds of issues unchecked → do add keyboard and screen reader passes
  • You see tests that click by CSS selector on divs → it means non-semantic UI → do use buttons and roles; test by role

⚠ Common Mistakes

  • Testing only the happy path and ignoring error and loading states
  • Adding ARIA to fix things native HTML would do
  • Leaving accessibility to a pre-launch audit

✓ Tips & Best Practices

  • Add an axe check to every component test file
  • Do a keyboard-only pass on each new flow
  • Fix issues in shared components first

Quick Summary

  • WCAG AA — the usual target
  • axe — automated, ~1/3 of issues
  • keyboard + screen reader — manual
  • query by role — a11y check for free
