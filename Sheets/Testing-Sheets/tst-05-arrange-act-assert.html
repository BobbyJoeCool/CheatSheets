Sheet 05

Arrange-Act-Assert & Given-When-Then

AAA structure · Given-When-Then · one act per test · setup vs test body · house style for this set

A Shape Every Reader Recognizes

Arrange-Act-Assert splits a test into three parts: build the situation, perform one action, check the outcome. Given-When-Then is the same idea in behavior language. Keeping the parts visibly separate (blank lines or comments) makes any test readable at a glance, and a single Act keeps the reason for a failure obvious. This sheet also defines the pseudocode style used throughout the set.

Notes

  • If you need two Acts, you probably have two tests
  • Shared Arrange code moves to fixtures / setup, not copy-paste
  • Asserting several facts about one outcome is fine
  • Avoid conditionals and loops in tests; they hide which path ran

House Style for This Set

test "<behavior in plain words>":        # one test, one behavior
    # Arrange
    user  = make_user(role="admin")        # factories (sheet 08)
    clock = FixedClock("2026-11-04")       # injected dependencies
    mailer = fake Mailer()                 # doubles named by role (sheet 10)

    # Act
    result = invite(user, "bo@example.com", clock, mailer)

    # Assert
    assert result.status == "SENT"
    assert mailer.sent_to == ["bo@example.com"]

expect(x).visible       # UI / async assertion that waits
raises Error: f(x)      # assert that f(x) raises
given / when / then     # behavior-style steps (sheet 15)

Code Explained

make_… builds test data with defaults (sheet 08)
fake, stub, mock say what kind of double an object is
Two asserts about the same result are one logical check
The real syntax for each line is one click away in In Your Stack

Smell Check

  • You see Act → Assert → Act → Assert in one test → it means several tests glued together → do split them
  • You see 40 lines of Arrange → it means missing factories or a design smell → do extract builders or simplify the API

Rules of Thumb

⚠ Common Mistakes

  • Hiding the Act inside a helper so readers can't see what's tested
  • Assertions in setup code that fail before the test starts
  • Using if in a test to choose expectations

✓ Tips & Best Practices

  • Read only the Act line: does it match the test name?
  • Put the expected value as a literal in the Assert
  • Use parameterized tests instead of loops

Quick Summary

  • Arrange — situation
  • Act — one action
  • Assert — outcome
  • Given / When / Then — same idea, behavior words
