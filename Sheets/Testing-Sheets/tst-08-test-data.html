Sheet 08

Test Data

literal data · builders · object mother · factories · fixtures · randomized data & seeds · golden files

Make the Important Data Obvious

Test data should show only what matters to the test and default everything else. A factory or builder creates a valid object with sensible defaults, and the test overrides just the fields it cares about. An object mother offers named, ready-made objects (premiumCustomer()). Random data can find surprises, but always log the seed. Golden files hold large expected outputs.

Notes

  • Mystery data ("why is age 37?") makes tests hard to read
  • Factories keep tests valid when a required field is added
  • Avoid sharing one mutable fixture across tests
  • Keep fixture files small and named for the scenario

Factories and Builders

# a factory with defaults: tests override only what matters
make_order(**overrides):
    defaults = { customer: make_customer(), status: "NEW",
                 lines: [line(sku="A1", qty=1, price=10.00)],
                 created_at: "2026-11-04T09:00:00Z" }
    return Order(defaults | overrides)

test "paid orders can't be cancelled":
    order = make_order(status="PAID")          # the one fact that matters
    raises CannotCancel: cancel(order)

# builder for complex objects
order = OrderBuilder().for_customer("ann").with_line("A1", 2).paid().build()

# object mother for well-known personas
customer = Customers.premium_in_germany()

# random data: reproducible with a seed
rng = Random(seed=env("TEST_SEED", default=1234))
email = fake.email(rng)

Code Explained

The test reads "a PAID order"; everything else is a valid default
Adding a required field later only changes the factory, not every test
Builders read well for objects with many optional parts
Logging and reusing the seed makes a random failure reproducible

Smell Check

  • You see a 30-field object literal in every test → it means no factory → do add one with defaults
  • You see tests reading one shared test_data.json → it means hidden coupling between tests → do give each test its own data

Data Patterns

PatternBest for
Literal valuesSmall, obvious inputs
Factory with defaultsMost domain objects
BuilderObjects with many optional parts
Object motherNamed personas reused widely
Fixture / seed fileReference data (countries, plans)
Golden fileLarge expected outputs

Random Data Rules

RuleWhy
Log the seedReproduce failures
Allow fixing the seedDebug locally
Keep values validTest the logic, not the generator
Prefer property-based toolsShrinking finds minimal cases

⚠ Common Mistakes

  • Unexplained magic numbers in test data
  • Production data dumps in test fixtures (privacy and size)
  • Random data without a logged seed

✓ Tips & Best Practices

  • Name test data after the scenario: expired_coupon, not coupon2
  • Keep factories next to the domain model they build
  • Use property-based testing (sheet 23) when you want lots of varied data on purpose

Quick Summary

  • factories — valid defaults, override what matters
  • builders / object mothers — readable complex data
  • seeds — reproducible randomness
  • golden files — large expected output
