Sheet 06

Naming & Organizing Tests

naming patterns (should…when…) · one behavior per test · grouping by unit / feature · file layout · test-to-code mapping

Find the Test, Read the Failure

A test name should state the behavior and the situation, so a failure report reads like a broken requirement: "rejects an expired coupon". Group tests the way readers look for them: by unit (one file per module) or by feature (one file per user-facing capability). Mirror the source tree so every code file has an obvious test file.

Notes

  • Names are for humans; long and specific beats short and vague
  • Nested groups (describe / @Nested / classes) express situations
  • Keep fixtures next to the tests that use them
  • Pick one naming pattern per repo and stick to it

Names That Read as Requirements

# ✗ vague
test "test1"
test "coupon"
test "testApplyCouponWorks"

# ✓ behavior + situation
group "apply_coupon":
    group "when the coupon is valid":
        test "takes 10% off the subtotal"
        test "records the coupon on the order"
    group "when the coupon is expired":
        test "rejects it with COUPON_EXPIRED"
        test "leaves the total unchanged"

# file layout mirrors the code
src/checkout/coupons.py      →  tests/checkout/test_coupons.py
src/cart/Cart.java           →  src/test/java/cart/CartTest.java
src/cart/cart.ts             →  src/cart/cart.test.ts

Code Explained

A failure reads "apply_coupon › when the coupon is expired › rejects it with COUPON_EXPIRED"
Groups hold shared setup for their situation
"Works" says nothing about what working means
Mirrored paths make the test for any file easy to find

In Your Stack

  • pytest test_*.py mirroring src/; classes as groups ↗03
  • Vitest describe nesting; *.test.ts next to the code ↗04
  • JUnit @Nested + @DisplayName ↗06
  • Playwright test.describe per page or flow ↗06

Smell Check

  • You see a test called testProcess with 12 asserts → it means an unnamed bundle of behaviors → do split and name each one
  • You see helpers duplicated across test files → it means no shared fixtures → do move them to a fixtures / conftest / support module

Naming Patterns

PatternExample
Behaviorrejects an expired coupon

Organizing Options

⚠ Common Mistakes

  • Naming tests after the method instead of the behavior
  • One giant test file per package
  • Test files that drift from the code layout after a refactor

✓ Tips & Best Practices

  • Read the test report like a spec; rename tests that don't make sense
  • Use groups for situations, test names for outcomes
  • Move or rename test files in the same commit as the code they cover

Quick Summary

  • name = behavior + situation
  • groups = situations
  • mirror the source tree
  • one pattern per repo
