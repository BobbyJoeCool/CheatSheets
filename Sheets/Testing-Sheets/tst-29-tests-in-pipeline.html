Tests in the Pipeline

pre-commit hooks · PR checks · stages (fast → slow) · fail fast · required checks · nightly suites

Fast Feedback First, Thorough Checks Later

Arrange checks so the fastest run first and the slowest run least often. Pre-commit hooks catch formatting and lint in seconds. PR checks run unit and integration tests and must pass to merge (required checks). Slower suites (full E2E, performance, mutation) run on merge, nightly or before release. Fail fast so people get the first signal in minutes.

Notes

  • Target: PR feedback in under ~10 minutes
  • Run tests affected by the change first where tools support it
  • Make the CI command the same as the local one
  • Nightly failures need an owner the next morning

A Staged Pipeline

# pre-commit (seconds, on the developer's machine)
- format + lint + type-check on changed files

# pull request (minutes, required to merge)
stages:
  - lint-and-types          # ~1 min, fail fast
  - unit-tests              # ~3 min, parallel
  - integration-tests       # ~5 min, real DB in a container
  - e2e-smoke               # ~3 min, critical journeys only

# main branch (after merge)
  - full e2e suite
  - build + deploy to staging
  - smoke tests against staging

# nightly
  - mutation tests on changed modules
  - performance / load tests
  - fuzzing (time-boxed)

Code Explained

Cheap checks run first so obvious mistakes fail in a minute
Only the PR stages block merging
Smoke tests against the deployed environment catch config problems
Expensive suites still run, just less often

In Your Stack

  • pytest pytest -x locally, matrix in CI, --junitxml ↗23
  • Vitest vitest run --changed in PRs, full on main ↗22
  • JUnit mvn verify / gradle check with Failsafe ITs ↗23
  • Playwright smoke tag on PR, full suite on main, sharded ↗63

Smell Check

  • You see a 45-minute PR pipeline → it means slow suites block every change → do move slow suites to post-merge or nightly
  • You see nightly failures unread for a week → it means no owner → do alert a rotating owner

⚠ Common Mistakes

  • Running everything on every commit until the pipeline is too slow to use
  • Optional checks that people ignore
  • CI commands that differ from what developers run locally

✓ Tips & Best Practices

  • Set a time budget for PR checks and defend it
  • Run tests in parallel and shard large suites (sheet 30)
  • Keep a small, reliable smoke suite for deploys

Quick Summary

  • fast checks first, slow ones later
  • PR checks required
  • nightly for expensive suites
  • same command locally and in CI
