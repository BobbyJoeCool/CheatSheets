TDD Styles

classicist (Chicago) vs mockist (London) · outside-in · inside-out · when TDD helps · when it doesn't

Two Schools and Two Directions

Classicist (Chicago / Detroit) TDD uses real objects and checks final state, mocking only awkward boundaries. Mockist (London) TDD mocks collaborators and checks interactions, discovering interfaces as it goes. Inside-out starts with core domain logic and builds up; outside-in starts from a user-facing (often acceptance) test and works inward. Most teams mix them.

Notes

  • Classicist tests survive refactoring better
  • Mockist tests give faster design feedback on roles and interfaces
  • Outside-in pairs well with BDD acceptance tests
  • Spikes and exploratory code are fine without TDD; rewrite with tests afterward

Same Feature, Two Styles

# CLASSICIST — real collaborators, check state
test "placing an order stores it and reserves stock":
    stock = InMemoryStock({ "A1": 5 })
    orders = InMemoryOrders()
    service = OrderService(orders, stock)
    service.place(cart_with("A1", qty=2))
    assert orders.count() == 1
    assert stock.available("A1") == 3

# MOCKIST — collaborators mocked, check interactions
test "placing an order saves it and reserves stock":
    orders = mock Orders; stock = mock Stock
    service = OrderService(orders, stock)
    service.place(cart_with("A1", qty=2))
    verify stock.reserve("A1", 2)
    verify orders.save(any Order)

# OUTSIDE-IN — start from the outermost failing test
acceptance "customer places an order"   → fails
  → controller test (mocks service)     → fails → passes
  → service test (fakes repositories)   → fails → passes
acceptance test now passes

Code Explained

The classicist test fails only if behavior changes
The mockist test also fails if the internal collaboration changes
Outside-in keeps every piece of code tied to a real need
In-memory fakes give classicist tests mockist-like speed

In Your Stack

  • pytest fakes in fixtures (classicist) or mocker (mockist) ↗14
  • Vitest vi.fn / vi.mock for mockist style ↗11
  • JUnit Mockito-heavy (mockist) vs fakes + slices ↗17
  • Playwright outside-in: start with a failing E2E test ↗25

Smell Check

  • You see every refactor breaking dozens of mock-based tests → it means over-specified interactions → do shift to state checks with fakes
  • You see no tests above the unit level → it means inside-out never reached the outside → do add an acceptance test per feature

⚠ Common Mistakes

  • Treating one school as the only "real" TDD
  • Outside-in without ever replacing mocks with integration coverage
  • Applying TDD to throwaway spikes and wasting time

✓ Tips & Best Practices

  • Default to classicist style; mock at boundaries
  • Use outside-in for new features with clear user stories
  • Throw away spike code and redo it test-first

Quick Summary

  • classicist — real objects, state checks
  • mockist — mocks, interaction checks
  • outside-in — start from the user
  • inside-out — start from the core
