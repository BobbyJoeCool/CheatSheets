Sheet 03

Types of Tests

unit · integration · end-to-end · contract · smoke · regression · acceptance · exploratory

Names for What a Test Covers and Why

Test types describe scope (how much of the system a test touches) or purpose (why it exists). Scope: unit, integration, end-to-end. Purpose: smoke (does it start at all?), regression (did a fixed bug come back?), acceptance (does it meet the requirement?), contract (do services agree on an API?). Exploratory testing is a person probing the app without a script. Teams use the words differently, so agree on definitions.

Notes

  • "Unit" can mean one function or one module; define it for your team
  • A regression test is usually added with the bug fix it guards
  • Smoke tests run right after deploy and must be fast
  • Tags / marks let one suite run different types at different times

Interview Angle

  • Q: "Unit vs integration vs end-to-end?" Define each by what it touches and what it can catch
  • Say where *you* draw the unit / integration line (e.g. "anything that touches the database is integration")
  • Mention contract tests for services — it signals experience

Same Product, Different Purposes

# SMOKE — after deploy: is the app alive?
test "health endpoint is up" [tag: smoke]:
    assert http_get("/health").status == 200

# REGRESSION — bug #142 must never return
test "order with 0.1 + 0.2 discount rounds to cents" [tag: regression]:
    assert order_total([10.00], discount=0.3) == 7.00

# ACCEPTANCE — written from the requirement
test "guest can check out without an account" [tag: acceptance]:
    given a guest with an item in the cart
    when they check out with an email only
    then an order confirmation is emailed

# CONTRACT — consumer's expectation of a provider API
contract "orders-ui expects GET /orders/7":
    response has { id: number, status: "NEW" | "PAID" }

Code Explained

Tags let you run smoke tests on deploy and the full suite on every PR
Regression tests name the bug they guard so nobody deletes them casually
Acceptance tests often use Given/When/Then (sheet 15)
Contract tests check API shape without running both services together (sheet 19)

In Your Stack

  • pytest @pytest.mark.smoke + -m smoke ↗12
  • Vitest projects or name filters per type ↗21
  • JUnit @Tag("smoke") + build tag filters ↗06
  • Playwright { tag: "@smoke" } + --grep @smoke ↗07

Smell Check

  • You see "unit tests" that need Docker → it means mislabeled integration tests → do tag them and run them separately
  • You see a bug fixed with no test → it means it can quietly return → do add a regression test in the same PR

By Scope

TypeTouches
UnitOne function / class, no I/O
IntegrationSeveral parts + real DB / HTTP / queue
End-to-endWhole deployed system via UI or API
ComponentOne UI component rendered in isolation

By Purpose

TypeAnswersWhen it runs
SmokeIs it alive?After every deploy
RegressionDid an old bug return?Every run
AcceptanceDoes it meet the requirement?PR / release
ContractDo services agree on the API?Both sides' CI
PerformanceIs it fast enough? (sheet 32)Nightly / pre-release
ExploratoryWhat did we not think of?By people, any time

⚠ Common Mistakes

  • Arguing about labels instead of what each test catches
  • Running slow integration tests in the "fast" job because they're called unit tests
  • Dropping manual exploratory testing entirely

✓ Tips & Best Practices

  • Write down your team's definitions in the repo's testing guide
  • Tag tests by type so CI can run them on different schedules
  • Name regression tests after the issue number

Quick Summary

  • scope — unit · integration · E2E
  • purpose — smoke · regression · acceptance · contract
  • exploratory — humans probing
  • tags — run types at different times
