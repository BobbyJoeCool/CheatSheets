Component Tests vs End-to-End Tests

what each catches · Testing Library philosophy · query by role · component test boundaries · cost per test

Test UI at the Lowest Level That Works

A component test renders one UI component (or a small group) in isolation with fake data and checks what a user sees and can do. An end-to-end test drives the real app in a real browser. Component tests are faster and pinpoint problems; E2E tests prove the whole thing works together. Both should interact like a user: find elements by role and label, not by CSS classes.

Notes

  • "The more your tests resemble the way your software is used, the more confidence they give" (Testing Library)
  • Mock the network at the component level; use the real backend in E2E
  • Visual and layout checks need a real browser
  • Querying by role doubles as an accessibility check

Same Form, Two Levels

# COMPONENT TEST — one component, fake data, fast
test "login form shows an error for a wrong password":
    render(LoginForm, onSubmit=fake returning error("wrong password"))
    type(by_label("Email"), "ann@x.com")
    type(by_label("Password"), "nope")
    click(by_role("button", name="Sign in"))
    expect(by_role("alert")).has_text("Wrong password")

# END-TO-END — real app, real backend, real browser
test "user can sign in and see their orders":
    open_page("/login")
    fill(by_label("Email"), "ann@x.com")
    fill(by_label("Password"), test_password)
    click(by_role("button", name="Sign in"))
    expect(by_role("heading", name="Your orders")).visible

Code Explained

The component test covers the error state without a server
The E2E test covers the real login flow once
Both find elements by label and role, as a screen reader would
Edge cases (lockout, validation) belong in component or API tests

Smell Check

  • You see selectors like .btn-primary > span:nth-child(2) → it means tests coupled to markup → do query by role, label or text
  • You see every UI state tested end-to-end → it means slow, flaky suite → do move states into component tests

⚠ Common Mistakes

  • Snapshotting whole component trees instead of asserting behavior
  • Testing implementation details like component state or hooks directly
  • No E2E test at all for the main flows

✓ Tips & Best Practices

  • Cover every visual state of a component (loading, empty, error, full)
  • If an element can't be found by role, fix its accessibility
  • Keep E2E for journeys that cross pages or services

Quick Summary

  • component — one piece, fake data, fast
  • E2E — whole app, real browser
  • query by role / label, like a user
  • states in component tests, journeys in E2E
