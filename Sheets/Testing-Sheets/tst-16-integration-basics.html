Integration Testing Basics

what "integration" covers · real vs fake dependencies · in-memory database pitfalls · test isolation · speed budget

Prove the Pieces Fit

An integration test runs several parts of the system together, usually with real infrastructure: a real database, message broker, or HTTP stack. It catches what unit tests can't: wrong SQL, mismatched serialization, missing configuration, transaction bugs. The trade-offs are speed and isolation: each test must start from a known state and clean up.

Notes

  • Use the same database engine as production (containers make this easy)
  • In-memory stand-ins (H2, SQLite for Postgres) hide dialect bugs
  • Keep a separate, slower job for integration tests if needed
  • Start the app once per suite; reset data per test

An Integration Test With Real Infrastructure

suite setup (once):
    db  = start_container("postgres:17")
    app = start_app(database_url=db.url)

each test setup:
    db.begin_transaction()            # or truncate tables

test "placing an order writes order and lines":
    response = app.post("/orders", { sku: "A1", qty: 2 })
    assert response.status == 201
    row = db.query_one("select status, total from orders where id = ?", response.body.id)
    assert row == ("NEW", 20.00)

each test teardown:
    db.rollback()

suite teardown:
    app.stop(); db.stop()

Code Explained

Expensive things (container, app) start once per suite
Each test runs in a transaction rolled back afterward, so tests stay independent
The test checks the database row, proving the SQL and mapping really work
The same pattern works for queues, caches and search engines

Smell Check

  • You see integration tests that pass on H2 but fail on Postgres → it means the stand-in lies → do test on the real engine in a container
  • You see tests that only pass in a fixed order → it means leftover data → do reset state per test

What Integration Tests Catch

BugExample
Wrong SQL / queryMissing join condition
Mapping / serializationField renamed in JSON
TransactionsPartial write on failure
ConfigurationWrong connection settings
MigrationsColumn missing in real schema

Isolation Strategies

StrategyTrade-off
Transaction rollbackFast; can't test commits or multiple connections
Truncate tablesReal commits; slower
Fresh schema per testStrong isolation; slowest
Unique data per testParallel-safe; needs discipline

⚠ Common Mistakes

  • Calling everything with a database an "integration test" but mocking the database
  • Sharing one database between parallel test workers without unique data
  • No integration tests at all, trusting mocks completely

✓ Tips & Best Practices

  • Test each adapter (repository, HTTP client, queue) against the real thing at least once
  • Keep integration tests in their own folder / tag
  • Measure suite time and set a budget

Quick Summary

  • integration — real pieces + real infra
  • same engine as production
  • start once, reset per test
  • catches SQL, config and mapping bugs
