Sheet 11

When (and When Not) to Mock

mock at boundaries · don't mock what you don't own · ports & adapters · over-mocking · mocks that test the mock

Mock the Edges, Not the Middle

Doubles belong at boundaries: the network, the clock, the file system, payment gateways, email. Inside your own code, use real objects. Don't mock what you don't own: instead of mocking a third-party SDK's many methods, wrap it in a small port (interface) you own, mock that, and test the adapter against the real thing in an integration test. Over-mocking produces tests that pass while the real system is broken.

Notes

  • A mock encodes your assumption about a dependency; if it's wrong, the test lies
  • Integration tests check those assumptions
  • Network-level fakes (MSW, WireMock, page.route) avoid mocking client libraries
  • Classicist vs mockist styles: sheet 14

Interview Angle

  • Q: "When shouldn't you mock?" — your own domain objects, value objects, and libraries you don't own
  • Explain ports and adapters: mock your interface, integration-test the adapter
  • Mention that heavy mocking makes refactoring painful

Wrap, Then Mock Your Own Port

# ✗ mocking a third-party SDK directly
stripe = mock StripeSDK
stripe.customers.create(...) returns { id: "cus_1" }
stripe.payment_intents.create(...) returns { status: "succeeded" }
# … 6 more stubs mirroring Stripe's API, wrong in subtle ways

# ✓ a small port you own
interface PaymentGateway:
    charge(customer_email, amount_cents) -> Receipt

# unit tests: fake the port
gateway = FakePaymentGateway(always="succeeded")
checkout = Checkout(gateway)
assert checkout.pay(cart).status == "PAID"

# integration test: the real adapter against Stripe's test mode
test "StripeGateway charges in test mode" [tag: integration]:
    receipt = StripeGateway(test_key).charge("ann@x.com", 1999)
    assert receipt.status == "succeeded"

Code Explained

Mocking the SDK copies its API into every test and drifts from reality
The port describes what *your* app needs, in your terms
Unit tests use a fake gateway and stay fast
One integration test proves the adapter works with the real service

In Your Stack

  • pytest monkeypatch your port; respx / responses at HTTP level ↗13
  • Vitest MSW intercepts HTTP instead of mocking clients ↗15
  • JUnit Mockito on your interface; WireMock for HTTP ↗18
  • Playwright page.route / HAR for third-party calls ↗29

Smell Check

  • You see a test that only checks mocks talked to each other → it means nothing real is tested → do use real collaborators or an integration test
  • You see mocks of requests / axios / RestTemplate everywhere → it means missing port → do wrap the client, or fake at the HTTP level

Mock or Real?

Ports & Adapters

PartTested by
Domain logicUnit tests with fakes of ports
Port (interface)Contract tests shared by fake and adapter
Adapter (SDK / DB / HTTP)Integration tests against the real thing
Whole sliceA few end-to-end tests

⚠ Common Mistakes

  • Mocking the class under test
  • Mocking a library's internals and breaking on every upgrade
  • Never running the real adapter anywhere

✓ Tips & Best Practices

  • When a mock setup gets long, introduce a port
  • Run the same contract tests against your fake and the real adapter
  • Prefer network-level fakes over client-library mocks

Quick Summary

  • mock at boundaries
  • don't mock what you don't own — wrap it
  • ports & adapters — fake the port, integration-test the adapter
  • over-mocking — tests that lie
