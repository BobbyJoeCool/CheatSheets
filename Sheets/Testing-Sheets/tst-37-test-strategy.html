A Test Strategy for a Project

risk-based testing · what to test where · web app example · API example · library example · writing it down

Decide Where Testing Effort Goes

A test strategy answers: what are the risks, which kinds of tests cover them, at which level, and when they run. Start from risk: what breaks most often, costs the most, or would embarrass you? Put most effort there, at the cheapest level that catches the problem. Write the strategy down in a short page in the repo so the team shares the same picture.

Notes

  • Different projects get different shapes; a library ≠ a web app
  • Revisit the strategy when incidents show gaps
  • Include non-functional risks (performance, security, accessibility)
  • One page is enough

Interview Angle

  • Q: "How would you test this feature?" Start with risks, then map tests to levels using the pyramid
  • Mention unit edge cases, an integration test at the real boundary, one E2E journey
  • Add non-functional checks if relevant and say what you would *not* test

A One-Page Strategy (web shop)

# TESTING.md — Orders web app

Top risks
  1. wrong totals / tax / discounts          (money)
  2. checkout breaks after deploy            (revenue)
  3. one customer sees another's data        (security)
  4. slow checkout at peak                   (performance)

Coverage plan
  pricing rules        → unit tests + property tests       (risk 1)
  order API            → API tests incl. every error code  (risks 1, 3)
  DB / payments        → integration tests, containers     (risk 2)
  checkout journey     → 3 E2E tests, smoke after deploy   (risk 2)
  access control       → per-endpoint auth tests           (risk 3)
  peak traffic         → k6 load test nightly, p95 < 300ms (risk 4)

Not tested automatically
  marketing pages (manual review), admin CSV export layout

Runs
  PR: lint, unit, API, integration, E2E smoke   (< 10 min)
  nightly: full E2E, load, mutation on pricing

Code Explained

Risks drive everything else in the document
Each test type is tied to the risk it covers
Saying what you won't test is part of the strategy
Run schedules match the cost of each suite

Smell Check

  • You see testing effort spread evenly over all code → it means no risk analysis → do rank risks and focus there
  • You see no written strategy → it means every developer guesses → do write one page and keep it current

⚠ Common Mistakes

  • Copying another project's strategy without considering your risks
  • A 30-page strategy nobody reads
  • Never updating the strategy after incidents

✓ Tips & Best Practices

  • Start with a short risk list and grow from there
  • Link each incident post-mortem to a strategy change
  • Keep the strategy in the repo next to the code

Quick Summary

  • risk first
  • cheapest level that catches it
  • say what you won't test
  • one page, in the repo
