Sheet 19

Contract Testing

consumer-driven contracts · Pact · provider verification · broker · OpenAPI-based contracts · contract vs E2E

Services Agree Without Running Together

When services talk over APIs, a change on one side can break the other. Contract tests check that both sides agree on the API without deploying them together. In consumer-driven contracts (Pact), the consumer's tests record the requests it makes and the responses it needs; the provider then replays them in its own CI to verify it still satisfies every consumer. A broker shares contracts and results.

Notes

  • Contracts test the shape of interactions, not business logic
  • Each consumer records only the fields it uses, so providers can add fields freely
  • "Can I deploy?" checks with the broker gate releases
  • Schema-based alternatives compare against an OpenAPI spec

Interview Angle

  • Q: "What is contract testing?" Consumer records expectations; provider verifies them in its own pipeline
  • Why not just E2E? Faster, pinpoints which side broke, no shared environment needed
  • Mention Pact and a broker by name

Consumer Test → Contract → Provider Verification

# CONSUMER (orders-ui) — runs against a mock provider
contract "orders-ui" ↔ "orders-api":
    given "order 7 exists"
    upon receiving GET /orders/7
    respond with 200 {
        id:     like(7),            # any number
        status: term("NEW|PAID", example="PAID"),
        total:  like(45.00)
    }
test "order page shows the status":
    order = OrdersClient(mock_provider.url).get(7)
    assert order.status == "PAID"
# → writes contract file, published to the broker

# PROVIDER (orders-api) — in its own CI
verify contracts from broker for "orders-api":
    state "order 7 exists": db.insert(Order(id=7, status="PAID"))
    replay each request against the real API, compare responses
# → results published; deploy gated on "can-i-deploy"

Code Explained

Matchers like like() check type, not exact values
Provider states set up data so each interaction can be replayed
If the provider renames status, its CI fails before release
Both sides deploy independently once verification passes

Smell Check

  • You see a shared staging environment where teams wait to run E2E suites → it means integration is checked too late → do add contract tests per service pair
  • You see contracts that pin every response field exactly → it means brittle contracts → do use type matchers and only fields the consumer uses

⚠ Common Mistakes

  • Using contract tests to test business logic
  • Consumers asserting fields they don't use
  • Never verifying contracts on the provider side

✓ Tips & Best Practices

  • Start with your most-changed API between two teams
  • Wire "can-i-deploy" into release pipelines
  • Keep a few E2E tests for critical journeys on top

Quick Summary
