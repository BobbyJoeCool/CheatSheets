Code Coverage

line · branch · condition · function coverage · thresholds · coverage on changed code · what coverage misses

Which Code Ran — Not Whether It Was Checked

Coverage tools record which code executed during the tests. Line coverage counts executed lines; branch coverage checks both sides of every if; condition coverage checks each part of a compound condition. Coverage is great at showing untested code, and weak at proving tested code is checked: a test with no assertions still adds coverage. Use thresholds as a floor, and watch coverage on changed code.

Notes

  • Branch coverage is stricter and more useful than line coverage
  • Exclude generated code and trivial boilerplate
  • Coverage on new / changed lines matters more than the total
  • Mutation testing (sheet 25) checks what coverage can't

Interview Angle

  • Q: "What does code coverage tell you?" — which code ran during tests, not whether it was verified
  • Line vs branch: branch catches the untested else
  • Good answer: use it to find gaps and as a floor on changed code, not as a target to game

Line vs Branch Coverage

function fee(total, member):
    if total > 100 or member:          # condition with two parts
        return 0
    return 5

test "big orders are free":   assert fee(150, member=false) == 0

# line coverage:   2 of 3 lines   = 67%  ("return 5" never ran)
# branch coverage: 1 of 2 branches = 50% (the false branch never taken)
# condition coverage: "member" was never true → 50%

test "small orders pay 5":     assert fee(20, member=false) == 5
test "members ship free":      assert fee(20, member=true) == 0
# now 100% line, branch and condition coverage

# coverage can't see this bug:
test "does something":         fee(20, member=false)    # no assert, still "covered"

Code Explained

Line coverage misses the untaken branch until a test hits return 5
Condition coverage forces a test where only member is true
The last test adds coverage while checking nothing
Report missing lines and branches, then decide which matter

Smell Check

  • You see a coverage target of 100% enforced → it means people write assertion-free tests to hit it → do set a sensible floor and review what's untested
  • You see coverage rising while bugs keep shipping → it means coverage measures execution, not checking → do add mutation testing on critical code

⚠ Common Mistakes

  • Treating the coverage number as the goal
  • Including generated code or vendored libraries in the measurement
  • Ignoring which lines are uncovered and only reading the total

✓ Tips & Best Practices

  • Check the coverage diff in PRs: are the new lines tested?
  • Turn on branch coverage everywhere
  • Read uncovered lines in risky modules first

Quick Summary

  • coverage — what ran, not what was checked
  • branch > line
  • floor on changed code, not a 100% target
  • pair with mutation testing
