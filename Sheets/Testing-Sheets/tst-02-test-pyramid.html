Sheet 02

The Test Pyramid & Its Alternatives

unit / integration / E2E layers · speed vs confidence · testing trophy · honeycomb · ice-cream cone anti-pattern

How Many Tests at Each Level

The test pyramid says: many fast unit tests at the bottom, fewer integration tests in the middle, a handful of slow end-to-end tests at the top. Lower tests are cheap and precise; higher tests give more confidence that the pieces work together but are slower and flakier. The testing trophy (front-end) and honeycomb (microservices) shift weight toward integration tests. The ice-cream cone is the anti-pattern: mostly manual and E2E.

Notes

  • The shape is a guideline about cost and feedback speed, not a quota
  • Static checks (types, linters) form the trophy's base
  • Pick the lowest level that can catch the bug
  • Each layer should test what the layers below can't

Interview Angle

  • Q: "Describe the test pyramid." Explain the three layers and the cost / speed / confidence trade-off
  • Say *why* it's shaped that way: cheap, fast feedback at the bottom
  • Mention when the trophy fits better (UI apps, thin logic) — shows judgment, not dogma

One Feature, Three Levels

# Feature: "checkout applies a coupon"

# UNIT — pure logic, milliseconds, many of these
test "coupon SAVE10 takes 10% off":
    assert apply_coupon(total=50.00, code="SAVE10") == 45.00

# INTEGRATION — real pieces wired together, a real DB
test "checkout endpoint stores discounted order":
    response = http_post("/checkout", { cart_id: 7, coupon: "SAVE10" })
    assert response.status == 201
    assert db.orders.find(7).total == 45.00

# END-TO-END — real browser, whole app, few of these
test "shopper can use a coupon at checkout":
    open_page("/cart")
    fill("Coupon", "SAVE10"); click("Apply")
    expect(text("Total: $45.00")).visible

Code Explained

Edge cases (expired, unknown, stacked coupons) belong in fast unit tests
The integration test proves the endpoint, logic and database agree
One E2E test proves a user can actually do it; it doesn't re-test every edge case
If the E2E test fails but unit tests pass, the bug is in the wiring

Smell Check

  • You see 300 E2E tests and 20 unit tests → it means an ice-cream cone: slow, flaky feedback → do push edge cases down to unit tests
  • You see every unit test mocking everything → it means no proof the pieces fit → do add integration tests at real boundaries

⚠ Common Mistakes

  • Testing every edge case through the UI
  • Counting tests per layer instead of asking what each test catches
  • Calling a test "unit" while it hits a real network service

✓ Tips & Best Practices

  • Ask "what's the cheapest test that would catch this bug?"
  • Keep E2E tests to critical user journeys
  • Add integration tests at the seams where bugs actually happen (DB, HTTP, queues)

Quick Summary

  • unit — many, fast, precise
  • integration — real pieces together
  • E2E — few, slow, high confidence
  • trophy / honeycomb — more integration
