Testing HTTP APIs

Test the Contract Your Clients Use

An API test sends a request and checks status, headers and body, the parts clients depend on. Test the error paths as carefully as success: validation errors, missing auth, wrong role, not found, conflicts. In-process test clients call the app without a network and are fast; real HTTP against a running server catches proxy, TLS and serialization issues. The HTTP set covers status codes and headers.

Notes

  • Validate responses against the OpenAPI schema to catch drift
  • Create a token / session once per test file, not per request
  • Check Content-Type, Location and cache headers, not just status
  • Test pagination edges: empty page, last page, invalid cursor

Success and Failure Paths

test "POST /orders creates an order":
    res = client.post("/orders", json={ sku: "A1", qty: 2 }, auth=token("ann"))
    assert res.status == 201
    assert res.headers["Location"] == "/orders/" + res.body.id
    assert res.body matches schema("Order")

test "POST /orders without a token is 401":
    assert client.post("/orders", json={…}).status == 401

test "POST /orders by a read-only user is 403":
    assert client.post("/orders", json={…}, auth=token("viewer")).status == 403

test "invalid quantity returns a problem+json error":
    res = client.post("/orders", json={ sku: "A1", qty: 0 }, auth=token("ann"))
    assert res.status == 422
    assert res.headers["Content-Type"] == "application/problem+json"
    assert res.body.errors == [{ field: "qty", message: "must be > 0" }]

test "GET another user's order is 404, not 403":
    assert client.get("/orders/" + bob_order, auth=token("ann")).status == 404

Code Explained

Status, Location header and schema are all part of the contract
401 (who are you?) vs 403 (not allowed) vs 404 (hide existence) each get a test
Validation errors check the machine-readable error body
Schema validation catches fields added or renamed by accident

Smell Check

  • You see only happy-path API tests → it means auth and validation bugs go unnoticed → do add a test per error status
  • You see assertions only on status codes → it means body and header regressions slip through → do validate the body against the schema

⚠ Common Mistakes

  • Asserting on the exact error message text that product changes often
  • Reusing one admin token for every test and missing authorization bugs
  • Testing through the UI what an API test could cover faster

✓ Tips & Best Practices

  • Generate request / response types from the OpenAPI spec and reuse them in tests
  • Keep one test per status code an endpoint can return
  • Run a small API smoke suite against each deployed environment

Quick Summary

  • status + headers + body = the contract
  • test every error path (400 / 401 / 403 / 404 / 409 / 422)
  • schema validation catches drift
  • test client fast · real HTTP thorough
