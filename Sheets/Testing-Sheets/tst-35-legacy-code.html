Sheet 35

Testing Legacy Code

characterization tests · finding seams · sprout & wrap · golden master · refactor under test

Add a Safety Net Before You Change Anything

Legacy code is code without tests (Michael Feathers' definition). Before changing it, pin its current behavior with characterization tests: run it, record what it does, assert exactly that, bugs included. Then find seams to break dependencies, add new code in tested pieces (sprout) or around old code (wrap), and refactor in small steps under the tests. A golden master captures large outputs wholesale.

Notes

  • Characterization tests describe what *is*, not what *should be*
  • Fix bugs in separate, deliberate changes
  • Start where you need to change code, not everywhere
  • Book: *Working Effectively with Legacy Code*

Interview Angle

  • Q: "How do you add tests to legacy code?" Characterization tests first, then seams, then refactor
  • Mention sprout / wrap for new behavior
  • Stress small, safe steps over a big rewrite

Pinning Behavior, Then Changing It

# 1. characterization: what does it do today?
test "legacy price calc — current behavior":
    assert legacy_price(qty=10, customer="gold") == 87.30     # observed, not designed
    assert legacy_price(qty=0,  customer="gold") == -2.70     # a bug! pinned for now

# 2. golden master for big outputs
for each input in recorded_inputs(1000):
    assert legacy_report(input) == read_golden(input.id)

# 3. sprout: new behavior in a new, tested function
function loyalty_discount(customer, total):   # TDD'd separately
    ...
legacy_price(...):
    total = old_logic(...)
    return total - loyalty_discount(customer, total)   # one-line change

# 4. refactor under the tests in small steps
#    extract method → run tests → rename → run tests → ...

Code Explained

Characterization tests capture current behavior, including the negative price bug
A golden master over recorded inputs pins behavior that's too big to assert by hand
Sprouting keeps new logic tested even inside untested code
Each refactoring step runs the tests before the next one

In Your Stack

  • pytest golden files / syrupy over recorded inputs ↗22
  • Vitest snapshot tests to pin current output ↗16
  • JUnit ApprovalTests or @TestFactory over recorded cases ↗13
  • Playwright visual snapshots to pin UI before a redesign ↗35

Smell Check

  • You see a big-bang rewrite of untested code → it means no way to know what broke → do characterize first, then change in small steps
  • You see characterization tests "fixed" to expected behavior during refactoring → it means behavior changed silently → do change behavior only in separate, deliberate commits

Common Seams in Legacy Code

SeamHow
Parameterize constructorPass a dependency instead of new-ing it
Extract and overrideSubclass in test, override the awkward call
Extract interfacePut an interface over a concrete dependency
Link / module seamSwap a module at import / link time
Global → parameterPass what used to be global

⚠ Common Mistakes

  • Fixing bugs while adding characterization tests
  • Refactoring without any tests in place
  • Trying to test the whole legacy system before touching anything

✓ Tips & Best Practices

  • Add tests only around the code you're about to change
  • Commit characterization tests separately from changes
  • Use approval / golden tests to cover a lot of behavior quickly

Quick Summary

  • characterization tests — pin what is
  • seams — break dependencies
  • sprout & wrap — new code, tested
  • refactor in small steps under tests
