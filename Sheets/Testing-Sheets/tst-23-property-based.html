Property-Based Testing

properties vs examples · generators · shrinking · round-trip · invariants · Hypothesis · fast-check · jqwik

State a Rule, Let the Tool Find Counterexamples

Example tests check a few hand-picked inputs. Property-based tests state a rule that should hold for all inputs (a property), and a library generates hundreds of inputs to try to break it. When it finds a failure, it shrinks the input to the smallest case that still fails. Good properties: round-trips (decode(encode(x)) == x), invariants (total never negative), and agreement with a simple reference implementation.

Notes

  • Properties complement examples; keep a few examples for readability
  • Failing inputs are saved and replayed on the next run
  • Avoid re-implementing the function in the test
  • Great for parsers, serializers, math, data structures

Properties Instead of Examples

# round-trip
property "decode reverses encode":
    for all s in strings():
        assert decode(encode(s)) == s

# invariant
property "cart total is never negative":
    for all prices in lists(floats(min=0, max=1e6)), d in floats(0, 0.99):
        assert cart_total(prices, discount=d) >= 0

# idempotence
property "normalizing an email twice changes nothing":
    for all e in emails():
        assert normalize(normalize(e)) == normalize(e)

# agreement with a simple reference (oracle)
property "fast_sort agrees with built-in sort":
    for all xs in lists(integers()):
        assert fast_sort(xs) == sorted(xs)

# failure output after shrinking:
#   Falsifying example: s = "\x00"    (minimal input)

Code Explained

A round-trip test catches encoding bugs no one thought to try
Shrinking turns a 400-character random string into the one character that breaks it
Idempotence and invariants describe behavior without computing exact outputs
A slow but obviously correct reference checks a fast implementation

Smell Check

  • You see a property that re-computes the expected value the same way the code does → it means the test copies the bug → do use a different property (round-trip, invariant, oracle)
  • You see generators restricted until nothing interesting is generated → it means the property is too strict → do widen inputs and handle edge cases explicitly

⚠ Common Mistakes

  • Writing properties that are just the implementation again
  • Ignoring the saved failing example and "fixing" by narrowing generators
  • Using property tests for code with side effects and no clear rule

✓ Tips & Best Practices

  • Start with round-trip properties for any serializer or parser
  • Keep the generator close to real input shapes
  • Turn each shrunk failure into a permanent example test

Quick Summary

  • property — a rule for all inputs
  • generators — many inputs
  • shrinking — minimal failing case
  • round-trip · invariant · idempotence · oracle
