Sheet 30

Parallelism & Sharding

isolation requirements · splitting by file vs timing · sharding across machines · merging reports · shared resources

Make Big Suites Fast

Parallelism runs tests at the same time on one machine (workers or threads); sharding splits the suite across several CI machines. Both need isolated tests: no shared files, ports, database rows or global state. Split by timing (balance by past duration) rather than file count for even shards, then merge the reports so failures show in one place.

Notes

  • Find order and isolation bugs before turning on parallelism
  • Database per worker or unique data per test
  • Too many workers can slow a resource-bound machine
  • Timing data improves shard balance over time

From 40 Minutes to 8

before: 1 machine, 1 worker → 40 min

step 1 — parallel workers on one machine
    workers = cpu_count            # 4
    each worker: own DB schema "test_" + worker_id
    → 12 min

step 2 — shard across 4 CI machines
    shard i of 4 gets tests balanced by last run's timings
    each shard runs with 4 workers
    → ~3 min per shard (+ setup)

step 3 — merge results
    collect report-shard-1..4 → merge → one JUnit / HTML report
    → total wall time ≈ 8 min

isolation checklist:
    [ ] no fixed ports (use port 0 / random)
    [ ] temp files per test
    [ ] unique data or per-worker database
    [ ] no reliance on test order

Code Explained

Workers need their own resources or they collide
Timing-based shards finish at about the same time
Merged reports keep failures in one view
Setup time per shard limits how far sharding helps

Smell Check

  • You see tests that pass serially but fail with workers → it means shared state → do give each worker its own resources
  • You see one shard always finishing last → it means splitting by count → do split by timing

⚠ Common Mistakes

  • Turning on parallelism before fixing order-dependent tests
  • Sharding by file count with very uneven file sizes
  • Forgetting to merge shard reports

✓ Tips & Best Practices

  • Randomize order first; parallel second
  • Store timing data from CI to balance shards
  • Measure: more workers isn't always faster

Quick Summary

  • parallel — workers on one machine
  • sharding — split across machines
  • isolation is the prerequisite
  • split by timing, merge reports
