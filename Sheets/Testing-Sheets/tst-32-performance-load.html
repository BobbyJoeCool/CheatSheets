Performance & Load Testing

load · stress · soak · spike · p50 / p95 / p99 · throughput · k6 · thresholds in CI

Fast Enough Under Real Traffic

Functional tests ask "is it right?"; performance tests ask "is it fast enough, for how many users?" Load tests apply expected traffic, stress tests push past it to find the breaking point, soak tests hold load for hours to find leaks, and spike tests jump suddenly. Measure latency percentiles (p95, p99) and throughput, not averages, and set pass/fail thresholds.

Notes

  • Averages hide the slow requests users feel; use percentiles
  • Test in an environment sized like production
  • Ramp up gradually; record errors as well as latency
  • Micro-benchmarks (one function) are a different tool from load tests

Interview Angle

  • Q: "How would you load-test an API?" Define expected traffic, ramp up, measure p95 / p99 latency and error rate
  • State a pass/fail threshold (e.g. p95 < 300 ms, errors < 1%)
  • Mention a tool (k6, Gatling, Locust) and testing in a production-like environment

A Load Test With Thresholds

scenario "checkout API under expected peak":
    stages:
        ramp from 0 to 200 virtual users over 2 min
        hold 200 users for 10 min
        ramp down over 1 min
    each user loop:
        GET  /products?page=1
        POST /cart      { sku: random_sku() }
        POST /checkout  { cart_id }
        think 1–3 s
    thresholds:
        http_req_duration p95 < 300 ms
        http_req_duration p99 < 800 ms
        http_req_failed   rate < 1%

result:  p50 120 ms · p95 280 ms · p99 1.2 s ✗ · errors 0.4%
→ p99 fails: slow DB query on /checkout under load

Code Explained

Ramping up shows where latency starts to climb
Think time makes virtual users behave like people
Thresholds turn the run into a pass / fail check for CI
p99 exposes the slow tail that the average hides

In Your Stack

  • Vitest vitest bench for micro-benchmarks; k6 for load ↗03
  • JUnit JMH for micro-benchmarks; Gatling for load

Smell Check

  • You see performance judged by the average response time → it means slow outliers are invisible → do report p95 / p99
  • You see load tests run against a laptop-sized environment → it means results don't transfer → do test production-like capacity

⚠ Common Mistakes

  • Using averages as the only latency number
  • Load testing production without coordination
  • Ignoring error rate while reading latency

✓ Tips & Best Practices

  • Start with a baseline run and compare every change against it
  • Run a short load test in CI with thresholds, a long one nightly
  • Profile the slowest endpoint before buying more servers

Quick Summary

  • load · stress · soak · spike
  • percentiles, not averages
  • thresholds → pass / fail
  • production-like environment
