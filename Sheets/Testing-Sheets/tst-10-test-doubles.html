Sheet 10

Dummy, Stub, Fake, Spy & Mock

the five doubles · state vs interaction verification · which to reach for · naming doubles by role

Stand-Ins for Real Collaborators

A test double replaces a real dependency in a test. A dummy is passed but never used. A stub returns canned answers. A fake is a working lightweight version (an in-memory repository). A spy records how it was called. A mock is set up with expectations and checks them. Libraries call everything a "mock", but knowing which you need keeps tests simpler.

Notes

  • Stubs and fakes support state verification (check results)
  • Spies and mocks support interaction verification (check calls)
  • Fakes are often worth sharing across the suite
  • Terms from Gerard Meszaros, *xUnit Test Patterns*

Interview Angle

  • Q: "Mock vs stub vs fake?" Give a one-line definition each
  • Stub = canned answer, fake = working shortcut, mock = expectations on calls
  • Example: stub a price API, fake a repository in memory, mock the email sender to verify it was called

One of Each

# DUMMY — required parameter, never used
report = make_report(data, logger=DummyLogger())

# STUB — canned answer
rates = stub RateService { get("EUR") -> 1.1 }
assert convert(10, "EUR", rates) == 11.0

# FAKE — real behavior, simpler implementation
repo = InMemoryOrderRepository()
service = OrderService(repo)
service.place(cart)
assert repo.count() == 1

# SPY — records calls, then you check
mailer = spy Mailer()
service.place(cart, mailer)
assert mailer.calls == [("send", "ann@x.com", "Order received")]

# MOCK — expectations set up front
mailer = mock Mailer() expecting send("ann@x.com", any) once
service.place(cart, mailer)
mailer.verify()

Code Explained

The stub only answers questions; nobody checks how it was used
The fake behaves like a real repository, so tests check final state
Spies check after the fact; mocks declare expectations first (most libraries blur this)
Prefer state checks; use interaction checks for side effects like email

Smell Check

  • You see mocks for value objects and DTOs → it means doubling things that are cheap to build → do use real instances
  • You see a mock set up with 15 when calls → it means a fat interface or the wrong boundary → do use a fake or narrow the dependency

⚠ Common Mistakes

  • Mocking everything by reflex
  • Verifying stubbed calls (when x then verify x) — redundant
  • Fakes that drift from the real behavior without their own tests

✓ Tips & Best Practices

  • Test your fakes against the same contract tests as the real thing
  • Name doubles by role: fake_repo, stub_rates, spy_mailer
  • Prefer state verification when you can

Quick Summary

  • dummy · stub · fake · spy · mock
  • state verification — stubs, fakes
  • interaction verification — spies, mocks
  • real objects when they're cheap
