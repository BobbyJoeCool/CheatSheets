Testing Time, Async & Concurrency

fake clocks · fake timers · awaiting vs polling · eventual consistency · race conditions · never sleep

Make Time and Ordering Test Inputs

Code that depends on time, timers, background work or concurrency is the main source of slow and flaky tests. Control time with an injected clock or fake timers. Await async work directly; for work that completes later (queues, eventual consistency), poll for a condition with a timeout instead of sleeping. For races, make interleavings deterministic or run many iterations to expose them.

Notes

  • sleep in a test is a guess: too short = flaky, too long = slow
  • Polling assertions retry until true or time out
  • Fake timers advance time instantly
  • Concurrency bugs need stress runs, thread-safety tools, or deterministic schedulers

Time, Async and Eventual Consistency

# time: inject a clock
test "session expires after 30 minutes":
    clock = FakeClock("2026-11-04T10:00:00Z")
    s = Session(clock); clock.advance(minutes=31)
    assert s.expired()

# timers: fake them
test "autosave fires once after typing stops":
    timers.fake(); editor.type("hello"); timers.advance(ms=999)
    assert saves == 0
    timers.advance(ms=1);  assert saves == 1

# async: await, don't sleep
test "fetches the profile":
    profile = await api.get_profile(7)
    assert profile.name == "Ann"

# eventual consistency: poll with a timeout
test "order event updates the search index":
    publish(OrderPlaced(id=7))
    eventually(timeout=5s): assert search("order 7").count == 1

# ✗ never
sleep(2); assert search("order 7").count == 1

Code Explained

Advancing a fake clock tests a 30-minute rule in microseconds
Fake timers let a test check "not yet" and "now" exactly
Awaiting the promise / future means no guessing
eventually retries quickly and fails with a clear timeout

Smell Check

  • You see sleep(5) before an assertion → it means a timing guess → do await the work or poll for the condition
  • You see tests that fail around midnight or month-end → it means real time leaks in → do inject a clock and test those dates on purpose

⚠ Common Mistakes

  • Sleeping instead of waiting for a condition
  • Using the real clock in business-rule tests
  • Testing concurrency once and declaring it safe

✓ Tips & Best Practices

  • Search the test suite for sleep and replace each one
  • Test date edge cases explicitly with a fake clock
  • Run concurrent code under stress loops in CI nightly

Quick Summary

  • inject clocks, fake timers
  • await async work directly
  • poll with timeout for eventual results
  • never sleep to wait
