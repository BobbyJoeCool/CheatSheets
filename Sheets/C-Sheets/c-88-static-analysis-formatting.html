Static Analysis & Formatting

Static analyzers read your code without running it and find bugs the compiler doesn't warn about: null dereferences on rare paths, leaks, uninitialized values and API misuse. clang-tidy combines analysis with style and modernization checks, cppcheck is a standalone analyzer, and GCC has -fanalyzer. clang-format formats code consistently from a .clang-format file.

Notes

  • Analyzers need your real compile flags
  • compile_commands.json supplies those flags
  • Expect some false positives; suppress narrowly
  • Run formatters in pre-commit hooks or CI

Running the Tools

# Compile database (needed by clang-tidy / clangd)
cmake -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
bear -- make                         # for Makefile projects

# Analyzers
clang-tidy src/*.c -p build -checks='clang-analyzer-*,bugprone-*,cert-*'
cppcheck --enable=warning,style --std=c17 src/
gcc -fanalyzer -c src/parser.c
scan-build make                      # Clang static analyzer report

# Formatting
clang-format -i src/*.c include/*.h  # rewrite in place
clang-format --dry-run --Werror src/*.c   # CI check

# .clang-format
#   BasedOnStyle: LLVM
#   IndentWidth: 4
#   ColumnLimit: 100

Code Explained

-p build — where compile_commands.json lives
-checks= — choose check groups
scan-build make — wrap any build, HTML report
clang-format -i — format files in place
--dry-run --Werror — fail CI on unformatted code

⚠ Common Mistakes

  • Running clang-tidy without a compile database: it guesses flags and reports noise
  • Turning on every check at once, then ignoring the flood
  • Mixing formatting changes with logic changes in one commit

✓ Tips & Best Practices

  • Start with bugprone-* and clang-analyzer-*, then add more
  • Commit a .clang-format and .clang-tidy at the repo root
  • Silence one line with // NOLINT(check-name) and a reason

Quick Summary

  • clang-tidy / cppcheck / -fanalyzer
  • compile_commands.json — real flags
  • clang-format + .clang-format
  • Run all of them in CI
