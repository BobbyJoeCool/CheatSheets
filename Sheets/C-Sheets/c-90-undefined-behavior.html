Undefined Behavior

Undefined behavior (UB) means the standard places no requirements on what happens. The program might crash, appear to work, or behave differently at -O2. Optimizers assume UB never happens and transform code on that basis, so a signed-overflow check or a null check placed after a dereference can be deleted. It's different from implementation-defined (documented choice) and unspecified (one of several outcomes) behavior.

Notes

  • UB anywhere can affect code before it executes
  • "It works" proves nothing about UB
  • UBSan catches many cases at runtime
  • C23 Annex J lists ~200 UB cases

UB the Optimizer Exploits

int will_overflow(int x) {
    return x + 1 < x;          // "always false" → compiled to: return 0
}

int get(int *p) {
    int v = *p;                // deref: compiler now assumes p != NULL
    if (p == NULL) return -1;  // check may be removed
    return v;
}

int table[4];
bool exists(int v) {
    for (int i = 0; i <= 4; i++)   // reads table[4]: UB
        if (table[i] == v) return true;
    return false;              // may be optimized to "return true"
}

int x;  printf("%d\n", x);     // uninitialized read
int s = 1 << 32;               // shift ≥ width
float f = 1.5f; int bits = *(int *)&f;   // strict aliasing

Code Explained

x + 1 < x — signed overflow "can't happen", so it's false
Deref before check — the null check is dead code to the compiler
i <= 4 — out-of-bounds lets the compiler assume the loop exits early
Uninitialized reads, big shifts, type-punned pointers — all UB

⚠ Common Mistakes

  • Testing for overflow with a + b < a after the fact
  • Assuming -O0 behavior is "the real" behavior; optimized builds may differ legally
  • Reasoning about UB in terms of what the hardware does

✓ Tips & Best Practices

  • Build tests with -fsanitize=undefined,address
  • Use -fno-strict-aliasing / -fwrapv only as a last resort for legacy code
  • Read John Regehr's and the LLVM blog posts on UB for intuition

Quick Summary

  • UB — no guarantees at all
  • Optimizers assume it never happens
  • Unspecified / impl-defined are milder
  • UBSan + warnings catch much of it
