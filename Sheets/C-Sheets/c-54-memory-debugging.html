AddressSanitizer · UBSan · Valgrind (Linux) · leaks (macOS) · MallocStackLogging · ownership conventions · common leak patterns

Finding Memory Bugs

Memory bugs are easiest to catch with tools. AddressSanitizer (ASan) instruments the build and reports overflows, use-after-free and leaks with stack traces. UBSan catches undefined behavior such as signed overflow. Valgrind runs an unmodified binary under a checker on Linux. On macOS, leaks and Xcode Instruments check a running process.

Notes

  • ASan slows code ~2× and uses ~3× memory
  • Valgrind slows code 20–50×
  • LeakSanitizer is built into ASan on Linux
  • Apple clang's ASan has no leak checker; use leaks

Running the Tools

# AddressSanitizer + UBSan
cc -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer \
   main.c -o app
./app

# Valgrind (Linux)
cc -g -O0 main.c -o app
valgrind --leak-check=full --track-origins=yes ./app

# macOS: leaks tool
MallocStackLogging=1 leaks --atExit -- ./app

# Static analysis
gcc -fanalyzer main.c
clang --analyze main.c

Code Explained

-fno-omit-frame-pointer — better stack traces
--leak-check=full — list each leaked block
--track-origins=yes — where uninitialized values came from
leaks --atExit — report leaks when the program ends
-fanalyzer — compile-time path analysis (GCC 10+)

⚠ Common Mistakes

  • Running ASan builds with Valgrind; use one or the other
  • Ignoring "still reachable" leaks forever; they hide real ones in long-running programs
  • Debugging a crash at -O2 without -g; the stack trace is unreadable

✓ Tips & Best Practices

  • Make an ASan+UBSan build target and run tests with it in CI
  • Use ASAN_OPTIONS=abort_on_error=1 to get a core dump / debugger stop
  • Fix the first error reported; later ones are often consequences

Quick Summary

  • ASan — memory errors, fast
  • UBSan — undefined behavior
  • Valgrind — Linux, no rebuild
  • leaks — macOS
