Sheet 04

Compiler Flags & Warnings

-Wall -Wextra -Wpedantic · -Werror · -Wconversion / -Wshadow · -O0…-O3 / -Os · -g · -D NAME=val · -fsanitize=address,undefined

Flags Worth Using Every Time

C compilers are quiet by default and will build code with obvious bugs. Warning flags turn on hundreds of checks for things like unused variables, wrong printf formats and implicit conversions. Optimization flags change speed and size, debug flags add symbols for the debugger, and sanitizers add runtime checks that catch memory errors and undefined behavior while the program runs.

Recommended Sets

  • Dev: -std=c17 -Wall -Wextra -g -O0
  • Bug hunting: add -fsanitize=address,undefined
  • Release: -O2 -DNDEBUG (keep warnings on)
  • -Wall is not all warnings

Typical Command Lines

# Strict development build
cc -std=c17 -Wall -Wextra -Wpedantic -Wshadow \
   -Wconversion -g -O0 main.c -o app

# Treat warnings as errors (CI)
cc -Wall -Wextra -Werror main.c -o app

# Sanitizer build: crashes with a report on bugs
cc -g -O1 -fsanitize=address,undefined \
   -fno-omit-frame-pointer main.c -o app

# Release build, with a macro defined
cc -O2 -DNDEBUG -DVERSION=\"1.2\" main.c -o app

Code Explained

-Wpedantic — warn on non-ISO extensions for the chosen -std
-Wconversion — implicit conversions that may change a value
-Werror — any warning stops the build
-fsanitize=address — out-of-bounds, use-after-free, leaks
-DNAME=val — like #define NAME val in every file

Warning Flags

FlagCatches
-Wallunused vars, bad printf args, missing return
-Wextraunused params, signed/unsigned compares
-Wshadowinner variable hides an outer one
-Wconversionint → char, double → int truncation
-Wformat=2stricter printf / scanf checks

Optimization

FlagEffect
-O0no optimization; best for debugging
-Oglight; keeps debugging usable
-O2standard release level
-O3aggressive (vectorizing, inlining)
-Os / -Ozoptimize for size
-gdebug symbols (combine with any -O)

Sanitizers

FlagDetects
addressoverflows, use-after-free, double free
undefinedsigned overflow, bad shifts, null deref
threaddata races (not with ASan)
memoryuninitialized reads (Clang, Linux)

⚠ Common Mistakes

  • Shipping a binary built with -O0 -g and wondering why it's slow
  • Ignoring warnings because "it runs". A printf format mismatch or uninitialized variable is a real bug
  • Combining -fsanitize=address with -fsanitize=thread; they can't run together

✓ Tips & Best Practices

  • Put flags in a Makefile/CMake variable so every file gets the same set
  • Run tests under ASan + UBSan regularly; it's the cheapest way to find memory bugs
  • Use -Werror in CI, not necessarily on your laptop, so new compiler versions don't block you

Quick Summary

  • -Wall -Wextra -Wpedantic — baseline warnings
  • -g -O0 — debug; -O2 — release
  • -fsanitize=address,undefined — runtime bug detection
  • -DNAME=val — define a macro at build time
