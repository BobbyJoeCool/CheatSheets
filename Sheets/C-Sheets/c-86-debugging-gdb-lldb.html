Debugging with gdb & lldb

A debugger runs your program under control: stop at breakpoints, step line by line, inspect variables and memory, and print the call stack when it crashes. Compile with -g (debug info) and -O0 or -Og so variables aren't optimized away. Linux uses gdb; macOS ships lldb (gdb is hard to set up there). The commands are similar.

Notes

  • Pressing Enter repeats the last command
  • bt after a crash shows where it happened
  • Core dumps: ulimit -c unlimited first
  • Editors (VS Code, CLion) drive the same debuggers

A Debugging Session

cc -g -O0 main.c -o app

gdb --args ./app input.txt        # or: lldb -- ./app input.txt
(gdb) break parse_line            # stop at a function
(gdb) break main.c:42 if i == 10  # conditional breakpoint
(gdb) run
(gdb) next                        # step over
(gdb) step                        # step into
(gdb) print count                 # $1 = 7
(gdb) print *node                 # whole struct
(gdb) print arr[0]@5              # 5 array elements
(gdb) watch total                 # stop when total changes
(gdb) backtrace                   # call stack
(gdb) frame 1                     # inspect caller
(gdb) finish                      # run until function returns
(gdb) continue

Code Explained

--args — pass program arguments
break file:line if cond — conditional stop
next vs step — over vs into calls
print arr[0]@5 — gdb array slice
watch — data breakpoint

⚠ Common Mistakes

  • Debugging an -O2 build: variables show <optimized out> and lines jump around
  • Forgetting -g: no source lines, only addresses
  • Using print to debug memory corruption; use ASan first, the debugger second

✓ Tips & Best Practices

  • Run under ASan with ASAN_OPTIONS=abort_on_error=1 and debug the stop
  • Use tui enable (gdb) for a source view in the terminal
  • Save breakpoints in .gdbinit / .lldbinit for repeated sessions

Quick Summary

  • -g -O0 — debuggable build
  • break / run / next / step
  • print / watch / bt
  • gdb on Linux, lldb on macOS
