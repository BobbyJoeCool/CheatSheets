Environment Variables & Config Layering

defaults → file → env → CLI flags · 12-factor config · NODE_ENV / profiles · naming (APP_DB__HOST) · secrets managers · precedence

Later Layers Override Earlier Ones

Real apps merge config from layers: built-in defaults, then a checked-in file, then a per-environment file, then environment variables, then command-line flags. Each layer overrides the one before, so the same build runs everywhere with different settings. The 12-factor rule: anything that changes between deploys (URLs, credentials, feature flags) comes from the environment, not from code.

Notes

  • Env var names: UPPER_SNAKE_CASE, letters, digits, _
  • Nesting by convention: APP_DB__HOST (double underscore) in .NET, Pydantic, many libraries
  • NODE_ENV, Spring profiles, ASPNETCORE_ENVIRONMENT pick the per-env file
  • Kubernetes ConfigMaps / Secrets and CI secrets arrive as env vars

Layers in Practice (Spring Boot order)

# 1. defaults in code       @Value("${server.port:8080}")
# 2. application.yml        server: { port: 8080 }
# 3. application-prod.yml   server: { port: 80 }      (profile "prod")
# 4. environment variable   SERVER_PORT=9000
# 5. command line           java -jar app.jar --server.port=9100
#    → final value: 9100

# Same idea in other stacks
# Node:    defaults → config/default.json → config/production.json
#          → process.env → argv           (the "config" package)
# .NET:    appsettings.json → appsettings.Production.json
#          → env vars (Logging__LogLevel__Default) → args
# Python:  pydantic-settings: defaults → .env → env vars → init args

Code Explained

Spring maps SERVER_PORT to server.port (relaxed binding: uppercase, . → _)
In .NET, __ in an env var name means a nested key (Logging:LogLevel:Default)
Command-line flags are the last word, good for one-off overrides
Log the final merged config (minus secrets) at start-up to debug layering

Same Data In…

  • .env SERVER_PORT=9000
  • TOML [server] / port = 9000
  • CLI --server.port=9000 · PORT=9000 npm start

Gotcha

  • A variable set in CI or the container image overrides your file and is easy to forget
  • Env vars can't hold structure; complex values arrive as JSON strings or comma lists you must parse

⚠ Common Mistakes

  • Reading process.env all over the code instead of once into a config object
  • Shipping browser-exposed vars (VITE_, NEXT_PUBLIC_) that contain secrets
  • Not knowing which layer won, then "fixing" the wrong file

✓ Tips & Best Practices

  • Load and validate config in one module; the rest of the app imports typed values
  • Fail start-up when a required variable is missing
  • Keep secrets in the platform (Kubernetes Secrets, GitHub secrets, a vault), injected as env vars

Quick Summary

  • layers — defaults → files → env → flags
  • 12-factor — deploy-specific values from env
  • __ — nesting in env var names
  • validate once — typed config object
