Sheet 02

Choosing & Comparing Formats

human-edited vs machine-written · typed vs strings-only · comments · deep nesting · tooling support · decision table

When the Choice Is Yours

For your own app, ask four questions: Who edits it (people or programs)? How deep is the data? Do you need comments? What do your language and deployment tools read without a dependency? People editing flat-ish settings → TOML. Deep data written by programs → JSON. Deployment and CI → YAML because the tools require it. Secrets and per-machine values → environment variables.

Notes

  • Python 3.11+ reads TOML with tomllib (standard library)
  • Every language reads JSON without extra packages
  • YAML needs a library almost everywhere and has the most surprises
  • XML is still right for document-like data and schemas (see the XML set)

A Typical Split for One App

# config.toml — checked in, edited by people
[app]
name = "orders"
log_level = "info"

[database]
pool_size = 10
timeout_seconds = 5

[features]
new_checkout = false

# .env — NOT checked in, one per machine
# DATABASE_URL=postgres://app:secret@db:5432/orders
# STRIPE_KEY=sk_live_...

# compose.yaml / CI workflow — YAML because the tools need it
# package.json / tsconfig.json — JSON because the tools need it

Code Explained

Settings that are the same everywhere go in the checked-in file
Secrets and values that change per machine come from the environment
Tool configs stay in the tool's format; don't wrap them
This split is the 12-factor idea covered on sheet 10

Same Data In…

  • JSON {"app": {"name": "orders", "log_level": "info"}}
  • YAML app: {name: orders, log_level: info}
  • INI [app] / name = orders / log_level = info

Gotcha

  • TOML gets awkward past three levels of nesting; that's a sign JSON or YAML fits better
  • JSON written by people breaks on a trailing comma; JSONC / JSON5 fix that but need a different parser

⚠ Common Mistakes

  • Putting secrets in a checked-in config file "for now"
  • Inventing nested structure in INI with dotted section names that only your parser understands
  • Choosing YAML for a new app's settings and adding a parser dependency plus its security notes

✓ Tips & Best Practices

  • Prefer the format your runtime reads natively so config never needs a dependency
  • Write a schema or a typed config class and validate at start-up
  • Document every key next to it in comments (another reason JSON is a poor fit for hand-edited config)

Quick Summary

  • TOML — hand-edited settings
  • JSON — machine-written data
  • YAML — when the tool says so
  • env vars — secrets and per-deploy values
