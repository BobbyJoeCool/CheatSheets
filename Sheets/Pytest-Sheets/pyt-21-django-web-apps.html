Testing Web Apps With pytest

pytest-django sets up Django for pytest: it creates a test database, gives you fixtures such as client, admin_client, rf (request factory) and settings, and blocks database access unless a test is marked django_db. For FastAPI and Starlette, TestClient calls the app in memory. Flask has app.test_client(). The Django set covers the app side.

Notes

  • Point pytest at settings: DJANGO_SETTINGS_MODULE = "mysite.settings" in config
  • Each django_db test runs in a transaction rolled back afterwards
  • transaction=True for tests that need real commits
  • Use factory_boy or factory fixtures for model data

pytest-django and FastAPI

# pyproject.toml
# [tool.pytest]
# DJANGO_SETTINGS_MODULE = "mysite.settings"
# addopts = ["--reuse-db"]

import pytest
from orders.models import Order

@pytest.mark.django_db
def test_order_list(client, django_user_model):
    user = django_user_model.objects.create_user("ann", password="pw")
    Order.objects.create(owner=user, total=10)
    client.force_login(user)
    resp = client.get("/orders/")
    assert resp.status_code == 200
    assert "10.00" in resp.content.decode()

def test_admin_page(admin_client):
    assert admin_client.get("/admin/").status_code == 200

def test_feature_flag(settings, client, db):
    settings.NEW_CHECKOUT = True          # undone after the test
    assert client.get("/checkout/").status_code == 200

def test_query_count(django_assert_num_queries, db):
    with django_assert_num_queries(2):
        list(Order.objects.select_related("owner"))

# FastAPI
from fastapi.testclient import TestClient
def test_health():
    assert TestClient(app).get("/health").json() == {"ok": True}

Code Explained

django_user_model is the project's user model, whatever it's called
Requesting the db fixture is the same as @pytest.mark.django_db
settings changes are reverted after the test
--reuse-db keeps the test database between runs for speed

unittest Equivalent

  • pytest-django → Django's TestCase and manage.py test
  • client fixture → self.client
  • django_db → TestCase wraps each test in a transaction
  • settings fixture → @override_settings(...)

Prefer / Avoid

  • django.test.TestCase classes for new tests → plain functions with fixtures
  • raw Model.objects.create with many fields in every test → factories
  • testing views through Selenium → client for logic, Playwright for real browser flows

⚠ Common Mistakes

  • Forgetting django_db and getting "Database access not allowed"
  • Using transaction=True everywhere and making the suite slow
  • Running pytest without DJANGO_SETTINGS_MODULE configured

✓ Tips & Best Practices

  • Use --reuse-db locally and --create-db after migrations change
  • Check N+1 problems with django_assert_num_queries
  • Test views with client; test business logic without HTTP at all

Quick Summary

  • pytest-django — Django fixtures and test DB
  • django_db — allow database access
  • client / admin_client / settings — common fixtures
  • TestClient — FastAPI in memory
