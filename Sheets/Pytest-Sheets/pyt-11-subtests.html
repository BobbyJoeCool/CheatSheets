Several Checks, Each Reported

pytest 9 adds a built-in subtests fixture (it used to be the pytest-subtests plugin). Inside one test, each with subtests.test(...) block is reported separately, and a failure in one block doesn't stop the others. Use it when the cases are only known at run time (rows from a file, items from an API); use parametrize when they're known when the test is collected.

Notes

  • Keyword arguments to subtests.test label the block in the report
  • A failing subtest marks the whole test as failed
  • unittest.TestCase.subTest blocks are now reported the same way
  • Fixtures run once for the test, not once per subtest

subtests in Practice

import json

def test_every_fixture_file_loads(subtests, tmp_path):
    for path in sorted(Path("tests/data").glob("*.json")):
        with subtests.test(msg="loads", file=path.name):
            data = json.loads(path.read_text())
            assert "id" in data

def test_all_routes_require_auth(subtests, client):
    for route in app.routes():               # known only at run time
        with subtests.test(route=route.path):
            assert client.get(route.path).status_code == 401

# Output (abridged):
# test_api.py::test_all_routes_require_auth [route='/admin'] SUBFAIL
# test_api.py::test_all_routes_require_auth [route='/orders'] SUBPASS
# test_api.py::test_all_routes_require_auth FAILED

# unittest style, also reported per block in pytest 9:
class TestFiles(unittest.TestCase):
    def test_load(self):
        for name in names:
            with self.subTest(name=name):
                self.assertTrue(load(name))

Code Explained

Each block's label comes from msg and the keyword arguments
The loop keeps going after a failing block, so you see every bad route at once
The parent test is reported as failed if any subtest failed
Expensive fixtures (like client) are built once, not per subtest

unittest Equivalent

  • subtests.test(route=…) → self.subTest(route=…) (same idea, now reported per block by pytest)
  • pytest runs existing subTest code without changes

Prefer / Avoid

  • a for loop with bare asserts → subtests.test blocks
  • subtests for a fixed list known up front → parametrize
  • dozens of subtests per test → split the test; reports get hard to read

Subtests vs Parametrize

QuestionParametrizeSubtests
Cases known at collection?RequiredNot needed
Each case a separate test ID?YesNo (one test)
Run one case alone?Yes (-k / node ID)No
Fixtures rebuilt per case?Yes (function scope)No

⚠ Common Mistakes

  • Using subtests where parametrize fits and losing the ability to rerun one case
  • Expecting a fresh fixture per subtest; state carries over between blocks
  • Installing the old pytest-subtests plugin alongside pytest 9

✓ Tips & Best Practices

  • Put the identifying value in the keyword arguments so the failing case is obvious
  • Use subtests for data-driven checks over files, routes or database rows
  • Remove pytest-subtests from dependencies when moving to pytest 9

Quick Summary

  • subtests.test(**labels) — report each block
  • keeps going after a failure
  • cases at run time → subtests
  • cases at collection → parametrize
