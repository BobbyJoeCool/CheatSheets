Fixture Basics

@pytest.fixture · requesting by argument name · return values · fixtures using fixtures · autouse=True · usefixtures

Setup That Tests Ask For

A fixture is a function decorated with @pytest.fixture that builds something a test needs: an object, a temp file, a database connection. A test requests it by naming it as a parameter; pytest calls the fixture and passes in the result. Fixtures can request other fixtures, so setup is built from small, reusable pieces instead of one big setUp method.

Notes

  • Each test gets a fresh fixture value by default (function scope)
  • A fixture runs only for tests that request it (unless autouse)
  • pytest --fixtures lists every available fixture with its docstring
  • @pytest.mark.usefixtures("name") runs one without passing its value

Under the Hood

  • pytest matches each test parameter by name to a registered fixture
  • It builds a dependency graph per test and calls fixtures in order, each once per scope
  • The request fixture gives a fixture access to the test that asked for it (request.node, request.param)

Fixtures Building on Fixtures

import pytest
from shop.cart import Cart
from shop.catalog import Catalog

@pytest.fixture
def catalog():
    """A catalog with two products."""
    return Catalog({"apple": 0.50, "pear": 0.75})

@pytest.fixture
def cart(catalog):                 # fixture requests a fixture
    return Cart(catalog)

def test_add_item(cart):
    cart.add("apple", qty=4)
    assert cart.total() == 2.00

def test_unknown_item(cart):
    with pytest.raises(KeyError):
        cart.add("kiwi")

@pytest.fixture(autouse=True)
def fixed_clock(monkeypatch):      # runs for every test in scope
    monkeypatch.setattr("shop.cart.now", lambda: 1_700_000_000)

@pytest.mark.usefixtures("clean_db")
def test_checkout(cart): ...

Code Explained

cart requests catalog, so pytest builds the catalog first and passes it in
Each test gets its own cart, so tests can't affect each other
autouse=True applies the fixture to every test in its module (or below its conftest.py)
The docstring shows up in pytest --fixtures

unittest Equivalent

  • fixture → setUp(self) storing self.cart
  • fixture requesting fixture → setUp calling helper methods in order
  • autouse → setUp in a base class every test class inherits

Prefer / Avoid

  • a setup_method that builds everything → small fixtures each test requests
  • global objects created at module import → fixtures
  • calling a fixture function directly → request it as a parameter

⚠ Common Mistakes

  • Calling cart() directly inside a test; pytest raises an error, request it instead
  • Making a heavy fixture autouse and slowing every test
  • Mutating a shared fixture object in one test and relying on it in another

✓ Tips & Best Practices

  • Keep fixtures small and compose them; it's easier to see what each test needs
  • Give fixtures docstrings so pytest --fixtures documents them
  • Name fixtures as nouns (cart, admin_user), not verbs

Quick Summary

  • @pytest.fixture — setup as a function
  • request by parameter name
  • fixtures can use fixtures
  • autouse / usefixtures — setup without the value
