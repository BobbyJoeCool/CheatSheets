Output & Debugging

-v / -q · -s · -rA summary · --tb=short · --pdb · breakpoint() · --durations · -l locals

Read Failures and Drop Into a Debugger

pytest captures print output and shows it only for failing tests. Control how much you see with -v / -q, the traceback style with --tb, and the end-of-run summary with -r. When a failure isn't obvious, --pdb opens the debugger at the failing line, and a breakpoint() call in a test or in your code stops there with capture turned off.

Notes

  • -s turns capture off so prints appear live
  • --pdb with -x stops at the first failure and debugs it
  • --durations=10 lists the slowest tests and fixtures
  • log_cli = true streams log records as tests run

Under the Hood

  • Capture works at the file-descriptor level by default (--capture=fd), catching output from C code too
  • Captured output is attached to the report and printed only for failures
  • breakpoint() and --pdb suspend capture so the debugger can talk to the terminal

Debugging a Failure

pytest -v                      # one line per test
pytest -q                      # quieter
pytest -s                      # show print() output live
pytest -rA                     # summary of all outcomes at the end
pytest -rfE                    # summary of failures and errors only
pytest --tb=short              # shorter tracebacks (also line / no / native)
pytest -l                      # show local variables in tracebacks
pytest -x --pdb                # debugger at the first failure
pytest --trace tests/test_cart.py::test_total   # debugger at test start
pytest --durations=10          # slowest 10 setups / calls / teardowns
pytest -o log_cli=true --log-cli-level=DEBUG

# in code or a test:
def test_total():
    cart = build_cart()
    breakpoint()               # (Pdb) p cart.items   n   s   c   q

Code Explained

-r takes letters: f failed, E error, s skipped, x xfailed, X xpassed, p passed, A all
--tb=short is usually enough; long (default) shows full context
-o overrides any config key from the command line
In pdb: p expr print, n next, s step in, c continue, q quit

unittest Equivalent

  • -v → python -m unittest -v
  • --pdb → no flag; run under python -m pdb or add breakpoint()
  • -s → unittest doesn't capture by default; -b buffers output

Prefer / Avoid

  • adding prints and rerunning → --pdb or breakpoint()
  • reading full tracebacks every time → --tb=short in addopts
  • guessing why the suite is slow → --durations=10

⚠ Common Mistakes

  • Leaving breakpoint() in committed code; CI hangs or errors waiting for input
  • Using -s all the time and drowning failures in output
  • Reading only the last line of a traceback and missing the real cause above it

✓ Tips & Best Practices

  • Set PYTHONBREAKPOINT=0 in CI to make stray breakpoint() calls no-ops
  • Use --pdbcls=IPython.terminal.debugger:TerminalPdb for a nicer debugger
  • Add --durations=10 to CI to catch tests getting slower

Quick Summary

  • -v / -q / -s — verbosity and capture
  • -r / --tb — summary and traceback style
  • --pdb / breakpoint() — debug
  • --durations — find slow tests
