Testing Patterns in pytest

Arrange-Act-Assert · test data factories · golden files · snapshot testing (syrupy) · Hypothesis @given · testing CLIs

Patterns That Keep Tests Clear

Most good tests follow Arrange-Act-Assert: set up, do one thing, check the result. Factories build test data with sensible defaults; golden files and snapshot tests (syrupy) compare output to a stored, reviewed version; Hypothesis generates hundreds of inputs to check a property holds. The Testing set explains when to use each; this sheet shows the pytest way.

Notes

  • pip install syrupy hypothesis
  • Snapshots are files you commit and review in diffs
  • Hypothesis shrinks a failing input to the smallest example
  • Test CLIs by calling main(argv) with capsys, not by spawning a process

Factories, Snapshots, Properties, CLIs

from hypothesis import given, strategies as st

def test_refund(make_order):               # Arrange-Act-Assert
    order = make_order(total=50)           # arrange
    refund(order, 20)                      # act
    assert order.balance == 30             # assert

def test_invoice_render(snapshot):         # syrupy
    assert render_invoice(sample_order()) == snapshot
# $ pytest --snapshot-update   (then review the diff)

def test_report_matches_golden(tmp_path):
    out = tmp_path / "report.csv"
    export_report(out)
    assert out.read_text() == Path("tests/golden/report.csv").read_text()

@given(st.lists(st.floats(min_value=0, max_value=1e6)))
def test_total_never_negative(prices):     # property-based
    assert total(prices) >= 0

def test_cli(capsys):
    exit_code = main(["export", "--format", "json"])
    assert exit_code == 0
    assert capsys.readouterr().out.startswith("{")

Code Explained

Blank lines between arrange, act and assert make the structure visible
syrupy stores snapshots under __snapshots__/; --snapshot-update rewrites them
A golden file is a hand-checked expected output kept in the repo
@given runs the test with many generated lists; failures show the minimal example

unittest Equivalent

  • factories → helper methods on a base TestCase
  • syrupy → no built-in snapshot support
  • Hypothesis → works with unittest too (@given on test methods)

Prefer / Avoid

  • updating snapshots without reading the diff → review every snapshot change
  • many near-identical example tests → one Hypothesis property
  • spawning subprocess for every CLI test → call main(argv) directly

⚠ Common Mistakes

  • Snapshot tests on output with timestamps or IDs that change every run
  • Hypothesis tests that just re-implement the function to compute the expected value
  • Arrange sections so long the test's point is lost

✓ Tips & Best Practices

  • Strip or freeze volatile fields (dates, UUIDs) before snapshotting
  • Look for properties like round-trips (decode(encode(x)) == x) and invariants
  • Keep each test's Act to a single call

Quick Summary

  • Arrange-Act-Assert — one action per test
  • syrupy / golden files — compare stored output
  • Hypothesis @given — property-based
  • main(argv) + capsys — test CLIs
