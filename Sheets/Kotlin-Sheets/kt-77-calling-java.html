Sheet 77

Calling Java from Kotlin

platform types T! · getters/setters as properties · nullability annotations · SAM conversions · Java collections · checked exceptions ignored

Using Java Libraries

Kotlin calls Java code directly. Java getters and setters appear as properties, single-method interfaces accept lambdas, and checked exceptions need no handling. Values from Java have platform types (String!): Kotlin does not know if they can be null, so you decide when you assign them.

Key Points

  • T! can be treated as T or T?; choosing T risks an NPE
  • Nullability annotations (@Nullable, JSpecify) turn platform types into real types
  • getName() → name; isActive() → isActive
  • Java keywords that clash in Kotlin need backticks: is

Under the JVM

  • Kotlin inserts a null check when a platform value is assigned to a non-null type
  • Java collections are read as (Mutable)List<T!>: read-only or mutable is your choice
  • @NotNull / @Nullable from JetBrains, JSpecify, Jakarta and Android are understood

Java APIs from Kotlin

import java.time.LocalDate
import java.util.concurrent.Executors

val today = LocalDate.now()
println(today.year)                        // getYear() as a property
println(today.dayOfWeek)                   // getDayOfWeek()

val sb = java.lang.StringBuilder()
sb.append("a").append("b")

val props = System.getProperties()
val home: String? = System.getenv("HOME")  // platform type → choose nullable
val path: String = System.getProperty("user.dir")   // checked at assignment

val executor = Executors.newFixedThreadPool(2)
executor.submit { println("running") }     // lambda → Runnable (SAM)

val list = java.util.ArrayList<String>()   // MutableList at the Kotlin side
list.add("x")

val file = java.io.File("x.txt")
val text = file.readText()  // no try/catch needed for IOException

val obj = SomeJavaClass()
obj.`is`(5)                                // Java method named "is"
obj.name = "Ada"                           // calls setName("Ada")

Code Explained

today.year calls getYear()
Assigning System.getenv to String? keeps null handling explicit
submit { } converts the lambda to a Runnable
Checked exceptions from Java are not forced to be caught

Java Equivalent

  • today.getYear(), obj.setName("Ada")
  • executor.submit(() -> System.out.println("running"))
  • Checked exceptions must be caught or declared

Idiomatic Kotlin

  • trusting platform types as non-null → declare T? unless the API guarantees non-null
  • obj.getName() → obj.name

⚠ Common Mistakes

  • NPE from a platform-typed value assumed non-null
  • Modifying a Java list that is actually unmodifiable (UnsupportedOperationException)
  • Forgetting that Java collections are mutable underneath

✓ Tips & Best Practices

  • Annotate your own Java code with JSpecify @Nullable/@NonNull
  • Wrap risky Java APIs in small Kotlin functions with clear null types
  • Read IntelliJ's platform type hints

Quick Summary

  • getters → properties
  • T! — platform type
  • lambdas → SAM interfaces
  • no checked exceptions
