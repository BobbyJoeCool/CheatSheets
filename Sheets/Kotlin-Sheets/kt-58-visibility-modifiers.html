Visibility Modifiers

public (default) · private · protected · internal & modules · top-level visibility · constructor visibility

Who Can See What

Kotlin has four visibility modifiers. public is the default. private means visible inside the class, or inside the file for top-level declarations. protected adds subclasses. internal means visible anywhere in the same module (a Gradle source set or Maven project), which Java has no direct equivalent for.

Key Points

  • No package-private visibility in Kotlin
  • Top-level private = file-private
  • internal is ideal for library code not meant for users
  • Overriding members keep their visibility unless widened

Visibility in Practice

// File: PaymentService.kt  (module :payments)
package com.example.payments

private const val MAX_RETRIES = 3          // visible in this file only

internal class Gateway {                   // visible in module :payments
    fun charge(amount: Long) = true
}

class PaymentService internal constructor( // public class, internal constructor
    private val gateway: Gateway
) {
    fun pay(amount: Long): Boolean {       // public (default)
        repeat(MAX_RETRIES) { if (tryCharge(amount)) return true }
        return false
    }

    private fun tryCharge(amount: Long) = gateway.charge(amount)

    protected open fun audit() {}          // warning: class is final
}

open class Base {
    protected val secret = 42
    internal val moduleOnly = "m"
}
class Derived : Base() {
    fun reveal() = secret                  // OK: subclass
}
// Base().secret                           // error: protected

Code Explained

MAX_RETRIES cannot be seen from other files
Gateway is usable in the payments module but hidden from apps that use it
The internal constructor lets only the module create PaymentService
protected members are visible in subclasses only

Java Equivalent

  • public, private, protected, plus package-private (no modifier)
  • Java protected also allows access from the same package
  • Module-level hiding needs JPMS module-info.java exports

Idiomatic Kotlin

  • everything public by default → internal / private where possible
  • package-private Java habits → file-private or internal

⚠ Common Mistakes

  • Assuming package-private exists
  • Using public on everything in a library API
  • Expecting protected to allow same-package access like Java

✓ Tips & Best Practices

  • Default to private, then widen as needed
  • Use internal for library implementation classes
  • Turn on explicit API mode (kotlin { explicitApi() }) in libraries

Quick Summary

  • public — default
  • private — class or file
  • protected — subclasses
  • internal — same module
