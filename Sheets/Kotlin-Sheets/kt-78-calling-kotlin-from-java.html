Sheet 78

Calling Kotlin from Java

@JvmStatic · @JvmOverloads · @JvmField · @JvmName / @file:JvmName · Companion access · @Throws

Making Kotlin Nice for Java

Kotlin code is callable from Java, but some features look odd there: top-level functions live in a FileNameKt class, companion members go through Companion, defaults do not exist, and properties become getters. A handful of @Jvm… annotations shape what Java sees.

Key Points

  • Properties become getX() / setX(); isX stays isX()
  • Default parameters need @JvmOverloads
  • Extension functions become static methods taking the receiver
  • Non-null parameters are checked at runtime

Under the JVM

  • Top-level declarations in Util.kt compile to class UtilKt with static members
  • @JvmField removes the getter and exposes a public field
  • Inline functions with reified types cannot be called from Java

Kotlin Side and Java Side

// Kotlin: Prices.kt
@file:JvmName("Prices")
package com.example

fun withTax(amount: Double, rate: Double = 0.06) = amount * (1 + rate)

class Product @JvmOverloads constructor(
    @JvmField val sku: String,
    val name: String = "",
    var price: Double = 0.0
) {
    companion object {
        @JvmStatic fun of(sku: String) = Product(sku)
        const val CURRENCY = "USD"
    }

    @Throws(java.io.IOException::class)
    fun export(path: String) { java.io.File(path).writeText(name) }
}

fun String.toSlug() = lowercase().replace(" ", "-")

/* Java usage:
   double t = Prices.withTax(10.0, 0.06);      // no default: pass both
   Product p = new Product("A1");              // @JvmOverloads
   String s = p.sku;                           // @JvmField: public field
   p.setPrice(9.99);                           // property setter
   Product q = Product.of("B2");               // @JvmStatic
   String c = Product.CURRENCY;                // const → static field
   String slug = Prices.toSlug("Hello World"); // extension → static
   try { p.export("x.txt"); } catch (IOException e) { }
*/

Code Explained

@file:JvmName("Prices") replaces the default PricesKt class name
@JvmOverloads generates the shorter constructors
@JvmStatic avoids Product.Companion.of(...)
@Throws lets Java catch the checked IOException

Java Equivalent

  • This is the Java view: static methods, fields and overloads
  • Without @JvmStatic: Product.Companion.of("B2")
  • Without @JvmName: PricesKt.withTax(…)

Idiomatic Kotlin

  • Java callers using Companion and …Kt names → @JvmStatic and @file:JvmName
  • Java callers passing every default → @JvmOverloads

Annotations

AnnotationJava Sees
@file:JvmName("X")Class X for top-levels
@JvmStaticStatic method
@JvmOverloadsOverloads for defaults
@JvmFieldPublic field, no getter
@JvmName("f")Renamed method
@Throws(E::class)throws clause
@JvmRecordJava record
@JvmSuppressWildcardsNo ? extends

⚠ Common Mistakes

  • Leaving Java callers with Companion and …Kt names
  • Assuming Java can use default arguments
  • Passing null from Java into non-null parameters (runtime exception)

✓ Tips & Best Practices

  • Design Kotlin APIs used by Java with these annotations from the start
  • Use @JvmName to fix clashes from generic erasure
  • Test the Java call site in a small Java file

Quick Summary

  • @file:JvmName — class name
  • @JvmStatic — static
  • @JvmOverloads — defaults
  • @JvmField / @Throws
