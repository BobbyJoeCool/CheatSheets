Exceptions in Coroutines

propagation in launch vs async · CoroutineExceptionHandler · supervisorScope · SupervisorJob · rethrowing cancellation

When a Coroutine Fails

An exception in launch propagates up to the parent, cancelling it and its other children. An exception in async is stored and rethrown when you call await(), but it still cancels the parent scope. supervisorScope and SupervisorJob stop failures from spreading to siblings, and a CoroutineExceptionHandler logs uncaught ones.

Key Points

  • Wrap await() in try/catch to handle async failures
  • Handlers only work on root coroutines (and launch)
  • In a supervisor, each child must handle its own errors
  • Cancellation exceptions are not treated as failures

Handling Failures

import kotlinx.coroutines.*

val handler = CoroutineExceptionHandler { ctx, e ->
    println("Uncaught in ${ctx[CoroutineName]}: ${e.message}")
}

fun main() = runBlocking {
    // try/catch around await
    val result = runCatching {
        coroutineScope { async { error("price API down") }.await() }
    }
    println(result.exceptionOrNull()?.message)        // price API down

    // supervisor: one failure does not cancel the others
    supervisorScope {
        val a = launch(handler + CoroutineName("a")) { error("A failed") }
        val b = launch { delay(100); println("B still finished") }
        joinAll(a, b)
    }
    // Uncaught in CoroutineName(a): A failed
    // B still finished

    // long-lived scope with a supervisor job and a handler
    val ctx = SupervisorJob() + Dispatchers.Default + handler
    val appScope = CoroutineScope(ctx)
    appScope.launch { error("task failed") }  // logged, scope survives
    delay(100)
}

suspend fun safeLoad(id: Int): User? = try {
    api.user(id)
} catch (e: CancellationException) {
    throw e                                               // keep cancellation
} catch (e: IOException) {
    null
}

Code Explained

The failed async is caught where await is called
In supervisorScope, coroutine b finishes even though a failed
The handler logs the uncaught exception from coroutine a
A SupervisorJob keeps the app scope alive after one task fails

Java Equivalent

  • future.exceptionally(e -> …) / handle(…) on CompletableFuture
  • Uncaught thread exceptions: Thread.setDefaultUncaughtExceptionHandler
  • ExecutorService tasks swallow exceptions until future.get()

Idiomatic Kotlin

  • try/catch around launch (does not catch child failures) → catch inside the coroutine or use a handler
  • one failing child killing a whole service scope → SupervisorJob

⚠ Common Mistakes

  • Wrapping launch { } in try/catch and expecting to catch its failure
  • Installing a handler on a child coroutine (ignored)
  • Swallowing CancellationException in catch-all blocks

✓ Tips & Best Practices

  • Handle errors where you can act on them (inside the coroutine)
  • Use SupervisorJob for long-lived service scopes
  • Always log with a handler at the root of app scopes

Quick Summary

  • launch — propagates up
  • async — rethrows on await
  • supervisorScope — isolate failures
