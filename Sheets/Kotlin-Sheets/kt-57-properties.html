Fields with Built-in Accessors

Kotlin classes have properties, not public fields. Each property has a getter (and a setter for var) generated for you. You can customize them with get() and set(value), use field to reach the backing storage, restrict the setter with private set, or compute a value on every read.

Key Points

  • Callers use obj.prop, never getProp()
  • Computed properties have no backing field
  • field is only valid inside accessors
  • Backing property pattern: private _items, public read-only items

Custom Accessors

class Rectangle(val width: Double, val height: Double) {
    val area: Double                       // computed on each read
        get() = width * height
    val isSquare get() = width == height
}

class User(name: String) {
    var name: String = name
        set(value) {
            require(value.isNotBlank())
            field = value.trim()           // field = backing storage
        }

    var loginCount = 0
        private set                        // public read, private write

    fun login() { loginCount++ }
}

class Cart {
    private val _items = mutableListOf<String>()
    val items: List<String> get() = _items // read-only view

    fun add(item: String) { _items += item }
}

val r = Rectangle(3.0, 4.0)
println(r.area)                            // 12.0
val u = User("  Ada ")
u.name = " Lovelace "
println(u.name)                            // Lovelace
// u.loginCount = 5                        // error: private setter

Code Explained

area has a getter but no stored value
The custom setter validates and trims before storing in field
private set blocks outside writes
The backing property hides the mutable list behind a List

Java Equivalent

  • private double width; public double getWidth()
  • public void setName(String n) { … this.name = n.trim(); }
  • Collections.unmodifiableList(items) for read-only views

Idiomatic Kotlin

  • getX() / setX() methods → properties with accessors
  • public MutableList fields → private _items + public List

⚠ Common Mistakes

  • Writing name = value inside its own setter (infinite recursion; use field)
  • Expensive work in a getter that looks like a cheap field read
  • Exposing mutable collections directly

✓ Tips & Best Practices

  • Use computed properties for derived values
  • Use private set for state changed only by methods
  • Keep getters cheap and side-effect free

Quick Summary

  • properties — not fields
  • get() / set() — custom
  • field — backing storage
  • private set — read-only outside
