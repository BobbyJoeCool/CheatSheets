Handling Exceptions

Kotlin uses try, catch and finally like Java, but try is an expression: the value of the try or catch block becomes the result. Catch blocks are checked top to bottom, so put specific exception types before general ones. finally always runs, and its value is ignored.

Key Points

  • Kotlin exceptions are Java exceptions (kotlin.Exception = java.lang.Exception)
  • No multi-catch catch (A | B e): use when inside one catch
  • The last expression of try or catch is the value
  • Prefer use { } over finally for closing resources

try as an Expression

fun parseAge(s: String): Int = try {
    s.toInt()
} catch (e: NumberFormatException) {
    -1                                   // value when parsing fails
}

println(parseAge("42"))                  // 42
println(parseAge("x"))                   // -1

fun readConfig(path: String): String {
    try {
        return File(path).readText()
    } catch (e: FileNotFoundException) {
        println("Missing: ${e.message}")
        return ""
    } catch (e: IOException) {
        throw IllegalStateException("Cannot read $path", e)  // wrap
    } finally {
        println("done reading $path")    // always runs
    }
}

try {
    riskyCall()
} catch (e: Exception) {
    when (e) {                           // instead of multi-catch
        is IllegalArgumentException, is IllegalStateException -> log(e)
        else -> throw e
    }
}

Code Explained

parseAge returns the try block's value or -1
Specific FileNotFoundException comes before general IOException
Passing e as the cause keeps the original stack trace
when with is handles several types in one catch

Java Equivalent

  • try { … } catch (NumberFormatException e) { … } as a statement only
  • catch (IllegalArgumentException | IllegalStateException e) multi-catch
  • try-with-resources try (var r = …) ≈ Kotlin use { }

Idiomatic Kotlin

  • var x; try { x = … } catch { x = … } → val x = try { … } catch (…) { … }
  • empty catch blocks → log, rethrow, or return a fallback on purpose

⚠ Common Mistakes

  • Catching Exception first so specific handlers never run
  • Catching Throwable and swallowing errors like OutOfMemoryError
  • Returning a value from finally (it is ignored as an expression)

✓ Tips & Best Practices

  • Wrap low-level exceptions with context and the original cause
  • Use toIntOrNull() style APIs to avoid exceptions for expected failures
  • Use runCatching for functional style (sheet 35)

Quick Summary
