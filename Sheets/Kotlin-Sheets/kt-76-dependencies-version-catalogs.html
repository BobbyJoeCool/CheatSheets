Dependencies & Version Catalogs

Managing Libraries

Dependencies are declared in build.gradle.kts with configurations like implementation and testImplementation. A version catalog (gradle/libs.versions.toml) keeps every version in one place and gives type-safe accessors like libs.ktor.server.core. BOMs align versions across a library family.

Key Points

  • implementation hides the dependency from consumers; api exposes it
  • Catalog aliases use dashes; accessors use dots
  • Kotlin compiler plugins: serialization, spring, jpa, compose
  • See the Gradle set for full detail

Version Catalog + Build Script

// gradle/libs.versions.toml
// [versions]
// kotlin = "2.2.0"
// coroutines = "1.10.2"
// ktor = "3.2.0"
//
// [libraries]
// coroutines-core = { module = "org.jetbrains.kotlinx:kotlinx-coroutines-core",
//                    version.ref = "coroutines" }
// ktor-server-core = { module = "io.ktor:ktor-server-core",
//                     version.ref = "ktor" }
// coroutines-bom = { module = "org.jetbrains.kotlinx:kotlinx-coroutines-bom",
//                    version.ref = "coroutines" }
// mockk = "io.mockk:mockk:1.14.2"
//
// [plugins]
// kotlin-jvm = { id = "org.jetbrains.kotlin.jvm", version.ref = "kotlin" }
// kotlin-serialization = { id = "org.jetbrains.kotlin.plugin.serialization",
//                         version.ref = "kotlin" }

// build.gradle.kts
plugins {
    alias(libs.plugins.kotlin.jvm)
    alias(libs.plugins.kotlin.serialization)
}

dependencies {
    implementation(libs.coroutines.core)
    implementation(libs.ktor.server.core)
    implementation(platform(libs.coroutines.bom))   // BOM
    testImplementation(kotlin("test"))
    testImplementation(libs.mockk)
}

Code Explained

version.ref shares one version across several libraries
coroutines-core becomes libs.coroutines.core
alias(libs.plugins.…) applies plugins from the catalog
platform(...) imports a BOM to align versions

Java Equivalent

  • Maven <dependencyManagement> with a BOM
  • Gradle Java projects use the same catalogs
  • <properties><kotlin.version> for shared versions in Maven

Idiomatic Kotlin

  • versions scattered in build files → libs.versions.toml
  • mismatched Kotlin library versions → BOMs / one kotlin version

⚠ Common Mistakes

  • Kotlin plugin version different from the Kotlin stdlib/library expectations
  • Using api everywhere and leaking dependencies
  • Hard-coding versions in several modules

✓ Tips & Best Practices

  • Run ./gradlew dependencies to debug version conflicts
  • Use KSP instead of kapt for annotation processing when supported
  • Keep one catalog for the whole repository

Quick Summary

  • implementation — normal deps
  • libs.versions.toml — one place
  • platform() — BOMs
  • compiler plugins — per feature
