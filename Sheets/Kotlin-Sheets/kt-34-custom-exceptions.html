Custom Exceptions & No Checked Exceptions

class MyException : Exception() · no checked exceptions · @Throws for Java callers · exception chaining cause · sealed error types

Your Own Exception Types

Custom exceptions are ordinary classes extending Exception or RuntimeException. Kotlin has no checked exceptions: you never declare throws and callers are never forced to catch. For expected failures, many Kotlin codebases return a sealed result type instead of throwing.

Key Points

  • Pass message and cause to the superclass
  • Add @Throws(IOException::class) if Java code must catch it
  • Checked Java exceptions can be thrown and caught freely
  • Sealed types make failures part of the return type

Under the JVM

  • Checked exceptions are a Java compiler rule; the JVM does not enforce them
  • Without @Throws, Java callers cannot write catch (IOException e) around the call
  • Kotlin Exception is a typealias for java.lang.Exception

Exceptions vs a Sealed Result

class InsufficientFundsException(
    val needed: Double,
    cause: Throwable? = null
) : RuntimeException("Need $needed more", cause)

class Account(var balance: Double) {
    @Throws(InsufficientFundsException::class)   // for Java callers
    fun withdraw(amount: Double) {
        if (amount > balance) throw InsufficientFundsException(amount - balance)
        balance -= amount
    }
}

// No throws clause needed, no forced catch:
fun load(path: String): String = File(path).readText()  // may throw IOException

// Expected failure as a value instead:
sealed interface Withdrawal {
    data class Ok(val newBalance: Double) : Withdrawal
    data class Declined(val shortBy: Double) : Withdrawal
}

fun tryWithdraw(acct: Account, amt: Double): Withdrawal =
    if (amt <= acct.balance) Withdrawal.Ok(acct.balance - amt)
    else Withdrawal.Declined(amt - acct.balance)

when (val r = tryWithdraw(Account(50.0), 80.0)) {
    is Withdrawal.Ok       -> println("Left: ${r.newBalance}")
    is Withdrawal.Declined -> println("Short by ${r.shortBy}")  // Short by 30.0
}

Code Explained

The custom exception carries data (needed) and an optional cause
@Throws only affects how Java sees the method
load can throw IOException without declaring it
The sealed result forces callers to handle both outcomes

Java Equivalent

  • class InsufficientFundsException extends RuntimeException
  • void load() throws IOException is required for checked exceptions
  • Sealed interfaces + records (Java 17) for result types

Idiomatic Kotlin

  • exceptions for normal control flow → sealed result types
  • catching and rethrowing to satisfy "throws" → just let it propagate

⚠ Common Mistakes

  • Forgetting @Throws so Java callers cannot catch a checked exception
  • Swallowing exceptions because the compiler no longer forces handling
  • Losing the original cause when wrapping

✓ Tips & Best Practices

  • Throw for programmer errors; return sealed results for expected outcomes
  • Document thrown exceptions in KDoc @throws
  • Keep custom exceptions few and meaningful

Quick Summary

  • extend Exception
  • no checked exceptions
  • @Throws — Java interop
  • sealed results — expected failures
