Extending Classes

Kotlin classes and members are final by default: mark a class open to allow subclasses, and mark members open to allow overriding. Subclasses call the superclass constructor in their header, overriding members must say override, and super calls the parent version.

Key Points

  • Syntax: class Dog : Animal("dog")
  • override members are open unless marked final override
  • Override val with var, not the reverse
  • Abstract classes and interfaces are open automatically

open, override, super

open class Animal(val name: String) {
    open val sound = "..."
    open fun speak() = "$name says $sound"
    fun describe() = "Animal: $name"            // final: cannot override
}

class Dog(name: String) : Animal(name) {        // call super constructor
    override val sound = "Woof"
    override fun speak() = super.speak() + "!"  // reuse parent version
}

open class Cat(name: String) : Animal(name) {
    final override fun speak() = "$name purrs"  // subclasses cannot change it
}

val pets: List<Animal> = listOf(Dog("Rex"), Cat("Tom"))
pets.forEach { println(it.speak()) }
// Rex says Woof!
// Tom purrs

open class View(val id: Int) {
    constructor(id: Int, tag: String) : this(id)
}
class Button : View {
    constructor(id: Int) : super(id)            // no primary constructor
}

Code Explained

open on Animal allows Dog : Animal(name)
override val sound replaces the property
super.speak() calls the parent function
final override stops further overriding

Java Equivalent

  • Java classes are open by default; final opts out
  • @Override is optional in Java, override is required in Kotlin
  • super(name) in the constructor body

Idiomatic Kotlin

  • deep inheritance trees → interfaces + composition / delegation (sheet 67)
  • making everything open → open only what is designed for extension

⚠ Common Mistakes

  • Forgetting open and getting "this type is final"
  • Calling open members from a constructor
  • Framework issues with final classes (Spring/JPA need the all-open plugin, sheet 93)

✓ Tips & Best Practices

  • Prefer composition over inheritance
  • Use the kotlin-spring / kotlin-jpa plugins for frameworks that proxy classes
  • Use sealed classes for closed hierarchies (sheet 63)
