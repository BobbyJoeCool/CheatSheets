Threading & Responsive UIs

threading.Thread · queue.Queue · after() polling · not thread-safe · daemon threads · concurrent.futures

Keeping the UI Responsive

Tk runs everything on one thread: while a callback works, the window can't redraw or respond. Move slow work (network, files, heavy math) to a worker thread, but remember that Tkinter is not thread-safe: workers must not touch widgets or Tk variables. Instead they put results on a queue.Queue, and the main thread polls the queue with after() and updates the UI. concurrent.futures works the same way with a future you check from an after() loop.

Notes

  • Mark workers daemon=True so they don't block exit
  • Pass data, not widgets, into worker functions
  • Disable the start button while work runs
  • Catch exceptions in the worker and queue them
  • CPU-bound work may need multiprocessing instead

Worker Thread + Queue + after()

import tkinter as tk, threading, queue, time
from tkinter import ttk

root = tk.Tk(); q = queue.Queue()
bar = ttk.Progressbar(root, length=260); bar.pack(padx=10, pady=8)
status = ttk.Label(root, text="Idle"); status.pack()
def worker(n):                        # runs off the main thread
    try:
        for i in range(1, n + 1):
            time.sleep(0.05)          # slow work stand-in
            q.put(("progress", i * 100 / n))
        q.put(("done", f"Processed {n} items"))
    except Exception as exc:
        q.put(("error", str(exc)))
def poll():                           # runs on the main thread
    while not q.empty():
        kind, value = q.get_nowait()
        if kind == "progress":
            bar["value"] = value
        else:
            status.config(text=value); start.state(["!disabled"]); return
    root.after(50, poll)
def begin():
    start.state(["disabled"]); status.config(text="Working…")
    threading.Thread(target=worker, args=(60,), daemon=True).start(); poll()
start = ttk.Button(root, text="Start", command=begin); start.pack(pady=8)

Code Explained

The worker only writes to the queue, never to widgets
Errors are sent through the queue too
poll() drains all queued messages each tick
Polling stops after the final message
The button is disabled while work runs

⚠ Common Mistakes

  • Calling label.config() from a worker thread
  • Using q.get() (blocking) on the main thread
  • Starting a new poll loop on every click

✓ Tips & Best Practices

  • Wrap the pattern in a small helper class
  • Send tagged tuples like ("progress", 40)
  • Show progress or a spinner for anything over ~0.2 s

Quick Summary

  • One UI thread; never block it
  • Workers → queue → after() poll
  • Never touch Tk from workers
  • Disable controls while busy
