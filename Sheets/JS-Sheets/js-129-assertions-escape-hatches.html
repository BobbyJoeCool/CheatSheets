Assertions & Escape Hatches

as · as unknown as · ! · @ts-expect-error · @ts-ignore · any vs unknown

Overview

Sometimes you know more than the compiler. Type assertions (as T) and the non-null assertion (!) override its judgment, and @ts-expect-error/@ts-ignore silence specific errors. These are escape hatches: they remove safety rather than add it, so use them sparingly, narrowly, and with a comment explaining why.

Notes

  • Assertions don't change runtime values or do conversions
  • TS blocks wildly incompatible assertions unless you go through unknown
  • @ts-expect-error fails if there's no error, so stale ones get noticed
  • as const is an assertion too, but a safe one

Escape hatches

const input = document.getElementById("email") as HTMLInputElement;
input.value;                               // OK, but no runtime check

const el = document.querySelector(".total")!;   // asserts non-null
el.textContent = "42";                     // crashes if it's missing

const n = "42" as unknown as number;       // double assertion: a lie
n.toFixed(2);                              // runtime TypeError

// @ts-expect-error: legacy API takes a string here, fixed in v3
legacyFormat(123);

// @ts-ignore                              // silences anything (avoid)
riskyCall();

// safer alternatives
const maybe = document.querySelector<HTMLInputElement>("#email");
if (maybe) maybe.value;                    // real check
function assertEl<T extends Element>(e: T | null): T {
  if (!e) throw new Error("element missing");
  return e;
}
const total = assertEl(document.querySelector(".total"));

Code Explained

as T — tell TS the type; unchecked
! — remove null/undefined from the type
as unknown as T — forces any assertion
@ts-expect-error — preferred over @ts-ignore
Assertion helpers — keep the check, keep the type

⚠ Common Mistakes

  • Asserting API data with as User instead of validating it
  • Sprinkling ! after every DOM query
  • Leaving @ts-ignore comments that hide new, unrelated errors later

✓ Tips & Best Practices

  • Require a reason after @ts-expect-error (typescript-eslint ban-ts-comment)
  • Search the codebase for as unknown as periodically
  • Enable no-non-null-assertion as a warning

Quick Summary

  • as T — unchecked cast
  • ! — assume non-null
  • @ts-expect-error — documented suppression
  • prefer guards and validation
