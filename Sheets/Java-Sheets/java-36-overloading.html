Method Overloading

overloading · signature · parameter types · arity · type promotion · ambiguity · constructors

Same Name, Different Parameters

Overloading means defining several methods with the same name but different parameter lists (count, types, or order). The compiler chooses which one to call at compile time based on the arguments. It's how println accepts int, String, double, and more. Return type alone cannot distinguish overloads.

Notes

  • Differing only by return type is a compile error
  • Parameter names don't count toward the signature
  • The compiler picks the most specific match
  • Constructors are commonly overloaded

Overload Set

static int    max(int a, int b)          { return a > b ? a : b; }
static double max(double a, double b)    { return a > b ? a : b; }
static int    max(int a, int b, int c)   { return max(max(a, b), c); }
static String max(String a, String b)    { return a.compareTo(b) >= 0 ? a : b; }

max(3, 7);           // 7       → max(int, int)
max(2.5, 1.0);       // 2.5     → max(double, double)
max(3, 9, 4);        // 9       → max(int, int, int)
max(3, 2.5);         // 3.0     → int widened to double
max("pear", "fig");  // "pear"

// Default-argument style
static void log(String msg)            { log(msg, "INFO"); }
static void log(String msg, String lvl){ System.out.println(lvl + ": " + msg); }

Notes

max(3, 2.5) widens the int; no exact match exists
One overload delegating to another simulates default values
Overloads should do the same thing conceptually

Resolution Order

PhaseCompiler tries
1Exact match / widening (no boxing)
2Boxing and unboxing
3Varargs

Valid vs Invalid Overloads

PairValid?
f(int) / f(long)Yes
f(int, String) / f(String, int)Yes, order differs
f(int) / int f(int) returning other typeNo
f(int a) / f(int b)No, same signature
f(List<String>) / f(List<Integer>)No, erasure clash

⚠ Common Mistakes

  • f(null) with overloads f(String) and f(Integer) is ambiguous — cast the null
  • Overloading f(Object) and f(String) and expecting runtime type to decide — the compiler uses the declared type
  • Making overloads with different behavior; readers assume they're equivalent

✓ Tips & Best Practices

  • Delegate to the most complete overload to avoid duplicated logic
  • Avoid overloads with the same number of parameters of similar types
  • Overloading is compile-time; overriding (Sheet 64) is runtime

Quick Summary

  • Same name, different params
  • Chosen at compile time
  • Return type alone isn't enough
  • Delegate for default values
