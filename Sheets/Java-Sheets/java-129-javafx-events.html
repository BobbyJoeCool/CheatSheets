Handling Input and Background Work

JavaFX nodes fire events for actions, mouse, keyboard, and drag-and-drop. Register handlers with convenience setters like setOnAction, or with addEventHandler for multiple handlers. Events travel down (filters) then up (handlers) the scene graph, and consume() stops them. Long work runs in a Task so the UI stays responsive.

Notes

  • Handlers run on the JavaFX Application Thread
  • addEventFilter sees events before children do
  • Task<T> updates progress/message properties safely
  • Platform.runLater posts code to the FX thread

Events & Tasks

Button save = new Button("Save");
save.setOnAction(e -> saveFile());

Rectangle box = new Rectangle(100, 60);
box.setOnMouseClicked(e -> {
    if (e.getButton() == MouseButton.SECONDARY) showMenu(e.getScreenX());
});

scene.setOnKeyPressed(e -> {
    if (e.isControlDown() && e.getCode() == KeyCode.S) saveFile();
});
textField.addEventFilter(KeyEvent.KEY_TYPED, e -> {
    if (!e.getCharacter().matches("\\d")) e.consume();   // digits only
});

Task<List<String>> load = new Task<>() {
    @Override protected List<String> call() throws Exception {
        updateMessage("Downloading…");
        return fetchLines();                     // background thread
    }
};
load.setOnSucceeded(e -> list.getItems().setAll(load.getValue())); // FX
load.setOnFailed(e -> status.setText("Error: " + load.getException()));
status.textProperty().bind(load.messageProperty());
new Thread(load).start();

Notes

consume() blocks the keystroke from reaching the field
call() runs off the FX thread
setOnSucceeded/setOnFailed run on the FX thread
Binding to messageProperty shows progress text

⚠ Common Mistakes

  • Calling list.getItems().add(...) inside call() — UI change off the FX thread
  • Blocking the FX thread with Thread.sleep or network calls
  • Using a filter where a handler would do, accidentally consuming events for children

✓ Tips & Best Practices

  • Bind progress bars: bar.progressProperty().bind(task.progressProperty())
  • Run tasks on an ExecutorService rather than raw threads
  • Use setOnCloseRequest to confirm unsaved changes
