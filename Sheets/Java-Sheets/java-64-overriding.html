Method Overriding

@Override · override rules · covariant return · dynamic dispatch · final method · hiding · equals/hashCode

Replacing Inherited Behavior

A subclass overrides a method by declaring one with the same name and parameters as the parent. At runtime Java calls the version that matches the actual object type, not the variable type (dynamic dispatch). Always annotate overrides with @Override so the compiler catches signature mistakes.

Notes

  • Can't reduce visibility (public → protected ✖)
  • Can return a subtype (covariant return)
  • Can't throw broader checked exceptions
  • final, static, and private methods can't be overridden

Overriding in Practice

class Shape {
    double area() { return 0; }
    Shape copy() { return new Shape(); }
}
class Circle extends Shape {
    final double r;
    Circle(double r) { this.r = r; }

    @Override double area() { return Math.PI * r * r; }
    @Override Circle copy() { return new Circle(r); }   // covariant

    @Override
    public boolean equals(Object o) {
        return o instanceof Circle c && c.r == r;
    }
    @Override
    public int hashCode() { return Double.hashCode(r); }
}

Shape s = new Circle(1);
s.area();                 // 3.14159…  Circle's version runs
// @Override double area(int x)   ✖ compile error: doesn't override

Notes

The variable type is Shape, but Circle.area() runs
@Override turns a silent overload into a compile error
Override equals and hashCode together

⚠ Common Mistakes

  • public boolean equals(Circle c) — overloads instead of overriding equals(Object)
  • Overriding equals without hashCode; HashSet and HashMap break
  • Omitting @Override and not noticing a typo in the method name

✓ Tips & Best Practices

  • Always write @Override
  • Use final on methods subclasses must not change
  • Let your IDE or a record generate equals/hashCode

Quick Summary

  • Same signature in subclass
  • Runtime type decides
  • @Override — compiler check
  • Covariant returns allowed
