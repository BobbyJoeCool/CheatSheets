Other Out-of-Tree Platforms

out-of-tree platform model · React Native OpenHarmony · React Native Skia (Linux) · community forks · picking a platform

Beyond the Big Three

React Native's core targets iOS and Android. Everything else is out-of-tree: a fork or add-on package that implements the renderer and native modules for another OS, tracked against core releases. The React Native docs list partner platforms (macOS, Windows, visionOS, OpenHarmony) and community ones (tvOS, Web, Skia). Each has its own setup, release cadence, and library compatibility.

Evaluating a Platform

  • Which RN version does it support today?
  • New Architecture support?
  • Do your key libraries support it?
  • Who maintains it, and how active is it?

How Out-of-Tree Platforms Plug In

// 1. Install the platform package (version matched to RN)
//    yarn add react-native-windows@^0.84.0
// 2. Metro resolves platform-specific files
//    Screen.windows.tsx · Screen.macos.tsx · Screen.harmony.tsx
// 3. Platform.OS reports the platform
switch (Platform.OS) {
  case 'ios': case 'android': break
  case 'windows': case 'macos': /* desktop UI */ break
  case 'web': /* browser */ break
  default: /* other out-of-tree platforms */
}
// 4. Native modules need an implementation per platform;
//    unsupported ones should fail gracefully:
const Haptics = NativeModules.Haptics ?? { impact: () => {} }

// react-native.config.js can declare extra platforms for autolinking
module.exports = { project: { windows: { sourceDir: 'windows' } } }

Notes

Version match — platform packages track RN minors
Platform files — Metro picks by extension
Platform.OS — string per platform
Graceful fallbacks — keep shared code safe
react-native.config.js — per-platform project settings

iOS

  • iOS and Android are in-tree — maintained in core
  • macOS, tvOS and visionOS are forks that track iOS
  • Apple targets reuse most iOS native code

Android

  • Android-based devices need no extra platform
  • TV, Quest, Android XR and ChromeOS use the Android build
  • HarmonyOS NEXT isn't Android — needs RNOH

⚠ Common Mistakes

  • Picking a platform without checking its RN version; you may be stuck several releases behind core
  • Assuming a library's iOS support covers macOS or visionOS; each platform needs its own native code
  • Mixing a fork package and core react-native in one project

✓ Tips & Best Practices

  • Keep business logic platform-agnostic and push differences to the edges
  • Use reactnative.directory filters to check platform support before adopting a library
  • Follow each platform's release notes alongside core RN's

Quick Summary

  • Out-of-tree — forks/add-ons per OS
  • Match RN versions — critical
  • Platform files + Platform.OS — branch code
  • Partners vs community — maintenance levels
