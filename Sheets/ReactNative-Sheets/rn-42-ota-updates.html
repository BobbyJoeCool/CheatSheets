Over-the-Air Updates

expo-updates · EAS Update · channels & branches · runtimeVersion · rollouts · store policy limits

Ship JS Fixes Without the Store

EAS Update publishes a new JS bundle and assets that installed apps download on launch, so you can fix bugs without a store review. Updates can only change JS and assets; native code changes still need a new build. The runtimeVersion ties each update to compatible native builds, and channels route updates to the right builds.

Store Rules

  • Apple and Google allow OTA for bug fixes and small changes
  • Don't change the app's primary purpose via OTA
  • Updates must target the same native runtime
  • Keep a rollback path for bad updates

Config and Publishing

# app.json
# "runtimeVersion": { "policy": "fingerprint" },
# "updates": { "url": "https://u.expo.dev/<project-id>" }

npx expo install expo-updates
eas update:configure

# Publish to the branch mapped to the "production" channel
eas update --channel production --message "Fix checkout crash"
eas update --branch preview --message "Try new onboarding"

# Gradual rollout and rollback
eas update --channel production --rollout-percentage 10
eas update:rollback
eas channel:edit production --branch release-1.4

iOS

  • The embedded bundle is the fallback if no update loads
  • Suspended apps can run for days — Updates.reloadAsync() for urgent fixes
  • Updates must stay within App Review rules

Android

  • Google Play allows JS updates that don't change native code
  • Debug builds load from Metro and ignore updates
  • Test updates on a release build

In-App Checks

import * as Updates from 'expo-updates'

async function checkForUpdate() {
  if (__DEV__) return
  const result = await Updates.checkForUpdateAsync()
  if (result.isAvailable) {
    await Updates.fetchUpdateAsync()
    await Updates.reloadAsync()          // apply now
  }
}

// Or reactively
const { isUpdateAvailable, isUpdatePending } = Updates.useUpdates()
Updates.channel                           // 'production'
Updates.runtimeVersion                    // native compatibility key

⚠ Common Mistakes

  • Publishing an update that calls a native module the installed build doesn't have; the app crashes
  • Forgetting the update applies on next launch by default; users may not see it immediately
  • Using OTA to bypass review for new features; it violates store guidelines

✓ Tips & Best Practices

  • Use the fingerprint policy so incompatible updates are never delivered
  • Roll out to 10% first and watch crash reports before going to 100%
  • Test updates on a preview channel build before production
