Sheet 14

Configuring Plugins

<build><plugins> · <pluginManagement> · <configuration> · <executions> · binding a goal to a phase · pinning versions · help:describe

Plugins Do the Work

Plugins are configured under <build><plugins>. Plugin-wide settings go in <configuration>. To run a goal at a specific point in the build, add an <execution> with an id, a phase and the goals. <pluginManagement> sets versions and defaults without activating a plugin, which is how parents share plugin setup.

Notes

  • Always pin plugin versions; Maven warns when they're missing
  • Core plugins use groupId org.apache.maven.plugins (may be omitted)
  • Configuration inside an execution applies to that execution only

Under the Hood

  • Each goal is a Mojo class; @Parameter fields receive the <configuration> XML
  • Executions with the same id merge across parent and child
  • Built-in bindings use ids like default-compile; CLI calls use default-cli

pluginManagement, configuration, executions

<build>
  <pluginManagement>                       <!-- versions + defaults -->
    <plugins>
      <plugin>
        <artifactId>maven-surefire-plugin</artifactId>
        <version>3.5.3</version>
      </plugin>
    </plugins>
  </pluginManagement>

  <plugins>                                <!-- actually used -->
    <plugin>
      <groupId>org.codehaus.mojo</groupId>
      <artifactId>build-helper-maven-plugin</artifactId>
      <version>3.6.1</version>
      <executions>
        <execution>
          <id>add-generated</id>
          <phase>generate-sources</phase>
          <goals><goal>add-source</goal></goals>
          <configuration>
            <sources><source>target/generated/java</source></sources>
          </configuration>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

Code Explained

Surefire is bound by default; pluginManagement only pins its version
<id> — unique name; lets children override this execution
<phase> — when the goal runs; many goals have a default phase
Check what a goal accepts: help:describe -Dplugin=… -Dgoal=… -Ddetail

Gradle Equivalent

  • <plugin> → plugins { id("…") version "…" }
  • pluginManagement → pluginManagement / apply false
  • An execution → a task wired with dependsOn
  • See Gradle 06

Idiomatic Maven

  • plugins without <version> → versions in pluginManagement
  • maven-antrun-plugin scripts → a purpose-built plugin
  • same execution config in 10 modules → parent pluginManagement

Plugin Elements

ElementPurpose
<version>Pin it for reproducible builds
<configuration>Settings for all executions
<executions>Goal-to-phase bindings
<dependencies>Extra classpath for the plugin itself
<inherited>falseDon't pass to children
<extensions>truePlugin adds packaging / lifecycle

⚠ Common Mistakes

  • Configuring a plugin in pluginManagement only and wondering why it never runs
  • Two executions with no <id> — both become default and merge into one
  • Using <configuration> names from a blog for a different plugin version

✓ Tips & Best Practices

  • Add the enforcer's requirePluginVersions rule to catch unpinned plugins
  • Override a built-in binding by reusing its id (default-jar)
  • Disable an inherited execution with <phase>none</phase>

Quick Summary

  • <plugins> — plugins that run
  • <pluginManagement> — versions and defaults only
  • <execution> — bind goals to phases
  • help:describe — find parameters
