Sheet 19

Multi-Module Projects

<modules> · aggregator vs parent · packaging pom · reactor build order · -pl :app -am / -amd · -rf resume · CI-friendly ${revision}

One Build, Many Modules

A multi-module project has a root POM with packaging pom that lists child folders in <modules>. Building the root builds every module in one reactor run, in dependency order. The root is usually both the aggregator (lists modules) and the parent (shares config), but the two roles are separate. Modules depend on each other with normal <dependency> entries.

Notes

  • Use ${project.version} for sibling dependencies
  • CI-friendly ${revision} sets one version for all modules
  • Maven 3 needs flatten-maven-plugin to publish ${revision} POMs

Under the Hood

  • The reactor sorts modules by their dependency graph, not by <modules> order
  • -am adds the upstream modules you depend on; -amd the downstream ones
  • In-build module output wins over older copies in ~/.m2

Root POM + Module

<!-- root pom.xml -->
<groupId>com.acme</groupId>
<artifactId>billing</artifactId>
<version>${revision}</version>
<packaging>pom</packaging>
<properties><revision>2.4.0-SNAPSHOT</revision></properties>
<modules>
  <module>core</module>
  <module>api</module>
  <module>app</module>
</modules>

<!-- app/pom.xml -->
<parent>
  <groupId>com.acme</groupId><artifactId>billing</artifactId>
  <version>${revision}</version>
</parent>
<artifactId>app</artifactId>
<dependencies>
  <dependency><groupId>com.acme</groupId><artifactId>core</artifactId>
    <version>${project.version}</version></dependency>
</dependencies>

mvn verify                     # whole reactor
mvn verify -pl app -am         # app + what it needs
mvn verify -pl core -amd       # core + everything using it
mvn verify -rf :api            # resume after a failure

Code Explained

packaging pom — the root builds no JAR
${revision} — change the version in one place
-pl app — select by folder or :artifactId
-rf :api — skip modules that already passed

Gradle Equivalent

  • <modules> → include("core", "api", "app")
  • Sibling dependency → implementation(project(":core"))
  • -pl app -am → ./gradlew :app:build
  • See Gradle 17

Idiomatic Maven

  • mvn install so siblings can see each other → mvn verify from the root
  • hard-coded sibling versions → ${project.version}
  • versions:set on every release → CI-friendly -Drevision=2.4.0

Reactor Flags

FlagEffect
-pl a,bOnly these modules
-pl !cAll except c
-amAlso make upstream deps
-amdAlso make downstream dependents
-rf :xResume from module x
-T 1CBuild independent modules in parallel

Aggregator vs Parent

RoleMeans
AggregatorLists <modules>, builds them together
ParentChildren inherit its config
BothThe usual root POM
Maven 4<subprojects> replaces <modules>

⚠ Common Mistakes

  • Running mvn test inside one module folder — siblings resolve from stale ~/.m2 copies
  • A dependency cycle between modules — "The projects in the reactor contain a cyclic reference"
  • Deploying ${revision} POMs without flattening in Maven 3 — consumers can't resolve them

✓ Tips & Best Practices

  • Run one module's tests from the root: mvn test -pl app -am
  • Use flatten-maven-plugin with flattenMode=resolveCiFriendliesOnly
  • Keep a -bom module listing every module for consumers

Quick Summary

  • <modules> — build children together
  • Reactor — orders modules by dependencies
  • -pl / -am / -amd — build a slice
  • ${revision} — one version for all
