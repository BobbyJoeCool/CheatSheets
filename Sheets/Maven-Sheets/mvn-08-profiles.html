Sheet 08

Build Profiles

<profiles> · <activation> (jdk, os, property, file) · activeByDefault · -P id / -P !id · help:active-profiles · profiles in settings.xml

Conditional Configuration

A profile is a named block of POM settings that applies only when activated: on the command line with -P, or automatically through an <activation> condition (JDK version, OS, a property, or a file). Profiles can change properties, dependencies, plugins and modules. Use them for real environmental differences (OS, JDK, CI), not as a way to build different apps from one POM.

Notes

  • Profiles can live in the POM or in settings.xml
  • activeByDefault turns off as soon as another profile in that POM is activated
  • Several conditions in one <activation> must all match (Maven 3.2.2+)

Profiles with Activation

<profiles>
  <profile>
    <id>ci</id>
    <activation>
      <property><name>env.CI</name></property>   <!-- CI sets CI=true -->
    </activation>
    <properties><skipITs>false</skipITs></properties>
  </profile>

  <profile>
    <id>windows</id>
    <activation><os><family>windows</family></os></activation>
    <properties><script.ext>.cmd</script.ext></properties>
  </profile>

  <profile>
    <id>jdk25</id>
    <activation><jdk>[25,)</jdk></activation>
  </profile>

  <profile>
    <id>native</id>                 <!-- only with -Pnative -->
    <build><plugins>…</plugins></build>
  </profile>
</profiles>
<!-- mvn verify -Pnative,!ci   ·   mvn help:active-profiles -->

Code Explained

<property><name>env.CI — active when the env var exists
<os><family> — windows, mac, unix
[25,) — version range: JDK 25 or newer
-P native,!ci — turn one on, one off

Gradle Equivalent

  • No profiles: use if (providers.gradleProperty("ci").isPresent)
  • -Pnative → -Pnative=true read as a property
  • OS / JDK checks → plain Kotlin conditions in the build script
  • See Gradle 08

Idiomatic Maven

  • dev / prod profiles building different JARs → one artifact + runtime config
  • activeByDefault → put the default config outside any profile
  • secrets in a POM profile → a settings.xml profile or env vars

Activation Conditions

ElementActive when
<jdk>21</jdk>JDK version starts with 21
<jdk>[17,21)</jdk>Range: 17 up to, not incl., 21
<os>…</os>family, name, arch, version
<property> nameProperty is set
<property> name + valueProperty equals value (!value negates)
<file><exists>File exists / <missing>

Commands

CommandShows / does
-P a,bActivate a and b
-P !a (or -P -a)Deactivate a
help:active-profilesWhich profiles are on
help:all-profilesEvery profile available

⚠ Common Mistakes

  • Relying on activeByDefault — it silently switches off when you add -Pother
  • Typing -P!ci in bash — ! triggers history expansion; quote it: -P '!ci'
  • Profiles that change dependencies of a published library — consumers never see them

✓ Tips & Best Practices

  • Keep profiles few and named for the condition (ci, windows), not the person
  • Check activation before debugging anything else: mvn help:active-profiles
  • Use a settings.xml profile for per-machine repositories or credentials

Quick Summary

  • <profile> — conditional POM settings
  • <activation> — jdk, os, property, file
  • -P id / !id — on / off manually
  • help:active-profiles — check what's on
