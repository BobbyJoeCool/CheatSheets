Build Lifecycles & Phases

clean / default / site · validate → compile → test → package → verify → install → deploy · bindings by packaging · install vs verify

Three Lifecycles, Many Phases

Maven has three built-in lifecycles: clean wipes target/, default builds and ships, and site generates documentation. Each is an ordered list of phases. Asking for a phase runs every phase before it in the same lifecycle. Phases do nothing on their own: the project's packaging binds plugin goals to them, and you can bind more.

Notes

  • The main phases: validate · compile · test · package · verify · install · deploy
  • verify = package + integration tests + checks
  • Show what runs: mvn help:describe -Dcmd=verify

Under the Hood

  • packaging decides the default bindings (jar vs pom vs war)
  • Phases are just names; goals do the work, so an empty phase is a no-op
  • clean is its own lifecycle: mvn verify never cleans

What Each Command Runs

mvn clean           # pre-clean → clean
mvn compile         # validate → initialize → generate-sources
                    # → process-sources → generate-resources
                    # → process-resources → compile
mvn test            # … → process-classes → test-compile → test
mvn package         # … → prepare-package → package
mvn verify          # … → pre-integration-test → integration-test
                    # → post-integration-test → verify
mvn install         # … → install   (copy to ~/.m2)
mvn deploy          # … → deploy    (upload to remote repo)

mvn clean verify    # two lifecycles, left to right

# see the plan for a phase
mvn help:describe -Dcmd=package
# 'package' is a phase corresponding to this plugin:
# org.apache.maven.plugins:maven-jar-plugin:3.4.1:jar

Code Explained

generate-sources — where code generators (OpenAPI, jOOQ) bind
process-resources — copies and filters src/main/resources
pre/post-integration-test — start / stop a server or container
Exact plugin versions depend on your Maven version

Gradle Equivalent

  • Phases → lifecycle tasks: assemble, check, build
  • mvn install → publishToMavenLocal
  • Binding a goal to a phase → dependsOn / finalizedBy
  • See Gradle 01 · Gradle 07

Idiomatic Maven

  • mvn clean install in CI → mvn verify (deploy when releasing)
  • mvn clean before every build → only when output is stale or renamed
  • mvn package to run integration tests → mvn verify

⚠ Common Mistakes

  • Expecting mvn deploy to skip tests — it runs every earlier phase, tests included
  • Running mvn install just to compile — slower and fills ~/.m2 with SNAPSHOTs
  • Binding work to integration-test and calling mvn integration-test — post-integration-test cleanup never runs; call verify

✓ Tips & Best Practices

  • Use mvn validate as a fast "is the POM OK" check
  • Get a list of every phase with mvn help:describe -Dcmd=deploy
  • Learn the seven main phases; the in-between ones matter only when binding plugins

Quick Summary

  • clean / default / site — three lifecycles
  • Phase — runs all earlier phases
  • Packaging — decides default goal bindings
  • verify — the CI phase
