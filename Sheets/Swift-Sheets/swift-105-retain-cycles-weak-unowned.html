Retain Cycles, weak & unowned

retain cycles · weak · unowned · [weak self] · Memory Graph Debugger · Instruments Leaks

Breaking Reference Cycles

If two objects hold strong references to each other, neither count reaches zero and both leak. Break the cycle by making one side weak (becomes nil when the target is freed; must be an optional var) or unowned (no nil, crashes if used after the target is freed). Closures stored by self are the most common cycle source.

Notes

  • Parent → child strong; child → parent weak
  • Delegates are almost always weak var delegate
  • Use unowned only when the target always outlives the reference
  • Timers and NotificationCenter blocks retain their closures

weak, unowned, Closures

final class Owner {
    var pet: Pet?
    deinit { print("owner freed") }
}
final class Pet {
    weak var owner: Owner?               // weak breaks the cycle
    deinit { print("pet freed") }
}
var o: Owner? = Owner()
o!.pet = Pet(); o!.pet!.owner = o
o = nil                                  // owner freed, pet freed

protocol PlayerDelegate: AnyObject { func didFinish() }
final class Player { weak var delegate: PlayerDelegate? }

final class Customer {
    let card: CreditCard
    init() { card = CreditCard(); card.holder = self }
}
final class CreditCard { unowned var holder: Customer! }   // never outlives

final class ViewModel {
    var onUpdate: (() -> Void)?
    func bind() { onUpdate = { [weak self] in self?.refresh() } }
    func refresh() {}
}

Code Explained

weak var owner — optional, auto-nil
protocol …: AnyObject — needed for weak delegates
unowned — non-optional, must outlive
[weak self] — closure doesn't retain self

The Swifty Way

  • ✗ var delegate: MyDelegate? (strong)
    ✓ weak var delegate: MyDelegate? — delegates usually own you

Coming From…

  • Java GC handles cycles; no weak needed in most code
  • Kotlin Same as Java on JVM
  • Python weakref ≈ weak; cycles are collected eventually there

⚠ Common Mistakes

  • Strong delegate properties: classic view-controller leak
  • unowned self in a network callback that can outlive the object: crash
  • Timers retain their target, so deinit never runs to stop them: invalidate when the screen closes

✓ Tips & Best Practices

  • Make delegate protocols AnyObject-constrained so they can be weak
  • Use the Memory Graph button in Xcode's debug bar after closing a screen
  • Prefer [weak self] + guard let self over unowned

Quick Summary

  • strong ↔ strong = leak
  • weak (optional) / unowned (non-optional)
  • [weak self] in stored closures
