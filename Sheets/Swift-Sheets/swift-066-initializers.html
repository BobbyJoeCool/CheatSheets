Initializers

init · designated · convenience · init? · required · two-phase initialization

Initialization

An initializer must give every stored property a value before the instance is used. Structs get a memberwise init; classes need their own. Classes have designated initializers (full setup, calling super.init) and convenience initializers (delegating to another init on the same class). A failable init? returns nil for invalid input.

Notes

  • Two-phase init: set own properties, then call super.init, then customize
  • required init forces every subclass to implement it
  • self.init(...) delegates within the same type
  • Structs can delegate with self.init too (no convenience keyword)

Designated, Convenience, Failable

class Vehicle {
    let wheels: Int
    init(wheels: Int) { self.wheels = wheels }            // designated
    convenience init() { self.init(wheels: 4) }           // delegates
}

final class Bike: Vehicle {
    let hasBell: Bool
    init(hasBell: Bool) {
        self.hasBell = hasBell          // 1. own properties first
        super.init(wheels: 2)           // 2. then super
        print("bike ready")             // 3. now self is usable
    }
}

struct Email {
    let value: String
    init?(_ raw: String) {                                // failable
        guard raw.contains("@") else { return nil }
        value = raw.lowercased()
    }
}
Email("ada@example.com")?.value         // "ada@example.com"
Email("nope")                           // nil

Initializer Types

Code Explained

designated init — sets all properties
convenience init — must call self.init
two-phase — own props, super.init, then use self
init? — returns nil on bad input

The Swifty Way

  • ✗ a validate() call after init
    ✓ init? or init(…) throws — invalid instances never exist

Coming From…

  • Kotlin Primary/secondary constructors ≈ designated/convenience
  • Java Constructor chaining this(...) ≈ self.init
  • Python __init__ with super().__init__() (order reversed)

⚠ Common Mistakes

  • Calling a method on self before every property is set: compile error
  • Calling super.init before setting the subclass's own properties
  • Using init? and losing the reason for failure: use throws when callers need it

✓ Tips & Best Practices

  • Prefer default property values over long init parameter lists
  • Put extra struct inits in an extension to keep the memberwise one
  • Use throws inits for parsing where errors explain what failed

Quick Summary

  • every stored property set before use
  • designated vs convenience
  • init? / init() throws — can fail
