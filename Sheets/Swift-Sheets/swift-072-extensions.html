Extending Types

An extension adds computed properties, methods, initializers, nested types, subscripts and protocol conformances to an existing type, even ones you don't own like String or Int. Extensions can't add stored properties. They're also used to organize your own types: one extension per protocol conformance.

Notes

  • Extensions can't add stored properties or override existing methods
  • Inits added in an extension keep a struct's memberwise init
  • private members in the type are visible in same-file extensions
  • Extending other modules' types with their protocols needs @retroactive

Extensions

extension Int {
    var isEven: Bool { isMultiple(of: 2) }
    func times(_ body: () -> Void) { for _ in 0..<self { body() } }
}
4.isEven                                    // true
3.times { print("hi") }                     // hi hi hi

extension String {
    var trimmed: String { trimmingCharacters(in: .whitespacesAndNewlines) }
}
"  hey \n".trimmed                          // "hey"

struct Player { var name: String; var score: Int }

// MARK: - CustomStringConvertible
extension Player: CustomStringConvertible {
    var description: String { "\(name) (\(score))" }
}

extension Player {
    enum Rank { case rookie, pro }          // nested type
    var rank: Rank { score > 100 ? .pro : .rookie }
}

Coming From…

  • Kotlin Extension functions ≈ extensions (but can add conformance here)
  • C# Extension methods ≈ extensions
  • TypeScript Declaration merging/prototype hacks; extensions are safe

⚠ Common Mistakes

  • Trying to add var cache: [Int] = [] in an extension: stored property
  • Polluting String with dozens of app-specific helpers
  • Name clashes when two modules extend the same type with the same method

✓ Tips & Best Practices

  • Keep extensions on stdlib types internal or private
  • Organize big types: main declaration + one extension per protocol
  • Use constrained extensions: extension Array where Element == User
