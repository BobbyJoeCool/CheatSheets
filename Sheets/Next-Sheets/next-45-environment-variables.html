Sheet 45

Environment Variables

.env · .env.local · .env.production · NEXT_PUBLIC_ · load order · build-time inlining

Config Through the Environment

Next.js loads .env* files into process.env automatically. Variables are server-only by default. Prefixing a name with NEXT_PUBLIC_ makes it available in the browser by inlining its value at build time, which means changing it later requires a rebuild. Runtime-config options were removed in 16; use env vars.

Rules

  • .env.local is for secrets; keep it out of git
  • .env.local is ignored when NODE_ENV=test
  • Variables already set in the shell win over files
  • Reference vars by full name: no dynamic lookups

Defining and Reading Variables

# .env                      (committed defaults)
NEXT_PUBLIC_SITE_URL=https://acme.com
API_BASE=https://api.acme.com
# .env.local                (secrets, not committed)
DATABASE_URL=postgres://user:pass@localhost:5432/acme
STRIPE_SECRET_KEY=sk_test_123
# Expansion
API_USERS=${API_BASE}/users

// server code
const db = new Pool({ connectionString: process.env.DATABASE_URL })
// client code — replaced at build with the literal string
const url = process.env.NEXT_PUBLIC_SITE_URL       // 'https://acme.com'
const bad = process.env['NEXT_PUBLIC_' + name]      // ✖ undefined

Notes

${VAR} — expand another variable
Only literal process.env.NEXT_PUBLIC_X is inlined
Server code reads values at runtime (e.g. next start)
@next/env loadEnvConfig() loads them in scripts and tests
experimental.typedEnv generates types for env vars

Load Order (first wins)

#Source
1process.env (shell / platform)
2.env.$(NODE_ENV).local
3.env.local (not in test)
4.env.$(NODE_ENV)
5.env

Which File?

FileCommit?Use
.env✔Shared defaults
.env.development✔next dev defaults
.env.production✔next build/start defaults
.env.local✖Local secrets
.env.test✔Test runs

⚠ Common Mistakes

  • Changing a NEXT_PUBLIC_ value on the host and expecting the client to update without a rebuild
  • Committing .env.local; add .env*.local to .gitignore
  • Reading process.env.SECRET in a Client Component; it's undefined there

✓ Tips & Best Practices

  • Validate env vars at startup with Zod (or @t3-oss/env-nextjs) so bad deploys fail fast
  • For one image across environments, read config on the server at runtime and pass it down
  • Commit a .env.example listing every required variable

Quick Summary

  • .env* — loaded automatically
  • NEXT_PUBLIC_ — inlined into client at build
  • .env.local — secrets, not committed
  • Shell env — overrides every file
