Sheet 11

Inserting Documents

insertOne · insertMany · ordered · generated _id · write result · duplicate key error

Adding Documents

insertOne adds one document and insertMany adds an array of them in batches. If a document has no _id, the driver generates an ObjectId before sending it. A duplicate _id or unique-index value fails with error E11000. With ordered: true (the default) insertMany stops at the first error; with ordered: false it skips failures and inserts the rest. The write concern says how many replicas must confirm the write before the call returns.

Notes

  • insert() is deprecated; use insertOne / insertMany
  • Default write concern is w: "majority"
  • Schema validation runs on insert (sheet 26)

insertOne, insertMany & Errors

db.products.insertOne({ name: "Mechanical Keyboard", category: "Electronics",
  price: NumberDecimal("89.00"), stock: 25 })
// { acknowledged: true, insertedId: ObjectId("…") }

db.products.insertMany([
  { _id: 21, name: "Desk Mat", price: NumberDecimal("24.50"), stock: 40 },
  { _id: 22, name: "Monitor Arm", price: NumberDecimal("79.00"), stock: 12 }
])
// { acknowledged: true, insertedIds: { '0': 21, '1': 22 } }

// duplicate _id → E11000; ordered: false keeps going
db.products.insertMany(
  [ { _id: 22, name: "Duplicate" }, { _id: 23, name: "Desk Lamp" } ],
  { ordered: false })
// MongoBulkWriteError: E11000 duplicate key error … insertedCount: 1

// stronger durability for an important write
db.orders.insertOne(
  { _id: 1002, customerId: 42, status: "pending", items: [] },
  { writeConcern: { w: "majority", j: true, wtimeout: 5000 } })

Code Explained

insertedId is the generated or supplied _id
With ordered: false the "Desk Lamp" document is inserted even though the first one failed
j: true waits for the on-disk journal; wtimeout fails the call if replicas don't confirm in time
A failed write-concern wait doesn't undo the write; it may still be applied

SQL Equivalent

  • insertOne ↔ INSERT INTO products (…) VALUES (…) RETURNING product_id
  • insertMany ↔ multi-row VALUES; E11000 ↔ unique violation (23505) · See SQL 50

Across Engines

  • Redis SET and HSET create or overwrite; SET … NX inserts only if missing
  • DynamoDB PutItem overwrites; add attribute_not_exists(PK) for insert-only
  • Cassandra INSERT is an upsert; IF NOT EXISTS for insert-only (lightweight transaction)
  • Neo4j CREATE always adds; MERGE avoids duplicates

In Your Code

  • Node const { insertedId } = await products.insertOne(doc)
  • Python products.insert_one(doc).inserted_id
  • Java products.insertOne(doc).getInsertedId()

Write Concern

SettingMeaning
w: 1Primary confirmed
w: "majority"Most members confirmed (default)
w: 0Fire and forget
j: trueWritten to the journal
wtimeout: msGive up waiting after ms

⚠ Common Mistakes

  • Assuming ordered: false inserts in a predictable order
  • Parsing error message strings instead of checking error code 11000
  • Using w: 0 for data you can't lose

✓ Tips & Best Practices

  • Supply your own _id when you need idempotent retries
  • Batch inserts with insertMany instead of loops
  • Catch duplicate-key errors by code (err.code === 11000)

Quick Summary

  • insertOne / insertMany
  • _id generated if missing
  • E11000 — duplicate key
  • ordered: false — keep going
