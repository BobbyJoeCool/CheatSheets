Polyglot Persistence

SQL + cache · SQL + search · CQRS read models · outbox / CDC · dual-write pitfalls · consistency between stores

More Than One Store

Polyglot persistence means using different stores for different jobs: SQL or MongoDB as the source of truth, Redis as a cache, a search engine for text, a graph for recommendations. The hard part is keeping copies in step. Writing to two stores in one request (dual write) drifts when one write fails. Instead, record changes once and propagate them: the outbox pattern or change data capture (CDC) feeds events to consumers that update read models (CQRS).

Notes

  • Copies are eventually consistent by design
  • Consumers must be idempotent: events can repeat
  • Debezium reads change logs from PostgreSQL, MySQL, MongoDB and more
  • Each extra store adds operations work

Production Check

  • Dual writes leave stores out of sync when the second write fails; use an outbox or CDC
  • Name one source of truth for each piece of data; every other store is a rebuildable copy
  • Plan for rebuilds: you should be able to reindex search or refill a cache from the source

Outbox, Relay & Consumers

// 1. change + event in ONE database transaction (outbox)
await sql.begin(async tx => {
  await tx`UPDATE products SET price = ${price} WHERE product_id = ${id}`
  await tx`INSERT INTO outbox (aggregate, aggregate_id, type, payload)
           VALUES ('product', ${id}, 'PriceChanged',
                   ${JSON.stringify({ id, price })})`
})

// 2. relay (or Debezium CDC) publishes outbox rows, then marks them sent
const batch = await sql`SELECT * FROM outbox WHERE sent_at IS NULL ORDER BY id LIMIT 100`
for (const evt of batch) {
  await producer.send({ topic: "product-events",
    messages: [ { key: String(evt.aggregate_id), value: evt.payload } ] })
  await sql`UPDATE outbox SET sent_at = now() WHERE id = ${evt.id}`
}

// 3. consumers update their own stores (safe to run twice)
on("PriceChanged", async ({ id, price }) => {
  await redis.del(`product:${id}`)                                    // cache
  await es.update({ index: "products", id: String(id), doc: { price } })  // search
  await mongo.collection("productViews")
    .updateOne({ _id: id }, { $set: { price } }, { upsert: true })   // read model
})

Code Explained

The price change and its event commit together, or neither does
If the relay crashes after sending but before marking, the event is sent again; consumers must tolerate that
Keying messages by product id keeps one product's events in order
Each consumer owns its store and can be rebuilt by replaying events

SQL Equivalent

  • The outbox is an ordinary SQL table written in the same transaction
  • CDC reads PostgreSQL's write-ahead log through logical decoding · See SQL 68, 67

Across Engines

  • MongoDB a source of truth or a read model; change streams act as CDC
  • Redis cache and session store in front of the source of truth
  • DynamoDB often the source of truth; Streams feed other stores
  • Cassandra high-volume events or time series beside a SQL core
  • Neo4j recommendation and relationship queries on a copy synced from SQL

In Your Code

  • Node postgres.js + kafkajs + node-redis, or a CDC connector instead of a relay

⚠ Common Mistakes

  • Writing to the database and the cache / search index in the same request
  • No way to rebuild a copy from the source
  • Consumers that break when an event arrives twice

✓ Tips & Best Practices

  • Add stores only for a measured need
  • Make every consumer idempotent with upserts and version checks
  • Monitor lag between the source and each copy

Quick Summary

  • Different stores, different jobs
  • One source of truth
  • Outbox or CDC, never dual writes
  • Idempotent consumers
