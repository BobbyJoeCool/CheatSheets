Sheet 02

SQL vs NoSQL: When to Use Which

access patterns · joins vs embedding · scale-out · schema flexibility · transactions · decision table

Pick by Access Pattern, Not Hype

SQL databases shine when data is relational, questions are unpredictable and integrity matters: joins, constraints and multi-row transactions come built in. NoSQL engines shine when the access patterns are known and narrow, the data is naturally nested or connected, or the load has to spread across many machines. NoSQL reads are fast because the data was arranged ahead of time for that exact question. Many real systems use both (sheet 58).

Notes

  • MongoDB, DynamoDB and Neo4j all support ACID transactions now
  • Most "scale problems" are missing indexes or bad schemas first
  • Team skills and operations cost matter as much as features

Same Question, Three Designs

// Question: a customer's 10 newest orders with line counts

// SQL: two tables, joined and grouped at read time
SELECT o.order_id, o.order_date, o.total, COUNT(*) AS lines
FROM orders o JOIN order_items i USING (order_id)
WHERE o.customer_id = 42
GROUP BY o.order_id
ORDER BY o.order_date DESC LIMIT 10;

// MongoDB: items embedded, one indexed read, no join
db.orders.find({ customerId: 42 },
               { orderDate: 1, total: 1, lines: { $size: "$items" } })
  .sort({ orderDate: -1 }).limit(10)

// DynamoDB: one Query on the customer's partition
aws dynamodb query --table-name Shop \
  --key-condition-expression "PK = :c AND begins_with(SK, :o)" \
  --expression-attribute-values \
    '{":c":{"S":"CUSTOMER#42"},":o":{"S":"ORDER#"}}' \
  --no-scan-index-forward --limit 10

Code Explained

SQL builds the answer's shape at read time from normalized tables
MongoDB stores the shape: the line items are already inside the order
The DynamoDB sort key ORDER#<date>#<id> sorts by date; --no-scan-index-forward returns newest first
A new question (say, "orders containing product 7") is easy in SQL and may need a new index or table in NoSQL

SQL Equivalent

  • What SQL keeps that NoSQL often drops: ad hoc joins, FOREIGN KEY and CHECK constraints, multi-table transactions
  • Normalization removes duplication; NoSQL designs duplicate on purpose · See SQL 61, 62

Across Engines

  • MongoDB nested records that vary per item, with rich queries: catalogs, content, profiles
  • Redis caching, sessions, counters, leaderboards, rate limits, queues
  • DynamoDB serverless AWS apps with known key-based access at any scale
  • Cassandra huge write volumes across regions: events, IoT, messaging
  • Neo4j questions about connections: recommendations, fraud, permissions

In Your Code

  • Node SQL: Prisma or pg · NoSQL: Mongoose or the mongodb driver
  • Python SQL: SQLAlchemy · NoSQL: PyMongo or Beanie
  • Java Spring Data JPA and Spring Data MongoDB share the same Repository style

Decision Table

If you need…Lean toward
Ad hoc reporting and joinsSQL
Integrity rules across tablesSQL
Nested records that varyDocument
Key lookups at very high ratesKey-value
Massive writes, many regionsWide-column
Relationship-heavy queriesGraph
Full-text relevanceSearch engine

Myths

MythReality
"NoSQL has no schema"The schema lives in your code
"NoSQL has no transactions"MongoDB, DynamoDB, Neo4j have ACID transactions
"SQL can't scale"Replicas, partitioning and Citus scale far
"NoSQL is faster"Only for the access patterns it was modeled for

⚠ Common Mistakes

  • Switching to NoSQL and then needing joins everywhere
  • Modeling NoSQL data as normalized tables
  • Forgetting that reporting and analytics will still want SQL

✓ Tips & Best Practices

  • Write down the top five queries before choosing
  • Prototype the hardest query in both
  • A common mix: SQL as source of truth, Redis as cache

Quick Summary

  • SQL — joins, constraints, ad hoc
  • NoSQL — known access patterns
  • Duplicate on purpose in NoSQL
  • Mixing both is normal
