Sheet 49

CQL: Keyspaces & Tables

CREATE KEYSPACE · partition key · clustering columns · PRIMARY KEY ((a), b) · data types · collections

Keys Decide Everything

CQL looks like SQL, but the primary key controls storage. In PRIMARY KEY ((a, b), c, d), the inner parentheses are the partition key (which node, and the unit of a fast read) and the rest are clustering columns (sort order inside the partition). Columns are typed, and collections (list, set, map) and user-defined types hold small nested data. A keyspace sets the replication strategy and factor.

Notes

  • frozen<> stores a collection or UDT as one value
  • Adding columns is cheap; changing the primary key means a new table
  • timeuuid gives unique, time-ordered ids
  • Every write is an upsert

Production Check

  • QUORUM needs a majority of replicas: with RF 3, two must answer; with RF 1, any down node fails the query
  • In multi-datacenter clusters use LOCAL_QUORUM so requests don't wait on the far region
  • Choose partition keys that spread data and keep each partition under about 100 MB

Keyspace, Types & Tables

CREATE KEYSPACE IF NOT EXISTS shop
  WITH replication = { 'class': 'NetworkTopologyStrategy', 'dc1': 3, 'dc2': 3 };

CREATE TYPE IF NOT EXISTS shop.line_item (
  product_id int, name text, qty int, unit_price decimal);

CREATE TABLE IF NOT EXISTS shop.orders (
  order_id    int,
  customer_id int,
  order_date  date,
  status      text,
  total       decimal,
  items       list<frozen<line_item>>,
  tags        set<text>,
  attrs       map<text, text>,
  created_at  timestamp,
  PRIMARY KEY (order_id)                          -- partition key only
);

CREATE TABLE IF NOT EXISTS shop.orders_by_customer (
  customer_id int, order_date date, order_id int,
  status text, total decimal,
  PRIMARY KEY ((customer_id), order_date, order_id)
) WITH CLUSTERING ORDER BY (order_date DESC, order_id ASC);

-- composite partition key: one partition per product per month
CREATE TABLE IF NOT EXISTS shop.events_by_product (
  product_id int, month text, ts timeuuid, type text,
  PRIMARY KEY ((product_id, month), ts));

ALTER TABLE shop.orders ADD coupon text;
DESCRIBE TABLE shop.orders;

Code Explained

dc1: 3, dc2: 3 keeps three copies in each of two datacenters
The order lines become a list of a user-defined type inside the order row
orders_by_customer sorts each customer's orders by date, newest first
Adding month to the partition key stops one product's events growing into one giant partition

SQL Equivalent

  • PRIMARY KEY ((a), b) ↔ PRIMARY KEY (a, b), except a picks the server and b sorts rows inside it
  • UDT ↔ a composite type · collections ↔ arrays or child tables · See SQL 55, 56

Across Engines

  • MongoDB no table DDL; collections take any document
  • Redis no DDL; keys appear when written
  • DynamoDB only the key schema is declared: partition = HASH, sort = RANGE
  • Neo4j no table DDL; only constraints and indexes

In Your Code

⚠ Common Mistakes

  • A partition key with few values (status), creating huge, hot partitions
  • Large collections; they're read whole
  • Expecting to change a table's primary key with ALTER

✓ Tips & Best Practices

  • Name tables after their query: orders_by_customer
  • Bucket time series by day or month in the partition key
  • Use prepared statements for every repeated query

Quick Summary
