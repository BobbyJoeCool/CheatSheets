Query-First Modeling

one table per query · denormalized tables · WHERE rules · bucketing · materialized views · SAI indexes

One Table per Query

Cassandra modeling starts from the queries and builds one table for each, keyed so the query reads a single partition in order. The same data is written to several tables (denormalized), often together in a logged batch. WHERE must give the whole partition key (with = or IN) and may restrict clustering columns in order. SAI indexes (5.0) allow filtering on other columns within the rules, so fewer extra tables are needed.

Notes

  • Logged batches guarantee all statements apply eventually, without isolation
  • Don't use batches to speed up bulk loads
  • Materialized views are experimental; prefer your own tables
  • Query a range only on the last restricted clustering column

Two Queries, Two Tables

-- Q1: a customer's orders, newest first → partition by customer
CREATE TABLE orders_by_customer (
  customer_id int, order_date date, order_id int, status text, total decimal,
  PRIMARY KEY ((customer_id), order_date, order_id)
) WITH CLUSTERING ORDER BY (order_date DESC, order_id DESC);

-- Q2: orders by status for one day → another table, same data
CREATE TABLE orders_by_status_day (
  status text, day date, order_id int, customer_id int, total decimal,
  PRIMARY KEY ((status, day), order_id));

-- write both copies together
BEGIN BATCH
  INSERT INTO orders_by_customer (customer_id, order_date, order_id, status, total)
    VALUES (42, '2026-11-01', 1001, 'pending', 49.97);
  INSERT INTO orders_by_status_day (status, day, order_id, customer_id, total)
    VALUES ('pending', '2026-11-01', 1001, 42, 49.97);
APPLY BATCH;

-- allowed: full partition key, then clustering columns in order
SELECT * FROM orders_by_customer
 WHERE customer_id = 42 AND order_date >= '2026-10-01';
-- rejected: no partition key
SELECT * FROM orders_by_customer WHERE order_date = '2026-11-01';

-- SAI (5.0): filter a non-key column without a new table
CREATE INDEX orders_status_sai ON orders_by_customer (status) USING 'sai';
SELECT * FROM orders_by_customer WHERE customer_id = 42 AND status = 'pending';

Code Explained

Each table answers exactly one question with one partition read
(status, day) in the partition key bounds each partition to one day of one status
The rejected query would have to ask every node; Cassandra refuses unless you add ALLOW FILTERING
SAI combined with the partition key stays a single-partition read

SQL Equivalent

  • One table per query ↔ denormalized reporting tables kept in sync by the app
  • Logged batch ↔ a transaction without isolation or rollback · See SQL 61, 74

Across Engines

  • MongoDB usually one collection plus several indexes covers many queries
  • Redis one key per lookup: the same query-first mindset
  • DynamoDB GSIs do what the extra tables do here
  • Neo4j one graph answers many questions; model the traversals

In Your Code

  • Node await client.execute("SELECT * FROM orders_by_customer WHERE customer_id = ?", [42], { prepare: true })
  • Python cqlengine: class OrderByCustomer(Model): customer_id = columns.Integer(partition_key=True)
  • Java Spring Data Cassandra: @PrimaryKeyColumn(name = "customer_id", type = PrimaryKeyType.PARTITIONED)

WHERE Rules

RestrictionAllowed?
All partition key columns with = / INYes
Clustering columns, left to rightYes
Range on the last restricted clustering columnYes
Skip a clustering columnNo (SAI may help)
Non-key columnOnly with SAI or ALLOW FILTERING

⚠ Common Mistakes

  • Modeling from an ER diagram and then fighting WHERE rules
  • Unlogged batches across many partitions to "speed up" writes
  • Partitions that grow forever (all events for one product)

✓ Tips & Best Practices

  • Write the query first, then the table
  • Use logged batches only to keep denormalized copies in step
  • Try SAI before adding another table

Quick Summary

  • One table per query
  • Denormalize writes
  • Partition key required in WHERE
  • SAI for extra filters
