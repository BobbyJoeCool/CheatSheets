Single-Table Design

access-pattern table · composite sort keys · item collections · adjacency list · when not to

One Table, Many Entities

Single-table design stores several entity types in one table, with generic key names (PK, SK) and typed key values (CUSTOMER#42, ORDER#1001). Entities read together share a partition key, so one Query returns a pre-joined item collection. It starts from an access-pattern table: each pattern maps to a key condition on the table or a GSI. It shines for known, high-volume patterns and hurts when questions change often.

Notes

  • Store a type attribute on every item
  • Copy display fields into child items to avoid extra reads
  • GSI overloading: one index, many entity types
  • Adjacency lists model many-to-many

Production Check

  • Hot partitions: one partition key taking most traffic is throttled (about 3,000 reads / 1,000 writes per second); use high-cardinality keys or write sharding
  • With an LSI, each item collection is capped at 10 GB
  • Single-table makes new ad hoc questions hard; if access patterns are still unclear, start with one table per entity

Shop as One Table

// Items in table "Shop" (typed key values, generic names)
{ PK: "CUSTOMER#42", SK: "PROFILE", type: "customer",
  name: "Ada Lovelace", email: "ada@example.com" }
{ PK: "CUSTOMER#42", SK: "ORDER#2026-11-01#1001", type: "order",
  status: "pending", total: 49.97, GSI1PK: "ORDER#1001", GSI1SK: "META" }
{ PK: "ORDER#1001", SK: "ITEM#7", type: "line",
  qty: 2, unitPrice: 19.99, name: "SQL Pocket Guide" }
{ PK: "ORDER#1001", SK: "ITEM#3", type: "line",
  qty: 1, unitPrice: 9.99, name: "USB-C Cable" }
{ PK: "PRODUCT#7", SK: "META", type: "product",
  name: "SQL Pocket Guide", stock: 10,
  GSI1PK: "CATEGORY#Books", GSI1SK: "PRODUCT#7" }

// Access patterns → key conditions
// AP1 profile + recent orders      PK = CUSTOMER#42
// AP2 orders, newest first         PK = CUSTOMER#42 AND begins_with(SK, "ORDER#"), reversed
// AP3 an order's lines             PK = ORDER#1001
// AP4 order header by id           GSI1: GSI1PK = ORDER#1001
// AP5 products in a category       GSI1: GSI1PK = CATEGORY#Books

Code Explained

AP1 returns the profile and all orders in one Query because they share a partition key
Line items copy the product name so an order page needs no product lookups
GSI1 serves two unrelated patterns because its key values are typed
Adding AP6 later may mean a new GSI or a backfill of new key attributes

SQL Equivalent

  • Several entities in one table is the opposite of normalization; an item collection is a stored join
  • Adjacency lists ↔ a junction table for many-to-many · See SQL 61, 62

Across Engines

  • MongoDB one collection per entity, with related data embedded
  • Redis key prefixes play the same role (order:1001:items)
  • Cassandra one table per query rather than one table for everything
  • Neo4j no keys to design; relationships carry the structure

In Your Code

  • Node ElectroDB or DynamoDB Toolbox model several entities on one table
  • Python PynamoDB models, or boto3 with small key-builder functions
  • Java Enhanced Client beans per entity with @DynamoDbPartitionKey / @DynamoDbSortKey on one table

Single Table or Not?

SituationChoose
Patterns known and stableSingle table
High volume, low latencySingle table
Patterns still changingTable per entity
Heavy analytics needsExport to an analytics store
Team new to DynamoDBTable per entity first

⚠ Common Mistakes

  • Starting with the item layout instead of the access-pattern table
  • Generic keys with no type attribute, impossible to debug
  • Putting every customer's orders under one partition key like ORDERS

✓ Tips & Best Practices

  • Keep the access-pattern table next to the code
  • Write helper functions that build keys
  • Use NoSQL Workbench to visualize the table

Quick Summary

  • Entities share one table
  • Typed key values
  • Item collections = stored joins
  • Design from access patterns
