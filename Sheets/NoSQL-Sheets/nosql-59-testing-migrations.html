Sheet 59

Testing & Schema Migration

Testcontainers · DynamoDB Local · in-memory fakes · seed data · schema versioning · lazy vs batch migration

Real Engines in Tests, Gradual Schema Change

Test against the real engine: Testcontainers starts MongoDB, Redis, Cassandra or Neo4j in Docker for a test run, and DynamoDB Local or LocalStack stands in for AWS. Seed known data before each test and clean it after. Schemas still change without ALTER TABLE: lazy migration upgrades documents when they're read, batch migration rewrites them in the background. Tag documents with a schemaVersion so code knows what it's looking at.

Notes

  • In-memory fakes are fast but miss real query behavior
  • Reuse containers across a test run; Cassandra starts slowly
  • Keep migration scripts in version control
  • Code must read both old and new shapes during a migration

Testcontainers & Migrations

// Testcontainers: a real MongoDB for the test run
import { MongoDBContainer } from "@testcontainers/mongodb"
import { MongoClient } from "mongodb"

let mongo, client
beforeAll(async () => {
  mongo = await new MongoDBContainer("mongo:8").start()
  client = new MongoClient(mongo.getConnectionString(), { directConnection: true })
  await client.connect()
  await client.db("shop").collection("products").insertMany(seedProducts)
}, 60_000)
afterAll(async () => { await client.close(); await mongo.stop() })

test("reserves stock atomically", async () => {
  const products = client.db("shop").collection("products")
  const r = await products.updateOne({ _id: 7, stock: { $gte: 2 } },
                                     { $inc: { stock: -2 } })
  expect(r.modifiedCount).toBe(1)
})

// lazy migration: upgrade when read
function upgrade(doc) {
  if ((doc.schemaVersion ?? 1) < 2) {
    const [first, ...rest] = doc.name.split(" ")
    return { ...doc, name: { first, last: rest.join(" ") }, schemaVersion: 2 }
  }
  return doc
}

// batch migration (mongosh): rewrite old documents in place
db.customers.updateMany({ schemaVersion: { $exists: false } }, [
  { $set: { name: { first: { $arrayElemAt: [ { $split: ["$name", " "] }, 0 ] },
                    last:  { $arrayElemAt: [ { $split: ["$name", " "] }, 1 ] } },
            schemaVersion: 2 } } ])

Code Explained

The container is a single-node replica set, so transactions and change streams work in tests
directConnection: true talks to that one node directly
Lazy migration spreads the work but leaves old shapes until each document is read
The batch migration uses an update pipeline so it can read name while rewriting it

SQL Equivalent

  • Migration tools like Flyway and Liquibase ↔ migrate-mongo, Mongock, Neo4j-Migrations
  • ALTER TABLE happens at once; NoSQL migrations are usually gradual · See SQL 59

Across Engines

  • MongoDB Testcontainers or mongodb-memory-server; migrate-mongo / Mongock
  • Redis Testcontainers; FLUSHDB between tests
  • DynamoDB DynamoDB Local or LocalStack; create tables in test setup
  • Cassandra Testcontainers with a reused container; cassandra-migration
  • Neo4j Testcontainers or Neo4j Harness; Neo4j-Migrations

In Your Code

  • Node @testcontainers/mongodb, @testcontainers/redis
  • Python with MongoDbContainer("mongo:8") as m: client = m.get_connection_client()
  • Java @Container static MongoDBContainer mongo = new MongoDBContainer("mongo:8");

Migration Strategies

StrategyHow
LazyUpgrade on read, save on next write
BatchBackground job rewrites documents
Dual-shape codeRead old and new until done
Expand / contractAdd new field, migrate, remove old

⚠ Common Mistakes

  • Mocking the driver and missing real query bugs
  • Tests that depend on leftover data from earlier tests
  • Removing support for the old shape before every document is migrated

✓ Tips & Best Practices

  • Seed each test with only the data it needs
  • Run batch migrations in small, resumable chunks
  • Count documents per schemaVersion to track progress

Quick Summary

  • Testcontainers — real engines
  • Seed and clean per test
  • Lazy or batch migration
  • schemaVersion on documents
