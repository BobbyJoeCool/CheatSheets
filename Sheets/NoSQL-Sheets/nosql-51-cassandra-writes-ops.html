Writes, TTL & Operations

USING TTL · tombstones · lightweight transactions IF · batches · nodetool · compaction

Expiry, Compare-and-Set, Upkeep

Writes can expire with USING TTL (or a table default). Because data is immutable on disk, a delete or expiry writes a tombstone that hides old values until compaction removes it after gc_grace_seconds (10 days). Lightweight transactions (IF NOT EXISTS, IF col = value) use Paxos for compare-and-set within one partition, at higher latency. Counter columns live in their own tables. Keep clusters healthy with regular repair and watch compaction.

Notes

  • Every cell stores a write timestamp; the newest wins
  • LWTs cost about four round trips
  • Counters can't mix with normal columns or use TTL
  • Unified Compaction Strategy arrived in 5.0

Production Check

  • Deletes and expired TTLs write tombstones; reading partitions full of them is slow and fails at 100,000 (tombstone_failure_threshold). Avoid queue-like delete patterns
  • ALLOW FILTERING scans whole partitions or the whole cluster; never ship it on large tables
  • Run repair within gc_grace_seconds (10 days) or deleted data can come back

TTL, LWT, Counters & Deletes

-- TTL per write, read it back, table default
INSERT INTO sessions (id, customer_id) VALUES (uuid(), 42) USING TTL 1800;
UPDATE carts USING TTL 86400 SET items = items + [7] WHERE customer_id = 42;
SELECT TTL(customer_id), WRITETIME(customer_id) FROM sessions WHERE id = ?;
ALTER TABLE sessions WITH default_time_to_live = 1800;

-- lightweight transactions: compare-and-set in one partition
INSERT INTO users_by_email (email, customer_id)
  VALUES ('ada@example.com', 42) IF NOT EXISTS;
UPDATE products SET stock = 8 WHERE product_id = 7 IF stock = 10;
--  [applied] | stock
--      False |     9        ← not applied; shows the current value

-- counters live in their own tables
CREATE TABLE product_views (product_id int PRIMARY KEY, views counter);
UPDATE product_views SET views = views + 1 WHERE product_id = 7;

-- a delete writes a tombstone
DELETE FROM orders_by_customer
 WHERE customer_id = 42 AND order_date = '2026-11-01' AND order_id = 1001;

-- whole partitions delete cheaply (one tombstone)
DELETE FROM orders_by_customer WHERE customer_id = 42;

Code Explained

TTL() shows seconds left; WRITETIME() shows the write's microsecond timestamp
IF NOT EXISTS makes email unique without a read-then-write race
A failed LWT returns [applied] = False and the current values
Deleting a whole partition writes one tombstone instead of one per row

SQL Equivalent

  • IF NOT EXISTS ↔ INSERT … ON CONFLICT DO NOTHING · IF stock = 10 ↔ optimistic UPDATE … WHERE stock = 10
  • Counter ↔ UPDATE … SET n = n + 1; TTL has no SQL equivalent · See SQL 53, 70

Across Engines

  • MongoDB TTL indexes; conditional updates through filters
  • Redis EXPIRE; SET NX; INCR
  • DynamoDB TTL attribute; condition expressions; atomic ADD
  • Neo4j no TTL; MERGE + uniqueness constraints for insert-if-absent

In Your Code

⚠ Common Mistakes

  • Using a table as a queue (insert, read, delete) and drowning in tombstones
  • LWTs on hot paths where plain writes would do
  • Skipping repairs for weeks

✓ Tips & Best Practices

  • Use TWCS for TTL-heavy time series
  • Delete whole partitions rather than many rows
  • Schedule repairs with Cassandra Reaper or your platform's tool

Quick Summary

  • USING TTL — expiry
  • Tombstones — deletes cost reads
  • IF — compare-and-set (LWT)
  • Repair within 10 days
