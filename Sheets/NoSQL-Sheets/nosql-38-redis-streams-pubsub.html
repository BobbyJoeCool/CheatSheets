Streams & Pub/Sub

XADD · XREAD · consumer groups · XACK · PUBLISH / SUBSCRIBE · streams vs pub/sub

Logs and Broadcasts

A stream is an append-only log: each entry gets an ID (<ms>-<seq>) and a set of fields. Readers can replay from any ID, block for new entries, and form consumer groups where each entry goes to one consumer and must be acknowledged. Pub/Sub is different: a message goes to everyone subscribed right now and is gone, with no history and no acknowledgement. Use streams for work and events you can't lose, Pub/Sub for live notifications.

Notes

  • * lets Redis generate the entry ID
  • $ means "only new entries"; > means "never delivered to this group"
  • Cap stream length with MAXLEN ~ n
  • Sharded Pub/Sub (SPUBLISH) scales in Cluster

Streams, Consumer Groups & Pub/Sub

# append events
> XADD orders:events * type placed orderId 1001 total 49.97
"1793491200123-0"
> XADD orders:events MAXLEN ~ 100000 * type paid orderId 1001
> XLEN orders:events
> XRANGE orders:events - + COUNT 10
> XREAD COUNT 10 BLOCK 5000 STREAMS orders:events $   # wait for new ones

# consumer groups: each entry to one worker, acknowledged
> XGROUP CREATE orders:events billing $ MKSTREAM
> XREADGROUP GROUP billing worker-1 COUNT 10 BLOCK 5000 STREAMS orders:events >
> XACK orders:events billing 1793491200123-0
> XPENDING orders:events billing
> XAUTOCLAIM orders:events billing worker-2 60000 0-0  # take stuck entries

# pub/sub: everyone listening now, no history
> SUBSCRIBE price-changes
> PUBLISH price-changes '{"productId":7,"price":17.99}'
(integer) 2                                         # receivers
> PSUBSCRIBE orders.*

Code Explained

MAXLEN ~ 100000 trims roughly, which is much cheaper than an exact trim
Each group keeps its own position, so billing and shipping can both read every event
XPENDING lists delivered but unacknowledged entries
XAUTOCLAIM hands entries idle for 60 s to another worker

SQL Equivalent

  • Streams ↔ an events table read by polling; Pub/Sub ↔ LISTEN / NOTIFY
  • Neither has a direct SQL equivalent; triggers are the closest in-database hook · See SQL 67

Across Engines

  • MongoDB change streams (sheet 28) or a capped collection
  • DynamoDB DynamoDB Streams to Lambda
  • Cassandra time-bucketed append-only tables; Kafka usually sits alongside
  • Neo4j CDC feeds; not a queue

In Your Code

  • Node await r.xAdd("orders:events", "*", { type: "placed", orderId: "1001" })
  • Python r.xadd("orders:events", {"type": "placed", "orderId": 1001})
  • Java jedis.xadd("orders:events", StreamEntryID.NEW_ENTRY, Map.of("type", "placed"));

Streams vs Pub/Sub

StreamsPub/Sub
HistoryKept (until trimmed)None
Offline consumersCatch up laterMiss messages
AcknowledgementYes (groups)No
DeliveryOne consumer per groupEvery subscriber
Use forJobs, event logsLive updates, invalidation

Stream Commands

CommandDoes

⚠ Common Mistakes

  • Using Pub/Sub for work that must not be lost
  • Never trimming streams
  • Forgetting XACK, so the pending list grows forever

✓ Tips & Best Practices

  • Make consumers idempotent; entries can be delivered twice
  • Monitor XPENDING for stuck work
  • Use one stream per event type or aggregate

Quick Summary

  • Stream — durable log
  • Consumer groups + XACK
  • Pub/Sub — live, no history
  • MAXLEN ~ to cap
