Sheet 45

Secondary Indexes

GSI · LSI · projections · sparse indexes · index overloading · eventual consistency

Other Ways In

A global secondary index (GSI) is a copy of selected attributes with a different partition and sort key, so you can Query by something other than the table key. It can be added any time and is eventually consistent. A local secondary index (LSI) keeps the table's partition key with a different sort key, supports strong reads, but must be created with the table. Items without the index key attributes are left out, which makes sparse indexes a cheap filter.

Notes

  • GSIs have their own capacity on provisioned tables
  • Projection decides which attributes are copied
  • One GSI can serve several entity types (overloading)
  • LSIs cap an item collection at 10 GB

Production Check

  • GSIs are eventually consistent: a Query right after a write may not see it
  • A throttled GSI holds back writes to the base table; give GSIs enough capacity (on-demand helps)
  • Every projected attribute is copied and billed on write; project only what the query needs

Add, Fill & Query a GSI

# GSI1: orders by status, newest first
aws dynamodb update-table --table-name Shop \
  --attribute-definitions AttributeName=GSI1PK,AttributeType=S \
                          AttributeName=GSI1SK,AttributeType=S \
  --global-secondary-index-updates '[{"Create":{"IndexName":"GSI1",
     "KeySchema":[{"AttributeName":"GSI1PK","KeyType":"HASH"},
                  {"AttributeName":"GSI1SK","KeyType":"RANGE"}],
     "Projection":{"ProjectionType":"INCLUDE","NonKeyAttributes":["total"]}}}]'

# an item joins the index by having the GSI key attributes
aws dynamodb update-item --table-name Shop \
  --key '{"PK":{"S":"CUSTOMER#42"},"SK":{"S":"ORDER#2026-11-01#1001"}}' \
  --update-expression "SET GSI1PK = :s, GSI1SK = :d" \
  --expression-attribute-values '{":s":{"S":"STATUS#pending"},
                                  ":d":{"S":"2026-11-01#1001"}}'

aws dynamodb query --table-name Shop --index-name GSI1 \
  --key-condition-expression "GSI1PK = :s" \
  --expression-attribute-values '{":s":{"S":"STATUS#pending"}}' \
  --no-scan-index-forward

# LSI: only at create-table time
#   --local-secondary-indexes '[{"IndexName":"ByTotal","KeySchema":[
#     {"AttributeName":"PK","KeyType":"HASH"},{"AttributeName":"total","KeyType":"RANGE"}],
#     "Projection":{"ProjectionType":"KEYS_ONLY"}}]'

In Your Code

  • Node new QueryCommand({ TableName: "Shop", IndexName: "GSI1", KeyConditionExpression: "GSI1PK = :s", ExpressionAttributeValues: { ":s": "STATUS#pending" } })
  • Python table.query(IndexName="GSI1", KeyConditionExpression=Key("GSI1PK").eq("STATUS#pending"))
  • Java table.index("GSI1").query(QueryConditional.keyEqualTo(k -> k.partitionValue("STATUS#pending")))

Code Explained

Generic names (GSI1PK) let one index serve many access patterns
INCLUDE copies the keys plus total; other attributes need a second read
Removing GSI1PK (when an order ships) drops it from the index: a sparse index of pending orders
A busy status value is a hot GSI partition; add a shard suffix if it gets heavy

SQL Equivalent

  • GSI ↔ CREATE INDEX on other columns, but kept as an async copy · LSI ↔ an index sharing the partition
  • INCLUDE projection ↔ CREATE INDEX … INCLUDE (total) · See SQL 72

Across Engines

  • MongoDB secondary indexes are synchronous and always consistent
  • Redis hand-built index sets, or FT.CREATE
  • Cassandra SAI, or a second table per query
  • Neo4j indexes on label properties, always consistent

⚠ Common Mistakes

  • Reading from a GSI right after writing and expecting the new item
  • Projecting ALL on every index
  • Planning on an LSI after the table exists

✓ Tips & Best Practices

  • Overload one or two GSIs instead of creating many
  • Use sparse indexes for "items in state X"
  • Shard hot GSI keys: STATUS#pending#3

Quick Summary

  • GSI — new key, any time, eventual
  • LSI — same partition, at create
  • Sparse indexes filter for free
  • Project only what you read
