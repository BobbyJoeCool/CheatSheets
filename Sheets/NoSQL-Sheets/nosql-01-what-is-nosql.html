What Is NoSQL?

non-relational · document · key-value · wide-column · graph · search / vector · schema-flexible

Databases Beyond Tables

NoSQL ("not only SQL") is the family name for databases that don't store data as rows in fixed relational tables. The main kinds are document stores (MongoDB), key-value stores (Redis, DynamoDB), wide-column stores (Cassandra) and graph databases (Neo4j), plus search and vector engines. Each gives up some relational features, such as joins, a fixed schema or multi-table transactions, in exchange for a flexible schema, easy horizontal scale or a data model that matches how the app reads.

Notes

  • Schema-flexible, not schemaless: the app still expects a shape
  • Several now offer ACID transactions and SQL-like languages (CQL, PartiQL)
  • PostgreSQL jsonb blurs the line from the SQL side

One Order in Each Model

// Document (MongoDB): the order with its items embedded
{ _id: 1001, customerId: 42, status: "pending", total: 49.97,
  items: [ { productId: 7, qty: 2, unitPrice: 19.99 },
           { productId: 3, qty: 1, unitPrice: 9.99 } ] }

// Key-value (Redis): a key points at a value or structure
HSET order:1001 customerId 42 status pending total 49.97
RPUSH order:1001:items "7:2:19.99" "3:1:9.99"

// Key-value item (DynamoDB): partition key + sort key
{ "PK": "CUSTOMER#42", "SK": "ORDER#2026-11-01#1001",
  "status": "pending", "total": 49.97 }

// Wide-column (Cassandra CQL): rows grouped into partitions
CREATE TABLE orders_by_customer (
  customer_id int, order_date date, order_id int,
  status text, total decimal,
  PRIMARY KEY ((customer_id), order_date, order_id));

// Graph (Neo4j Cypher): nodes joined by stored relationships
(:Customer {id: 42})-[:PLACED]->(:Order {id: 1001})
  -[:CONTAINS {qty: 2}]->(:Product {id: 7})

Code Explained

A document keeps related data together, so one read returns the whole order
Key-value stores look up by key only; the key name carries the structure
DynamoDB groups items by partition key and sorts them by sort key
Cassandra's partition key picks the node; clustering columns sort rows inside it
A graph stores relationships as data, so following them is cheap

SQL Equivalent

  • In SQL the same order is two tables, orders and order_items, joined when read
  • SQL normalizes first and answers any question later; most NoSQL designs start from the questions · See SQL 4

Across Engines

  • MongoDB documents (BSON) in collections; rich queries and secondary indexes
  • Redis in-memory data structures by key; sub-millisecond reads
  • DynamoDB managed key-value and document store on AWS; you design the keys
  • Cassandra wide-column rows across many equal nodes; built for heavy writes
  • Neo4j nodes and relationships; traversals instead of joins

⚠ Common Mistakes

  • Choosing NoSQL "because SQL doesn't scale" without a measured need
  • Reading "schemaless" as "no design needed"
  • Using one engine for every workload
