Sheet 29

Replica Sets & Sharding

primary / secondary · elections · oplog · shard key · chunks · mongos · hashed vs ranged

Copies and Slices

A replica set is a group of mongod servers holding the same data: one primary takes writes and secondaries copy them from the oplog. If the primary fails, members hold an election and promote a secondary in seconds. Sharding splits a collection across several replica sets (shards) by a shard key; the mongos router sends each query to the right shards. Hashed keys spread writes evenly; ranged keys keep nearby values together.

Notes

  • Use an odd number of voting members (3 or 5)
  • Drivers discover the primary and follow elections
  • Data moves between shards in ranges (chunks) by the balancer
  • Since 6.0 shardCollection enables sharding for the database

Production Check

  • The shard key is hard to change: resharding (5.0+) works but copies the whole collection. Choose it from your top queries
  • A steadily increasing key (ObjectId, timestamps) sends every insert to one shard; use a hashed or compound key
  • Queries without the shard key go to every shard (scatter-gather)

Replica Set & Sharding Commands

# three-member replica set for local testing
docker network create mongo-net
for n in m1 m2 m3; do
  docker run -d --name $n --net mongo-net mongo:8 --replSet rs0 --bind_ip_all
done
mongosh --host m1 --eval 'rs.initiate({ _id: "rs0", members: [
  { _id: 0, host: "m1:27017" }, { _id: 1, host: "m2:27017" },
  { _id: 2, host: "m3:27017" } ] })'

# in mongosh
rs.status()                            # PRIMARY / SECONDARY per member
rs.printSecondaryReplicationInfo()     # replication lag
rs.stepDown()                          # force an election

# sharding: connect to mongos
sh.shardCollection("shop.orders", { customerId: "hashed" })
sh.shardCollection("shop.events", { tenantId: 1, ts: 1 })     # ranged
sh.status()
db.orders.getShardDistribution()
db.adminCommand({ reshardCollection: "shop.orders",
                  key: { customerId: 1, orderDate: 1 } })

Code Explained

--replSet rs0 names the set; rs.initiate lists its members
A hashed key on customerId spreads customers evenly across shards
A compound ranged key keeps one tenant's events together and in time order
getShardDistribution shows how evenly data is spread

SQL Equivalent

  • Replica set ↔ PostgreSQL streaming replication plus automatic failover (for example Patroni)
  • PostgreSQL has no built-in sharding; the nearest is Citus · See SQL 74

Across Engines

  • Redis replicas + Sentinel for failover; Cluster shards by 16,384 hash slots
  • DynamoDB automatic: partitions split by size and traffic; you only choose the key
  • Cassandra every node is equal; consistent hashing over the token ring
  • Neo4j clusters replicate; scale-out reads via secondaries, sharding via composite databases (Enterprise)

In Your Code

  • Node new MongoClient("mongodb://m1,m2,m3/?replicaSet=rs0")
  • Python MongoClient("mongodb://m1,m2,m3/?replicaSet=rs0&readPreference=secondaryPreferred")
  • Java MongoClients.create("mongodb://m1,m2,m3/?replicaSet=rs0&w=majority")

Replica Set Members

RoleDoes
PrimaryAccepts writes
SecondaryCopies the oplog; can serve reads
ArbiterVotes only, no data (avoid if you can)
Hidden / delayedBackups, analytics, undo window

Shard Key Choices

KeyEffect
Hashed _idEven writes; range queries hit all shards
Ranged tsHot last shard
Compound { tenantId, ts }Spread by tenant, ordered within
Low cardinality (status)Few chunks, uneven

⚠ Common Mistakes

  • Two-member replica sets that can't elect a primary when one fails
  • Sharding before you need it
  • Picking a shard key nobody filters on

✓ Tips & Best Practices

  • Always connect with the replica set name so drivers follow failover
  • Test failover with rs.stepDown() before production
  • Shard on the field your most frequent queries include

Quick Summary

  • Replica set — primary + secondaries
  • Elections fail over in seconds
  • Shard key decides the shard
  • Hashed for even writes
