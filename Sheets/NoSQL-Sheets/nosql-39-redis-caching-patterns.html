Caching Patterns

cache-aside · write-through · TTL strategy · invalidation · stampede protection · session store

Redis as a Cache

The most common use of Redis is as a cache in front of a slower source of truth. In cache-aside, the app checks Redis first, loads from the database on a miss, and stores the result with a TTL. On writes, update the database and then delete the cache key so the next read refills it. Protect hot keys from a stampede (many requests rebuilding at once) with a short lock or early refresh, and add jitter to TTLs.

Notes

  • Cache what's expensive and read often
  • Key names should include versions: v2:product:7
  • Session stores are caches with sliding TTLs
  • Measure hit rate (keyspace_hits / keyspace_misses)

Production Check

  • Cache stampede: a hot key expires and thousands of requests hit the database together. Use a short SET NX EX lock, early refresh or TTL jitter
  • Stale data after writes: delete the cache key after the database commit, not before
  • On cache-only instances set maxmemory and maxmemory-policy allkeys-lru (or lfu)

Cache-Aside, Invalidation & Stampede Lock

// cache-aside: read through the cache, fill on a miss
async function getProduct(id) {
  const key = `product:${id}`
  const hit = await redis.get(key)
  if (hit) return JSON.parse(hit)
  const p = await db.collection("products").findOne({ _id: id })
  const ttl = 3600 + Math.floor(Math.random() * 300)      // TTL + jitter
  await redis.set(key, JSON.stringify(p), { EX: ttl })
  return p
}

// write: update the source of truth, then drop the cache entry
async function updatePrice(id, price) {
  await db.collection("products").updateOne({ _id: id }, { $set: { price } })
  await redis.del(`product:${id}`)
}

// stampede protection: one caller rebuilds, others wait briefly
async function getWithLock(key, load, ttl = 3600) {
  const hit = await redis.get(key)
  if (hit) return JSON.parse(hit)
  if (await redis.set(`lock:${key}`, "1", { NX: true, EX: 10 })) {
    const v = await load()
    await redis.set(key, JSON.stringify(v), { EX: ttl })
    await redis.del(`lock:${key}`)
    return v
  }
  await new Promise(r => setTimeout(r, 50))
  return getWithLock(key, load, ttl)
}

Code Explained

Jitter spreads expiry times so a batch of keys doesn't expire together
Deleting rather than updating the cache avoids racing writers storing old values
The lock expires after 10 s even if the loader crashes
Callers that miss the lock retry after 50 ms and usually find the fresh value

SQL Equivalent

  • A cache is a copy kept outside the database; the nearest SQL feature is a materialized view
  • The database's own buffer cache saves disk reads, not network round trips · See SQL 64

Across Engines

  • MongoDB WiredTiger keeps hot data in RAM; Redis still saves the network and query work
  • DynamoDB DAX: a write-through cache with microsecond reads
  • Cassandra key and row caches; Redis often fronts hot rows
  • Neo4j page cache; cache computed recommendations in Redis

In Your Code

  • Node await redis.set(key, JSON.stringify(p), { EX: 3600 })
  • Python r.set(key, json.dumps(p), ex=3600)

⚠ Common Mistakes

  • Updating the cache before the database commit
  • Caching without TTLs and serving stale data forever
  • Caching per-user data under shared keys

✓ Tips & Best Practices

  • Start with cache-aside and delete-on-write
  • Version key names when the cached shape changes
  • Track hit rate; under ~80% means the cache may not be worth it

Quick Summary

  • Cache-aside — fill on miss
  • Delete key after write
  • TTL + jitter
  • Lock against stampedes
