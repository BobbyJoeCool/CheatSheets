Sheet 03

CAP, Consistency & BASE

CAP theorem · PACELC · strong vs eventual consistency · read-your-writes · quorum · BASE vs ACID

Consistency Is a Dial

The CAP theorem says that during a network partition a distributed database must choose between consistency (every read sees the latest write) and availability (every request gets an answer). PACELC adds that even without a partition you trade latency for consistency. With eventual consistency replicas converge after a short delay. Quorums give strong reads when R + W > N (replicas read + replicas written > replication factor). BASE (basically available, soft state, eventually consistent) is the counterpart to ACID.

Notes

  • CAP only describes behavior during a network partition
  • Most engines let you choose per request
  • "Eventual" is usually milliseconds, not hours
  • CAP's C (latest value) is not ACID's C (valid state)

Production Check

  • A user saves a profile and the next page reads a stale replica. Read from the primary, or use a strongly consistent read, right after a write
  • Choose per request: strong for stock and balances, eventual for feeds and counts
  • Strong reads cost more: in DynamoDB they use twice the read capacity, in Cassandra they wait on more replicas

Consistency Knobs per Engine

// MongoDB: write and read concern, read preference
db.orders.insertOne(doc, { writeConcern: { w: "majority" } })
db.orders.find({ customerId: 42 })
  .readConcern("majority")      // only majority-acknowledged data
  .readPref("primary")          // read your own writes

// DynamoDB: eventual by default, strong on request
aws dynamodb get-item --table-name Shop \
  --key '{"PK":{"S":"ORDER#1001"},"SK":{"S":"META"}}' \
  --consistent-read

// Cassandra (cqlsh): consistency level per statement
CONSISTENCY QUORUM;
SELECT * FROM orders_by_customer WHERE customer_id = 42;

// Redis: async replicas; WAIT blocks until n replicas ack
SET order:1001:status "paid"
WAIT 1 100                      // replicas that acknowledged

// Neo4j cluster: bookmarks give causal consistency
const session = driver.session({ bookmarks: lastBookmarks })

Code Explained

w: "majority" returns only after most replica-set members have the write
--consistent-read works on tables and local indexes, not on global secondary indexes
QUORUM with replication factor 3 means 2 replicas; reading and writing at QUORUM gives 2 + 2 > 3
WAIT narrows Redis's replication gap but doesn't make it strongly consistent

SQL Equivalent

  • One PostgreSQL primary is strongly consistent; its read replicas are eventually consistent, the same trade-off
  • Isolation levels are about concurrent transactions, a different axis from replica lag · See SQL 69

Across Engines

  • MongoDB strong on the primary; secondaries lag; tune with read and write concern
  • Redis asynchronous replicas; replica reads may be stale
  • DynamoDB eventual by default; ConsistentRead on tables and LSIs only
  • Cassandra tunable per query: ONE, QUORUM, LOCAL_QUORUM, ALL
  • Neo4j causal consistency in clusters through bookmarks

In Your Code

  • Node orders.find(q, { readPreference: "primary" })
  • Python db.get_collection("orders", read_concern=ReadConcern("majority"))
  • Java orders.withReadConcern(ReadConcern.MAJORITY)

Consistency Models

ModelGuarantee
Strong (linearizable)Every read sees the latest write
CausalYou see the writes yours depended on
Read-your-writesA client sees its own writes
Monotonic readsReads never go back in time
EventualReplicas converge once writes stop

Quorum Math (N = 3)

Write / ReadResult
QUORUM / QUORUM2 + 2 > 3: strong
ONE / ONE1 + 1 ≤ 3: eventual, fastest
ALL / ONEStrong; writes fail if a node is down
ONE / ALLStrong; reads fail if a node is down

⚠ Common Mistakes

  • Assuming a replica read is current
  • Using the strongest setting everywhere and paying the latency
  • Confusing CAP consistency with ACID consistency

✓ Tips & Best Practices

  • List which reads must be strong
  • Read from the primary right after writing in the same session
  • Monitor replication lag

Quick Summary

  • CAP — choose during partitions
  • PACELC — latency vs consistency
  • R + W > N — strong quorums
  • Pick per request
