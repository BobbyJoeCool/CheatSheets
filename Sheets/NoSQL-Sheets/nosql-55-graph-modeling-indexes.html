Sheet 55

Graph Modeling, Indexes & Constraints

relationship vs property · intermediate nodes · CREATE INDEX · uniqueness constraint · PROFILE · recommendations

Model the Questions, Index the Entry Points

Make something a node when you query from it or connect it to many things; make it a property when it just describes something. Turn events into intermediate nodes ((:Customer)-[:PLACED]->(:Order)-[:CONTAINS]->(:Product) rather than one :BOUGHT relationship) so they can hold data and links. Traversals start from a node you look up, so index and constrain those lookup properties, then check plans with PROFILE.

Notes

  • A uniqueness constraint also creates an index
  • Node key and type constraints are Enterprise features
  • Specific relationship types are faster than filtering on properties
  • Check plans: NodeIndexSeek good, NodeByLabelScan to fix

Production Check

  • A MATCH on an unindexed property scans every node with that label; index your lookup properties
  • MERGE without a uniqueness constraint can create duplicates under concurrent writes
  • Super nodes with millions of relationships slow traversals; split them with intermediate nodes or more specific relationship types

Constraints, Indexes, Plans & Recommendations

// constraints (each also creates an index)
CREATE CONSTRAINT customer_id IF NOT EXISTS
  FOR (c:Customer) REQUIRE c.id IS UNIQUE;
CREATE CONSTRAINT product_id IF NOT EXISTS
  FOR (p:Product) REQUIRE p.id IS UNIQUE;
CREATE CONSTRAINT order_key IF NOT EXISTS
  FOR (o:Order) REQUIRE o.id IS NODE KEY;            // Enterprise

// indexes
CREATE INDEX product_category IF NOT EXISTS FOR (p:Product) ON (p.category);
CREATE TEXT INDEX product_name IF NOT EXISTS FOR (p:Product) ON (p.name);
CREATE FULLTEXT INDEX product_search IF NOT EXISTS
  FOR (p:Product) ON EACH [p.name, p.description];
CREATE VECTOR INDEX product_embedding IF NOT EXISTS
  FOR (p:Product) ON (p.embedding)
  OPTIONS { indexConfig: { `vector.dimensions`: 384,
                           `vector.similarity_function`: 'cosine' } };
SHOW INDEXES;
SHOW CONSTRAINTS;

// check the plan
PROFILE MATCH (p:Product {category: "Books"}) RETURN p.name;
// NodeIndexSeek = uses the index · NodeByLabelScan = add one

// recommendations: bought together with product 7
MATCH (:Product {id: 7})<-[:CONTAINS]-(:Order)-[:CONTAINS]->(rec:Product)
RETURN rec.name, count(*) AS together
ORDER BY together DESC LIMIT 5;

Code Explained

Uniqueness constraints make MERGE on id safe and fast
TEXT indexes speed up CONTAINS / ENDS WITH on strings
The full-text index is queried with db.index.fulltext.queryNodes
Orders as intermediate nodes make "bought together" a two-hop pattern

SQL Equivalent

  • Uniqueness ↔ UNIQUE · node key ↔ PRIMARY KEY · property existence ↔ NOT NULL
  • PROFILE ↔ EXPLAIN ANALYZE; intermediate node ↔ a junction table with its own columns · See SQL 57, 73

Across Engines

  • MongoDB unique indexes; explain()
  • Redis no constraints; SET NX for uniqueness
  • DynamoDB uniqueness via a conditional put on a key item
  • Cassandra uniqueness via IF NOT EXISTS on a lookup table

In Your Code

  • Node plain driver with MERGE on constrained keys (or an OGM such as Neogma)
  • Python neomodel: class Product(StructuredNode): pid = IntegerProperty(unique_index=True)
  • Java Spring Data Neo4j: @Node class Product { @Id Long id; @Relationship("IN_CATEGORY") Category category; }

Modeling Rules

⚠ Common Mistakes

  • No constraint on the property every MERGE uses
  • Turning every attribute into a node
  • One giant node (:Country {name: "US"}) linked to everything

✓ Tips & Best Practices

  • Create constraints before loading data
  • Profile your top five queries
  • Use specific relationship types: :PLACED, :REVIEWED, :VIEWED

Quick Summary

  • Index the entry points
  • Constraints make MERGE safe
  • Intermediate nodes for events
  • PROFILE every hot query
