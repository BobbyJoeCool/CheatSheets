DynamoDB Concepts

tables · items · partition key · sort key · on-demand vs provisioned · DynamoDB Local · shop data

Managed Key-Value at Any Scale

DynamoDB is AWS's fully managed, serverless key-value and document database. A table holds items (up to 400 KB each) made of attributes. Only the primary key is declared: a partition key alone, or a partition key plus a sort key. Items with the same partition key form an item collection, stored together and sorted by sort key. You pay per request (on-demand) or for reserved read / write capacity (provisioned). DynamoDB Local runs it on your machine.

Notes

  • Every item needs the full primary key; other attributes vary per item
  • Partition key = HASH, sort key = RANGE in the API
  • Data is replicated across three Availability Zones
  • Global tables replicate across regions

Create a Table and Load Shop Items

docker run -d -p 8000:8000 amazon/dynamodb-local
export AWS_ENDPOINT_URL=http://localhost:8000    # point the CLI at Local

aws dynamodb create-table --table-name Shop \
  --attribute-definitions AttributeName=PK,AttributeType=S \
                          AttributeName=SK,AttributeType=S \
  --key-schema AttributeName=PK,KeyType=HASH AttributeName=SK,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST

# items read together share a partition key
aws dynamodb put-item --table-name Shop --item '{
  "PK": {"S": "CUSTOMER#42"}, "SK": {"S": "PROFILE"},
  "name": {"S": "Ada Lovelace"}, "email": {"S": "ada@example.com"} }'
aws dynamodb put-item --table-name Shop --item '{
  "PK": {"S": "CUSTOMER#42"}, "SK": {"S": "ORDER#2026-11-01#1001"},
  "status": {"S": "pending"}, "total": {"N": "49.97"} }'
aws dynamodb put-item --table-name Shop --item '{
  "PK": {"S": "ORDER#1001"}, "SK": {"S": "ITEM#7"},
  "qty": {"N": "2"}, "unitPrice": {"N": "19.99"} }'

aws dynamodb describe-table --table-name Shop

Code Explained

AWS_ENDPOINT_URL sends every AWS CLI call to DynamoDB Local (any credentials work)
Only PK and SK are declared; name, status and qty are free-form
The customer's profile and orders share CUSTOMER#42, so one Query returns both
Typed JSON ({"S": …}, {"N": …}) is the low-level format; SDK document clients hide it

SQL Equivalent

  • Table ↔ table without fixed columns · PK + SK ↔ a composite primary key
  • No joins, no ad hoc WHERE: every read names a key or an index · See SQL 56

Across Engines

  • MongoDB a collection per entity with _id as key
  • Redis key names like customer:42 do the same job as partition keys
  • Cassandra closest cousin: partition key + clustering columns
  • Neo4j nodes with labels; no partition key to design

In Your Code

  • Node const doc = DynamoDBDocumentClient.from(new DynamoDBClient({ region: "us-east-2" }))
  • Python table = boto3.resource("dynamodb").Table("Shop")
  • Java DynamoDbTable<Order> t = DynamoDbEnhancedClient.create().table("Shop", TableSchema.fromBean(Order.class));

⚠ Common Mistakes

  • Designing tables like SQL tables, one per entity with no access-pattern plan
  • Using a low-cardinality partition key such as status
  • Forgetting that number attributes are sent as strings in the low-level API

✓ Tips & Best Practices

  • Prefix key values with the entity type: CUSTOMER#42
  • Start with on-demand capacity
  • Use the document client so you work with plain objects

Quick Summary

  • Table → items → attributes
  • Partition key + sort key
  • On-demand or provisioned
  • DynamoDB Local for dev
