Sheet 26

Schema Validation

$jsonSchema · validator · validationLevel · validationAction · required fields · collMod

Rules on the Server

Schema validation makes MongoDB check documents on insert and update with a $jsonSchema validator: required fields, BSON types, ranges, patterns and allowed values. validationLevel decides which documents are checked (strict: all; moderate: only those already valid) and validationAction decides what happens to a bad write (error rejects it, warn logs it). Change the rules later with collMod.

Notes

  • Validation doesn't touch existing documents until they're updated
  • Failed writes report which rule failed (errInfo)
  • Use bypassDocumentValidation only for repair jobs
  • App-side validation still gives better error messages

$jsonSchema Validator

db.createCollection("customers", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["name", "email", "createdAt"],
    properties: {
      name:      { bsonType: "string", minLength: 1, maxLength: 100 },
      email:     { bsonType: "string", pattern: "^[^@\\s]+@[^@\\s]+$" },
      country:   { enum: ["US", "CA", "GB", "DE"] },
      createdAt: { bsonType: "date" },
      credit:    { bsonType: "decimal", minimum: 0 },
      addresses: { bsonType: "array", maxItems: 5,
                   items: { bsonType: "object", required: ["city"] } }
    }
  } },
  validationLevel: "strict",
  validationAction: "error"
})

// change the rules on an existing collection
db.runCommand({ collMod: "customers",
  validator: { $jsonSchema: newSchema },
  validationLevel: "moderate" })

// find documents that break the rules
db.customers.find({ $nor: [ { $jsonSchema: newSchema } ] })
db.getCollectionInfos({ name: "customers" })[0].options.validator

Code Explained

required lists fields that must exist; properties sets rules for each
enum limits a field to listed values
moderate lets old invalid documents be updated without fixing them first
The $nor query lists documents to clean up before switching to strict

SQL Equivalent

  • $jsonSchema ↔ column types, NOT NULL and CHECK constraints · enum ↔ CHECK (country IN …)
  • moderate ↔ adding a constraint NOT VALID · See SQL 57

Across Engines

  • Redis no validation; validate in the app
  • DynamoDB only key attributes are typed; validate in code
  • Cassandra typed columns enforce types; no CHECK constraints
  • Neo4j uniqueness and key constraints; existence and type constraints in Enterprise

In Your Code

  • Node Mongoose: new Schema({ email: { type: String, required: true, match: /@/ } })
  • Python Pydantic models (Beanie / ODMantic) validate before writing
  • Java Bean Validation: @NotBlank @Email String email; on the document class

Level & Action

SettingEffect
strictCheck every insert and update
moderateSkip updates to already-invalid docs
offNo checks
errorReject invalid writes
warnAllow, but log

⚠ Common Mistakes

  • Turning on strict without checking existing data
  • Using type instead of bsonType for BSON-specific types like decimal
  • additionalProperties: false without listing _id

✓ Tips & Best Practices

  • Start with warn, watch the logs, then switch to error
  • Keep the schema in version control and apply it with migrations
  • Validate in the app too, for friendly messages

Quick Summary
