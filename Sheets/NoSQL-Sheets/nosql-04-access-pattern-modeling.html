Sheet 04

Modeling From Access Patterns

list queries first · read / write ratio · query-driven design · denormalization · duplication trade-offs

List the Questions First

NoSQL modeling starts from the access patterns: the questions the app asks, with how often and how fast each must answer. Rank them, then shape the data so each common question is one read from one place. That usually means denormalizing: copying data to where it's read and accepting extra work on writes. Rare or slow questions can fall back to secondary indexes, batch jobs or an analytics store.

Notes

  • Reads usually outnumber writes, so optimize them first
  • Every copy of data needs a plan for updating it
  • Key design is hard to change later in DynamoDB and Cassandra
  • Keep the access-pattern list in the repo

Access-Pattern Worksheet

# shop access patterns, most frequent first
- id: AP1
  question: Show a product page
  key: productId
  rate: 2000/s
  needs: product, average rating, 3 newest reviews
- id: AP2
  question: Customer's recent orders
  key: customerId, newest first
  rate: 150/s
  needs: date, status, total, line count
- id: AP3
  question: One order with its items
  key: orderId
  rate: 300/s
- id: AP4
  question: Reserve stock when an order is placed
  key: productId
  rate: 80/s
  rule: stock never below 0
- id: AP5
  question: Monthly sales by category
  rate: nightly
  rule: can be slow, read from analytics

Code Explained

AP1: keep the 3 newest reviews and the rating total on the product (subset and computed patterns, sheet 25)
AP2: store orders keyed by customer, sorted by date
AP3: embed line items in the order, since they're always read together
AP4: a conditional atomic update on one record
AP5: don't model the operational store for it; export or aggregate offline

SQL Equivalent

  • SQL models entities first and adds indexes for queries; NoSQL models the queries first
  • Denormalizing is an optimization in SQL and the default in NoSQL · See SQL 61, 63

Across Engines

  • MongoDB embed what's read together, reference what grows
  • Redis one key per lookup; pick the structure by operation
  • DynamoDB choose PK / SK so each pattern is a single Query
  • Cassandra one table per query
  • Neo4j model the traversals: which things connect to which

In Your Code

  • Node const recent = (id) => orders.find({ customerId: id }).sort({ orderDate: -1 }).limit(10).toArray()
  • Python def recent(cid): return list(orders.find({"customerId": cid}).sort("orderDate", -1).limit(10))
  • Java List<Order> findTop10ByCustomerIdOrderByOrderDateDesc(int customerId);

Denormalizing Trade-offs

ChoiceReadWrite
EmbedOne readRewrites the parent
Copy a fieldNo joinUpdate every copy
Precompute a totalInstantRecompute on change
ReferenceExtra readOne place to update

⚠ Common Mistakes

  • Designing from the ER diagram instead of the queries
  • Ignoring how fast arrays and partitions grow
  • Copying data without a way to keep copies in sync

✓ Tips & Best Practices

  • Rank patterns by frequency and latency
  • Design for the top patterns; index or batch the rest
  • Revisit with real traffic numbers

Quick Summary

  • Questions first
  • One read per common question
  • Denormalize on purpose
  • Plan the update path
