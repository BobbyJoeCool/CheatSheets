Index Strategy & explain()

ESR rule · covered queries · explain("executionStats") · COLLSCAN vs IXSCAN · hint

Design Indexes for Queries

Build compound indexes with the ESR rule: Equality fields first, then Sort fields, then Range fields. Check every important query with explain("executionStats"): an IXSCAN with keys examined close to documents returned is healthy, a COLLSCAN means a full scan. A covered query is answered from the index alone, with zero documents examined.

Notes

  • queryPlanner shows the plan; executionStats also runs it
  • The planner caches the winning plan per query shape
  • $indexStats shows how often each index is used
  • Atlas Performance Advisor suggests indexes

Production Check

  • Every index slows writes and uses RAM; drop unused ones (check $indexStats) on write-heavy collections
  • Order compound fields by ESR; a range field before a sort field forces an in-memory sort
  • Build large indexes off-peak: builds hold an exclusive lock briefly at the start and end

ESR, explain() & Covered Queries

// query: a customer's pending orders over $20, newest first
db.orders.find({ customerId: 42, status: "pending", total: { $gt: 20 } })
         .sort({ orderDate: -1 })

// ESR: Equality (customerId, status) → Sort (orderDate) → Range (total)
db.orders.createIndex({ customerId: 1, status: 1, orderDate: -1, total: 1 })

db.orders.find({ customerId: 42, status: "pending", total: { $gt: 20 } })
  .sort({ orderDate: -1 })
  .explain("executionStats")
// winningPlan.inputStage.stage: "IXSCAN"   (COLLSCAN = full scan)
// nReturned: 3, totalKeysExamined: 4, totalDocsExamined: 3

// covered: every field comes from the index
db.orders.find({ customerId: 42 }, { _id: 0, customerId: 1, orderDate: 1 })
// totalDocsExamined: 0

// force a plan while testing
db.orders.find({ customerId: 42 }).hint({ customerId: 1, status: 1, orderDate: -1, total: 1 })

// how often is each index used?
db.orders.aggregate([ { $indexStats: {} } ])

Code Explained

Equality fields narrow to one slice of the index; the sort field then reads in order; the range filters last
Keys examined ≈ returned means the index fits the query
A covered query must exclude _id unless _id is in the index
hint is for testing; let the planner choose in production

SQL Equivalent

  • explain() ↔ EXPLAIN ANALYZE · COLLSCAN ↔ Seq Scan · IXSCAN ↔ Index Scan
  • Covered query ↔ Index Only Scan · See SQL 73, 74

Plan Stages

StageMeaning
COLLSCANRead every document
IXSCANWalk an index
FETCHLoad documents after IXSCAN
SORTIn-memory sort (no index order)
PROJECTION_COVEREDAnswered from the index

Healthy Numbers

MetricAim for
totalKeysExamined / nReturnedClose to 1

⚠ Common Mistakes

  • Putting the range field before the sort field
  • Adding an index for every query instead of sharing compound prefixes
  • Judging speed on a tiny dev dataset

✓ Tips & Best Practices

  • Explain with production-sized data
  • Check $indexStats before adding another index
  • Turn on the profiler (db.setProfilingLevel(1, { slowms: 100 })) to find slow queries

Quick Summary

  • ESR — Equality, Sort, Range
  • IXSCAN good, COLLSCAN bad
  • Keys ≈ returned
  • Covered — 0 docs examined
