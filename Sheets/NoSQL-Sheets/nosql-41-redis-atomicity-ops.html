Atomic Groups, Scripts and Durability

Redis runs commands one at a time, so every single command is atomic. MULTI … EXEC queues commands and runs them as one block that no other client can interleave with, but there is no rollback: if one command fails at run time the others still apply. WATCH adds optimistic locking, and EXEC returns nil if a watched key changed. Lua scripts (EVAL) and Functions (FCALL, Redis 7+) run logic on the server atomically. Pipelining only saves round trips. For durability, Redis offers RDB snapshots, an AOF write log, replicas and Cluster sharding.

Notes

  • A syntax error while queuing aborts the whole EXEC; a wrong-type error at run time doesn't
  • Scripts block the server while they run; Redis answers BUSY after 5 s (busy-reply-threshold)
  • Pass every key a script touches in KEYS, not built inside the script

Production Check

  • Out of the box Redis saves only RDB snapshots, so a crash loses writes since the last one. Set appendonly yes with appendfsync everysec to lose at most about 1 s
  • In Cluster, a transaction or script touching keys in different slots fails with CROSSSLOT. Group keys with hash tags: {order:1001}:items
  • Replication is asynchronous; a failover can drop acknowledged writes. WAIT 1 100 narrows the gap but isn't strong consistency

Transactions, Scripts & Persistence

# MULTI / EXEC: queue, then run as one block
> MULTI
OK
> DECRBY product:7:stock 2
QUEUED
> RPUSH order:1001:items "7:2"
QUEUED
> EXEC
1) (integer) 8
2) (integer) 1

# WATCH: optimistic lock on the stock key
> WATCH product:7:stock
> GET product:7:stock            # "8", client checks it's >= 2
> MULTI
> DECRBY product:7:stock 2
> EXEC                           # (nil) = changed by someone else, retry

# Lua: check and decrement in one atomic step
$ redis-cli EVAL "
    local s = tonumber(redis.call('GET', KEYS[1]))
    if s and s >= tonumber(ARGV[1]) then
      return redis.call('DECRBY', KEYS[1], ARGV[1]) end
    return -1" 1 product:7:stock 2

# Functions (Redis 7+): load a library once, call by name
$ redis-cli FUNCTION LOAD "$(cat shop.lua)"
> FCALL reserve_stock 1 product:7:stock 2

# Persistence and replication
> CONFIG SET appendonly yes
> BGSAVE                         # RDB snapshot in the background
> REPLICAOF 10.0.0.5 6379        # follow a primary

Code Explained

QUEUED means accepted for later; nothing runs until EXEC, which returns one reply per command
WATCH must come before MULTI; any write to the key by another client makes EXEC return nil, so wrap it in a retry loop
The 1 after the script is the number of keys; then come KEYS[1] and ARGV[1]
A function library starts with #!lua name=shop and calls redis.register_function

SQL Equivalent

  • MULTI / EXEC ↔ BEGIN … COMMIT, but Redis has no ROLLBACK
  • WATCH ↔ optimistic locking with a version column (UPDATE … WHERE version = 3); SQL also offers SELECT … FOR UPDATE
  • Lua and Functions ↔ stored procedures · See SQL 68, 66

Across Engines

  • MongoDB single-document writes are atomic; session.withTransaction() spans documents and rolls back on error
  • DynamoDB TransactWriteItems: up to 100 actions, all-or-nothing, with condition checks
  • Cassandra no multi-partition transactions; lightweight transactions (IF) per partition; logged batches apply eventually
  • Neo4j full ACID; every Cypher query runs in a transaction that rolls back on error

In Your Code

  • Node await client.multi().decrBy("product:7:stock", 2).rPush("order:1001:items", "7:2").exec()
  • Python r.pipeline().decrby("product:7:stock", 2).rpush("order:1001:items", "7:2").execute()
  • Java Transaction t = jedis.multi(); t.decrBy("product:7:stock", 2); t.exec();

⚠ Common Mistakes

  • Expecting EXEC to roll back when one command fails
  • Treating a pipeline as a transaction; other clients can run between its commands
  • Using WATCH without a retry loop, so a nil EXEC silently drops the write

✓ Tips & Best Practices

  • Reach for a single atomic command first (INCRBY, SET NX EX, LMOVE)
  • Prefer Functions over EVAL for logic you call often; EVALSHA avoids resending scripts
  • Run INFO persistence after config changes to confirm AOF is on

Quick Summary

  • MULTI / EXEC — atomic, no rollback
  • WATCH — optimistic lock
  • Lua / Functions — server-side logic
  • RDB + AOF — durability
