Transactions, Read & Write Concerns

single-document atomicity · startSession · withTransaction · write concern majority · read concern · read preference

Atomic Across Documents

Every write to one document is atomic, which covers most needs when related data is embedded. For changes across documents or collections, MongoDB has multi-document transactions on replica sets and sharded clusters: start a session, run the operations, then commit or abort. Write concern (how many replicas confirm), read concern (how committed the data must be) and read preference (which member to read) tune durability and freshness.

Notes

  • withTransaction() retries transient errors and commits for you
  • Pass the session to every operation inside the transaction
  • Transactions can't create collections on sharded clusters
  • Prefer a schema that needs one document

Production Check

  • Transactions need a replica set or sharded cluster; a standalone server rejects them. Run a one-node replica set locally
  • Keep transactions short: they abort after 60 s by default and hold cache while open
  • Retry on TransientTransactionError and UnknownTransactionCommitResult; withTransaction() does this

Single-Document Atomicity & Transactions

// one document: already atomic, no transaction needed
db.products.updateOne({ _id: 7, stock: { $gte: 2 } }, { $inc: { stock: -2 } })

// several documents: a transaction
const session = db.getMongo().startSession()
const shop = session.getDatabase("shop")
session.withTransaction(() => {
  const r = shop.products.updateOne({ _id: 7, stock: { $gte: 2 } },
                                    { $inc: { stock: -2 } })
  if (r.modifiedCount === 0) throw new Error("out of stock")   // aborts
  shop.orders.insertOne({ _id: 1002, customerId: 42, status: "pending",
    items: [ { productId: 7, qty: 2, unitPrice: NumberDecimal("19.99") } ] })
}, { readConcern: { level: "snapshot" }, writeConcern: { w: "majority" } })
session.endSession()

// concerns outside transactions
db.orders.insertOne(doc, { writeConcern: { w: "majority", j: true } })
db.orders.find().readConcern("majority")
db.orders.find().readPref("secondaryPreferred")

Code Explained

The filter stock: { $gte: 2 } makes the decrement conditional and race-free
Throwing inside the callback aborts and rolls back both writes
snapshot reads see one consistent point in time for the whole transaction
secondaryPreferred reads may be slightly stale

SQL Equivalent

  • startSession + withTransaction ↔ BEGIN … COMMIT; throwing ↔ ROLLBACK
  • snapshot read concern ↔ snapshot isolation (REPEATABLE READ in PostgreSQL) · See SQL 68, 69

Across Engines

  • Redis MULTI / EXEC without rollback (sheet 41)
  • DynamoDB TransactWriteItems: up to 100 actions, all-or-nothing
  • Cassandra lightweight transactions per partition only
  • Neo4j every query runs in a transaction; session.executeWrite() retries

In Your Code

  • Node await session.withTransaction(async () => { await products.updateOne(f, u, { session }) })
  • Python with client.start_session() as s: s.with_transaction(lambda s: products.update_one(f, u, session=s))
  • Java session.withTransaction(() -> { products.updateOne(session, f, u); return null; })

⚠ Common Mistakes

  • Forgetting to pass session to an operation, which then runs outside the transaction
  • Long transactions that do slow work (HTTP calls) inside
  • Using transactions to patch a schema that should embed

✓ Tips & Best Practices

  • Model so most changes touch one document
  • Use conditional updates for stock and balances
  • Keep transactions under a few hundred milliseconds

Quick Summary

  • One document — always atomic
  • Sessions + withTransaction()
  • Write concern — durability
  • Read concern / preference — freshness
