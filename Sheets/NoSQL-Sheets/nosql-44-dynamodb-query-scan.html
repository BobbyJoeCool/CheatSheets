Query vs Scan

Query · key condition · begins_with · filter expression · pagination · Scan cost · PartiQL

Read by Key, Not by Search

Query reads one item collection: it needs the partition key with = and can narrow by sort key (begins_with, BETWEEN, <, >), returning items in sort-key order. Scan reads the entire table. A filter expression removes items after they're read, so it saves bandwidth but not cost. Results come in pages of up to 1 MB; continue from LastEvaluatedKey. PartiQL offers SQL-like syntax over the same rules.

Notes

  • The CLI follows pages for you; SDKs give you LastEvaluatedKey
  • Limit caps items read, before filtering
  • Parallel Scan splits a table into segments for exports
  • A PartiQL SELECT without a key condition becomes a Scan

Production Check

  • Scan reads every item and bills for all of it, even with a filter; use Query on a key or a GSI
  • Filters run after the read: a Query that returns 10 of 10,000 items still pays for 10,000
  • Results come in 1 MB pages; loop on LastEvaluatedKey or you silently miss data

Query, Filters, Paging, Scan & PartiQL

# a customer's orders, newest first
aws dynamodb query --table-name Shop \
  --key-condition-expression "PK = :c AND begins_with(SK, :o)" \
  --expression-attribute-values '{":c":{"S":"CUSTOMER#42"},":o":{"S":"ORDER#"}}' \
  --no-scan-index-forward --max-items 10

# sort-key range: November 2026
aws dynamodb query --table-name Shop \
  --key-condition-expression "PK = :c AND SK BETWEEN :a AND :b" \
  --expression-attribute-values '{":c":{"S":"CUSTOMER#42"},
     ":a":{"S":"ORDER#2026-11"},":b":{"S":"ORDER#2026-12"}}'

# filter after reading (still billed for what was read)
  --filter-expression "#s = :p" --expression-attribute-names '{"#s":"status"}'

# next page with the CLI
  --max-items 10 --starting-token <NextToken from the last call>

# Scan: whole table; segments for parallel exports
aws dynamodb scan --table-name Shop --total-segments 4 --segment 0

# PartiQL: SQL-like, same rules underneath
aws dynamodb execute-statement --statement \
  "SELECT * FROM Shop WHERE PK = 'CUSTOMER#42' AND begins_with(SK, 'ORDER#')"

Code Explained

--no-scan-index-forward reverses sort-key order: newest dates first
ORDER#2026-12 sorts after every November key, so BETWEEN covers the month
The filter lines are added to a query like the one above
PartiQL with a key condition runs as a Query; without one, as a Scan

SQL Equivalent

  • Query ↔ SELECT … WHERE pk = ? using the index · Scan ↔ a full table scan
  • Filter expression ↔ WHERE on an unindexed column, applied after reading · See SQL 73

Across Engines

  • MongoDB any field can be filtered; indexes decide the cost
  • Redis key lookups, or SCAN through keys
  • Cassandra same rule: WHERE must name the partition key
  • Neo4j MATCH on an indexed property seeks; otherwise it scans the label

In Your Code

  • Node new QueryCommand({ TableName: "Shop", KeyConditionExpression: "PK = :c", ExpressionAttributeValues: { ":c": "CUSTOMER#42" }, ScanIndexForward: false })
  • Python table.query(KeyConditionExpression=Key("PK").eq("CUSTOMER#42") & Key("SK").begins_with("ORDER#"), ScanIndexForward=False)
  • Java table.query(QueryConditional.sortBeginsWith(Key.builder().partitionValue("CUSTOMER#42").sortValue("ORDER#").build()))

⚠ Common Mistakes

  • Using Scan + filter as a general query
  • Ignoring pagination and returning the first page only
  • Expecting Limit to mean "results after filtering"

✓ Tips & Best Practices

  • Design keys so every frequent read is a Query
  • Put dates in sort keys in ISO format so they sort correctly
  • Use parallel Scan or export to S3 for bulk jobs

Quick Summary

  • Query — partition key + sort condition
  • Scan — whole table, avoid
  • Filters don't save cost
  • Page on LastEvaluatedKey
