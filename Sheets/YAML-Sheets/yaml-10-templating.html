Sheet 10

Templating & Config Layering

${VAR:-default} · .env · compose override · Helm {{ .Values }} · -f values.yaml · Kustomize overlays

YAML Has No Variables

Plain YAML has no variables, includes, conditionals or loops — anchors are its only reuse feature. Every tool that needs more adds its own layer on top: variable substitution (Docker Compose), text templating that renders YAML from a template (Helm, Ansible/Jinja, GitHub Actions ${{ }}), file merging (Compose override files, Helm values files) and structural patching (Kustomize). Knowing which layer you are in tells you what syntax works and when it runs.

Which Approach?

  • Substitution — swap in environment values; no logic. Compose, many CI systems
  • Templating — full logic (if, range) but the template is not valid YAML until rendered. Helm, Ansible
  • Merging — later files override earlier ones key by key. Compose -f, Helm -f
  • Patching — plain YAML base + overlays; nothing to render. Kustomize
  • Inspect the final YAML: docker compose config, helm template, kubectl kustomize

Notes

${VAR:-default} — default when unset or empty; ${VAR-default} only when unset
${VAR:?msg} — stop with an error if missing; good for secrets
$$ — escapes a literal dollar sign in Compose
.env — read automatically for substitution; not passed into containers unless listed
compose.override.yaml — merged on top of compose.yaml unless you pass explicit -f files
{{- ... }} — the dash trims whitespace before the tag; vital for correct indentation
toYaml .Values.resources | nindent 12 — dump a values block as YAML, on a new line indented 12 spaces
patches — Kustomize merges each patch into the base resource with the same kind + name

Docker Compose — Substitution

# compose.yaml   (values come from the shell or a .env file)
services:
  api:
    image: "myorg/api:${TAG:-latest}"     # default if unset or empty
    ports: ["${PORT:-8080}:8080"]
    environment:
      DB_URL: "${DB_URL:?DB_URL is required}"   # error if missing
      PRICE: "$$5"                        # literal $ → "$5"

Helm — Templates + Values

# templates/deployment.yaml (Go template → YAML)
spec:
  replicas: {{ .Values.replicas | default 1 }}
  template:
    spec:
      containers:
        - name: api
          image: "{{ .Values.image.repo }}:{{ .Values.image.tag }}"
          resources: {{- toYaml .Values.resources | nindent 12 }}

Kustomize — Base + Overlay

# overlays/prod/kustomization.yaml
resources: [../../base]
namePrefix: prod-
images:
  - name: myorg/api
    newTag: "1.4.2"
patches:
  - path: replicas.yaml       # partial Deployment: spec.replicas: 5

Compose Substitution Forms

FormResult
${VAR}value of VAR (empty if unset)
${VAR:-x}x if unset or empty
${VAR-x}x only if unset
${VAR:?msg}error if unset or empty
${VAR:+x}x if VAR is set and non-empty

Layering Order (later wins)

ToolOrder
Composecompose.yaml → override → each -f in order
Helmchart values.yaml → each -f → --set

GitHub Actionsworkflow env → job env → step env

Common Mistakes

  • Starting a value with {{ unquoted (Ansible, Helm values) — YAML reads { as a flow mapping; write "{{ var }}"
  • Using ${VAR} in a Helm chart or {{ }} in Compose — each tool only understands its own syntax
  • Forgetting {{- / nindent in Helm — rendered YAML ends up mis-indented and fails to parse
  • Expecting arrays to merge across Compose or Helm files — lists are usually replaced, not appended

Tips

  • Run docker compose config / helm template in CI and diff the output — review the YAML that actually ships
  • Keep secrets out of committed YAML: ${VAR:?} in Compose, --set/external secrets in Helm
  • Prefer Kustomize overlays when you only need small per-environment changes — the base stays plain YAML
  • Use anchors (Sheet 05) for repetition inside one file before reaching for a template engine

Summary

  • ${VAR:-default} — Compose substitution with fallback
  • compose.override.yaml / -f — later files override earlier
  • {{ .Values.x }} + toYaml | nindent — Helm templates
  • kustomization.yaml — plain base + patch overlays
