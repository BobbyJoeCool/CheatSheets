YAML in the Wild

YAML is the dominant configuration language for modern DevOps, cloud infrastructure, and API tooling. Each platform has its own schema and required top-level keys — but they all share the same YAML syntax rules. Understanding the structural patterns of each platform helps you read unfamiliar configs quickly and write new ones without referring to documentation for every field. The code block shows minimal but complete examples of the most common platforms.

Platform Key Fields

  • GitHub Actions: on, jobs, steps, uses, run
  • Docker Compose: version, services, networks, volumes
  • Kubernetes: apiVersion, kind, metadata, spec
  • Ansible: hosts, become, tasks, vars, handlers
  • OpenAPI 3: openapi, info, paths, components
  • Helm values: plain YAML; referenced in templates with {{ .Values.key }}

Minimal Real-World Examples

# ── GitHub Actions workflow ───────────────────────────────────
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test

# ── Docker Compose service ────────────────────────────────────
services:
  web:
    image: nginx:alpine
    ports: ["80:80"]
    volumes: [./html:/usr/share/nginx/html:ro]
    depends_on: [api]
  api:
    build: ./api
    environment:
      DATABASE_URL: postgres://db:5432/app

# ── Kubernetes Deployment (excerpt) ──────────────────────────
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  labels: {app: my-app}
spec:
  replicas: 3
  selector:
    matchLabels: {app: my-app}
  template:
    spec:
      containers:
        - name: app
          image: my-app:latest
          ports: [{containerPort: 8080}]

# ── Ansible task ─────────────────────────────────────────────
- name: Install nginx
  hosts: webservers
  become: true
  tasks:
    - name: Install package
      ansible.builtin.apt:
        name: nginx
        state: present

Notes

on: [push, pull_request] — GitHub Actions: note on is also a YAML 1.1 boolean — quote it if your parser is strict: "on":
uses: actions/checkout@v4 — references a reusable action from GitHub Marketplace
depends_on — Docker Compose: ensures db starts before api, but does not wait for readiness
apiVersion: apps/v1 — Kubernetes: version determines which fields are available; always check the API docs
matchLabels — Kubernetes selector must exactly match the pod template's labels or pods won't be managed
become: true — Ansible: escalates to root (sudo); required for package installation
ansible.builtin.apt — fully-qualified module name; preferred in modern Ansible over bare apt:

Common Mistakes

  • Using on: unquoted in GitHub Actions with YAML 1.1 parsers — some tools parse it as boolean true
  • Kubernetes matchLabels not matching template.metadata.labels — deployment silently manages zero pods
  • Docker Compose depends_on only controls start order, not readiness — use healthchecks for true readiness gating
  • Ansible tasks list is a sequence — forgetting the leading - on each task causes a parse or runtime error

Tips

  • Use kubectl apply --dry-run=client -f manifest.yaml to validate Kubernetes YAML without deploying
  • Use docker compose config to validate and print the fully-merged Compose file before running
  • Use ansible-playbook --syntax-check playbook.yml to catch YAML and Ansible structural errors early

Summary

  • GitHub Actions: on · jobs · steps · uses · run
  • Docker Compose: services · image · ports · volumes
  • Kubernetes: apiVersion · kind · metadata · spec
  • Ansible: hosts · become · tasks (sequence of maps)
  • Each platform has a strict schema — validate before applying
