Sheet 51

Master / Transaction File Update

balanced-line algorithm · matching keys · adds / changes / deletes · HIGH-VALUES sentinel · old master → new master

Classic Sequential Update

The balanced-line algorithm updates a sorted master file with a sorted transaction file. Both files are read in key order; compare the keys and act: transaction key lower means an add, equal means a change or delete, master key lower means copy the master unchanged. Output is a new master file.

Key Points

  • Both files sorted on the same key
  • At end of file, move HIGH-VALUES to that file's key
  • Loop until both keys are HIGH-VALUES
  • Unmatched changes and duplicate adds go to an error report

Balanced-Line Loop

       0000-MAIN.
           OPEN INPUT OLD-MAST TRANS OUTPUT NEW-MAST ERR-RPT
           PERFORM 8100-READ-MAST
           PERFORM 8200-READ-TRAN
           PERFORM UNTIL WS-MAST-KEY = HIGH-VALUES
                     AND WS-TRAN-KEY = HIGH-VALUES
              EVALUATE TRUE
                 WHEN WS-TRAN-KEY < WS-MAST-KEY
                    PERFORM 2000-ADD           *> new account
                    PERFORM 8200-READ-TRAN
                 WHEN WS-TRAN-KEY = WS-MAST-KEY
                    PERFORM 3000-CHANGE-OR-DELETE
                    PERFORM 8200-READ-TRAN
                 WHEN OTHER
                    WRITE NEW-REC FROM OM-REC  *> unchanged
                    PERFORM 8100-READ-MAST
              END-EVALUATE
           END-PERFORM
           CLOSE OLD-MAST TRANS NEW-MAST ERR-RPT
           GOBACK.

       8100-READ-MAST.
           READ OLD-MAST
              AT END     MOVE HIGH-VALUES TO WS-MAST-KEY
              NOT AT END MOVE OM-ACCT     TO WS-MAST-KEY
           END-READ.

Code Explained

HIGH-VALUES sort after every real key, so the other file drains first
3000 applies a change to the master in memory, or flags a delete
Multiple transactions for one account are applied in turn
The new master is written only when the master record moves on (not shown)

Modern Equivalent

  • Python A database UPDATE/INSERT/DELETE per transaction, or a merge-join of two sorted iterators
  • Java JDBC batch upserts, or a two-pointer merge over sorted streams
  • JavaScript SQL upserts, or a two-pointer merge over sorted arrays

Prefer / Avoid

  • in-place REWRITE of a tape-era master → keep old/new masters for restart
  • magic 999999 end keys → HIGH-VALUES

Key Comparison

ConditionAction
TRAN < MASTAdd (or error if not an add)
TRAN = MASTChange / delete (or error if add)
TRAN > MASTCopy master to new master
Both HIGH-VALUESDone

Transaction Codes

CodeValid When
A (add)No matching master

D (delete)Master exists
InvalidWrite to error report

⚠ Common Mistakes

  • Unsorted transactions, which produce adds for existing accounts
  • Using numeric keys with HIGH-VALUES (use alphanumeric keys or 9s)
  • Writing the master once per transaction instead of once per account

✓ Tips & Best Practices

  • Sort transactions by key, then by transaction type
  • Keep old and new masters so a failed run can rerun from the old one
  • Print control totals: masters in/out, adds, changes, deletes, errors

Quick Summary

  • sorted master + sorted trans
  • compare keys — add / change / copy
  • HIGH-VALUES — end sentinel
  • new master — restartable output
