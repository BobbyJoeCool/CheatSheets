Testing & DevOps for COBOL

COBOL Check · IBM zUnit · test copybooks & stubs · COBOL in Git · Zowe CLI in CI · IBM Dependency Based Build (DBB)

Modern Practices for Old Code

COBOL can be unit tested, kept in Git and built in CI like any other code. COBOL Check (open source) and IBM zUnit test individual paragraphs, mocking files and calls. Zowe CLI and IBM DBB let pipelines upload source, compile on z/OS and run tests from GitHub Actions or Jenkins.

Key Points

  • COBOL Check inserts test code into a copy of the program
  • Mock file I/O and CALLs so tests do not need datasets
  • DBB builds only programs affected by a change (incl. copybooks)
  • Git branches replace "copy the PDS member" workflows

A COBOL Check Test Suite

      *> File: src/test/cobol/PAYCALC/PayCalc.cut
           TestSuite "Overtime calculation"

           TestCase "40 hours or less has no overtime"
           MOVE 38 TO WS-HOURS
           MOVE 20.00 TO WS-RATE
           PERFORM 2000-CALC-PAY
           Expect WS-OVERTIME-PAY TO BE 0
           Expect WS-GROSS-PAY TO BE 760.00

           TestCase "Hours over 40 paid at 1.5x"
           MOVE 45 TO WS-HOURS
           MOVE 20.00 TO WS-RATE
           PERFORM 2000-CALC-PAY
           Expect WS-OVERTIME-PAY TO BE 150.00

           TestCase "Read error is reported"
           MOCK READ EMP-FILE
              MOVE "30" TO WS-EMP-FS
           END-MOCK
           PERFORM 8000-READ-EMP
           Expect WS-ERROR-FLAG TO BE "Y"

Code Explained

Each TestCase sets fields, PERFORMs a paragraph, then checks results
MOCK replaces a READ so no dataset is needed
5 overtime hours × 20.00 × 1.5 = 150.00
Run with the cobolcheck script; it compiles with GnuCOBOL or on z/OS

Modern Equivalent

  • Python pytest: def test_overtime(): assert calc_pay(45, 20) == …
  • Java JUnit: @Test void overtime() { assertEquals(…) }
  • JavaScript Vitest/Jest: test("overtime", () => expect(…).toBe(…))

Prefer / Avoid

  • manual testing in a shared test region → unit tests in Git + CI
  • whole-library rebuilds → DBB impact builds

⚠ Common Mistakes

  • Paragraphs that do I/O and logic together, which are hard to test
  • Tests that depend on shared test datasets other people change
  • Keeping source only in PDS libraries with no history

✓ Tips & Best Practices

  • Split calculation paragraphs from I/O paragraphs
  • Start tests on the most-changed business rules
  • Run COBOL Check on GnuCOBOL in CI before touching z/OS

Quick Summary

  • COBOL Check / zUnit — unit tests
  • MOCK — fake I/O and CALLs
  • Zowe + DBB — CI on z/OS
  • Git — history and reviews
