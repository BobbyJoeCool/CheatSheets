Embedded SQL with DB2

EXEC SQL … END-EXEC · host variables :WS-NAME · SQLCA / SQLCODE · DECLARE CURSOR / OPEN / FETCH / CLOSE · DCLGEN · precompile & BIND

Talking to DB2 from COBOL

SQL statements sit inside EXEC SQL … END-EXEC blocks and use COBOL fields as host variables prefixed with a colon. The DB2 precompiler (or coprocessor) turns them into calls, and after each statement SQLCODE reports the result: 0 success, 100 not found, negative an error.

Key Points

  • INCLUDE SQLCA defines SQLCODE and related fields
  • DCLGEN generates host-variable layouts from a table
  • Multi-row results need a cursor
  • Programs are bound into a package/plan before they run

Under the Hood

  • The SQL coprocessor (SQL compiler option) replaces the separate precompile step
  • BIND stores the access path; the plan/package name is used at run time
  • Batch DB2 programs run under IKJEFT01 DSN RUN (see the JCL set)

Single Row and Cursor

           EXEC SQL INCLUDE SQLCA END-EXEC.
           EXEC SQL INCLUDE DCLCUST END-EXEC.     *> DCLGEN output
       01  WS-STATE           PIC XX VALUE "IA".

      *>   Single-row SELECT
           MOVE 104217 TO CUST-ID
           EXEC SQL
              SELECT NAME, BALANCE
                INTO :CUST-NAME, :CUST-BALANCE
                FROM CUSTOMER
               WHERE ID = :CUST-ID
           END-EXEC
           EVALUATE SQLCODE
              WHEN 0     DISPLAY CUST-NAME
              WHEN 100   DISPLAY "NOT FOUND"
              WHEN OTHER DISPLAY "SQL ERROR " SQLCODE
           END-EVALUATE

      *>   Cursor for many rows
           EXEC SQL DECLARE C1 CURSOR FOR
              SELECT ID, NAME FROM CUSTOMER
               WHERE STATE = :WS-STATE ORDER BY NAME
           END-EXEC
           EXEC SQL OPEN C1 END-EXEC
           PERFORM UNTIL SQLCODE NOT = 0
              EXEC SQL FETCH C1 INTO :CUST-ID, :CUST-NAME
              END-EXEC
              IF SQLCODE = 0 PERFORM 2000-PRINT END-IF
           END-PERFORM
           EXEC SQL CLOSE C1 END-EXEC

Code Explained

:CUST-ID is a COBOL field used inside SQL
SQLCODE 100 means no row (or no more rows for FETCH)
The cursor loop stops at 100 or any error
A SELECT INTO that finds two rows returns -811

Modern Equivalent

  • Python cur.execute("SELECT … WHERE id = ?", (cid,)); cur.fetchone()
  • Java PreparedStatement ps = conn.prepareStatement("… WHERE id = ?")
  • JavaScript await client.query("… WHERE id = $1", [cid]) (node-postgres)

Prefer / Avoid

  • ignoring negative SQLCODEs → check SQLCODE after every statement
  • SELECT * → list columns to match host variables

⚠ Common Mistakes

  • Nullable columns fetched without an indicator variable (-305)
  • SELECT INTO a query that can return several rows (-811)
  • Treating +100 as an error in a FETCH loop

✓ Tips & Best Practices

  • Use DCLGEN layouts so host variables match column types
  • Add indicator variables (:NAME :NAME-IND) for nullable columns
  • COMMIT at regular intervals in long batch updates

Quick Summary

  • EXEC SQL … END-EXEC
  • :host-var — COBOL field in SQL
  • SQLCODE — 0 / 100 / negative
