Sheet 52

Data Validation & Error Handling

NUMERIC checks · range checks with 88s · error / reject files · RETURN-CODE special register · ON EXCEPTION · control totals

Rejecting Bad Data Without Abending

Batch programs validate every input field before using it. Bad records go to a reject file with a reason code instead of stopping the run. At the end, control totals prove nothing was lost, and RETURN-CODE tells the JCL whether the step was clean, had warnings or failed.

Key Points

  • Check NUMERIC before any arithmetic on input fields
  • Use 88-levels for valid code lists and ranges
  • Write rejects with the original record plus a reason
  • Set RETURN-CODE: 0 clean, 4 rejects, 16 fatal

Validate, Reject, Report

       01  WS-REASON            PIC X(30).
       01  WS-COUNTS.
           05 WS-READ           PIC 9(7) VALUE 0.
           05 WS-GOOD           PIC 9(7) VALUE 0.
           05 WS-BAD            PIC 9(7) VALUE 0.

       2100-VALIDATE.
           MOVE SPACES TO WS-REASON
           EVALUATE TRUE
              WHEN IN-ACCT NOT NUMERIC
                 MOVE "ACCOUNT NOT NUMERIC" TO WS-REASON
              WHEN IN-AMT NOT NUMERIC
                 MOVE "AMOUNT NOT NUMERIC"  TO WS-REASON
              WHEN NOT VALID-TRAN-CODE
                 MOVE "BAD TRAN CODE"       TO WS-REASON
              WHEN IN-AMT > 50000
                 MOVE "AMOUNT OVER LIMIT"   TO WS-REASON
           END-EVALUATE
           IF WS-REASON = SPACES
              ADD 1 TO WS-GOOD
           ELSE
              ADD 1 TO WS-BAD
              STRING WS-REASON DELIMITED BY SIZE
                     IN-REC    DELIMITED BY SIZE
                INTO REJECT-REC
              WRITE REJECT-REC
           END-IF.

       9000-TERM.
           DISPLAY "READ " WS-READ " GOOD " WS-GOOD " BAD " WS-BAD
           EVALUATE TRUE
              WHEN WS-READ NOT = WS-GOOD + WS-BAD
                 MOVE 16 TO RETURN-CODE
              WHEN WS-BAD > 0
                 MOVE 4 TO RETURN-CODE
           END-EVALUATE.

Code Explained

EVALUATE stops at the first failing check: one reason per record
The reject record keeps the reason and the original data
Read = good + bad proves every record was handled
RC 4 lets the next step run but flags the rejects

Modern Equivalent

  • Python Pydantic or manual checks; append bad rows to a rejects list or file
  • Java Bean Validation (@NotNull, @Max) and a reject writer
  • JavaScript Zod or Joi schemas; safeParse and log failures

Prefer / Avoid

  • abending on the first bad record → reject file + RC 4
  • no control totals → print counts and check they balance

Return Codes

RCMeaning
0All records good
4Some rejects
8Many rejects / threshold
16Totals off or fatal error

⚠ Common Mistakes

  • Doing arithmetic before validation and abending with S0C7
  • Rejects with no reason, so nobody can fix the data
  • Never comparing record counts at the end

✓ Tips & Best Practices

  • Use FUNCTION TEST-DATE-YYYYMMDD (returns 0 if valid) for dates
  • Add a reject threshold that fails the run if too many records are bad
  • Display control totals so they show in the job log

Quick Summary

  • validate before use
  • reject file — record + reason
  • control totals — read = good + bad
  • RETURN-CODE — 0 / 4 / 16
