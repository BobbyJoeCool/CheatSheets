Annotating Your Code

Type hints annotate parameters, return values, and variables with expected types. Python itself ignores them at runtime; tools such as mypy and pyright, along with editors, use them to catch bugs before you run the code. Modern syntax uses built-in generics like list[int] (3.9+), X | None (3.10+), and the type statement and [T] generics (3.12+).

Notes

  • Hints don't convert or validate values
  • Optional[X] means X | None, not "optional argument"
  • from __future__ import annotations defers evaluation
  • Use Any sparingly; it switches checking off
  • Pydantic and dataclasses can use hints at runtime

Hints in Practice

def greet(name: str, times: int = 1) -> str:
    return f"Hi {name}! " * times
scores: list[int] = [90, 85]           # built-in generics (3.9+)
lookup: dict[str, float] = {}
pair: tuple[int, str] = (1, "a")
maybe: int | None = None               # union syntax (3.10+)
from typing import Callable, TypedDict, Literal
def apply(f: Callable[[int], int], x: int) -> int:
    return f(x)
class Movie(TypedDict):
    title: str
    year: int
mode: Literal["r", "w"] = "r"
def first[T](items: list[T]) -> T:     # generic function (3.12+)
    return items[0]
type Vector = list[float]              # type alias (3.12+)
greet(42)                              # runs anyway; mypy reports it

⚠ Common Mistakes

  • Expecting hints to reject bad values at runtime — they don't
  • def f(x: list = []) — hints don't fix mutable defaults
  • Overusing Any — hides the bugs hints are meant to catch
  • Using List, Dict from typing in new code — use list, dict

✓ Tips & Best Practices

  • Annotate public functions first; locals are usually inferred
  • Run mypy or pyright in CI
  • Accept abstract types (Iterable), return concrete ones (list)
  • Use TypedDict or dataclasses for structured data
