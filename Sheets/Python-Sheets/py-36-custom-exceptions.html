Defining Your Own Errors

Create custom exceptions by subclassing Exception (never BaseException). A small hierarchy with one base error for your app or package lets callers catch all of your errors at once, or a specific one. Add attributes to carry structured details, and call super().__init__() with a readable message.

Notes

  • Name them with an Error suffix
  • An empty body (pass or a docstring) is often enough
  • Subclass a built-in when the meaning matches
  • Order except from specific to general

A Small Exception Hierarchy

class AppError(Exception):
    """Base class for this app's errors."""

class ValidationError(AppError, ValueError):
    def __init__(self, field, message):
        super().__init__(f"{field}: {message}")
        self.field = field

def save(user):
    if "@" not in user["email"]:
        raise ValidationError("email", "missing @")

try:
    save({"email": "ana.example.com"})
except ValidationError as e:
    print(e, "|", e.field)     # email: missing @ | email
except AppError:
    print("other app error")

Code Explained

AppError — one base to catch everything from your code
(AppError, ValueError) — also caught by except ValueError
super().__init__(msg) — sets str(e) and e.args
self.field — structured data for the handler

⚠ Common Mistakes

  • Subclassing BaseException — escapes except Exception
  • Skipping super().__init__() — str(e) and e.args come out empty or odd
  • Catching AppError before ValidationError — the specific handler never runs
  • Creating a class for every possible failure — keep the hierarchy small

✓ Tips & Best Practices

  • Expose your errors at the package top level for easy import
  • Document which exceptions each public function raises
  • Wrap third-party errors in your own: raise AppError(...) from e
  • Keep messages human-readable; put data in attributes
