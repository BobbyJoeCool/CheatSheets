Retry & Resilience

@EnableResilientMethods · @Retryable · maxRetries · backoff · @ConcurrencyLimit · RetryTemplate

Retries and Concurrency Limits

Spring Framework 7 brings resilience into the core: @Retryable re-runs a method when it throws, with configurable back-off and jitter, and @ConcurrencyLimit caps how many callers run a method at once. Turn both on with @EnableResilientMethods. For code-level control, RetryTemplate with a RetryPolicy does the same programmatically.

Notes

  • Annotations live in org.springframework.resilience
  • Defaults: any exception, maxRetries = 3, 1 s delay
  • Total attempts = 1 + maxRetries
  • Replaces the separate Spring Retry project for most uses

Annotations

@Configuration @EnableResilientMethods class ResilienceConfig { }

@Service
class InventoryClient {

    @Retryable(includes = ResourceAccessException.class,
               maxRetries = 4, delay = 200, multiplier = 2,
               maxDelay = 2000, jitter = 50)
    public Stock check(String sku) {
        return http.get().uri("/stock/{sku}", sku).retrieve().body(Stock.class);
    }

    @ConcurrencyLimit(10)              // at most 10 calls in flight
    public Report heavyReport() { … }
}

RetryTemplate

var policy = RetryPolicy.builder()
    .includes(IOException.class)
    .maxRetries(3)
    .delay(Duration.ofMillis(100))
    .multiplier(2)
    .build();

var template = new RetryTemplate(policy);
String body = template.invoke(() -> download(url));   // rethrows last error

Code Explained

Delays grow 200, 400, 800, 1600 ms, capped at 2 s
Only ResourceAccessException (I/O errors) is retried
@ConcurrencyLimit makes extra callers wait
execute() instead of invoke() throws RetryException with all attempts

⚠ Common Mistakes

  • Retrying everything, including bad requests that will never succeed
  • Retrying non-idempotent operations and charging a card twice
  • Calling the @Retryable method from the same class; no retries happen

✓ Tips & Best Practices

  • Always set timeouts before adding retries
  • Add jitter so many clients don't retry in lockstep
  • Use @ConcurrencyLimit to protect downstream services on virtual threads
