Repositories

Declare an interface extending JpaRepository<Entity, IdType> and Spring Data generates the implementation at startup: CRUD, paging, sorting and flushing with no code. Add your own query methods by name (Sheet 39) or with @Query (Sheet 40). Boot finds repositories under the main class's package automatically.

Notes

  • Repository methods are @Transactional (reads are read-only)
  • save() inserts when id is null, otherwise merges
  • findById() returns Optional<T>
  • List* interfaces return List instead of Iterable

Declaring and Using a Repository

public interface CustomerRepository extends JpaRepository<Customer, Long> {
    Optional<Customer> findByEmail(String email);      // derived query
}

@Service
class CustomerService {
    private final CustomerRepository repo;
    CustomerService(CustomerRepository repo) { this.repo = repo; }

    Customer register(String name, String email) {
        return repo.save(new Customer(name, email));   // INSERT, id set
    }

    Customer get(long id) {
        return repo.findById(id)
            .orElseThrow(() -> new CustomerNotFound(id));
    }

    void cleanup(List<Long> ids) {
        repo.deleteAllByIdInBatch(ids);                // one DELETE
    }
}

Code Explained

No implementation class: Spring Data creates a proxy
save() returns the managed entity; use the returned value
orElseThrow turns a missing row into your exception
…InBatch methods skip loading entities first

⚠ Common Mistakes

  • Ignoring the return value of save() for detached entities
  • findAll() on a big table; use paging (Sheet 41)
  • Calling save() after changing a managed entity; dirty checking already saves it

✓ Tips & Best Practices

  • Expose only the methods you need by extending Repository directly
  • Use getReferenceById to set a FK without loading the parent
  • Put business rules in services, not repository default methods
