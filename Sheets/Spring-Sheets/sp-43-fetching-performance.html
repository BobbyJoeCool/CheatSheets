Loading Data Efficiently

Lazy relations load on first access, which triggers the N+1 problem: one query for the list plus one per row. Accessing them after the transaction ends throws LazyInitializationException. Fix both by fetching what you need up front with JOIN FETCH, an @EntityGraph, or a projection, and watch the SQL Hibernate generates.

Notes

  • Boot's open-in-view is on by default and hides lazy errors
  • Set spring.jpa.open-in-view=false to catch them early
  • Batch fetching loads lazy collections in groups
  • Count queries with show-sql or Hibernate statistics

Fixing N+1

// ❌ N+1: 1 query for orders + 1 per order for its customer
repo.findAll().forEach(o -> System.out.println(o.getCustomer().getName()));

interface OrderRepository extends JpaRepository<Order, Long> {

    @Query("select o from Order o join fetch o.customer where o.status = :s")
    List<Order> withCustomer(Status s);                 // ✅ one query

    @EntityGraph(attributePaths = {"customer", "lines"})
    List<Order> findByStatus(Status s);                 // ✅ graph fetch

    @EntityGraph(attributePaths = "lines")
    Optional<Order> findWithLinesById(long id);
}

Diagnose and Tune

spring.jpa:
  open-in-view: false
  show-sql: true                           # print SQL (dev only)
  properties.hibernate:
    format_sql: true
    default_batch_fetch_size: 50           # IN (…) for lazy loads
    generate_statistics: true

Code Explained

join fetch loads orders and customers in a single SELECT
@EntityGraph does the same without writing JPQL
Fetching two collections at once causes a cartesian product
default_batch_fetch_size turns N queries into N/50

⚠ Common Mistakes

  • Switching relations to EAGER to silence LazyInitializationException
  • Fetch-joining two List collections → MultipleBagFetchException
  • Leaving open-in-view on so views fire queries during rendering

✓ Tips & Best Practices

  • Assert query counts in tests (e.g. Hibernate statistics)
  • Use Set for one of two collections you must fetch together
  • Fetch for the use case: different repository methods per screen

Quick Summary

  • N+1: one query per row
  • join fetch / @EntityGraph
  • open-in-view=false
  • default_batch_fetch_size
