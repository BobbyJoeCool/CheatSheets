Actions: Environments & Approvals

environment: · required reviewers · wait timer · deployment branches · environment secrets

Gates in Front of Deploys

An environment (Settings → Environments) represents a deploy target like staging or production. A job that names it with environment: must pass the environment's protection rules before it starts: required reviewers, a wait timer, or allowed branches/tags. It also gets that environment's own secrets and variables, and each run is recorded in the repo's deployment history.

Environment Facts

  • Referencing a missing environment creates it (no rules)
  • Up to 6 required reviewers; one approval is enough
  • Wait timer: 1–43,200 minutes (30 days)
  • Approval requests expire after 30 days

Staging, Then Approved Production

jobs:
  staging:
    runs-on: ubuntu-latest
    environment:
      name: staging
      url: https://staging.example.com
    steps:
      - run: ./deploy.sh staging
        env: { TOKEN: "${{ secrets.DEPLOY_TOKEN }}" }  # staging's
  production:
    needs: staging
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment:
      name: production                 # reviewers must approve
      url: ${{ steps.deploy.outputs.url }}
    steps:
      - id: deploy
        run: |
          ./deploy.sh prod
          echo "url=https://example.com" >> "$GITHUB_OUTPUT"
        env: { TOKEN: "${{ secrets.DEPLOY_TOKEN }}" }  # production's

Code Explained

environment.name — selects rules, secrets, variables
url — link shown on the run graph and deployments page
same secret name — different value per environment
needs: staging — prod waits for staging, then for approval

In the Logs

  • Waiting for review: production needs approval to start deploying changes. — a reviewer clicks Review deployments
  • Branch "feature/x" is not allowed to deploy to production due to environment protection rules. — deployment branch policy

Protection Rules

RuleEffect
Required reviewerspeople/teams approve each deploy
Prevent self-reviewthe person who triggered can't approve
Wait timerdelay before the job starts
Deployment branches and tagsonly matching refs may deploy
Custom rules (Apps)external checks, e.g. change windows

⚠ Common Mistakes

  • Typo in environment: prodution: GitHub silently creates a new, unprotected environment
  • Keeping prod secrets at repo level: any workflow can read them without approval
  • Expecting approvals to pause mid-job: the whole job waits before its first step

✓ Tips & Best Practices

  • Turn on Prevent self-review so deploys need a second person
  • Restrict production to main and v* tags with deployment branch rules
  • Pair environments with job-level concurrency to serialize deploys (Sheet 58)

Quick Summary
