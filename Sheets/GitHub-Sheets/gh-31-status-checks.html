Green Checks Before Merging

Every commit can carry status checks: check runs from GitHub Actions and Apps (with logs and annotations) or simple commit statuses from external CI. Rulesets can mark checks required, so a PR can't merge until those exact check names pass. A required check that never reports leaves the PR Expected — Waiting for status forever.

Check Facts

  • Actions check names are the job name (with matrix values)
  • Skipped jobs count as passing for required checks
  • Pick the expected source app to block spoofed statuses

Who Can Do This

  • Role: Admin (require checks) · Write (re-run)
  • Plan: Free for public; Pro/Team+ for private
  • Repos: public and private (plan-dependent)

Require CI to Pass

  1. Run CI on a PR once so the check names exist
  2. Ruleset → Require status checks to pass
  3. Add checks: search the job names
  4. Optionally set the expected source (GitHub Actions)
  5. Watch the merge box: all required checks must be ✓

Automate It

One stable required check for many jobs
all-checks:
  if: always()
  needs: [lint, test, build]
  runs-on: ubuntu-latest
  steps:
    - if: contains(needs.*.result, 'failure')   # or 'cancelled'
      run: exit 1

Naming Pitfalls

ChangeResult
Rename a jobold required name never reports
Add a matrix valuenew check names appear
Path filter skips workflowcheck missing → stuck
Job skipped by if:reported as skipped (passes)

⚠ Common Mistakes

  • Requiring every matrix job by name: any matrix change blocks all PRs
  • Path filters on workflows that hold required checks
  • Requiring a check before it has ever run: it can't be found in the picker

✓ Tips & Best Practices

  • Require one summary job (all-checks) instead of many
  • Use Re-run failed jobs for flaky checks, then fix the flake
  • Third-party CI can post statuses via the Statuses API

Quick Summary

  • check runs / statuses — results per commit
  • required checks — merge gate by name
  • skipped = pass, missing = stuck
  • summary job — one stable required check
