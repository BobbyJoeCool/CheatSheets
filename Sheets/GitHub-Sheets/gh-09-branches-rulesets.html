Guarding Important Branches

Rulesets (Settings → Rules) protect branches and tags: require pull requests and approvals, require status checks, block force pushes and deletions, require signed commits or linear history. Several rulesets can apply at once and their rules stack. A bypass list lets specific roles, teams or apps skip them. Classic branch protection rules still work, but rulesets are the newer, more flexible option.

Ruleset Facts

  • Status: Active, Evaluate (log only, Enterprise) or Disabled
  • Org rulesets can target many repos by name or property
  • Anyone with Read can see the rules that apply to a branch

Who Can Do This

  • Role: Admin (repo) · Org owner (org rulesets)
  • Plan: Free for public; Pro/Team/Enterprise for private
  • Repos: public and private (plan-dependent)

Protect main With a Ruleset

  1. Settings → Rules → Rulesets → New branch ruleset
  2. Name it, set Enforcement: Active
  3. Target branches → Include default branch
  4. Enable Require a pull request (1+ approvals, dismiss stale)
  5. Enable Require status checks and add your CI job names
  6. Keep Block force pushes + Restrict deletions on; add a bypass only if needed

Automate It

Export / import rulesets as JSON
{ "name": "protect-main", "target": "branch",
  "enforcement": "active",
  "conditions": { "ref_name": {
    "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "rules": [ { "type": "deletion" },
    { "type": "non_fast_forward" },
    { "type": "pull_request", "parameters": {
        "required_approving_review_count": 1 } } ] }

⚠ Common Mistakes

  • Requiring a status check name that never runs on PRs: every PR stays blocked
  • Adding yourself to the bypass list 'just in case': rules stop meaning anything
  • Mixing classic rules and rulesets without checking both: both apply

✓ Tips & Best Practices

  • Use ~DEFAULT_BRANCH so the ruleset follows a branch rename
  • Add a tag ruleset on v* to stop tag moves and deletions
  • Check Rules → Insights to see what a new ruleset blocked

Quick Summary
