Pull Request Basics

Proposing Changes

A pull request asks to merge a head branch into a base branch. It bundles the diff, a description, discussion, reviews and status checks in one place, and it updates automatically as you push more commits. Open it as a draft to share early work without requesting reviews; mark it Ready for review when it's done.

PR Facts

  • PRs can come from a branch in the same repo or a fork
  • Drafts can't be merged and don't notify code owners
  • Changing the base branch re-targets the diff

Who Can Do This

  • Role: Read (open from a fork) · Write (branch in repo, merge)
  • Plan: Free (drafts on private: Pro/Team+)
  • Repos: public and private

Open a Good PR

  1. Push a branch; click Compare & pull request in the banner
  2. Check base ← compare are right
  3. Title says what changes; body says why + how to test
  4. Add Fixes #N, reviewers, labels, project
  5. Create draft pull request for early feedback
  6. Self-review Files changed before marking ready

Automate It

Open a PR from a script (REST)
curl -X POST -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/O/R/pulls \
  -d '{"title":"Bump deps","head":"deps/bump","base":"main","draft":true}'

⚠ Common Mistakes

  • Wrong base branch (e.g. a fork's main instead of upstream's)
  • Giant PRs mixing refactors and features: reviews get skimmed
  • Opening a PR with failing tests and asking for review anyway

✓ Tips & Best Practices

  • Keep PRs under ~400 changed lines when you can
  • Use drafts to run CI before you ask anyone to look
  • Add ?expand=1 to a compare URL to open the PR form directly
