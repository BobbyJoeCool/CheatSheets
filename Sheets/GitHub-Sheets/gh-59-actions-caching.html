Sheet 59

Actions: Caching Dependencies

actions/cache · key · restore-keys · hashFiles · setup-node cache · cache-hit

Skip Reinstalling Every Time

actions/cache saves a folder at the end of a job and restores it at the start of the next run when the key matches. Build the key from a hash of your lockfile so it changes only when dependencies change; restore-keys give partial matches to fall back on. Most setup-* actions have a built-in cache: input that does all of this for you.

Cache Rules

  • Caches are immutable: an exact key hit is never re-saved
  • Scope: a branch can read its own caches and the default branch's
  • Unused caches are evicted after 7 days, oldest first over the repo limit
  • Repo limit defaults to 10 GB; admins can raise it

Explicit Cache and Built-In Cache

steps:
  - uses: actions/checkout@v6

  # Easiest: built into setup-node (also setup-python, -java, -go)
  - uses: actions/setup-node@v6
    with:
      node-version: 22
      cache: npm

  # Full control with actions/cache
  - id: cache
    uses: actions/cache@v5
    with:
      path: ~/.cache/pip
      key: ${{ runner.os }}-py-${{ hashFiles('requirements*.txt') }}
      restore-keys: |
        ${{ runner.os }}-py-
  - if: steps.cache.outputs.cache-hit != 'true'
    run: pip install -r requirements.txt

Code Explained

cache: npm — caches ~/.npm, keyed on package-lock.json
key — OS + lockfile hash: exact match restores
restore-keys — prefix match: newest partial cache
cache-hit — 'true' only on an exact key hit

Security Check

  • Risk: cache poisoning: a PR job that can write a cache your main-branch release later restores can slip in modified dependencies.
  • Fix: never restore caches in release/publish jobs; build those clean, or use actions/cache/restore only.

In the Logs

  • Cache not found for input keys: Linux-py-… — first run or a new lockfile; normal
  • Cache saved with key: … in the Post step / Cache hit occurred on the primary key …, not saving cache — expected

⚠ Common Mistakes

  • Caching node_modules across OS or Node versions: native modules break; cache ~/.npm instead
  • A key without a hash (npm-cache): it's saved once and never updated
  • Expecting a feature branch to see another feature branch's cache: it can't

✓ Tips & Best Practices

  • Put runner.os first in every key; caches aren't portable across OSes
  • Use the setup action's cache: input before writing your own actions/cache step
  • Purge a bad cache: Actions tab → Caches, or gh cache delete <key>

Quick Summary

  • actions/cache — restore + save a folder
  • key with hashFiles — invalidates on lockfile change
  • restore-keys — partial fallback
  • setup-* cache: — built-in shortcut
