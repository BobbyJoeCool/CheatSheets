Repository Security Advisories

draft advisory · private fork · request CVE · publish · GitHub Advisory Database · GHSA IDs · credit

Disclosing Your Own Vulnerabilities

When someone reports a vulnerability in your project, a repository security advisory gives you a private workspace: discuss it with the reporter, fix it in a temporary private fork, request a CVE (GitHub is a CVE Numbering Authority) and publish the advisory with the fix. Published advisories get a GHSA ID, enter the GitHub Advisory Database and trigger Dependabot alerts for everyone using the affected versions.

Facts

  • Private vulnerability reporting lets anyone submit privately
  • Drafts are visible only to admins and invited collaborators
  • Credit reporters on the published advisory

Who Can Do This

  • Role: Admin or security manager (create, publish) · anyone (report privately)
  • Plan: Free
  • Repos: public repos (drafts also on private)

Handle a Report

  1. Report arrives via Security → Advisories (private reporting)
  2. Accept it as a draft advisory; invite collaborators
  3. Start a temporary private fork; fix and review there
  4. Fill in ecosystem, package, affected and patched versions, severity
  5. Request CVE, merge the fix, release the patched version
  6. Publish advisory; credit the reporter

⚠ Common Mistakes

  • Fixing in a public PR before the release: you disclose the bug to attackers
  • Wrong affected-version ranges: Dependabot alerts miss users or spam safe ones
  • Publishing before the patched version is on the registry

✓ Tips & Best Practices

  • Turn on private vulnerability reporting for every public repo
  • Use the private fork's PR to get CI and review without leaking
  • Link the advisory in release notes once published

Quick Summary

  • draft advisory — private workspace
  • private fork — fix without disclosure
  • CVE + GHSA — identifiers
  • publish — alerts everyone affected
