100 MB file limit · Git LFS on GitHub · LFS quotas · archive (read-only) · rename / redirects · transfer · delete

Big Files and Repo Lifecycle

GitHub blocks files larger than 100 MB and warns above 50 MB; store large binaries with Git LFS or as release assets instead. When a project ends, archive it: the repo becomes read-only but stays visible. You can rename a repo (old URLs redirect), transfer it to another user or org (issues, stars and redirects come along) or delete it.

Limits

  • Keep repos under about 1 GB; under 5 GB is strongly recommended
  • Web uploads are limited to 25 MB per file
  • LFS storage and bandwidth count against your plan's quota

Who Can Do This

  • Role: Admin (archive, rename, transfer, delete)
  • Plan: Free
  • Repos: public and private

Archive or Transfer a Repo

  1. Add a note to the README saying why it's archived and where to go
  2. Settings → Danger Zone → Archive this repository
  3. To move: Danger Zone → Transfer, type the new owner
  4. Receiving org must allow the transfer; you may need repo creation rights
  5. Update remotes: git remote set-url origin <new-url> (redirects cover you meanwhile)
  6. Unarchive any time from the same menu

⚠ Common Mistakes

  • Committing a large file, then deleting it: it's still in history and still blocks the push
  • Creating a new repo with the old name after a rename: redirects stop working
  • Deleting instead of archiving: links, stars and issues are lost

✓ Tips & Best Practices

  • Use git filter-repo to purge big files from history (Git CLI set)
  • Put datasets and binaries in release assets or object storage
  • Archived repos still show on your profile; unpin them

Quick Summary

  • 100 MB — hard file limit; use LFS
  • archive — read-only, keeps everything
  • rename / transfer — redirects follow
  • delete — last resort
