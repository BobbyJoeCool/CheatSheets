Proving Where Builds Came From

Artifact attestations are signed statements, made in Actions, that a file or image was built by a specific workflow from a specific commit (SLSA build provenance). Consumers verify them before running the artifact. Combined with immutable releases, pinned actions and signed commits, they make the path from source to user tamper-evident.

Facts

  • Attestations are signed with Sigstore using the job's OIDC token
  • Public repos use the public Sigstore instance; private use GitHub's
  • Reusable build workflows help reach SLSA Build Level 3

Who Can Do This

  • Role: Write (run workflow) · anyone (verify public)
  • Plan: Free for public; Enterprise for private
  • Repos: public and private (plan-dependent)

Attest a Build, Then Verify It

# .github/workflows/release.yml (excerpt)
permissions:
  contents: write
  id-token: write          # sign with OIDC
  attestations: write      # store the attestation
steps:
  - uses: actions/checkout@v6
  - run: make dist         # produces dist/app.tar.gz
  - uses: actions/attest-build-provenance@v2
    with:
      subject-path: dist/app.tar.gz

# Consumer side (any machine with gh):
#   gh attestation verify app.tar.gz --repo octo-org/app
# Container images: subject-name + subject-digest instead

Code Explained

id-token: write — OIDC token used to sign
attestations: write — save it to the repo
subject-path — file(s) to attest (globs allowed)
gh attestation verify — checks signature + repo

LevelMeans
L1provenance exists
L2signed provenance from a hosted builder
L3isolated, hardened build (reusable workflow)

⚠ Common Mistakes

  • Attesting but never verifying: nobody checks, nothing is gained
  • Missing id-token: write: the signing step fails
  • Re-uploading release assets after attesting: hashes no longer match

✓ Tips & Best Practices

  • Verify attestations in your deploy job before shipping
  • Turn on immutable releases so assets can't be swapped later
  • Attest SBOMs too with actions/attest-sbom
