Merge Queues

require merge queue · merge_group event · build concurrency · merge limits · jump the queue · removed from queue

Merging Busy Branches Safely

On a busy branch, PRs that pass CI separately can break when combined. A merge queue fixes this: instead of merging, you add the PR to the queue; GitHub creates a temporary branch with the PR on top of the latest base plus PRs ahead of it, runs required checks on that, and merges only if they pass. CI must also run on the merge_group event.

Queue Facts

  • Enabled with the Require merge queue ruleset rule
  • Failed groups are removed; the rest re-run
  • Merge queues on private repos need Enterprise Cloud

Who Can Do This

  • Role: Admin (enable) · Write (add to queue)
  • Plan: Free for public org repos; Enterprise for private
  • Repos: org-owned repos

Turn On a Merge Queue

  1. Add merge_group to CI's on: (see box)
  2. Ruleset → Require merge queue
  3. Pick merge method, build concurrency, min/max group size
  4. Set Only merge non-failing pull requests
  5. On a PR: Merge when ready adds it to the queue

Automate It

CI must listen to merge_group
on:
  pull_request:
  merge_group:            # runs on the queue's temp branch

⚠ Common Mistakes

  • Turning on the queue before CI handles merge_group: every PR gets stuck
  • Path-filtered required workflows: they skip on merge_group and never report
  • Huge group sizes: one failure ejects and re-tests many PRs

✓ Tips & Best Practices

  • Start with build concurrency 5 and max group size 5; tune from there
  • Keep queue CI fast: run the slowest suites only on merge_group
  • Queues mostly pay off when several PRs merge per hour

Quick Summary

  • merge queue — test PRs on latest base
  • merge_group — required trigger
  • group size / concurrency — throughput
  • failed group — PR removed, others retried
