Actions: Push & Pull Request Triggers

push · pull_request · branches · tags · paths · types · pull_request_target

The Two Triggers You Use Most

push fires when commits or tags land on a branch. pull_request fires on PR activity and runs against a merge commit of the PR head into the base, so you test what would actually land. Both accept filters: branches, tags and paths (with -ignore variants) use glob patterns; types picks which PR activities count.

Filter Rules

  • Inside one event, branches and paths must both match
  • pull_request default types: opened, synchronize, reopened
  • branches on pull_request filters the base (target) branch, not the head
  • PRs from forks get a read-only token and no secrets

Filters in Action

on:
  push:
    branches:
      - main
      - "release/**"          # release/1.0, release/2.x/hotfix
      - "!release/**-alpha"   # ...but not these
    tags: ["v*"]              # v1.0.0, v2-beta
    paths-ignore: ["**.md", "docs/**"]
  pull_request:
    branches: [main]          # PRs that TARGET main
    types: [opened, synchronize, reopened, ready_for_review]
    paths: ["src/**", "package*.json"]
jobs:
  test:
    if: github.event.pull_request.draft != true
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - run: npm ci && npm test

Code Explained

"release/**" — ** matches across /; * stops at /
"!..." — exclude; order matters, later patterns win
tags: — with only tags, branch pushes don't trigger
paths-ignore — doc-only pushes skip CI
ready_for_review — run when a draft PR is marked ready
if: ...draft != true — skip drafts at job level

Security Check

  • Risk: pull_request_target runs in the base repo's context with secrets and a write token. Checking out and running the PR's code there lets a fork steal secrets.
  • Fix: use pull_request for building and testing untrusted code; keep pull_request_target for labeling or commenting only, and never check out github.event.pull_request.head.sha in it.

Common pull_request Types

⚠ Common Mistakes

  • Expecting branches: under pull_request to match the PR's source branch: it matches the target
  • Adding tags: and losing branch builds: once tags or branches is set, only the listed refs fire
  • Path filters on required checks: a skipped workflow leaves the check Pending forever, blocking merges

✓ Tips & Best Practices

  • For required checks with path filters, filter inside the job (e.g. dorny/paths-filter) so the check still reports
  • Use closed + if: github.event.pull_request.merged for post-merge actions on PRs
  • Pushes of more than 1,000 commits or very large diffs may skip path filtering and always run

Quick Summary

  • push — commits/tags; filter branches, tags, paths
  • pull_request — runs on the merge commit; read-only for forks
  • types: — which PR activities trigger
  • pull_request_target — base context, secrets: handle with care
