Conflicts & Updating Branches

Update branch (merge / rebase) · require up-to-date · web conflict editor · when to resolve locally · always suggest updating

Keeping PRs Current

When the base branch moves on, a PR can fall behind or conflict. Update branch merges (or rebases) the latest base into the PR from the browser. Simple conflicts can be fixed in the web conflict editor; complex ones should be resolved locally. A ruleset can require branches to be up to date before merging.

Facts

  • The web editor can't resolve conflicts in binary or very large files
  • Update with rebase rewrites the PR's commits (force-push)
  • Settings → Always suggest updating pull request branches

Who Can Do This

  • Role: Write (to the PR branch)
  • Plan: Free
  • Repos: public and private

Resolve a Conflict on GitHub

  1. Merge box → Resolve conflicts
  2. Edit between <<<<<<<, =======, >>>>>>>; delete the markers
  3. Mark as resolved for each file
  4. Commit merge to the PR branch
  5. Re-run checks and re-request review if logic changed
  6. Too complex? Resolve locally (Git CLI set) and push

Automate It

Update a PR branch (REST)
curl -X PUT -H "Authorization: Bearer $TOKEN" \

Renames / binary fileslocal

⚠ Common Mistakes

  • Hand-merging lockfiles: regenerate them (npm install) instead
  • Clicking Update with rebase while a teammate has the branch checked out
  • Leaving conflict markers in a file because the commit button worked

✓ Tips & Best Practices

  • Require up-to-date branches only if you don't use a merge queue
  • Small, short-lived PRs rarely conflict
  • Use Update branch before a long CI run so results reflect current base

Quick Summary

  • Update branch — bring base into the PR
  • web editor — simple conflicts
  • local — lockfiles, binaries, big conflicts
  • up-to-date rule or queue — keep main green
