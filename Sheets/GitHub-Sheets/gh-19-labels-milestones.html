Organizing Issues and PRs

Labels are colored tags shared by issues and PRs (bug, needs-triage, area:api). Every repo starts with a default set, and orgs can set their own defaults. Milestones group issues and PRs toward a goal or date and show percent complete. Assignees say who owns the work. All three power search filters and project views.

Label Tips

  • Use prefixes for families: area:, priority:, status:
  • good first issue and help wanted are surfaced to newcomers
  • Milestones are per repo; use Projects for cross-repo plans

Who Can Do This

  • Role: Triage (apply) · Write (create labels, milestones)
  • Plan: Free
  • Repos: public and private

Set Up a Label Scheme

  1. Issues → Labels → New label: name, description, color
  2. Delete or rename defaults you won't use
  3. Milestones → New milestone: title, due date, description
  4. Bulk-edit: tick issues in the list → Label / Milestone / Assign
  5. Org defaults: Org Settings → Repository defaults → Labels

Automate It

Label new issues automatically
on: { issues: { types: [opened] } }
# step:
- uses: actions/github-script@v8
  with:
    script: |
      await github.rest.issues.addLabels({ ...context.repo,
        issue_number: context.issue.number, labels: ["needs-triage"] });

⚠ Common Mistakes

  • Dozens of overlapping labels: nobody applies them consistently
  • Using labels for status *and* project columns: two sources of truth
  • Milestones without due dates: the progress bar means nothing

✓ Tips & Best Practices

  • Add label descriptions; they show on hover and help contributors
  • Use labels in .github/release.yml to sort release notes (Sheet 10)
  • Prefer issue types (Sheet 21) over bug/feature labels in orgs

Quick Summary

  • labels — shared tags for issues + PRs
  • milestones — goal or date with progress
  • assignees — who owns it
  • bulk edit — tick and apply
