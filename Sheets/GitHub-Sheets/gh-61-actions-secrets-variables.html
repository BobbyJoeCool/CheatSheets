Actions: Secrets & Variables

secrets.NAME · vars.NAME · repo / org / environment · masking · ::add-mask::

Keeping Config Out of YAML

Secrets are encrypted values (API keys, tokens) read with secrets.NAME; GitHub masks them as *** in logs. Variables are plain-text config (vars.NAME) for non-sensitive values like a region or URL. Both can be set at repository, organization or environment level; the most specific level wins (environment → repo → org).

Rules

  • Secrets aren't passed to workflows triggered by fork PRs
  • Names: letters, digits, _; can't start with GITHUB_
  • Max 48 KB per secret; 100 repo secrets
  • Secrets can't be read back in the UI, only replaced

Using Secrets and Variables

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production              # unlocks env-level secrets
    steps:
      - uses: actions/checkout@v6
      - name: Deploy
        env:
          API_TOKEN: ${{ secrets.API_TOKEN }}
          REGION: ${{ vars.AWS_REGION }}
        run: ./deploy.sh --region "$REGION"
      - name: Mask a derived value
        run: |
          TOKEN=$(./get-temp-token.sh)
          echo "::add-mask::$TOKEN"
          echo "TOKEN=$TOKEN" >> "$GITHUB_ENV"

# CLI:
# gh secret set API_TOKEN --body "$TOKEN"
# gh secret set API_TOKEN --env production < token.txt
# gh variable set AWS_REGION --body us-east-2

Code Explained

secrets.API_TOKEN — map into env:, read as $API_TOKEN
vars.AWS_REGION — visible, unmasked config
environment: — makes that environment's secrets available
::add-mask:: — mask values made at runtime

In the Logs

  • Secret value shows as *** — masking works
  • Empty value / Input required and not supplied: token — secret not set at this level, or a fork PR

Where to Store It

LevelBest for
Environmentprod/staging credentials behind approvals
Repositorykeys used by one repo
Organizationshared keys; choose which repos
Variables (vars)non-secret config: region, URLs, flags

What Gets Masked

ValueMasked?
secrets.X exact valueyes
base64 / transformed secretno — add ::add-mask::
structured JSON secretunreliable — store fields separately
vars.Xno

⚠ Common Mistakes

  • Passing secrets as command-line args: they show up in process lists; use env vars
  • Storing a JSON blob as one secret: individual fields may not be masked
  • Using pull_request_target just to get secrets for fork PRs (Sheet 43)

✓ Tips & Best Practices

  • Prefer OIDC over long-lived cloud keys (Sheet 63)
  • Rotate secrets on a schedule and after anyone with access leaves
  • Use environment secrets + required reviewers for anything production

Quick Summary

  • secrets.NAME — encrypted, masked
  • vars.NAME — plain config
  • environment > repo > org — precedence
  • ::add-mask:: — mask runtime values
