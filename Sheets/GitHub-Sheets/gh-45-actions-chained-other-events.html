Sheet 45

Actions: Chained & Other Events

workflow_run · repository_dispatch · release · issues · merge_group · [skip ci]

Beyond Push and PR

Workflows can react to almost any repo event. workflow_run starts one workflow when another finishes, which is how you separate an untrusted build from a privileged deploy. repository_dispatch lets an outside system trigger a run through the API. release, issues, issue_comment and merge_group cover releases, issue bots and merge queues.

Rules That Surprise People

  • workflow_run, issues, issue_comment, repository_dispatch and release use the workflow file on the default branch
  • Events made with GITHUB_TOKEN (e.g. a workflow's push) don't start new runs, except dispatch events
  • [skip ci], [ci skip], [no ci], [skip actions] in a commit message skip push and pull_request runs

Chaining and External Triggers

# deploy.yml — runs after CI finishes on main
on:
  workflow_run:
    workflows: ["CI"]          # the other workflow's name:
    types: [completed]
    branches: [main]
  repository_dispatch:
    types: [deploy-request]    # sent by an external system
  release:
    types: [published]
jobs:
  deploy:
    if: >-
      github.event_name != 'workflow_run' ||
      github.event.workflow_run.conclusion == 'success'
    runs-on: ubuntu-latest
    steps:
      - run: echo "Triggered by ${{ github.event_name }}"
      - run: echo "Payload: ${{ github.event.client_payload.env }}"
# Send: POST /repos/OWNER/REPO/dispatches {"event_type": "…"}

Code Explained

workflows: ["CI"] — matches the other file's name:, not its filename
types: [completed] — fires on success and failure; check conclusion
client_payload — your JSON from the dispatch call
release: published — skip created to avoid draft noise
>- — folded, keeps the long if: on one logical line

Security Check

  • Risk: a workflow_run deploy has secrets and write access, but the artifacts it downloads came from a run that may have built a fork's PR.
  • Fix: check the run's head_repository.full_name equals github.repository first, and treat artifact contents as data, never as code to run.

Telling Events Apart

ExpressionUse
github.event_name'push', 'pull_request'…
github.event.actionthe activity type, e.g. 'labeled'
github.event.workflow_run.conclusionsuccess / failure / cancelled
github.event.release.tag_namee.g. v1.2.0

⚠ Common Mistakes

  • Pushing a commit with GITHUB_TOKEN and waiting for CI to run on it: it won't
  • Using workflow_run without a conclusion == 'success' check: you deploy failed builds
  • Enabling a merge queue without adding merge_group to CI: PRs sit in the queue forever

✓ Tips & Best Practices

  • Mint a short-lived App token with actions/create-github-app-token when a push must trigger CI
  • [skip ci] doesn't apply to pull_request_target or scheduled runs
  • Log ${{ toJSON(github.event) }} once to discover payload fields

Quick Summary

  • workflow_run — chain after another workflow
  • repository_dispatch — external API trigger
  • release / issues / merge_group — repo activity
  • GITHUB_TOKEN events — don't re-trigger workflows
