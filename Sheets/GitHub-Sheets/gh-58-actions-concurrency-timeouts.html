Actions: Concurrency & Timeouts

concurrency: group · cancel-in-progress · github.ref · timeout-minutes

Stop Runs Piling Up

A concurrency group is a string; only one run (or job) with the same group can be running, and at most one more can be pending. A newer pending run replaces the older pending one. Add cancel-in-progress: true to cancel the running one instead, which is ideal for PR builds where only the latest commit matters. timeout-minutes stops runaway jobs and steps.

Behavior

  • Group names are case-insensitive and can use expressions
  • Works at workflow level or job level
  • Default job timeout: 360 minutes; set it lower
  • Timed-out jobs count as failure; cancelled ones as cancelled

PR Builds and Safe Deploys

# Cancel older runs for the same PR / branch
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v6
      - run: npm test
        timeout-minutes: 10

  deploy:
    needs: test
    runs-on: ubuntu-latest
    concurrency:                   # one deploy at a time, never cancel
      group: deploy-production
      cancel-in-progress: false
    steps:
      - run: ./deploy.sh

Code Explained

github.workflow + github.ref — one group per workflow per branch/PR
cancel-in-progress as an expression — cancel only on PRs
timeout-minutes — job and step level
job-level group: deploy-production — queue deploys

In the Logs

  • Canceling since a higher priority waiting request for 'ci-refs/heads/main' exists — concurrency at work
  • The job running on runner ... has exceeded the maximum execution time of 15 minutes. — timeout-minutes hit

Group Recipes

GroupEffect

deploy-${{ inputs.env }}one deploy per environment

What Happens

SituationResult

⚠ Common Mistakes

  • cancel-in-progress: true on deploy workflows: a half-finished deploy gets killed
  • A group of just ${{ github.workflow }}: pushes to different branches cancel each other
  • Relying on the 6-hour default timeout: a hung test burns hours of minutes

✓ Tips & Best Practices

  • Expect queued runs to be dropped: only the newest pending run per group survives
  • Use github.head_ref || github.run_id so push builds on main never cancel each other
  • Set org-wide guardrails: timeout-minutes on every job in your templates

Quick Summary

  • concurrency.group — one running per group
  • cancel-in-progress — replace the running one
  • job-level concurrency — serialize deploys
  • timeout-minutes — job and step limits
