Sheet 71

Package Access, Visibility & Cleanup

inherit repo access · package visibility · Manage Actions access · delete / restore versions · retention · storage billing

Who Can See and Use a Package

Container (and npm) packages can inherit access from their linked repo, so repo permissions decide who can read and write. Otherwise, each package has its own visibility and access list. Manage Actions access lets other repos' workflows read or write it. Old versions pile up, so delete them by hand or with a cleanup workflow; deleted versions can be restored for 30 days.

Facts

  • Changing a package to public is permanent
  • A public package version with 5,000+ downloads can't be deleted
  • Org setting can block public packages

Who Can Do This

  • Role: package Admin · Org owner (policies)
  • Plan: Free (private storage counts against quota)
  • Repos: public and private

Tidy Up a Package

  1. Profile/Org → Packages → open the package
  2. Package settings → Inherit access from source repository
  3. Manage Actions access → Add repository for other repos' workflows
  4. Set visibility (private by default for containers)
  5. Delete old versions from Versions, or automate cleanup

Automate It

Keep the newest 10 versions
- uses: actions/delete-package-versions@v5
  with:
    package-name: api
    package-type: container
    min-versions-to-keep: 10
    delete-only-untagged-versions: true

⚠ Common Mistakes

  • Making a package public to fix an access error: it can't go back
  • Cleanup workflows deleting tagged releases: restrict to untagged or old versions
  • Unlinked packages with stale access lists after team changes

✓ Tips & Best Practices

  • Link every package to a repo and inherit access
  • Schedule cleanup weekly for CI images that build on every push
  • Restore a deleted version within 30 days from package settings
