Secret Scanning & Push Protection

secret scanning alerts · partner patterns · push protection · bypass reasons · custom patterns · validity checks · rotate first

Catching Leaked Credentials

Secret scanning searches the full Git history, issues, PRs and discussions for tokens from hundreds of providers and alerts you. Partner providers (AWS, Stripe, Slack…) are notified about public leaks and may revoke them. Push protection stops the push before a secret ever reaches GitHub, unless the pusher bypasses with a reason. Validity checks show whether a found secret still works.

Facts

  • Enabled automatically on all public repos
  • Push protection is on by default for pushes to public repos
  • Revoke the secret first; deleting the commit isn't enough

Who Can Do This

  • Role: Admin (enable) · Write/committers (bypass push protection)
  • Plan: Free for public; Secret Protection for private
  • Repos: public and private

When a Secret Leaks

  1. Revoke / rotate the credential at the provider immediately
  2. Check provider logs for misuse since the leak
  3. Remove it from code; load it from a secret store
  4. Security → Secret scanning → close the alert as Revoked
  5. Optional: rewrite history (git filter-repo) and force-push

⚠ Common Mistakes

  • Deleting the file and thinking you're safe: it's in history and forks/clones
  • Bypassing push protection with "false positive" for a real key
  • Committing .env files: add them to .gitignore from day one

✓ Tips & Best Practices

  • Add custom patterns for internal token formats
  • Turn on delegated bypass so a security team approves bypasses
  • Use OIDC and short-lived tokens so leaks expire on their own

Quick Summary

  • push protection — block before push
