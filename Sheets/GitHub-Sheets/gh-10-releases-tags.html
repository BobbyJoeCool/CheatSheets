Shipping Versions

A release is a Git tag plus a title, notes and optional binary assets, shown on the repo's Releases page. Releases can be drafts (hidden until published), pre-releases, or marked latest. Generated release notes list merged PRs and contributors since the previous tag, grouped by label through .github/release.yml. Immutable releases lock a published release's tag and assets.

Release Facts

  • Source code zips are added automatically
  • Each asset can be up to 2 GB
  • Publishing a release triggers the release Actions event (Sheet 45)

Who Can Do This

  • Role: Write
  • Plan: Free
  • Repos: public and private

Grouping Generated Notes

# .github/release.yml
changelog:
  exclude:
    labels: [ignore-for-release, dependencies]
    authors: [dependabot]
  categories:
    - title: 🚀 Features
      labels: [feature, enhancement]
    - title: 🐛 Bug Fixes
      labels: [bug]
    - title: 📝 Other Changes
      labels: ["*"]

Code Explained

exclude.labels — PRs with these labels are skipped
categories — sections in order; first match wins
labels: ["*"] — catch-all for everything else
used by Generate release notes and --generate-notes

Automate It

Release from a tag push (Actions)
on: { push: { tags: ["v*"] } }
# step: run: gh release create
#   "$GITHUB_REF_NAME" --generate-notes

⚠ Common Mistakes

  • Moving or deleting a published tag: anyone pinned to it gets different code
  • Forgetting to label PRs: generated notes land in 'Other Changes'
  • Attaching build outputs made on a laptop: build release assets in CI instead

✓ Tips & Best Practices

  • Link …/releases/latest/download/app.zip for an always-latest download
  • Turn on immutable releases in Settings for supply-chain safety
  • Protect v* tags with a tag ruleset (Sheet 09)
