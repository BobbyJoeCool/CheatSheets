Actions: Introduction & Mental Model

workflow · event · job · step · action · runner · .github/workflows/

What GitHub Actions Is

GitHub Actions is the CI/CD and automation system built into GitHub. You commit a YAML workflow file to .github/workflows/; when an event happens (a push, a pull request, a schedule, a button click) GitHub starts a run. Each run contains one or more jobs, every job gets a fresh virtual machine called a runner, and each job runs its steps in order: shell commands (run:) or packaged, reusable actions (uses:).

Good to Know

  • Free for public repos on standard GitHub-hosted runners; private repos get a monthly minutes allowance
  • Jobs run in parallel by default; steps inside a job always run in order
  • Each job starts on a clean machine. Nothing carries over unless you use artifacts, caches or outputs
  • Git vs Actions: Git tracks history; Actions reacts to it (Git commands: see the Git CLI set)

Anatomy of a Workflow

# .github/workflows/ci.yml            ← one file = one workflow
name: CI                              # shown in the Actions tab
on: [push, pull_request]              # EVENTS that start a run

jobs:                                 # one or more JOBS
  test:                               # job id
    runs-on: ubuntu-latest            # RUNNER (fresh VM per job)
    steps:                            # STEPS run top to bottom
      - uses: actions/checkout@v6     # an ACTION (reusable step)
      - uses: actions/setup-node@v6
        with: { node-version: 22 }    # inputs to the action
      - run: npm ci                   # a shell command
      - run: npm test
  lint:                               # 2nd job: runs in parallel
    runs-on: ubuntu-latest
    steps: [{ uses: actions/checkout@v6 }, { run: npx eslint . }]

Code Explained

name: — label in the UI; defaults to the file path
on: — which events trigger the workflow (Sheets 43–45)
jobs.<id> — independent units of work; parallel unless linked with needs:
runs-on: — picks the runner image or label
uses: — runs an action from a repo, owner/repo@ref
run: — runs shell commands (bash on Linux/macOS, pwsh on Windows)
with: — passes inputs to an action

Core Vocabulary

TermMeaning
WorkflowA YAML file in .github/workflows/; the automation definition
EventWhat triggers a run: push, pull_request, schedule…
RunOne execution of a workflow; has a number and logs
JobA set of steps on one runner; has a result (success/failure/skipped)
StepOne command (run) or action (uses) inside a job
ActionReusable step from a repo, Docker image or local folder
RunnerThe machine that executes a job: GitHub-hosted or self-hosted

⚠ Common Mistakes

  • Putting workflows in .github/workflow/ (no s) or the repo root: GitHub ignores them silently
  • Expecting files from one job to exist in another: each job is a new machine
  • Assuming steps run in parallel like jobs: steps are always sequential within a job

✓ Tips & Best Practices

  • Start from a template: Actions tab → New workflow shows starters for your language
  • Keep one concern per workflow (ci.yml, deploy.yml, release.yml) so triggers stay simple
  • Read the run log top-down: every step is a collapsible group with its own timing

Quick Summary

  • workflow — YAML file that reacts to events
  • job — steps on one fresh runner; parallel by default
  • step — run: a command or uses: an action
  • runner — the VM picked by runs-on:
