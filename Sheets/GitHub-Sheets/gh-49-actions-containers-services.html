Actions: Job & Service Containers

container: · services: · postgres / redis · ports · --health-cmd · credentials

Docker Inside a Job

container: runs every step of a job inside a Docker image, so the job gets exactly that OS and toolset. services: starts sidecar containers (databases, caches, queues) for the job's lifetime. Both need a Linux runner with Docker. How you reach a service depends on where your steps run: by service name from a job container, by localhost + mapped port from the runner.

Rules

  • Linux runners only (hosted ubuntu-* or self-hosted Linux with Docker)
  • Services start before the first step and stop after the last
  • options: passes extra docker create flags
  • Private images: add credentials: { username, password }

Tests Against Postgres

jobs:
  test:
    runs-on: ubuntu-latest
    container: node:22                  # steps run in this image
    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_PASSWORD: pw
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 5s --health-retries 10
    steps:
      - uses: actions/checkout@v6
      - run: npm ci && npm test
        env:
          DATABASE_URL: postgres://postgres:pw@postgres:5432/postgres

Code Explained

container: node:22 — all run: steps execute inside it
services.postgres — key becomes the hostname postgres
--health-cmd — runner waits until healthy before steps start
@postgres:5432 — reach by name (steps are in a container)

In the Logs

  • Service container postgres failed. / unhealthy — check the health command and env; the service's logs appear in Initialize containers
  • ECONNREFUSED 127.0.0.1:5432 — you're in a job container: use the service name, not localhost

Which Hostname?

Steps run on…Connect to

⚠ Common Mistakes

  • Using localhost from a job container: services are on a Docker network, not the container's loopback
  • No health check: tests start before the database accepts connections
  • Expecting container: on Windows or macOS runners: not supported

✓ Tips & Best Practices

  • For services, prefer health checks over sleep 10
  • Pin image tags (postgres:17), never latest, so CI is reproducible
  • docker compose up -d --wait in a step is an alternative for complex stacks

Quick Summary

  • container: — run steps in an image
  • services: — sidecars for the job
  • service name — host from a job container
  • ports: + localhost — from the runner
