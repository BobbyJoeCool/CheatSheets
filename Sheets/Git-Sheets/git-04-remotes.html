Remotes & Tracking Branches

A remote is a named reference to another copy of the repository, typically on a server. The default remote created by git clone is called origin. Git stores a local read-only snapshot of each remote branch called a remote-tracking branch (e.g. origin/main). These snapshots are updated by git fetch but never touched by your local commits. git pull is shorthand for git fetch followed by git merge (or git rebase if configured). Understanding the difference between fetch and pull is essential for safe collaboration.

Key Facts

  • origin — conventional name for the primary remote
  • upstream — conventional name for the original repo when working with forks
  • origin/main — remote-tracking branch; read-only local snapshot
  • git fetch is always safe — it never changes your working tree
  • A tracking relationship links a local branch to a remote branch for push/pull defaults
  • HTTPS vs SSH: SSH requires key setup but avoids password prompts

Fetch · Pull · Push

CommandDescription
git fetchDownload all remote changes without merging
git fetch origin mainFetch only the remote main branch
git pullFetch + merge the tracking branch into current
git pull --rebaseFetch + rebase instead of merge (cleaner history)
git push origin mainPush local main to remote origin
git push -u origin featurePush and set tracking relationship (-u = --set-upstream)
git push --force-with-leaseSafer force push — fails if remote has new commits you haven't seen
git push origin --delete featureDelete a remote branch

Typical Remote Workflows

# ── Connect a local repo to GitHub ───────────────────────────
git remote add origin git@github.com:user/repo.git
git push -u origin main        # -u sets tracking; after this just: git push

# ── Fetch then inspect before merging ────────────────────────
git fetch origin               # update origin/* snapshots
git log HEAD..origin/main      # commits on remote that you don't have
git diff HEAD origin/main      # diff your work vs remote
git merge origin/main          # merge when ready

# ── Pull with rebase (preferred for cleaner history) ──────────
git pull --rebase origin main
# equivalent to:
git fetch origin
git rebase origin/main

# ── Work with a fork (open-source contribution) ───────────────
git remote add upstream git@github.com:original/repo.git
git fetch upstream             # get upstream changes
git merge upstream/main        # sync your fork's main

# ── Push a feature branch and delete after merge ─────────────
git push -u origin feature/login
# ... PR reviewed and merged on GitHub ...
git fetch --prune              # remove stale remote-tracking branches
git branch -d feature/login   # delete local branch

# ── Recover from rejected push ────────────────────────────────
git pull --rebase              # rebase your commits on top of remote
git push                       # now succeeds

Notes

-u / --set-upstream — only needed once per branch; after that git push and git pull work with no arguments
HEAD..origin/main — the double-dot range means "commits reachable from origin/main but not from HEAD"
--force-with-lease — always prefer this over --force; it won't overwrite teammates' commits you haven't fetched
--prune — removes origin/feature remote-tracking branches that no longer exist on the server
upstream remote — a second remote pointing at the repo you forked from, keeping your fork in sync with the original
git pull --rebase replays your local commits on top of fetched changes, avoiding a spurious merge commit

Common Mistakes

  • Using git push --force on a shared branch — this rewrites history for everyone; always use --force-with-lease and only on branches you alone own
  • Confusing git fetch and git pull — fetch is always safe; pull immediately integrates changes and can create conflicts
  • Forgetting -u on the first push — the next git pull will fail with "no tracking information" until a tracking relationship exists

Tips

  • Prefer git fetch + inspect + git merge over bare git pull — you see exactly what's coming before integrating it
  • Set git config --global pull.rebase true to make git pull always rebase instead of merge, keeping history linear
  • Run git fetch --prune regularly on long-lived projects; stale origin/* branches accumulate and clutter branch listings

Summary

  • git remote add — connect to a remote repository
  • git fetch — download changes without modifying working tree
  • git pull --rebase — fetch + rebase for clean linear history
  • git push -u — push and set tracking branch in one step
  • --force-with-lease — safe alternative to --force
