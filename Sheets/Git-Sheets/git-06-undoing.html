Sheet 06

Undoing Changes

restore · reset · revert · clean · amend · reflog · detached HEAD

Choosing the Right Undo

Git offers several undo mechanisms that operate at different levels of permanence. git restore discards working tree or staged changes without touching history. git reset moves the branch pointer backward, optionally changing the index and working tree. git revert creates a new commit that undoes a previous one — the only safe undo for shared history because it does not rewrite commits. The golden rule: never rewrite history that has already been pushed to a shared remote branch. Use git reflog as your safety net — it remembers every position HEAD has been at for 90 days.

Reset Modes

  • --soft — moves branch pointer; keeps index and working tree unchanged
  • --mixed — (default) moves pointer, resets index; keeps working tree
  • --hard — moves pointer, resets index and working tree; destructive
  • After --hard: recover via git reflog within 90 days
  • git revert is always safe on shared branches
  • git clean -n dry-run — shows what would be deleted

Notes

reset --soft — useful to re-commit with a better message; your changes stay staged and ready
reset --mixed — default; collapses commits back to working tree changes you can re-stage selectively
reset --hard — truly destructive for uncommitted work; always check git status first
git revert --no-commit — stages all reverts without committing; lets you combine multiple reverts into one commit
git reflog — records every time HEAD moved; the ultimate recovery tool even after --hard resets
HEAD@{1} — reflog syntax meaning "where HEAD was 1 move ago"; safe to branch from or reset to

reset · revert · reflog

# ── Undo last commit, keep changes staged ─────────────────────
git reset --soft HEAD~1
		# branch moves back; index unchanged

# ── Undo last commit, unstage changes (most common) ───────────
git reset HEAD~1        
		# --mixed is default
git reset HEAD~1 -- file.txt  
		# reset only one file in index

# ── Nuke last commit and all changes (dangerous) ──────────────
git reset --hard HEAD~1
# recover if needed:
git reflog              
		# find the orphaned commit hash, e.g. abc1234
git reset --hard abc1234
		# restore to it

# ── Safe undo for shared branches ────────────────────────────
git revert HEAD         
		# new commit that undoes HEAD
git revert abc1234      
		# undo a specific older commit
git revert HEAD~3..HEAD     
		# undo a range of commits (3 new reverts)
git revert --no-commit HEAD~3..HEAD  
		# stage reverts, commit manually

# ── Use reflog as a safety net ────────────────────────────────
git reflog                     
		# every HEAD movement for 90 days
# HEAD@{0}: reset --hard HEAD~1
# HEAD@{1}: commit: Add login form   ← the commit we lost
git switch -c recovery HEAD@{1}  
		# recover on a new branch

Undo Commands at a Glance

Command Touches History? Safe to Share?
git restore file No ✔
git restore --staged file No ✔
git commit --amend Yes — rewrites ✖ if pushed
git reset --soft HEAD~1 Yes — rewrites ✖ if pushed
git reset --hard HEAD~1 Yes — rewrites ✖ if pushed
git revert HEAD Yes — adds commit ✔
git clean -fd No ✔

restore & clean Variants

Command Description
git restore file.txt Discard working tree changes to file (irreversible)
git restore . Discard all working tree changes
git restore --staged file Unstage a file (keeps working tree change)
git restore --source HEAD~2 file Restore a file to its state 2 commits ago
git clean -n Dry run: show untracked files that would be removed
git clean -fd Remove untracked files (-f) and directories (-d)
git clean -fdx Also remove ignored files (full clean build state)

Common Mistakes

  • Using git reset --hard on a shared branch — this rewrites public history and forces every collaborator to manually reset their local branch
  • Running git clean -fd without a -n dry run first — untracked files are deleted permanently with no git recovery path
  • Using git restore file when you meant to unstage — restore without --staged discards working tree changes irreversibly

Tips

  • When in doubt on a shared branch, reach for git revert — it creates a paper trail and never forces teammates to change their history
  • Always run git reflog before panicking after a hard reset — the "lost" commits are almost certainly still there for 90 days
  • Use git reset --soft HEAD~1 to break a large commit into smaller ones: uncommit, re-add with -p, recommit in logical chunks

Summary

  • git restore — discard working tree / staged changes safely
  • git reset --soft/--mixed/--hard — move branch pointer back
  • git revert — safe undo for shared branches; adds a new commit
  • git clean -fd — remove untracked files and directories
  • git reflog — 90-day safety net for all HEAD movements
