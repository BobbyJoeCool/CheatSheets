Sheet 08

Advanced Rebase & Merging

rebase · interactive rebase · squash · cherry-pick · merge strategies · conflicts

Rebase vs Merge

git rebase replays your commits on top of another branch, producing a linear history as if development happened sequentially. git merge preserves the true branching topology with a merge commit. Both integrate changes; the difference is cosmetic and philosophical. Interactive rebase (-i) is a powerful history editor: squash noisy commits, reword messages, reorder or drop commits entirely — all before sharing. git cherry-pick copies one or more commits from any branch onto the current branch without a full merge. Never rebase shared/public branches.

Interactive Rebase Actions

  • pick — keep commit as-is
  • reword — keep commit, edit message
  • edit — pause to amend the commit
  • squash — combine with previous commit, merge messages
  • fixup — like squash, but discard this commit's message
  • drop — remove the commit entirely from history

Rebase Commands

CommandDescription
git rebase mainReplay current branch commits on top of main
git rebase -i HEAD~4Interactively edit the last 4 commits
git rebase -i mainInteractively edit all commits since branching from main
git rebase --continueContinue after resolving a conflict mid-rebase
git rebase --abortCancel and return to the pre-rebase state
git rebase --skipSkip a conflicting commit and continue
git rebase --onto new old branchRe-parent a branch range onto a different base

cherry-pick & Merge Strategies

CommandDescription
git cherry-pick abc1234Apply commit abc1234 onto the current branch
git cherry-pick abc..defApply a range of commits (exclusive of abc)
git cherry-pick -n abc1234Stage the change without committing (--no-commit)
git cherry-pick --abortCancel a conflicted cherry-pick
git merge -s ours featureMerge strategy: keep current branch content entirely
git merge -X theirs featureMerge strategy option: auto-resolve conflicts with their side
git merge -X ours featureMerge strategy option: auto-resolve conflicts with our side

Interactive Rebase & Cherry-pick

# ── Clean up feature branch before opening a PR ───────────────
git switch feature/login
git rebase -i HEAD~5
# Editor opens with last 5 commits:
# pick a1b2c3d Add login form
# pick d4e5f6a WIP: fix typo
# pick 789abcd WIP: another fix
# pick bcdef01 Add session handling
# pick 1234567 Add tests
#
# Change to:
# pick a1b2c3d Add login form
# fixup d4e5f6a WIP: fix typo       ← squash into previous, drop msg
# fixup 789abcd WIP: another fix     ← squash into previous, drop msg
# reword bcdef01 Add session handling ← keep but edit the message
# pick 1234567 Add tests
# Save and close → Git replays, pauses on "reword" for new message

# ── Rebase onto updated main ──────────────────────────────────
git fetch origin
git rebase origin/main             # replay your commits on remote main
# Resolve any conflicts, then:
git add conflicted-file.txt
git rebase --continue

# ── Cherry-pick a hotfix commit onto a release branch ─────────
git switch release/2.0
git cherry-pick abc1234            # copy one commit
git cherry-pick abc1234 def5678   # copy multiple commits

# ── --onto: move a sub-branch to a different base ─────────────
# Situation: feature/ui was branched from feature/api (not main)
# Move feature/ui commits so they start from main instead:
git rebase --onto main feature/api feature/ui

Notes

fixup vs squash — both combine commits; fixup silently discards the squashed message, squash opens the editor to merge messages
rebase --continue — after resolving each conflict file, git add it, then continue; do not git commit mid-rebase
rebase --onto — three-argument form: new base, old base (exclusive), branch tip; powerful for re-parenting work
cherry-pick -n — useful when you want to cherry-pick several commits and combine them into one before committing
-X theirs/ours — strategy option, not strategy; resolves conflicts automatically but still creates a merge commit
After rebasing, force-push the branch with --force-with-lease — hashes change so the remote ref must be updated

Common Mistakes

  • Rebasing main or any shared branch — rebase rewrites commit hashes; anyone who based work on the old hashes must reconcile the divergence manually
  • Running git commit during a rebase conflict — instead, resolve the conflict, git add, then git rebase --continue
  • Dropping a commit in interactive rebase by accident — recover via git reflog to find the original hash before the rebase

Tips

  • Make a backup branch before any interactive rebase: git branch backup/feature — you can always git reset --hard backup/feature if it goes wrong
  • Use git rebase -i main (not HEAD~N) so the rebase scope automatically covers exactly the commits since you branched
  • Cherry-pick is ideal for backporting fixes to release branches; keep a note of which commits are cherry-picked so the team doesn't apply them twice

Summary

  • git rebase main — replay commits for linear history
  • git rebase -i — edit, squash, reorder, or drop commits
  • fixup — squash into previous commit, discard message
  • git cherry-pick — copy specific commits onto current branch
  • Never rebase branches shared with others
