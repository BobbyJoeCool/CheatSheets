Core Workflow

init · clone · status · add · commit · log · staging area

The Three-Stage Model

Every file in a Git repo lives in one of three places. The working tree is the directory you edit. The staging area (also called the index) is a draft of your next commit — you explicitly add changes here before they become permanent. The repository is the permanent history stored in .git/. Moving changes left to right (add → commit) is the core loop you will repeat thousands of times. Moving right to left (restore, reset) is how you undo.

File States

  • Untracked — new file Git has never seen
  • Unmodified — tracked, matches last commit
  • Modified — tracked, changed in working tree
  • Staged — change is in the index, ready to commit
  • A file can be both staged and modified at once if edited after git add
  • git status -s shows a compact two-column state: index state | working tree state

Notes

git status -s — left column = index, right column = working tree; ?? means untracked
git add -p — "patch" mode lets you split one file's changes into separate commits for cleaner history
git commit -am — only stages already-tracked files; new (untracked) files still need a manual git add
--amend — rewrites the last commit; never amend commits that have already been pushed to a shared remote
git log --oneline --graph — best mental model of branch topology; pair with the lg alias from Sheet 01
git show HEAD — HEAD always refers to the current commit; HEAD~1 is one before it

A Full Commit Cycle

# ── Start a project ───────────────────────────────────────────
git init my-app && cd my-app

# ── Check state at any time ───────────────────────────────────
git status                     # full output
git status -s                  # short: XY filename
                        # ?? = untracked  M = modified  A = staged

# ── Stage and commit ─────────────────────────────────────────
echo "# My App" > README.md
git add README.md              # stage one file
git commit -m "Initial commit: add README"

# ── Make more changes ─────────────────────────────────────────
echo "hello" > app.js
git add .                      # stage everything
git status -s                  # A  app.js  (staged)

# ── Amend: forgot a file before pushing ──────────────────────
echo "*.log" > .gitignore
git add .gitignore
git commit --amend --no-edit   # add to last commit, keep message

# ── Inspect history ──────────────────────────────────────────
git log                        # full log
git log --oneline              # one line per commit
git log --oneline --graph      # with branch graph
git log -5                     # last 5 commits only
git log -- app.js              # commits that touched app.js

# ── Show a single commit ─────────────────────────────────────
git show HEAD                  # diff + metadata of latest commit
git show abc1234               # show a specific commit by hash

Starting a Repository

Command Description
git init Create a new repo in the current directory
git init my-project Create a new repo inside a new my-project/ folder
git clone <url> Download a repo and its full history
git clone <url> my-dir Clone into a custom directory name
git clone --depth 1 <url> Shallow clone — latest snapshot only, no full history

Staging Variants

Command Description
git add file.txt Stage a single file
git add src/ Stage all changes inside a directory
git add . Stage all changes in the working tree
git add -p Interactive: stage individual hunks within a file
git restore --staged file Unstage a file without losing the working tree change
git commit -m "msg" Commit staged changes with an inline message
git commit -am "msg" Stage all tracked modifications and commit in one step
git commit --amend Rewrite the last commit's message or add forgotten files

Common Mistakes

  • Using git commit -am expecting it to stage new files — -a only auto-stages files already tracked by Git
  • Amending a commit that was already pushed — this rewrites history and forces collaborators to reset their branches
  • Writing vague messages like "fix" or "update" — a good message completes the sentence "If applied, this commit will…"

Tips

  • Use git add -p to review your own diff before staging — it catches debug code and half-finished changes before they land in history
  • Run git status before every commit; it takes one second and eliminates most "oops I staged the wrong thing" moments
  • Keep commits atomic — one logical change per commit. It makes git bisect, git revert, and code review dramatically easier

Summary

  • git init / git clone — start a repo locally or from remote
  • git add — move changes from working tree → staging area
  • git commit — move staged changes → permanent history
  • git status -s — compact two-column file state view
  • git log --oneline --graph — visual history at a glance
