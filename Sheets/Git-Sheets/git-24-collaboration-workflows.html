Collaboration Workflows

feature branches · GitHub flow · Git flow · trunk-based · fork + sync upstream · gh pr create · gh pr checkout · release branches

How Teams Use Git

A workflow is the team agreement about which branches exist and how changes reach main. Most teams use short-lived feature branches + pull requests (GitHub flow) or trunk-based development with tiny, frequent merges. Open-source projects add forks. Git flow's long-lived develop and release branches suit scheduled, versioned releases.

Notes

  • Keep branches small: hours to a few days
  • Protect main: require PR review and passing CI
  • Pick one merge style per repo: merge, squash, or rebase
  • The gh CLI drives GitHub PRs from the terminal

Feature Branch + PR (GitHub flow)

git switch main && git pull --ff-only
git switch -c feature/search          # 1. branch from fresh main
git add -p && git commit -m "Add search box"   # 2. small commits
git fetch && git rebase origin/main   # 3. stay current
git push -u origin HEAD               # 4. publish
gh pr create --fill                   # 5. open a pull request
gh pr checkout 87                     # review someone else's PR locally
gh pr merge --squash --delete-branch  # 6. merge when approved

# Fork workflow (open source)
gh repo fork org/app --clone          # fork + clone + add upstream remote
git fetch upstream
git rebase upstream/main              # sync your branch with the original
git push --force-with-lease

Code Explained

pull --ff-only — refresh main without stray merges
rebase origin/main — resolve conflicts before review, not after
gh pr create --fill — title/body from your commits
gh pr checkout — fetches a PR into a local branch
gh repo fork --clone — sets origin (fork) and upstream
--delete-branch — cleans up after merging

PR Merge Styles

StyleResult on main
Merge commitall commits + a merge commit
Squashone commit per PR
Rebaseall commits, linear, no merge commit

⚠ Common Mistakes

  • Long-running feature branches. Conflicts grow every day; merge small pieces behind flags
  • Working directly on main in a fork. Use a branch, so syncing upstream stays a fast-forward
  • Mixing merge styles in one repo. History becomes hard to read and bisect

✓ Tips & Best Practices

  • Name branches by type: feature/, fix/, chore/
  • Write PR descriptions that explain why and how to test
  • Delete merged branches locally with git fetch --prune + git branch -d

Quick Summary

  • branch → commit → push → PR → merge
  • gh pr create / checkout / merge
  • forks: origin + upstream
  • short branches = small conflicts
