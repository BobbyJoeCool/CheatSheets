Choosing a Workflow

A Git workflow is a convention for how branches are named, when merges happen, and who can push where. The right workflow depends on team size, release cadence, and deployment model. GitHub Flow is simple: branch from main, open a pull request, merge after review. Git Flow adds structured long-lived branches for releases and hotfixes — useful for scheduled releases. Trunk-based development has everyone commit to main frequently behind feature flags — common at high-velocity teams. Whichever you pick, consistency matters more than the specific model.

Git Flow Branch Types

  • main — always production-ready; only receives merges from release/hotfix
  • develop — integration branch; features merge here first
  • feature/* — branches from develop, merges back to develop
  • release/* — branches from develop; only bugfixes; merges to main + develop
  • hotfix/* — branches from main; emergency fix; merges to main + develop

GitHub Flow Step-by-Step

StepAction
1. Branchgit switch -c feature/name from up-to-date main
2. CommitSmall, frequent commits with clear messages
3. Pushgit push -u origin feature/name
4. PROpen a pull request; describe what and why
5. ReviewAddress feedback with additional commits on the branch
6. MergeSquash or merge into main after approval
7. DeployCI/CD deploys main; delete the feature branch

Fork & PR Workflow

StepAction
1. ForkFork on GitHub; clone your fork locally
2. Upstreamgit remote add upstream <original-url>
3. Syncgit fetch upstream && git merge upstream/main
4. BranchWork on a feature branch in your fork
5. PushPush to your fork: git push origin feature
6. PROpen PR from fork's branch to original repo's main
7. SyncKeep in sync during review: fetch upstream, rebase

Common Mistakes

  • Opening a PR from main in your fork — always work on a named feature branch so the PR can be updated without polluting your fork's main
  • Mixing workflow models mid-project — pick one and document it in CONTRIBUTING.md; mixed conventions create confusion about where to branch from
  • Writing vague PR titles ("various fixes") — the title becomes part of the merge commit message and the permanent changelog; be specific

Tips

  • Use Conventional Commits (feat:, fix:, chore:) — they enable automated changelogs and semantic versioning tools like semantic-release
  • Add a CODEOWNERS file to auto-request review from the right people based on which files changed in a PR
  • Keep PRs small and focused — a PR touching fewer than 400 lines of changed code gets reviewed faster and more thoroughly than large ones

Summary

  • GitHub Flow — branch, PR, merge to main; ideal for CD
  • Git Flow — main + develop with release branches
  • Fork workflow — fork → upstream remote → PR to original
  • Conventional Commits — typed prefixes enable automation
  • Small, frequent PRs — faster reviews, less merge pain
