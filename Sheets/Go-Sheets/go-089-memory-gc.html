Memory & Garbage Collection

Go is garbage collected with a concurrent, low-pause collector; Green Tea, the default since Go 1.26, scans memory in page-sized batches for better CPU cache use. The compiler's escape analysis decides whether values live on the cheap stack or the GC-managed heap. Tuning knobs are GOGC (how much growth triggers a GC) and GOMEMLIMIT (a soft memory cap).

Notes

  • Values escape when they outlive the function (returned pointers, closures, interfaces)
  • GOGC=100 (default): collect when heap grows 100% since last GC
  • GOMEMLIMIT=1GiB makes the GC work harder near the limit (containers)
  • runtime.AddCleanup (1.24) replaces most SetFinalizer uses

Allocation Awareness

// $ go build -gcflags=-m ./...     → escape analysis report
func sum(xs []int) int { t := 0; for _, x := range xs { t += x }; return t }
                                     // t stays on the stack
func newUser() *User { return &User{} } // &User{} escapes to heap

out := make([]Row, 0, len(in))      // preallocate: 1 allocation
m := make(map[string]int, 1000)     // size hint

var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}
b := bufPool.Get().(*bytes.Buffer)
b.Reset(); defer bufPool.Put(b)     // reuse hot temporary objects

var ms runtime.MemStats
runtime.ReadMemStats(&ms)
fmt.Println(ms.HeapAlloc/1e6, "MB", ms.NumGC, "GCs")

debug.SetMemoryLimit(512 << 20)     // same as GOMEMLIMIT=512MiB
runtime.AddCleanup(f, func(fd int) { syscall.Close(fd) }, f.fd) // 1.24
wp := weak.Make(bigObj)             // weak pointer (1.24)
if obj := wp.Value(); obj != nil { use(obj) }

Code Explained

-gcflags=-m — shows what escapes and why
preallocation — avoids repeated growth copies
sync.Pool — reuse buffers under load
ReadMemStats — heap size and GC counts
weak.Make — reference that doesn't keep objects alive

Coming From…

  • Java — no JVM heap flags; GOMEMLIMIT ≈ -Xmx (soft)
  • Python — no refcounting; tracing GC only
  • C — no free; escape analysis picks stack vs heap

⚠ Common Mistakes

  • Optimizing allocations without a profile; measure with -benchmem and pprof first
  • Putting objects back into sync.Pool while still using them
  • Running in containers without GOMEMLIMIT and getting OOM-killed

✓ Tips & Best Practices

  • Set GOMEMLIMIT to ~90% of the container limit
  • Use testing.AllocsPerRun or -benchmem to lock in allocation counts
  • Since Go 1.25, GOMAXPROCS respects container CPU limits automatically

Quick Summary

  • stack vs heap — escape analysis decides
  • GOGC / GOMEMLIMIT — GC tuning
  • Green Tea — default GC since 1.26
  • sync.Pool, preallocation — fewer allocs
