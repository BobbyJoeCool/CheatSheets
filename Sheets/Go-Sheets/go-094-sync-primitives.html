sync Primitives

When goroutines share memory, the sync package protects it. Mutex allows one goroutine at a time; RWMutex allows many readers or one writer. WaitGroup waits for goroutines, Once runs initialization exactly once, and Pool recycles temporary objects. All zero values are ready to use and must not be copied after use.

Notes

  • Lock, then defer Unlock() on the next line
  • Embed the mutex next to the fields it guards
  • sync.OnceFunc / OnceValue / OnceValues (1.21) wrap functions
  • go vet copylocks catches accidental copies

Guarding Shared State

type Counter struct {
    mu sync.Mutex
    m  map[string]int          // guarded by mu
}
func (c *Counter) Inc(k string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.m[k]++
}

type Cache struct { mu sync.RWMutex; data map[string]string }
func (c *Cache) Get(k string) string {
    c.mu.RLock(); defer c.mu.RUnlock()   // many readers at once
    return c.data[k]
}

var wg sync.WaitGroup
for _, f := range files { wg.Go(func() { process(f) }) } // 1.25
wg.Wait()

var loadConfig = sync.OnceValue(mustLoad) // computed once
cfg := loadConfig()

Code Explained

Lock / defer Unlock — critical section
RLock — shared read lock
wg.Go — spawn + track (1.25)
sync.OnceValue — lazy init with a result
sync.Map — specialized concurrent map

⚠ Common Mistakes

  • Passing a struct with a mutex by value; each copy has its own lock
  • Forgetting to unlock on an early return; use defer
  • Calling a method that locks from inside another method holding the same lock: deadlock (not reentrant)

✓ Tips & Best Practices

  • Keep critical sections tiny: copy data out, unlock, then do slow work
  • Comment which fields a mutex guards
  • Run tests with -race to find unguarded access

Quick Summary

  • Mutex / RWMutex — protect shared data
  • WaitGroup / wg.Go — wait
  • Once* — one-time init
