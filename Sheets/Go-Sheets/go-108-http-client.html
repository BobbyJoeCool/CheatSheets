HTTP Client

http.Get and friends use http.DefaultClient, which has no timeout, so production code should create its own http.Client{Timeout: …} and reuse it (it pools connections). Build requests with http.NewRequestWithContext to set headers and support cancellation, always close resp.Body, and check resp.StatusCode yourself: non-2xx is not an error.

Notes

  • One http.Client per app; it's safe for concurrent use
  • Not reading/closing the body prevents connection reuse
  • err is only for transport failures (DNS, timeout, refused)
  • Use url.Values / url.Parse to build query strings safely

Making Requests

var client = &http.Client{Timeout: 10 * time.Second}

func getUser(ctx context.Context, id int) (*User, error) {
    u, _ := url.Parse("https://api.example.com/users")
    u.RawQuery = url.Values{"id": {strconv.Itoa(id)}}.Encode()
    req, err := http.NewRequestWithContext(ctx, "GET", u.String(), nil)
    if err != nil { return nil, err }
    req.Header.Set("Authorization", "Bearer "+token)

    resp, err := client.Do(req)
    if err != nil { return nil, err }           // network error
    defer resp.Body.Close()
    if resp.StatusCode != http.StatusOK {

        return nil, fmt.Errorf("status %d: %s", resp.StatusCode, b)
    }
    var user User
    return &user, json.NewDecoder(resp.Body).Decode(&user)
}

⚠ Common Mistakes

  • Using http.Get in production: no timeout, a slow server hangs your goroutine forever
  • Creating a new http.Client (and Transport) per request; connections aren't reused
  • Treating err == nil as success without checking resp.StatusCode

✓ Tips & Best Practices

  • Raise MaxIdleConnsPerHost when calling one host heavily
  • Add retries with backoff for idempotent requests (or use hashicorp/go-retryablehttp)
  • Test clients against httptest.NewServer

Quick Summary

  • http.Client{Timeout} — create once, reuse
  • NewRequestWithContext + headers
  • defer resp.Body.Close() — always
  • check StatusCode — non-2xx isn't an error
