Races, Deadlocks & Leaks

Concurrency bugs come in three main forms. A data race is unsynchronized access to the same memory with at least one write; the race detector (-race) finds them at runtime. A deadlock is when goroutines wait on each other forever. A goroutine leak is a goroutine blocked forever that's never cleaned up. Go 1.27's goroutineleak profile and testing/synctest help find the last two.

Notes

  • -race slows code 2-20× but finds real bugs; use it in CI tests
  • The runtime only detects deadlock when all goroutines are blocked
  • Leaks show up as a growing runtime.NumGoroutine()

Spot the Bug

count := 0                              // DATA RACE
for range 100 { go func() { count++ }() } // fix: atomic / mutex

ch := make(chan int)
ch <- 1     // fatal error: all goroutines are asleep - deadlock!

func search(q string) string {          // LEAK
    ch := make(chan string)             // fix: make(chan string, 1)
    go func() { ch <- slowLookup(q) }()
    select {
    case r := <-ch: return r
    case <-time.After(time.Second): return "" // sender stuck
    }
}

func TestTimeout(t *testing.T) {        // deterministic time
    synctest.Test(t, func(t *testing.T) {
        go worker()
        time.Sleep(time.Hour)           // instant: fake clock
        synctest.Wait()                 // until all goroutines block
    })
}
// $ go test -race ./...    ·   /debug/pprof/goroutineleak (1.27)

Code Explained

count++ from many goroutines — read-modify-write race
send with no receiver — blocks main forever
timeout path leaves the sender blocked: leak
buffer of 1 lets the sender finish and exit
synctest.Test — virtual time, Wait for quiescence

Coming From…

  • Java — -race has no built-in JVM equivalent
  • Rust — races caught at compile time there; here at runtime
  • Python — no GIL protection; races are real

⚠ Common Mistakes

  • Running -race only locally; enable it in CI where tests exercise concurrency
  • Assuming "it works on my machine" means no race; races are timing-dependent
  • Fixing flaky concurrent tests with longer time.Sleep calls

✓ Tips & Best Practices

  • Expose net/http/pprof on an internal port to inspect goroutines in production
  • Use go.uber.org/goleak in TestMain to fail tests that leak goroutines
  • Lock multiple mutexes in a fixed global order to avoid deadlocks

Quick Summary

  • -race — detect data races
  • deadlock — all goroutines blocked
  • leak — blocked goroutine never exits
  • synctest / goroutineleak — newer tools
