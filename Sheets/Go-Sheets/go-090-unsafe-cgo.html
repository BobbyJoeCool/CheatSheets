unsafe & cgo

unsafe bypasses the type system: converting between pointer types, reading struct layout, and building strings or slices from raw pointers. cgo lets Go call C code via a special import "C" preceded by a C preamble comment. Both sacrifice portability and safety guarantees; use them only for performance-critical or interop code.

Costs & Rules

  • A cgo call costs far more than a Go call; batch work per call
  • cgo breaks easy cross-compiling and static binaries
  • C memory isn't GC'd: free what you C.malloc / C.CString

unsafe & cgo

type Header struct { A byte; B int64; C byte }
unsafe.Sizeof(Header{})           // 24 (padding!)
unsafe.Alignof(int64(0))          // 8
unsafe.Offsetof(Header{}.B)       // 8

b := []byte("hello")
s := unsafe.String(&b[0], len(b)) // no copy; b must not change
sl := unsafe.Slice(unsafe.StringData(s), len(s)) // []byte view

f := 1.5
bits := *(*uint64)(unsafe.Pointer(&f)) // = math.Float64bits(f)

/*
#include <stdlib.h>
#include <string.h>
static int add(int a, int b) { return a + b; }
*/
import "C"

r := C.add(2, 3)                  // C.int 5
cs := C.CString("go")             // malloc'd copy
defer C.free(unsafe.Pointer(cs))
n := C.strlen(cs)                 // 2

Code Explained

C.CString + C.free — manual memory management

⚠ Common Mistakes

  • Mutating a []byte after creating a string from it with unsafe.String
  • Storing pointers as uintptr; the GC doesn't track them and memory can move/free
  • Blank line between the C preamble and import "C"; the preamble is ignored

✓ Tips & Best Practices

  • Use math.Float64bits, binary.* and slices before reaching for unsafe
  • Check for pure-Go alternatives (e.g. modernc.org/sqlite) to avoid cgo
  • Put cgo code in a small, well-tested package with a Go-friendly API

Quick Summary

  • unsafe — bypass type safety
  • unsafe.String/Slice — zero-copy views
  • import "C" — call C via cgo
  • costs — speed, portability, safety
