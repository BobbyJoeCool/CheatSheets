Sheet 58

Performance & Debugging

EDT violation checks · RepaintManager · setPrototypeCellValue · large table models · repaint storms · VisualVM · thread dumps

Fast and Correct

Most Swing slowness comes from three things: work on the EDT, too many repaints, and models that are expensive to read. Find EDT blocking with a thread dump (jstack or VisualVM) and look at what the AWT-EventQueue-0 thread is doing. Catch threading bugs with a checking RepaintManager. Then make models cheap and fire narrow events.

Notes

  • The EDT thread is named AWT-EventQueue-0
  • JFR + JDK Mission Control show EDT pauses
  • Renderers run for every visible cell, every repaint

EDT Check

  • A checking RepaintManager flags component access off the EDT
  • A thread dump shows exactly what is blocking the EDT

Catch EDT Violations and Slow Events

// Debug builds: report component changes made off the EDT
RepaintManager.setCurrentManager(new RepaintManager() {
    @Override public synchronized void addInvalidComponent(JComponent c) {
        check(); super.addInvalidComponent(c);
    }
    @Override public void addDirtyRegion(JComponent c, int x, int y,
                                         int w, int h) {
        check(); super.addDirtyRegion(c, x, y, w, h);
    }
    private void check() {
        if (!SwingUtilities.isEventDispatchThread())
            new Throwable("Swing used off the EDT").printStackTrace();
    }
});

// Speed up big lists and tables
list.setPrototypeCellValue(longestItem);       // skip measuring all rows
table.setRowHeight(22);                        // fixed heights are cheap
model.fireTableRowsUpdated(r, r);              // not fireTableDataChanged

// Find what froze the UI
// jcmd <pid> Thread.print | grep -A 20 AWT-EventQueue
// jcmd <pid> JFR.start duration=60s filename=ui.jfr

Code Explained

checking RepaintManager — stack trace per violation
prototype value — one measurement, not thousands
narrow fire… — repaint only what changed
jcmd Thread.print — see the EDT's stack

JavaFX Equivalent

  • checker → JavaFX throws on wrong thread itself
  • setPrototypeCellValue → setFixedCellSize
  • profiling → same JFR / VisualVM tools
  • See Java 129

Prefer / Avoid

  • guessing what's slow → thread dump or JFR first
  • fireTableDataChanged on each update → row-level events

⚠ Common Mistakes

  • Installing the checking RepaintManager in production — noisy and slower
  • Optimizing paint code before checking for EDT blocking — the wrong fix
  • Creating new Font/Color objects in renderers — garbage on every repaint

✓ Tips & Best Practices

  • Log a warning when a listener takes over 100 ms
  • Use ListModel / TableModel over your data instead of copying
  • Profile with real data sizes, not test fixtures

Quick Summary

  • EDT blocking — the #1 cause of slow Swing
  • checking RepaintManager — find threading bugs
  • prototype values + narrow events — fast lists/tables
  • thread dumps / JFR — measure first
