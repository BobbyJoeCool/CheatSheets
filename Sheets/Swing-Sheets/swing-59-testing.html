Testing Swing UIs

AssertJ Swing · FrameFixture · GuiActionRunner · java.awt.Robot · testing models without UI · java.awt.headless · Xvfb in CI

Testing Layers

Test most logic without Swing: models and presenters are plain classes (sheet 55). For the UI itself, AssertJ Swing drives real components with a Robot, finds them by name, and asserts on their state. GUI tests need a display; in CI on Linux run them under Xvfb. Keep GUI tests few and focused on wiring.

Notes

  • Give components names: setName("saveBtn")
  • Install FailOnThreadViolation… to catch EDT bugs
  • Headless mode can't create windows

EDT Check

  • GuiActionRunner.execute builds UI on the EDT
  • Fixtures wait for the EDT to go idle between steps

AssertJ Swing + JUnit 5

class LoginFrameTest {
    private FrameFixture window;

    @BeforeEach void setUp() {
        LoginFrame frame = GuiActionRunner.execute(LoginFrame::new); // EDT
        window = new FrameFixture(frame);
        window.show();
    }
    @AfterEach void tearDown() { window.cleanUp(); }

    @Test void showsErrorForBadPassword() {
        window.textBox("user").enterText("bob");
        window.textBox("password").enterText("wrong");
        window.button("login").click();
        window.label("status").requireText("Invalid password");
        window.button("login").requireEnabled();
    }
}

// Presenter test: no Swing needed
@Test void incrementFiresCount() {
    var m = new CounterModel();
    m.increment();
    assertEquals(1, m.count());
}
// CI (Linux): xvfb-run ./gradlew test

Code Explained

GuiActionRunner.execute — create on the EDT
FrameFixture — drives a real window
textBox("user") — find by setName
xvfb-run — virtual display in CI

JavaFX Equivalent

  • AssertJ Swing → TestFX
  • FrameFixture → FxRobot
  • Xvfb → Monocle headless for TestFX
  • See Java 102

Prefer / Avoid

  • testing logic through the GUI → test models/presenters directly
  • finding components by index → setName + lookup by name

⚠ Common Mistakes

  • Creating frames off the EDT in tests — flaky failures that are hard to reproduce
  • Forgetting cleanUp() — windows pile up and the Robot clicks the wrong one
  • Many slow GUI tests for logic that could be tested directly

✓ Tips & Best Practices

  • Name every interactive component in one place
  • Run GUI tests in their own Gradle task or JUnit tag
  • Take screenshots on failure for CI logs

Quick Summary

  • test logic without Swing first
  • AssertJ Swing — drive real components
  • setName — stable lookups
  • xvfb-run — GUI tests in Linux CI
