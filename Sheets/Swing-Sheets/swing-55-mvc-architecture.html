App Architecture (MVC & MVP)

Swing's model-delegate design · MVC · MVP · PropertyChangeSupport · keeping logic out of listeners · dependency injection

Structuring a Swing App

Swing components use a model-delegate design: a model holds state and a UI delegate draws it. Apply the same split to your app. Keep data and rules in models that fire PropertyChangeEvents, keep views thin, and put the glue in a presenter or controller. Listeners then become one-line calls, and the logic can be unit-tested without a window.

Notes

  • Views know presenters; models know neither
  • PropertyChangeSupport gives models events
  • Pass dependencies in through constructors

EDT Check

  • Models may change on any thread; views must re-dispatch to the EDT
  • Presenters start SwingWorkers for slow calls

Model + Presenter + Thin View

class CounterModel {
    private final PropertyChangeSupport pcs =
            new PropertyChangeSupport(this);
    private int count;
    void addListener(PropertyChangeListener l) {
        pcs.addPropertyChangeListener(l);
    }
    int count() { return count; }
    void increment() {
        int old = count;
        pcs.firePropertyChange("count", old, ++count);
    }
}
class CounterPresenter {
    CounterPresenter(CounterModel m, CounterView v) {
        v.onIncrement(m::increment);                     // view → model
        m.addListener(e -> SwingUtilities.invokeLater(   // model → view
                () -> v.showCount(m.count())));
    }
}
class CounterView extends JPanel {
    private final JLabel label = new JLabel("0");
    private final JButton plus = new JButton("+1");
    CounterView() { add(label); add(plus); }
    void onIncrement(Runnable r) { plus.addActionListener(e->r.run()); }
    void showCount(int n) { label.setText(Integer.toString(n)); }
}

Code Explained

PropertyChangeSupport — model fires events
presenter — wires view and model
invokeLater — model events may come from any thread
view — no logic, just show and forward

JavaFX Equivalent

  • PropertyChangeSupport → JavaFX properties
  • presenter wiring → bindings
  • FXML controller ≈ presenter
  • See Java 132

Prefer / Avoid

  • business logic in actionPerformed → presenter / service methods
  • static global state → constructor injection

⚠ Common Mistakes

  • Putting SQL and validation in listeners — impossible to test and reuse
  • Updating views straight from model events fired on a worker thread
  • Views reading each other's components — couple through models instead

✓ Tips & Best Practices

  • Unit-test models and presenters with no Swing at all
  • Use a small view interface so presenters can be tested with fakes
  • Keep one presenter per screen

Quick Summary

  • model-delegate — Swing's own design
  • models + PropertyChangeSupport — observable state
  • presenter — glue between view and model
  • thin views — easy to change, easy to test
