Sheet 16

Parallel Execution

junit.jupiter.execution.parallel.enabled · mode.default · @Execution · @ResourceLock · @Isolated · thread-safety

Run Tests on Several Threads

JUnit can run tests in parallel inside one JVM. Turn it on in junit-platform.properties, choose whether methods and classes run concurrently by default, then mark exceptions: @Execution(SAME_THREAD) for tests that must stay serial, @ResourceLock for tests sharing a resource, and @Isolated for a class that must run alone.

Notes

  • Off by default; tests must be thread-safe first
  • Strategy dynamic sizes the pool from CPU cores
  • Build-tool forking (Surefire forkCount, Gradle maxParallelForks) is a separate, process-level option
  • JUnit 6.1 adds a new parallel executor implementation

In Spring Boot

  • Spring's cached context is shared across threads; beans with mutable state break under parallel tests
  • @DirtiesContext and @MockitoBean changes don't play well with concurrent classes
  • Many teams keep @SpringBootTest classes SAME_THREAD and parallelize plain unit tests

Config and Annotations

# src/test/resources/junit-platform.properties
junit.jupiter.execution.parallel.enabled = true
junit.jupiter.execution.parallel.mode.default = concurrent
junit.jupiter.execution.parallel.mode.classes.default = concurrent
junit.jupiter.execution.parallel.config.strategy = dynamic
junit.jupiter.execution.parallel.config.dynamic.factor = 1

# In code:
# @Execution(ExecutionMode.SAME_THREAD)       — this class / method runs serially
# @ResourceLock(value = "db", mode = READ_WRITE)
# @ResourceLock(Resources.SYSTEM_PROPERTIES)  — built-in lock names
# @Isolated                                   — nothing else runs at the same time

# Process-level parallelism (separate JVMs):
# Maven Surefire: <forkCount>2</forkCount> <reuseForks>true</reuseForks>
# Gradle:        tasks.test { maxParallelForks = 2 }

Code Explained

mode.default controls methods within a class; mode.classes.default controls classes
dynamic with factor 1 uses one thread per core
@ResourceLock serializes only the tests that share the named resource
Forking runs separate JVMs, which isolates static state but costs memory

JUnit 4 / TestNG Equivalent

  • JUnit 4 No in-JVM parallel support (Surefire parallel option with JUnit 4 provider)
  • TestNG parallel="methods" / thread-count in testng.xml

Prefer / Avoid

  • global SAME_THREAD because of one bad test → @ResourceLock or @Isolated on that test
  • static mutable fields → instance state per test
  • turning on parallel mode without checking → run with --count/repeats first to flush races

⚠ Common Mistakes

  • Enabling parallel mode with tests that share static state or files
  • Parallel tests writing to System.out and asserting on captured output
  • Expecting @BeforeAll static setup to be thread-safe automatically

✓ Tips & Best Practices

  • Start with classes concurrent and methods same-thread, then widen
  • Lock shared resources explicitly with @ResourceLock
  • Measure; parallelism helps CPU-bound suites more than I/O-bound ones

Quick Summary

  • parallel.enabled = true
  • mode.default / mode.classes.default
  • @ResourceLock / @Isolated — exceptions
  • forking — separate JVMs
