The Extension Model

@ExtendWith · @RegisterExtension · lifecycle callbacks · ParameterResolver · ExtensionContext.Store · writing a small extension

Plug Behavior Into the Lifecycle

Everything JUnit 4 did with runners and rules, Jupiter does with extensions: classes that implement callback interfaces (BeforeEachCallback, AfterTestExecutionCallback…) or resolve parameters. Register them declaratively with @ExtendWith, or programmatically with @RegisterExtension on a field when they need configuration. Mockito, Spring and Testcontainers all integrate this way.

Notes

  • Several extensions can be combined; they run in registration order
  • ExtensionContext.Store keeps state per test, class or run
  • Meta-annotations bundle extensions: @ExtendWith(...) @interface IntegrationTest
  • Global auto-registration via ServiceLoader (opt-in)

In Spring Boot

  • @SpringBootTest is meta-annotated with @ExtendWith(SpringExtension.class)
  • SpringExtension resolves @Autowired constructor and method parameters
  • Order matters: put MockitoExtension after Spring if both are present

Using and Writing Extensions

@ExtendWith(MockitoExtension.class)
class OrderServiceTest { }

class TimingExtension implements BeforeTestExecutionCallback, AfterTestExecutionCallback {
    private static final Namespace NS = Namespace.create(TimingExtension.class);

    public void beforeTestExecution(ExtensionContext ctx) {
        ctx.getStore(NS).put("start", System.nanoTime());
    }
    public void afterTestExecution(ExtensionContext ctx) {
        long start = ctx.getStore(NS).remove("start", long.class);
        ctx.publishReportEntry("ms", String.valueOf((System.nanoTime() - start) / 1_000_000));
    }
}

class ClockResolver implements ParameterResolver {
    public boolean supportsParameter(ParameterContext p, ExtensionContext e) {
        return p.getParameter().getType() == Clock.class;
    }
    public Object resolveParameter(ParameterContext p, ExtensionContext e) {
        return Clock.fixed(Instant.parse("2026-11-04T12:00:00Z"), ZoneOffset.UTC);
    }
}

@ExtendWith({TimingExtension.class, ClockResolver.class})
class InvoiceTest {
    @RegisterExtension
    static WireMockExtension wm = WireMockExtension.newInstance().build();

    @Test void dueInThirtyDays(Clock clock) { /* clock injected */ }
}

Code Explained

The Store keeps the start time between the two callbacks for this test
publishReportEntry adds data to test reports
A ParameterResolver lets tests and lifecycle methods ask for a Clock
@RegisterExtension on a static field configures an extension instance in code

JUnit 4 / TestNG Equivalent

  • JUnit 4 @RunWith(MockitoJUnitRunner.class) (one runner per class) and @Rule / @ClassRule fields
  • TestNG @Listeners, ITestListener, IHookable

Prefer / Avoid

  • abstract base test classes for shared setup → extensions or meta-annotations
  • static helper state across tests → ExtensionContext.Store
  • manual Clock setup in every test → a ParameterResolver

⚠ Common Mistakes

  • Storing state in static fields of an extension, which breaks with parallel tests
  • Assuming extension order when registering with several annotations
  • Recreating Mockito / Spring integration by hand instead of using their extensions

✓ Tips & Best Practices

  • Bundle common extensions into a meta-annotation like @IntegrationTest
  • Use the Store with a unique Namespace
  • Check JUnit Pioneer and library docs before writing your own

Quick Summary

  • @ExtendWith — declarative
  • @RegisterExtension — configured instance

  • ExtensionContext.Store — per-test state
