Testcontainers

@Testcontainers · @Container · PostgreSQLContainer · @ServiceConnection · @DynamicPropertySource · container reuse

Real Databases and Services in Docker

Testcontainers starts real services (PostgreSQL, Kafka, Redis, any image) in Docker for your tests and throws them away afterwards. Tests run against the same database engine as production instead of an in-memory stand-in. In Spring Boot, @ServiceConnection wires the container's URL and credentials into your beans automatically.

Notes

  • Needs Docker (or a compatible runtime) on the machine and CI runner
  • Static @Container fields start once per class; instance fields once per test
  • Testcontainers 2 reorganized module packages; check imports when upgrading
  • Reuse containers across runs locally with withReuse(true) + testcontainers.reuse.enable=true

PostgreSQL in Tests

@SpringBootTest
@Testcontainers
class OrderRepositoryIT {

    @Container
    @ServiceConnection                              // Boot sets spring.datasource.*
    static PostgreSQLContainer postgres = new PostgreSQLContainer("postgres:17-alpine");

    @Autowired OrderRepository repo;

    @Test
    void savesAndLoads() {
        Order saved = repo.save(new Order(OrderStatus.NEW));
        assertThat(repo.findById(saved.getId())).isPresent();
    }
}

Code Explained

@Testcontainers starts and stops @Container fields around the class
@ServiceConnection knows how to configure Spring for common images
@DynamicPropertySource passes container ports to custom properties
Pin image tags (postgres:17-alpine) so tests don't change under you

JUnit 4 / TestNG Equivalent

  • JUnit 4 @ClassRule public static PostgreSQLContainer… with Testcontainers' JUnit 4 support
  • TestNG Start containers in @BeforeClass and stop in @AfterClass manually

Prefer / Avoid

  • H2 pretending to be Postgres → PostgreSQLContainer
  • one container per test method → static containers per class or a shared singleton
  • latest image tags → pinned versions

⚠ Common Mistakes

  • Running Testcontainers tests where Docker isn't available and getting confusing errors
  • Non-static @Container fields starting a fresh database for every test
  • Mixing up container-internal ports and mapped host ports

✓ Tips & Best Practices

  • Name integration tests *IT and run them with Failsafe / a separate Gradle task
  • Use @EnabledIf with Docker availability (sheet 10) for laptops without Docker
  • Prefer @ServiceConnection over hand-written properties

Quick Summary
