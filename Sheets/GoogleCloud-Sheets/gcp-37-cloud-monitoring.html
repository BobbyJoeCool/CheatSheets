Cloud Monitoring

metrics & resource types · alerting policies · notification channels · uptime checks · dashboards · Managed Service for Prometheus & PromQL

Metrics and Alerts

Cloud Monitoring collects metrics from Google Cloud services automatically, from VMs via the Ops Agent, and from apps via OpenTelemetry or Managed Service for Prometheus. Alerting policies fire on metric conditions (MQL is deprecated; use PromQL or filter-based conditions) and notify channels (email, Slack, PagerDuty, Pub/Sub). Uptime checks probe endpoints from around the world.

Key Points

  • Metrics scopes let one project view metrics from many projects
  • SLO monitoring with burn-rate alerts is built in
  • Ops Agent collects VM logs and metrics
  • Dashboards can be JSON-defined and version-controlled

Alert Policy, Channel, Uptime Check

gcloud beta monitoring channels create --display-name="On-call email" \
    --type=email --channel-labels=email_address=oncall@acme.com
gcloud monitoring policies create --policy-from-file=api-5xx.yaml
gcloud monitoring uptime create shop-home --resource-type=uptime-url \
    --resource-labels=host=shop.acme.com,project_id=shop-prod-4821 \
    --path=/healthz --protocol=https --period=1
gcloud monitoring dashboards create --config-from-file=dashboard.json

api-5xx.yaml

displayName: "API 5xx rate above 2%"
combiner: OR
conditions:
  - displayName: "5xx ratio"
    conditionPrometheusQueryLanguage:
      query: |
        sum(rate(run_googleapis_com:request_count{
          service_name="api",response_code_class="5xx"}[5m]))
        /
        sum(rate(run_googleapis_com:request_count{service_name="api"}[5m]))
        > 0.02
      duration: 300s
      evaluationInterval: 60s
notificationChannels:
  - projects/shop-prod-4821/notificationChannels/1234567890
documentation:
  content: "Runbook: https://wiki.acme.com/runbooks/api-5xx"
alertStrategy:
  autoClose: 1800s

Code Explained

The channel delivers alert notifications by email
The PromQL condition fires when 5xx exceeds 2% for 5 minutes
Documentation links the runbook in every notification
Uptime checks probe /healthz every minute from several regions

Cost Check

  • Google Cloud service metrics are free; custom / Prometheus samples bill per volume
  • Alerting bills per condition and time series scanned
  • High-cardinality labels multiply metric costs

Do & Don't

  • Do Alert on user-facing symptoms (errors, latency, SLO burn)
  • Do Add a runbook link to every policy
  • Don’t Write new alerts in MQL (deprecated)
  • Don’t Page on every CPU spike

Local Testing

  • Run Prometheus + Grafana locally to draft PromQL
  • Test policies in a dev project with low thresholds
  • Export dashboards as JSON and commit them

Production Checklist

  • SLOs with burn-rate alerts on key services
  • Uptime checks on public endpoints
  • Policies and dashboards as code
