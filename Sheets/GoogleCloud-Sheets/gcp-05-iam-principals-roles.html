Sheet 05

IAM Principals & Roles

principals (users, groups, service accounts) · basic vs predefined vs custom roles · gcloud projects add-iam-policy-binding · inheritance down the hierarchy · Google groups for access

Who Can Do What

Google Cloud IAM grants roles (bundles of permissions) to principals (Google accounts, Google groups, service accounts, domains, federated identities) on a resource: organization, folder, project or individual resource. Grants inherit downward. Basic roles (Owner, Editor, Viewer) are too broad; use predefined roles or narrow custom roles.

Key Points

  • Permissions look like service.resource.verb (run.services.update)
  • Role names: roles/run.developer, roles/storage.objectViewer
  • Grant to Google groups, not individuals
  • Allow policies are additive; deny policies override (sheet 06)

Grant, Inspect, Customize

gcloud projects add-iam-policy-binding shop-prod-4821 \
    --member="group:shop-devs@acme.com" --role="roles/run.developer"
gcloud projects add-iam-policy-binding shop-prod-4821 \
    --member="serviceAccount:api@shop-prod-4821.iam.gserviceaccount.com" \
    --role="roles/cloudsql.client"

# Resource-level grant: one bucket only
gcloud storage buckets add-iam-policy-binding gs://acme-media-prod \
    --member="serviceAccount:api@shop-prod-4821.iam.gserviceaccount.com" \
    --role="roles/storage.objectUser"

gcloud projects get-iam-policy shop-prod-4821 \
    --flatten="bindings[].members" --filter="bindings.members:group:shop-devs" \
    --format="table(bindings.role)"
gcloud iam roles describe roles/run.developer \
    --format="value(includedPermissions)"

gcloud iam roles create shopDeployer --project=shop-prod-4821 \
    --title="Shop Deployer" --stage=GA \
    --permissions=run.services.get,run.services.update,iam.serviceAccounts.actAs

Code Explained

Members are typed: user:, group:, serviceAccount:, domain:
Resource-level bindings keep access narrow
Flatten + filter lists the roles one group holds
The custom role has only what a deployer needs

AWS / Azure Equivalent

Cost Check

  • IAM is free
  • Broad Editor grants let anyone create expensive resources
  • Use org policies to restrict expensive services or locations

Do & Don't

  • Do Grant predefined roles to groups at the narrowest resource
  • Do Review the IAM recommender's excess-permission suggestions
  • Don’t Grant roles/owner or roles/editor to apps
  • Don’t Grant at the organization when a project would do

Local Testing

  • Policy Troubleshooter explains allow / deny for a principal and permission
  • gcloud projects get-iam-policy audits grants
  • Test with impersonation before granting widely

Production Checklist

  • No basic roles for workloads; groups for humans
  • IAM recommender reviewed regularly
  • Bindings managed in Terraform
