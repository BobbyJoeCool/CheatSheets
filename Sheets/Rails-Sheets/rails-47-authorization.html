Authorization

before_action guards · scoping to Current.user · role enums · Pundit policies · authorize / policy_scope · 403 vs 404

Who May Do What

Authentication answers "who are you"; authorization answers "may you do this". Rails has no built-in authorization framework. The simplest reliable approach is scoping: load records through the current user's associations. For role and rule-heavy apps, policy objects (Pundit, Action Policy) keep rules testable.

Notes

  • Scoped lookups (Current.user.posts.find(id)) raise 404 for others' records
  • Check permissions on the server for every action, not just by hiding buttons
  • Return 404 for private records to avoid revealing they exist; 403 when existence is public
  • Admin areas: a namespaced base controller with one guard

Scoping & Guards

class PostsController < ApplicationController
  before_action :set_post, only: %i[edit update destroy]

  private

  def set_post
    @post = Current.user.posts.find(params.expect(:id))   # 404 if not theirs
  end
end

class Admin::BaseController < ApplicationController
  before_action { head :forbidden unless Current.user&.admin? }
end

Pundit Policy

class PostPolicy < ApplicationPolicy
  def update? = user.admin? || record.user_id == user.id
  def destroy? = update?

  class Scope < ApplicationPolicy::Scope
    def resolve = user.admin? ? scope.all : scope.where(user:)
  end
end

class PostsController < ApplicationController
  include Pundit::Authorization
  def index  = @posts = policy_scope(Post)
  def update
    @post = Post.find(params.expect(:id))
    authorize @post                          # raises NotAuthorizedError
    @post.update!(post_params)
    redirect_to @post, status: :see_other
  end
end

Code Explained

Association scoping — authorization by construction
Inline before_action block — quick guard for a namespace
update? — one predicate per action
policy_scope — list only what the user may see
policy(@post).update? in views — hide links the user can't use

The Rails Way

  • Post.find(id) then if post.user != current_user → Current.user.posts.find(id)
  • Role checks scattered across views and controllers → one policy class per model
  • if user.role == "admin" strings → enum :role with admin?

⚠ Common Mistakes

  • Only hiding the Edit button; a crafted PATCH request still works without a server check
  • Loading by id first and authorizing after, then forgetting the check in one action
  • Policies that query the database for every list row (N+1 inside update?)

✓ Tips & Best Practices

  • Add after_action :verify_authorized (Pundit) to catch actions missing a check
  • Test policies as plain Ruby objects: fast and focused
  • Keep roles coarse; express fine rules in policy methods

Quick Summary

  • 404 / 403 — choose deliberately
