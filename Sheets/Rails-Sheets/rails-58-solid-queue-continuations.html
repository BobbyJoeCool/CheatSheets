Solid Queue & Job Continuations

Solid Queue · config/queue.yml · recurring.yml · bin/jobs · limits_concurrency · ActiveJob::Continuable (8.1) · step · Mission Control

The Rails 8 Job Backend

Solid Queue stores jobs in a database table and runs them with workers, dispatchers for scheduled jobs, and a scheduler for recurring tasks. No Redis needed. Rails 8.1 adds job continuations: long jobs are split into steps with cursors so a deploy or restart resumes where it left off instead of starting over.

Notes

  • Run workers with bin/jobs, or inside Puma with SOLID_QUEUE_IN_PUMA=1 (single-server default)
  • Recurring tasks are defined in config/recurring.yml
  • Concurrency controls limit how many jobs with the same key run at once
  • Mission Control – Jobs (gem) is a web UI for queues, failures and retries

config/recurring.yml

production:
  nightly_digest:
    class: SendAllDigestsJob
    queue: mailers
    schedule: every day at 6am
  clear_finished_jobs:
    command: "SolidQueue::Job.clear_finished_in_batches"
    schedule: every hour at minute 12

Concurrency Limits

class SyncAccountJob < ApplicationJob
  limits_concurrency to: 1, key: ->(account) { account }, duration: 10.minutes
  def perform(account) = account.sync!
end

Continuations (8.1)

class ImportJob < ApplicationJob
  include ActiveJob::Continuable

  def perform(import)
    @import = import
    step :validate do
      @import.validate!
    end
    step :process do |step|
      @import.rows.find_each(start: step.cursor) do |row|
        row.process!
        step.advance! from: row.id          # save progress
      end
    end
    step :finish                            # calls #finish
  end

  private def finish = @import.complete!
end

Code Explained

schedule: — natural-language schedules parsed by Fugit
command: — Ruby string evaluated on schedule, no job class needed
limits_concurrency — extra jobs wait (blocked) until the slot frees
step.cursor / advance! — checkpoint; resumes after interruption
Completed steps are skipped when the job resumes

The Rails Way

  • A separate cron box with rails runner → recurring.yml
  • Redis + Sidekiq for a small app → Solid Queue on the existing database
  • One giant job restarting from zero after each deploy → continuation steps

⚠ Common Mistakes

  • Mounting Mission Control without authentication
  • Running SOLID_QUEUE_IN_PUMA on several web servers and also a job server, doubling workers by accident
  • Expecting continuations to save local variables; only the cursor and completed steps persist

✓ Tips & Best Practices

  • Use separate queues for slow and fast work so one doesn't starve the other
  • Keep each continuation step resumable on its own; cursors should be stable ids
  • Check failed jobs regularly; Solid Queue keeps them until you retry or discard

Quick Summary

  • limits_concurrency — one at a time
