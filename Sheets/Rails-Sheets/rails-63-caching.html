Sheet 63

Caching & Solid Cache

Rails.cache.fetch · fragment caching · Russian doll · touch: true · cache keys & versions · Solid Cache · fresh_when / stale?

Do Expensive Work Once

Rails caches at several levels: low-level values with Rails.cache.fetch, fragments of views with cache, and whole responses with HTTP conditional GET. Cache keys include the record's updated_at version, so changing a record invalidates its fragments automatically. Rails 8 uses Solid Cache, a disk-friendly database-backed store.

Notes

  • Caching is off in development by default; toggle with bin/rails dev:cache
  • Key-based expiration: no manual deletes when keys include versions
  • touch: true on belongs_to bumps the parent so nested fragments refresh
  • Solid Cache can hold far more than RAM-based stores because it uses disk

Low-Level

Rails.cache.fetch(["weather", city], expires_in: 30.minutes) do
  WeatherApi.forecast(city)                   # only on a miss
end
Rails.cache.write("k", 1); Rails.cache.read("k"); Rails.cache.delete("k")
Rails.cache.fetch_multi(*posts) { |post| post.expensive_summary }
Rails.cache.increment("hits")

Fragments & Russian Dolls

<% cache @post do %>                             <%# key: views/posts/1-20261023… %>
  <h1><%= @post.title %></h1>
  <% @post.comments.each do |comment| %>
    <% cache comment do %><%= render comment %><% end %>
  <% end %>
<% end %>
<%= render partial: "comments/comment", collection: @post.comments, cached: true %>

Model & Config

class Comment < ApplicationRecord
  belongs_to :post, touch: true                 # comment change → post updated_at
end

# config/environments/production.rb
config.cache_store = :solid_cache_store

Code Explained

Array keys — joined; models contribute cache_key_with_version
fetch_multi — one round trip for many keys
cache @post — fragment invalidates when @post.updated_at changes
Nested caches reuse inner fragments when only one comment changes
touch: true — keeps the outer fragment fresh

The Rails Way

  • Manual Rails.cache.delete in callbacks → version-based keys
  • Caching a loop of renders → collection rendering with cached: true
  • Memcached/Redis just for cache in a small app → Solid Cache on the database

⚠ Common Mistakes

  • Caching per-user content under a shared key, leaking data between users
  • Forgetting touch: true, so edited comments show stale inside a cached post
  • Caching ActiveRecord relations (lazy) instead of computed values

✓ Tips & Best Practices

  • Include Current.user or locale in keys for personalized fragments
  • Use bin/rails dev:cache to test caching locally
  • Watch cache_read.active_support events to measure hit rates
