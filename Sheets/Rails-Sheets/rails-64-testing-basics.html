Testing Basics & Fixtures

ActiveSupport::TestCase · bin/rails test · test/ layout · fixtures · assert_difference · parallelize

Minitest, the Rails Default

Rails uses Minitest with Rails-specific test case classes and assertions. Each test runs in a transaction that rolls back, so tests don't affect each other. Fixtures are YAML files of sample rows loaded once into the test database and referenced by name.

Notes

  • Folders: test/models, controllers, integration, system, mailers, jobs, fixtures
  • test "name" do ... end defines test_name methods
  • parallelize(workers: :number_of_processors) is on by default
  • Fixtures support ERB and reference associations by label

test/models/post_test.rb

require "test_helper"

class PostTest < ActiveSupport::TestCase
  test "requires a title" do
    post = Post.new(title: "")
    assert_not post.valid?
    assert_includes post.errors[:title], "can't be blank"
  end

  test "publishing sets published_at" do
    post = posts(:draft)
    post.publish!
    assert post.published?
    assert_not_nil post.published_at
  end
end

test/fixtures/posts.yml

hello:
  title: Hello Rails
  user: ann                       # association by fixture label
  published: true
  created_at: <%= 2.days.ago %>
draft:
  title: Work in progress
  user: ann

Running

bin/rails test                        # all except system tests
bin/rails test test/models/post_test.rb:12   # one test by line
bin/rails test -n /publish/           # by name pattern
bin/rails test:all                    # including system tests

Code Explained

posts(:draft) — load a fixture by label
assert_not — reads better than assert !x
user: ann — fixture association, no ids needed
:12 — run the test at that line
Transactions — each test's writes roll back

The Rails Way

  • Creating every record in setup → fixtures for shared baseline data
  • assert post.valid? == false → assert_not post.valid?
  • Testing private methods → test public behavior

⚠ Common Mistakes

  • Relying on fixture ids; reference by label because ids are hashed from labels
  • Tests that depend on run order; parallel and random ordering will expose them
  • Fixtures that bypass validations becoming invalid over time; add a test that validates all fixtures

✓ Tips & Best Practices

  • Use bin/rails test --fail-fast (-f) while iterating
  • Keep fixtures small and realistic; add factories only if fixtures get unwieldy
  • Run bin/rails test in bin/ci (8.1) before pushing
