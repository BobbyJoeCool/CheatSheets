Migrations — Schema, Indexes & Seeds

schema.rb vs structure.sql · add_index · add_foreign_key · change_column_null · reversible · db:prepare · db:seed

Keeping the Schema Honest

The schema file is the authoritative snapshot of the database; new databases load it rather than replaying every migration. Use indexes for lookups and uniqueness, foreign keys and check constraints for integrity, and reversible or up/down for changes Rails can't reverse on its own. Seeds load starter data.

Schema Notes

  • schema.rb is database-agnostic Ruby; structure.sql keeps vendor-specific features (views, triggers)
  • Switch with config.active_record.schema_format = :sql
  • Unique indexes are the only reliable uniqueness guarantee
  • Seeds should be idempotent: running twice shouldn't duplicate data

Indexes & Constraints

class HardenOrders < ActiveRecord::Migration[8.1]
  def change
    add_index :orders, [:user_id, :created_at]               # composite
    add_index :orders, :number, unique: true
    add_index :orders, :status, where: "status = 'open'"     # partial (PG/SQLite)
    add_foreign_key :orders, :users, on_delete: :cascade
    add_check_constraint :orders, "total >= 0", name: "total_non_negative"
    change_column_null :orders, :email, false, ""             # backfill NULLs
    change_column_default :orders, :status, from: nil, to: "open"
  end
end

Irreversible Pieces

def change
  reversible do |dir|
    dir.up   { execute "CREATE VIEW open_orders AS SELECT * FROM orders WHERE status = 'open'" }
    dir.down { execute "DROP VIEW open_orders" }
  end
end

db/seeds.rb

%w[News Tutorials Releases].each do |name|
  Category.find_or_create_by!(name: name)
end
User.find_or_create_by!(email: "admin@example.com") do |u|
  u.password = "change-me-now"
end

Code Explained

Composite index — order matters: it also serves queries on user_id alone
where: — partial index, smaller and faster for hot subsets
change_column_null ..., false, "" — fill NULLs then add NOT NULL
from: / to: — makes a default change reversible
find_or_create_by! — idempotent seeds

The Rails Way

  • validates :email, uniqueness: true alone → also add_index ..., unique: true
  • Model.create! in seeds → find_or_create_by!
  • Running every migration on a fresh machine → bin/rails db:prepare (loads the schema)

Schema Formats

FormatKeeps
schema.rbTables, indexes, FKs, check constraints, enums (PG)
structure.sqlEverything the DB can dump: views, triggers, functions

Index Options

OptionUse
unique: trueEnforce uniqueness
where:Partial index
order: { created_at: :desc }Sort order
algorithm: :concurrentlyPG: no table lock (with disable_ddl_transaction!)
name:Custom (long names are truncated)

⚠ Common Mistakes

  • Adding an index on a large PostgreSQL table without algorithm: :concurrently, locking writes
  • Putting data changes (Model.update_all) in schema migrations that later break when the model changes
  • Seeds with create! that fail on the second run

✓ Tips & Best Practices

  • For data backfills, use a one-off script/ file or a job, not a migration
  • Add disable_ddl_transaction! with concurrent indexes
  • Check db/schema.rb diffs in code review; surprise changes mean someone's local DB drifted

Quick Summary

  • schema.rb — DB snapshot
  • add_index unique: — real uniqueness
  • reversible — custom up/down
  • seeds.rb — idempotent starter data
