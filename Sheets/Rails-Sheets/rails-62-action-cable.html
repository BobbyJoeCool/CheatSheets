Action Cable & Solid Cable

WebSockets in Rails

Action Cable adds WebSockets: a browser subscribes to a channel and the server pushes messages to it. Turbo Streams broadcasting uses Action Cable underneath, so many apps never write a channel. Rails 8 uses Solid Cable, which relays messages through the database instead of Redis.

Notes

  • Connection authenticates the socket once; channels authorize subscriptions
  • Use channels directly for chat, presence, or custom client-side handling
  • Solid Cable polls a table (default every 0.1 s) and trims old messages

app/channels/application_cable/connection.rb

module ApplicationCable
  class Connection < ActionCable::Connection::Base
    identified_by :current_user

    def connect
      session = Session.find_by(id: cookies.signed[:session_id])
      self.current_user = session&.user || reject_unauthorized_connection
    end
  end
end

app/channels/room_channel.rb

class RoomChannel < ApplicationCable::Channel
  def subscribed
    @room = current_user.rooms.find(params[:id])
    stream_for @room
  end

  def speak(data)                          # called from JS
    @room.messages.create!(user: current_user, body: data["body"])
  end
end

RoomChannel.broadcast_to(room, { body: "Hi", from: "Ann" })   # from anywhere

JavaScript Consumer

import consumer from "channels/consumer"
const room = consumer.subscriptions.create({ channel: "RoomChannel", id: 7 }, {
  received(data) { appendMessage(data) },
  speak(body)    { this.perform("speak", { body }) }
})

Code Explained

cookies.signed[:session_id] — reuse the auth generator's session cookie
reject_unauthorized_connection — refuse the socket
stream_for @room — subscribe to a stream named for the record
perform("speak") — calls the channel's speak method
config/cable.yml: adapter: solid_cable — DB-backed pub/sub, no Redis

The Rails Way

  • Custom channels for "update this list" → Turbo Stream broadcasts
  • Polling endpoints with setInterval → Action Cable or Turbo Streams
  • Trusting params[:id] in subscribed → scope through current_user

⚠ Common Mistakes

  • Authorizing only in connect and letting any user subscribe to any room id
  • Broadcasting from inside a transaction; clients may refetch before commit
  • Using the async adapter in production with multiple processes

✓ Tips & Best Practices

  • Start with Turbo Streams; write a channel only when the client needs custom JS handling
  • Keep payloads small; send ids or rendered HTML, not whole records
  • Test channels with ActionCable::Channel::TestCase and assert_broadcast_on

Quick Summary

  • Connection — authenticate socket
  • Channel — subscribe and act
  • broadcast_to — push messages
  • Solid Cable — DB-backed default
