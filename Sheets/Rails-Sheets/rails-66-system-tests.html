Sheet 66

System Tests

ApplicationSystemTestCase · driven_by · Capybara visit / click_on / fill_in · assert_selector · headless Chrome · screenshots

Testing in a Real Browser

System tests drive a real browser through Capybara, so JavaScript, Turbo and Stimulus behavior is exercised. They are the slowest tests, so keep them for critical user journeys. Failures save a screenshot automatically in tmp/screenshots.

Notes

  • bin/rails test skips system tests; run bin/rails test:system or test:all
  • Default driver: Selenium with headless Chrome
  • Capybara waits automatically for elements to appear (up to default_max_wait_time)
  • Generate with bin/rails g system_test posts

test/application_system_test_case.rb

class ApplicationSystemTestCase < ActionDispatch::SystemTestCase
  driven_by :selenium, using: :headless_chrome, screen_size: [1400, 1000]

  def sign_in_as(user)
    visit new_session_url
    fill_in "email_address", with: user.email_address
    fill_in "password", with: "password"
    click_on "Sign in"
  end
end

test/system/posts_test.rb

require "application_system_test_case"

class PostsTest < ApplicationSystemTestCase
  setup { sign_in_as users(:ann) }

  test "writing a post" do
    visit posts_url
    click_on "New post"
    fill_in "Title", with: "System tests"
    fill_in_rich_textarea "Body", with: "Run in Chrome"
    select "Tutorials", from: "Category"
    check "Featured"
    click_on "Create Post"

    assert_text "Post created"
    assert_selector "h1", text: "System tests"
  end
end

Code Explained

driven_by — browser, headless mode, window size
fill_in "Title" — finds by label, name or id
fill_in_rich_textarea — Action Text helper (8.0 name)
accept_confirm { click_on "Delete" } — handle the Turbo confirm dialog
assert_text — waits for the text to appear

The Rails Way

  • sleep 2 waiting for JS → Capybara's waiting matchers (assert_text)
  • System tests for every validation → integration tests; system tests for flows
  • Selecting by CSS classes → by visible labels and text, like a user

⚠ Common Mistakes

  • Using find(...).click then asserting with non-waiting Ruby (page.html.include?)
  • Sharing state between system tests through the database without fixtures
  • Forgetting system tests don't run in plain bin/rails test

✓ Tips & Best Practices

  • Use driven_by :cuprite (gem) for faster Chrome without Selenium
  • Run with HEADLESS=0-style toggles locally to watch the browser
  • Keep a small "smoke" suite of system tests for sign-in, checkout and other critical paths

Quick Summary

  • system test — real browser
  • Capybara — user-like actions
  • waiting matchers — no sleeps
  • test:system — run them
