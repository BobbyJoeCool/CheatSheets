Sheet 15

Sessions, Cookies & Flash

session · reset_session · cookies · signed / encrypted · permanent · flash · flash.now · notice: / alert:

State Between Requests

HTTP is stateless, so Rails stores small values in cookies. session is an encrypted cookie store by default. cookies.signed prevents tampering and cookies.encrypted also hides the value. Flash messages survive exactly one redirect, which is how "Post created" appears on the next page.

Storage Notes

  • Cookie session limit is about 4 KB: store ids, never whole objects
  • Signing/encryption uses secret_key_base from credentials
  • flash.now shows a message on the current render only
  • The Rails 8 auth generator stores a signed session_id cookie pointing at a Session row

Session & Cookies

session[:cart_id] = cart.id
session[:cart_id]                       # read in any later request
session.delete(:cart_id)
reset_session                           # on login/logout: blocks fixation

cookies[:theme] = "dark"                # plain, readable by JS
cookies[:theme] = { value: "dark", expires: 1.year, httponly: true }
cookies.signed[:user_id] = user.id      # tamper-proof, readable
cookies.encrypted[:token] = "s3cret"    # tamper-proof and hidden
cookies.permanent.signed[:remember] = user.id   # 20-year expiry
cookies.delete(:theme)

Flash

redirect_to @post, notice: "Saved"                  # flash[:notice]
redirect_to root_path, alert: "Access denied"
flash[:success] = "Welcome!"                        # custom key
flash.now[:alert] = "Fix the errors"; render :new, status: 422
flash.keep                                          # survive one more redirect

Layout

<% flash.each do |type, msg| %>
  <div class="flash flash-<%= type %>"><%= msg %></div>
<% end %>

Code Explained

reset_session — new session id; call it when privilege changes
httponly: true — JavaScript can't read the cookie
signed vs encrypted — integrity only vs integrity + secrecy
notice: / alert: — shortcuts built into redirect_to
flash.now + render — no redirect, so a normal flash would leak to the next page

The Rails Way

  • Storing a User object in the session → store the id and look it up
  • flash[:alert] before render → flash.now[:alert]
  • A plain cookie for anything security-related → cookies.signed or .encrypted

Session Stores

StoreNotes
CookieStoreDefault. Encrypted, 4 KB, no server state
CacheStoreUses Rails.cache (e.g. Solid Cache)
ActiveRecordStoreGem; DB table, server-side revoke
Auth generatorCookie holds Session id; rows revocable

Cookie Options

OptionEffect
expires:Time or duration; omit for browser-session
httponly:Hide from JavaScript
secure:HTTPS only (default in production)
same_site::lax (default), :strict, :none
domain::all to share across subdomains

⚠ Common Mistakes

  • Putting large or growing data in the cookie session and hitting CookieOverflow
  • Not calling reset_session on login, leaving the app open to session fixation
  • Trusting a plain cookies[:user_id]; users can edit it in the browser

✓ Tips & Best Practices

  • Use the auth generator's database-backed sessions so users can log out other devices
  • Render flash once in the layout, keyed by type for CSS classes
  • Rotate secret_key_base only with a rotation config, or every signed cookie becomes invalid

Quick Summary

  • session — encrypted per-user store
  • cookies.signed / encrypted — safe cookies
  • flash — next request
  • flash.now — this render
