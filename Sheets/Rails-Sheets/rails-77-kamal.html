Sheet 77

Deploying with Kamal

config/deploy.yml · kamal setup · kamal deploy · kamal-proxy · .kamal/secrets · accessories · registry-free deploys (8.1)

Zero-Downtime Deploys to Your Own Servers

Kamal (included in new apps) deploys the Docker image to any Linux server over SSH. kamal-proxy switches traffic to the new container only after its health check passes, giving zero-downtime deploys with automatic Let's Encrypt TLS. Accessories run supporting services such as a database. Rails 8.1's generated config can deploy without a remote image registry.

Notes

  • Servers need only SSH access and Docker (Kamal installs Docker if missing)
  • Secrets are read from .kamal/secrets, which pulls from ENV or password managers
  • Each deploy builds, pushes, pulls, boots, health-checks /up, then switches traffic
  • Roles let one image run web and job processes on different hosts

config/deploy.yml

service: blog
image: bob/blog

servers:
  web:
    - 203.0.113.10
  job:
    hosts:
      - 203.0.113.10
    cmd: bin/jobs

proxy:
  ssl: true
  host: blog.example.com

registry:
  username: bob
  password:
    - KAMAL_REGISTRY_PASSWORD

env:
  secret:
    - RAILS_MASTER_KEY        # .kamal/secrets: RAILS_MASTER_KEY=$(cat config/master.key)

volumes:
  - "blog_storage:/rails/storage"
asset_path: /rails/public/assets
builder:
  arch: amd64

Commands

bin/kamal setup              # first time: install Docker, proxy, deploy
bin/kamal deploy             # build + zero-downtime switch
bin/kamal app logs -f        # tail logs
bin/kamal accessory boot db  # start an accessory

Code Explained

servers roles — web behind the proxy, job runs bin/jobs
proxy.ssl + host — automatic Let's Encrypt certificate
env.secret — names only; values come from .kamal/secrets
asset_path — bridges old and new assets during deploys
builder.arch — build for the server's CPU

The Rails Way

  • Heroku-style PaaS for a single app → Kamal on a VPS you control
  • Copying files with scp and restarting → bin/kamal deploy
  • Secrets in deploy.yml → .kamal/secrets referencing ENV or a password manager

deploy.yml Keys

KeyPurpose
serversHosts per role (web, job)
proxykamal-proxy host, SSL, health check
accessoriesExtra services, e.g. postgres:17
aliasesconsole, shell, logs shortcuts

⚠ Common Mistakes

  • Pointing DNS at the server after kamal setup; Let's Encrypt needs DNS first
  • Committing real secret values in .kamal/secrets instead of references
  • Forgetting volumes, so SQLite data lives only inside a replaced container

✓ Tips & Best Practices

  • Run bin/kamal config to see the merged configuration before deploying
  • Use bin/kamal lock features to avoid two people deploying at once
  • Add bin/kamal deploy to a CI job on main after bin/ci passes

Quick Summary

  • deploy.yml — servers, proxy, env
  • kamal setup / deploy — ship it
  • kamal-proxy — zero downtime + TLS
  • .kamal/secrets — secret references
