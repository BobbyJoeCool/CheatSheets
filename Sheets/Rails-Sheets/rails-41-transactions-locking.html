Transactions & Locking

transaction · ActiveRecord::Rollback · lock · with_lock · lock_version · after_commit · nested transactions

All or Nothing

A transaction groups writes so they all succeed or all roll back. Any exception inside the block rolls back and re-raises; ActiveRecord::Rollback rolls back silently. Locking prevents two requests from changing the same row at once: pessimistic locks block, optimistic locks detect conflicts on save.

Notes

  • save and destroy already run in their own transaction
  • Nested transaction blocks join the outer one unless requires_new: true
  • Jobs, emails and API calls inside a transaction can't be rolled back: use after_commit
  • Optimistic locking needs an integer lock_version column

Transactions

ActiveRecord::Base.transaction do
  from.update!(balance: from.balance - amount)
  to.update!(balance: to.balance + amount)
  Transfer.create!(from:, to:, amount:)
end                                          # any raise → full rollback

Order.transaction do
  order.update!(status: "cancelled")
  raise ActiveRecord::Rollback if order.refund_failed?   # silent rollback
end

ActiveRecord::Base.transaction do |tx|
  order.save!
  tx.after_commit { OrderMailer.confirm(order).deliver_later }  # 7.2+
end

Locking

account = Account.lock.find(id)              # SELECT ... FOR UPDATE
account.with_lock do                         # reload + lock + transaction
  account.balance -= 10
  account.save!
end

# optimistic: posts.lock_version integer, default 0, null: false
post = Post.find(1)
post.update(title: "A")                      # lock_version 0 → 1
stale.update(title: "B")                     # raises ActiveRecord::StaleObjectError

Code Explained

update! (bang) — failures raise, so the transaction rolls back
ActiveRecord::Rollback — swallowed by transaction, not re-raised
tx.after_commit — run code only if this transaction commits
with_lock — row lock for the duration of the block
StaleObjectError — someone else saved first; reload and retry or show a conflict

The Rails Way

  • Non-bang update inside a transaction → update! so failures abort
  • Sending email inside the block → after_commit or tx.after_commit
  • Read-modify-write without locking → with_lock or update_counters

Pessimistic vs Optimistic

Pessimistic · Optimistic
MechanismFOR UPDATE row lock · lock_version check
On conflictSecond request waits · StaleObjectError
Best forShort critical sections, money · Forms edited by people
CostBlocking, deadlock risk · Retry / merge UI

⚠ Common Mistakes

  • Using save (non-bang) inside a transaction and continuing after it returns false
  • Doing slow network calls while holding a row lock
  • Rescuing exceptions inside the block, which prevents the rollback

✓ Tips & Best Practices

  • Keep transactions short and focused on the database
  • Use ActiveRecord.after_all_transactions_commit from service objects (7.2+)
  • Add a lock_version hidden field in edit forms to detect concurrent edits

Quick Summary

  • transaction — all or nothing
  • Rollback — silent abort
  • with_lock — pessimistic
