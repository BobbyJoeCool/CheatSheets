Batches & Bulk Operations

find_each · in_batches · insert_all · upsert_all · update_all · delete_all · touch_all · update_counters

Large Data Without Large Memory

Iterating Model.all.each loads every row into memory. Batch methods walk the table in chunks of 1,000 by primary key. Bulk methods write many rows in one SQL statement; they are much faster but skip validations and callbacks, so use them for imports, backfills and maintenance.

Notes

  • Batches order by primary key; custom order is ignored (or raises with error_on_ignored_order)
  • insert_all / upsert_all take an array of hashes and skip models entirely
  • update_all / delete_all run one statement: no callbacks, no updated_at
  • in_batches yields relations, so you can call update_all per batch

Batches

User.find_each { |u| u.recalculate! }                 # 1,000 at a time
User.where(active: true).find_each(batch_size: 500) { |u| u.sync! }
User.find_each(start: 10_000, finish: 20_000) { |u| u.sync! } # id range
User.find_in_batches { |users| Exporter.write(users) } # arrays
User.in_batches(of: 5_000) { |rel| rel.update_all(flag: true) }
User.in_batches.each_record { |u| u.touch }

Bulk Writes

Tag.insert_all([{ name: "ruby" }, { name: "rails" }])    # skip dups by unique index
Tag.insert_all!([{ name: "new" }])                      # raise on conflict
Price.upsert_all(rows, unique_by: :sku)                 # insert or update
Post.where(published: false).update_all(status: "draft")
Post.where("created_at < ?", 1.year.ago).delete_all
Post.where(user: user).touch_all                        # updated_at = now
Post.update_counters(post.id, views_count: 1)           # atomic += 1
Post.where(id: ids).update_all("views = views + 1")

Code Explained

find_each — yields records one by one, loaded in batches
start: / finish: — split work across processes
insert_all — INSERT ... ON CONFLICT DO NOTHING style
upsert_all — needs a unique index named by unique_by:
update_counters — race-free increment in SQL

The Rails Way

  • User.all.each over a big table → User.find_each
  • Creating 10,000 rows with create! in a loop → insert_all in chunks
  • post.update(views: post.views + 1) → Post.update_counters (no lost updates)

⚠ Common Mistakes

  • Adding .order(:name) before find_each and expecting that order
  • Using update_all and expecting cache keys to change; it doesn't touch updated_at
  • Running a 2-million-row update_all in one statement and locking the table; batch it

✓ Tips & Best Practices

  • Wrap long backfills in a job using in_batches so they can be retried
  • Pass returning: [:id] to insert_all on PostgreSQL to get new ids
  • Log progress inside batch loops; long silent scripts are hard to trust

Quick Summary

  • find_each — memory-safe iteration
  • insert_all / upsert_all — bulk insert
  • update_all / delete_all — one SQL statement
  • bulk = no callbacks
