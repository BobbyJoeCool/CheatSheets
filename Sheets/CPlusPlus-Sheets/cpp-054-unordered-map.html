std::unordered_map

hashing · buckets & load factor · reserve · std::hash · custom hash · ordered vs unordered

Hash Table

std::unordered_map<K, V> stores key/value pairs in a hash table: average O(1) lookup, insert, and erase, with no ordering. Keys need a hash function (std::hash<K>) and ==. The table is an array of buckets; when the load factor (elements ÷ buckets) passes max_load_factor(), it rehashes, which invalidates iterators. The interface mirrors std::map.

Notes

  • Iteration order is unspecified and changes after rehash
  • Worst case is O(n) when many keys collide
  • reserve(n) pre-sizes buckets to avoid rehashing
  • Standard std::hash exists for integers, pointers, strings, string_view

unordered_map + Custom Hash

#include <unordered_map>

std::unordered_map<std::string, int> wordCount;
for (const auto& w : words) ++wordCount[w];     // count occurrences
wordCount.reserve(10'000);                       // avoid rehash
wordCount.contains("the");                       // true / false
wordCount.load_factor();                         // e.g. 0.73

struct Point { int x, y; bool operator==(const Point&) const = default; };
struct PointHash {
    std::size_t operator()(const Point& p) const noexcept {
        auto h = std::hash<int>{}(p.x);
        auto g = std::hash<int>{}(p.y);
        return h ^ (g + 0x9e3779b9 + (h << 6) + (h >> 2));
    }
};
std::unordered_map<Point, std::string, PointHash> labels;
labels[{1, 2}] = "A";
template <> struct std::hash<Point> : PointHash {};  // or specialize
std::unordered_set<Point> pts;                      // no 2nd arg now

Code Explained

++wordCount[w] — missing keys start at 0, so counting is one line
reserve — sets bucket count for the expected size
operator== = default — needed alongside the hash
PointHash — combines member hashes (boost-style mixing)
specializing std::hash — then no third template argument is needed

⚠ Common Mistakes

  • Using a type with no std::hash specialization as a key, which causes a long template error
  • Writing a hash that ignores some fields used by ==; equal keys must have equal hashes
  • Keeping iterators across inserts; a rehash invalidates them all

✓ Tips & Best Practices

  • Call reserve() up front when you know the approximate element count
  • Use transparent hashing (is_transparent + std::equal_to<>) to look up string_view keys without allocating
  • For hot paths, consider open-addressing tables like absl::flat_hash_map or boost::unordered_flat_map

Quick Summary

  • std::unordered_map — hash table, O(1) average
  • std::hash<K> + == — key requirements
  • reserve — pre-size to avoid rehash
  • no ordering — use std::map when order matters
