Choosing a Container

Big-O table · contiguous vs node-based · std::flat_map / flat_set · std::inplace_vector (C++26) · invalidation rules · decision chart

Pick by Access Pattern

Choose a container by how you'll access the data, not by what sounds right. Contiguous containers (vector, array, flat_map) win most real-world benchmarks thanks to CPU caches, even when Big-O suggests otherwise. Node-based containers (list, map, set, unordered_*) pay a pointer chase per element but keep references stable. C++23 adds the flat containers, and C++26 adds std::inplace_vector, a fixed-capacity vector with no heap allocation.

Defaults

  • Sequence → std::vector
  • Fixed size → std::array
  • Key lookup → std::unordered_map (or flat_map if read-mostly)
  • Need sorted keys → std::map / std::flat_map

Decision Guide

// Need indexing + append?            → std::vector<T>
// Size known at compile time?        → std::array<T, N>
// Bounded size, no heap (C++26)?     → std::inplace_vector<T, N>
// Push/pop at both ends?             → std::deque<T>
// Stable iterators on middle edits?  → std::list<T>
// Key → value, any order, fast?      → std::unordered_map<K, V>
// Key → value, sorted / ranges?      → std::map<K, V>
// Mostly lookups, rare inserts?      → std::flat_map<K, V> (C++23)
// Unique membership?                 → std::unordered_set / std::set
// LIFO / FIFO / best-first?          → stack / queue / priority_queue
// View someone else's data?          → std::span / std::string_view

std::flat_map<std::string, int> fm{{"b", 2}, {"a", 1}};  // sorted vectors
std::inplace_vector<int, 8> small{1, 2, 3};              // capacity 8

Code Explained

start with vector; switch only for a specific reason
inplace_vector — embedded/real-time code that can't allocate
flat_map — two sorted vectors (keys, values): fast lookup, slow insert
views (span, string_view) — for parameters, not storage

⚠ Common Mistakes

  • Using std::map by habit when you never need ordering; unordered_map or flat_map is usually faster
  • Choosing std::list for performance without measuring
  • Storing pointers to vector elements while the vector still grows

✓ Tips & Best Practices

  • Benchmark with realistic sizes; for under ~100 elements a linear search in a vector often wins
  • Reserve capacity up front (vector::reserve, unordered_map::reserve)
  • Prefer std::flat_map for configuration-style data built once and read often

Quick Summary

  • std::vector — default choice
  • contiguous — cache-friendly, usually fastest
  • node-based — stable references, slower traversal
  • flat_map (C++23) / inplace_vector (C++26) — newer options
