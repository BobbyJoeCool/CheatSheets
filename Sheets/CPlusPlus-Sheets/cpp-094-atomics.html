Atomics & the Memory Model

std::atomic · load / store · fetch_add · compare_exchange · memory_order · data races = UB

Lock-Free Basics

std::atomic<T> (<atomic>) makes individual reads, writes, and read-modify-write operations indivisible, so threads can share simple variables without a mutex. The memory model defines what other threads observe: the default memory_order_seq_cst is easiest to reason about, while acquire/release and relaxed orderings trade simplicity for speed. Any non-atomic data accessed by two threads, with at least one writing and no synchronization, is a data race: undefined behavior.

Notes

  • Works for integers, pointers, bool, and trivially copyable types
  • is_lock_free() — whether the hardware supports it without a lock
  • std::atomic_flag — guaranteed lock-free
  • Atomics aren't copyable

Atomic Operations

#include <atomic>

std::atomic<int> hits{0};
hits++;                                   // atomic increment
hits.fetch_add(5);                        // returns old value
hits.load();                              // read
hits.store(0);                            // write
int old = hits.exchange(42);              // swap, returns previous

int expected = 42;
bool ok = hits.compare_exchange_strong(expected, 43); // CAS
                                          // ok == true, hits == 43
std::atomic<bool> ready{false};
int payload = 0;
// producer thread
payload = 99;
ready.store(true, std::memory_order_release);
// consumer thread
while (!ready.load(std::memory_order_acquire)) {}
assert(payload == 99);                    // guaranteed by acquire/release

Code Explained

hits++ — atomic read-modify-write
fetch_add — returns the value before adding
compare_exchange_strong — set only if the value equals expected
release store + acquire load — publish payload safely
default ordering is seq_cst when none is given

⚠ Common Mistakes

  • x = x + 1 on an atomic; that's a separate load and store, not atomic. Use ++x or fetch_add
  • Mixing atomics and plain variables without proper acquire/release ordering
  • Using memory_order_relaxed for flags that publish data; readers may see the flag but stale data

✓ Tips & Best Practices

  • Stick with the default seq_cst unless profiling proves it's a bottleneck
  • Use std::atomic<std::shared_ptr<T>> (C++20) for lock-free pointer swapping
  • Reach for a mutex as soon as more than one variable must change together

Quick Summary

  • std::atomic<T> — indivisible operations
  • fetch_add / exchange / CAS — RMW building blocks
  • acquire/release — publish data between threads
  • data race — UB; use atomics or mutexes
