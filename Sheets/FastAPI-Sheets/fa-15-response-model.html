Sheet 15

Response Models & Filtering

response_model= · -> return type · ItemIn / ItemOut · response_model_exclude_unset · from_attributes

Description

A response model controls what leaves your API. FastAPI validates the return value against it and filters out fields not in the model, which is how you keep password hashes and internal columns private. Declare it with a return annotation (-> UserOut) or response_model= when the function returns something else, like an ORM object.

Notes

  • Return type annotation is the preferred style
  • response_model= wins if both are set
  • from_attributes=True lets models read ORM objects
  • response_model=None disables validation for that route

Under the Hood

  • FastAPI serializes the return value through the response model's Pydantic serializer
  • Extra attributes are dropped during that serialization
  • Then jsonable_encoder rules make it JSON-safe

In / DB / Out Models

from pydantic import BaseModel, ConfigDict, EmailStr

class UserBase(BaseModel):
    email: EmailStr
    name: str

class UserIn(UserBase):
    password: str                   # in only, never returned

class UserOut(UserBase):
    model_config = ConfigDict(from_attributes=True)
    id: int

@app.post("/users", status_code=201)
def create_user(user: UserIn) -> UserOut:
    db_user = save(user)            # ORM obj w/ hashed_password
    return db_user                  # → id, email, name only

@app.get("/users", response_model=list[UserOut])
def list_users():
    return session.scalars(select(User)).all()

@app.patch("/users/{id}", response_model_exclude_unset=True)
def patch_user(id: int, data: UserPatch) -> UserOut: ...

Code Explained

UserIn / UserOut — inherit shared fields from UserBase
-> UserOut — documents and filters the output
from_attributes=True — read .email from ORM objects
list[UserOut] — arrays work the same way

Other Framework

  • Flask — build the dict yourself or use marshmallow dump()
  • Django — DRF serializer fields = [...] controls output

Prefer / Avoid

  • Avoid returning DB models directly without a schema · Prefer an Out model
  • Avoid deleting keys from dicts to hide data · Prefer a model that omits them

Response Model Options

OptionEffect
response_model_exclude_unsetonly fields actually set
response_model_exclude_nonedrop None values
response_model_exclude={...}drop named fields
response_model_include={...}keep only named fields

⚠ Common Mistakes

  • Returning a SQLAlchemy object without from_attributes=True: validation error
  • Annotating -> dict and losing filtering and docs
  • Using include/exclude everywhere instead of separate models

✓ Tips & Best Practices

  • Name schemas by role: Create, Update, Read
  • Make all Update fields optional and use exclude_unset
  • Check /docs → Schemas to confirm no secret fields leak

Quick Summary

  • -> Out — validate + filter output
  • In / Out models — never return passwords
  • from_attributes — accept ORM objects
  • exclude_unset — partial responses
