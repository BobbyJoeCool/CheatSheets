Request Hooks & Error Handling

before_request · after_request · teardown_appcontext · abort(404) · @app.errorhandler · error pages · logging

Description

Request hooks run code around every request: before_request (load the user, block requests), after_request (add headers), and teardown_appcontext (always clean up, even after errors). abort() raises an HTTP error; @app.errorhandler turns errors and exceptions into custom pages or JSON.

Notes

  • Returning a value from before_request skips the view
  • after_request must return the response
  • teardown_* gets the exception (or None) and can't change the response
  • app.logger is a standard logging.Logger

Hooks & Handlers

from flask import abort, g, request
from werkzeug.exceptions import HTTPException

@app.before_request
def require_login():
    public = {"auth.login", "static"}
    if request.endpoint not in public and not g.get("user"):
        abort(401)

@app.after_request
def security_headers(resp):
    resp.headers["X-Content-Type-Options"] = "nosniff"
    return resp

@app.teardown_appcontext
def close_db(exc):
    if (db := g.pop("db", None)) is not None:
        db.close()

@app.errorhandler(404)
def not_found(e):
    return render_template("404.html"), 404

@app.errorhandler(HTTPException)
def http_error(e):                       # JSON for every HTTP error
    return {"error": e.name, "detail": e.description}, e.code

Code Explained

before_request — abort(401) stops the request
after_request — modify and return the response
teardown_appcontext — always runs; close resources
errorhandler(404) — custom page + status
errorhandler(HTTPException) — catch them all

Other Framework

  • FastAPI — middleware + dependencies + @app.exception_handler (sheets 19, 27)
  • Django — middleware; handler404 / handler500 views

Prefer / Avoid

  • Avoid try/except in every view · Prefer error handlers
  • Avoid returning HTML errors from JSON APIs · Prefer a JSON handler

⚠ Common Mistakes

  • Forgetting return resp in after_request: request fails
  • Expecting after_request to run after an unhandled exception: use teardown
  • Showing stack traces in production error pages

✓ Tips & Best Practices

  • Log with app.logger.exception(...) inside a 500 handler
  • Use @bp.app_errorhandler to register app-wide handlers from a blueprint
  • Return problem JSON for API blueprints, HTML for pages

Quick Summary

  • before_request — gate or prepare
  • after_request — adjust response
  • teardown — always clean up
  • abort() + errorhandler — custom errors
