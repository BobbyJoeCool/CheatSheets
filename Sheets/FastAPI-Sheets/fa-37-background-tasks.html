Background Tasks

BackgroundTasks · add_task() · tasks in dependencies · Celery / ARQ / RQ · fire-and-forget limits

Description

BackgroundTasks runs small jobs after the response is sent, in the same process: sending a welcome email, writing an audit log, warming a cache. Declare a BackgroundTasks parameter and call add_task(). For anything slow, retryable or important, use a real task queue instead.

Notes

  • Tasks run after the response, in order added
  • def tasks run in the threadpool; async def on the loop
  • No retries, no persistence: a crash loses the task
  • Dependencies can add tasks too

After-Response Work

from fastapi import BackgroundTasks

def send_welcome(email: str, name: str):
    mailer.send(to=email, subject="Welcome!",
                body=f"Hi {name}, thanks for signing up.")

def write_audit(event: str, user_id: int):
    audit_log.append(event=event, user_id=user_id)

@app.post("/users", status_code=201)
def register(data: UserCreate, tasks: BackgroundTasks,
             db: DbSession) -> UserOut:
    user = create_user(db, data)
    tasks.add_task(send_welcome, user.email, name=user.name)
    tasks.add_task(write_audit, "register", user.id)
    return user                          # client gets this right away

def audit_dep(tasks: BackgroundTasks, request: Request):
    tasks.add_task(write_audit, f"hit {request.url.path}", 0)

Code Explained

tasks: BackgroundTasks — injected per request
add_task(fn, *args, **kwargs) — schedule work
Response is sent before tasks run
audit_dep — a dependency can add tasks as well

Other Framework

  • Flask — no built-in; use Celery, RQ or a thread
  • Django — django.tasks (6.0+) or Celery

Prefer / Avoid

  • Avoid long jobs in BackgroundTasks · Prefer Celery, ARQ, RQ or Dramatiq
  • Avoid passing ORM objects to tasks · Prefer IDs and reload

⚠ Common Mistakes

  • Using the request's DB session inside a task: it's closed by then
  • Expecting task errors to reach the client: the response is already sent
  • Running minutes-long work: holds a worker and dies on deploy

✓ Tips & Best Practices

  • Open a fresh session inside the task
  • Log task failures; nobody else will see them
  • Move to a queue as soon as you need retries

Quick Summary

  • BackgroundTasks — run after response
  • add_task(fn, ...) — schedule
  • same process — no retries, no persistence
  • task queue — for anything important
