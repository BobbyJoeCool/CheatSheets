Visibility

Methods are public by default. private methods can only be called without an explicit receiver (except self.x = setters), so they're internal helpers. protected methods can be called on other instances of the same class, which is useful for comparisons. Visibility can be set as a section or per method.

Notes

  • private with no args affects every method below it
  • private def helper marks a single method
  • Private methods can be called with self. since Ruby 2.7
  • send bypasses visibility (use public_send to respect it)

public, private, protected

class Account
  def initialize(balance) = @balance = balance
  def >(other) = balance > other.balance   # protected reader
  def summary = "Balance: #{formatted}"    # private helper

  protected

  attr_reader :balance

  private

  def formatted = format("$%.2f", @balance)
end

a, b = Account.new(50), Account.new(20)
a > b                    # true
a.summary                # "Balance: $50.00"
a.balance                # NoMethodError: protected method
a.formatted              # NoMethodError: private method
a.send(:formatted)       # "$50.00" (bypasses)

Code Explained

other.balance — protected: allowed on another Account
formatted — private: only callable without a receiver
protected / private sections — apply to methods below
send — ignores visibility (debugging, tests)

The Ruby Way

  • Prefixing helpers with _ to mean private → actually use private
  • private sections far from the method → private def name
  • send in app code to reach internals → expose a public method

In Rails

  • Rails · only public controller methods become actions; put helpers under private
  • Rails · before_action :load_user usually points at a private method

⚠ Common Mistakes

  • Placing attr_reader after private by accident and making a public API private
  • Expecting private to affect class methods defined with def self.; use private_class_method
  • Thinking protected means "subclasses only" as in Java; in Ruby it's about receivers of the same family

✓ Tips & Best Practices

  • Keep the public interface small; everything else goes under private
  • Use protected mainly for comparison methods (==, <=>) that read other instances
  • Tests should exercise public behavior rather than send-ing to private methods

Quick Summary

  • public — default
  • private — internal helpers, implicit receiver
  • protected — same-family instances
  • send — bypasses visibility
