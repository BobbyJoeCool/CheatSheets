Performance and Memory

Measure before optimizing: Benchmark (stdlib) and the benchmark-ips gem compare code, and GC.stat / ObjectSpace / memory_profiler show allocations. Common wins are fewer allocations (frozen strings, << instead of +), better algorithms (Sets, hashes), and enabling the YJIT JIT for long-running processes.

Notes

  • ruby --yjit or RUBY_YJIT_ENABLE=1 turns on YJIT
  • Ruby 4.0 adds the experimental ZJIT (--zjit)
  • Allocations drive GC time; fewer objects = faster
  • Profile with stackprof or vernier to find hot spots

Measuring

require "benchmark"
Benchmark.realtime { 1_000_000.times { "a" + "b" } }   # 0.08 (seconds)
Benchmark.bm(6) do |x|
  x.report("+=")  { s = +""; 10_000.times { s += "x" } }
  x.report("<<")  { s = +""; 10_000.times { s << "x" } }
end

require "benchmark/ips"
Benchmark.ips do |x|
  x.report("map+flatten") { [[1], [2]].map { it }.flatten }
  x.report("flat_map")    { [[1], [2]].flat_map { it } }
  x.compare!
end

GC.stat[:total_allocated_objects]      # running total
ObjectSpace.count_objects[:T_STRING]   # live strings
RubyVM::YJIT.enabled?                  # true with --yjit

require "memory_profiler"
MemoryProfiler.report { load_data }.pretty_print(scale_bytes: true)

Code Explained

Benchmark.realtime — wall time of one block
Benchmark.bm — side-by-side timings
benchmark-ips — iterations per second with error margins
GC.stat / ObjectSpace — allocation and object counts
MemoryProfiler.report — where memory is allocated

The Ruby Way

  • str += x in loops → str << x on a mutable buffer
  • arr.include? in a loop → a Set
  • map { }.flatten → flat_map; select { }.map { } → filter_map

In Rails

  • Rails · most slowness is N+1 queries; fix with includes(:posts) (the bullet gem detects them)
  • Rails · Rails.cache.fetch and fragment caching avoid repeated work
  • Rails · Rails 7.2+ enables YJIT by default when available

⚠ Common Mistakes

  • Optimizing without measuring; intuition about Ruby performance is often wrong
  • Benchmarking with too few iterations; use benchmark-ips for stable numbers
  • Turning on YJIT for short scripts and CLIs; warm-up cost can outweigh the gain

✓ Tips & Best Practices

  • Measure in production-like conditions (same Ruby, YJIT setting, data size)
  • GC.compact and RUBY_GC_HEAP_* settings tune long-running processes
  • Use vernier for profiling apps with threads or fibers

Quick Summary

  • memory_profiler / GC.stat — measure memory
  • fewer allocations — main optimization
  • --yjit / --zjit — JIT compilers
