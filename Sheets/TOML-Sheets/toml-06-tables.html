Tables

Headers Group the Keys Below Them

A table is a set of key/value pairs that starts with a header like [server]. Everything after a header belongs to it until the next header or the end of the file. Dots in a header nest tables ([a.b.c]), and missing parent tables are created implicitly.

Notes

  • Keys before the first header belong to the root table
  • Each table can be defined only once
  • A parent can come after its children: [a.b] then [a] is fine
  • Empty tables are allowed: [cache] with no keys
  • Header names follow key rules: [dog."tater.man"]

Headers, Nesting & Dotted Keys

name = "shop"              # root table

[server]
host = "0.0.0.0"
port = 8080

[server.tls]               # creates server.tls
cert = "/etc/ssl/shop.pem"

[database.primary]         # database made implicitly
url = "postgres://db1/shop"

[database]                 # defining the parent later is OK
pool = 10

[fruit]
apple.color = "red"        # dotted keys inside a table
apple.taste.sweet = true
# [fruit.apple]            # ERROR: apple already defined
[fruit.apple.texture]      # OK: a new sub-table
smooth = true

Code Explained

[server.tls] nests inside server; no indentation needed
[database.primary] makes database exist before its own header appears
apple.color inside [fruit] defines the table fruit.apple
A header for fruit.apple would redefine it; adding fruit.apple.texture is allowed

Same Data In…

  • JSON {"server": {"host": "0.0.0.0", "port": 8080, "tls": {"cert": "/etc/ssl/shop.pem"}}}
  • YAML server: / port: 8080 / tls: / cert: /etc/ssl/shop.pem
  • INI [server] / port = 8080 (one level; [server.tls] is just a name)

Gotcha

  • Writing [server] again near the end of the file is an error, not a merge
  • Whitespace around dots in headers is ignored, so [ a . b ] equals [a.b]

Table Rules

SituationResult
Same header twiceerror
[a.b] before [a]allowed
Header after dotted keys made the tableerror
Sub-table under a dotted-key tableallowed
Header for a key that holds a valueerror

⚠ Common Mistakes

  • Repeating a header to add more keys later in the file
  • Assuming indentation under a header nests anything
  • Mixing dotted keys and a header for the same table

✓ Tips & Best Practices

  • Order headers from general to specific so related keys stay together
  • Indent sub-table keys if it helps you read; parsers ignore it
  • Use dotted keys for 1–2 nested values and headers for anything bigger

Quick Summary

  • [name] — table header
  • [a.b.c] — nested header, parents implicit
  • root table — keys before any header
  • define each table once
