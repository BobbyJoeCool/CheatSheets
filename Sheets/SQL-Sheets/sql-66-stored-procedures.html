Stored Procedures

CREATE PROCEDURE · CALL · EXEC · IN / OUT params · DECLARE · IF / LOOP

Server-Side Routines

A stored procedure is a named block of statements stored in the database and run with CALL (SQL Server: EXEC). Unlike a function it isn't used inside a query, it can return values through OUT parameters, and in PostgreSQL 11+ it can COMMIT part-way through. Procedures keep multi-step operations ("place an order") in one round trip, close to the data, with variables (DECLARE), branches (IF) and loops.

Procedure Facts

  • Runs on the server: one network round trip
  • Errors abort it; RAISE EXCEPTION aborts on purpose
  • COMMIT inside fails if the caller opened a transaction
  • Business logic in SQL is harder to test and version

NoSQL Comparison

  • MongoDB has no stored procedures
  • Multi-document work uses driver transactions: session.withTransaction(…)
  • Logic stays in application code

CREATE PROCEDURE

CREATE PROCEDURE place_order(
  p_customer INT, p_product INT, p_qty INT,
  OUT p_order_id INT)
LANGUAGE plpgsql AS $$
DECLARE
  v_price NUMERIC;
BEGIN
  SELECT price INTO v_price
  FROM   products
  WHERE  product_id = p_product
  FOR UPDATE;                     -- lock the row
  IF NOT FOUND THEN
    RAISE EXCEPTION 'product % not found', p_product;
  END IF;
  INSERT INTO orders (customer_id, total)
  VALUES (p_customer, v_price * p_qty)
  RETURNING order_id INTO p_order_id;

  INSERT INTO order_items
  VALUES (p_order_id, p_product, p_qty, v_price);

  UPDATE products SET stock = stock - p_qty
  WHERE  product_id = p_product;
END $$;

CALL place_order(7, 3, 2, NULL);   -- returns p_order_id

Code Explained

OUT p_order_id comes back as a result row from CALL
FOR UPDATE stops two orders overselling stock (sheet 70)
NOT FOUND is set by the previous SELECT INTO
Pass NULL as the placeholder for the OUT argument

⚠ Common Mistakes

  • Building SQL strings inside procedures (injection, sheet 76)
  • Hiding core business rules where the app team can't see them
  • Forgetting row locks in read-then-write logic

✓ Tips & Best Practices

  • Keep procedures small and focused on data integrity
  • Keep their source in migrations and code review
  • Return clear errors with RAISE and SQLSTATE codes
