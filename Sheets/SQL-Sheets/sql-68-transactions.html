Sheet 68

Transactions

BEGIN · COMMIT · ROLLBACK · SAVEPOINT · autocommit · ACID

All or Nothing

A transaction groups statements so they succeed or fail as a unit. BEGIN starts one, COMMIT makes every change permanent and visible, and ROLLBACK undoes them all. Outside an explicit transaction, most clients run in autocommit mode: each statement commits by itself. A SAVEPOINT marks a point you can roll back to without abandoning the whole transaction. Together this gives the ACID guarantees.

Transaction Facts

  • Other sessions don't see your changes until COMMIT
  • PG: after an error, roll back before continuing
  • Keep transactions short: they hold locks
  • PG DDL is transactional too (CREATE, ALTER)

NoSQL Comparison

  • MongoDB: a single-document write is always atomic
  • Multi-document transactions (4.0+): session.withTransaction(async () => …)
  • Design documents so one write covers one change

BEGIN … COMMIT

BEGIN;
UPDATE products SET stock = stock - 2
WHERE  product_id = 7;
INSERT INTO orders (customer_id, total)
VALUES (42, 79.98);
COMMIT;              -- both changes become visible

BEGIN;
DELETE FROM order_items WHERE order_id = 101;
ROLLBACK;            -- as if it never happened
-- Partial rollback with a savepoint
BEGIN;
INSERT INTO customers (name, email)
VALUES ('Ada', 'ada@example.com');
SAVEPOINT before_order;
INSERT INTO orders (customer_id, total)
VALUES (99999, 10);  -- ERROR: foreign key violation
ROLLBACK TO SAVEPOINT before_order;
INSERT INTO orders (customer_id, total) VALUES (1, 10);
COMMIT;              -- customer + valid order saved
-- PostgreSQL: an error poisons the transaction
BEGIN;
SELECT 1 / 0;        -- ERROR
SELECT 1;            -- ERROR: transaction is aborted
ROLLBACK;

Code Explained

Stock and order change together, or not at all
ROLLBACK discards everything since BEGIN
ROLLBACK TO SAVEPOINT undoes only the failed part
PG refuses further statements until ROLLBACK

Dialect Notes

EngineSyntax / behavior
PostgreSQLBEGIN / START TRANSACTION; transactional DDL
MySQLSTART TRANSACTION; DDL commits implicitly

SQLiteBEGIN IMMEDIATE to take the write lock up front

In an ORM

await prisma.$transaction(async (tx) => {
  await tx.product.update({
    where: { id: 7 }, data: { stock: { decrement: 2 } },
  });
  await tx.order.create({
    data: { customerId: 42, total: 79.98 },
  });
});  // a thrown error → automatic ROLLBACK

ACID

LetterGuarantee
Atomicityall statements apply, or none do
Consistencyconstraints hold before and after
Isolationconcurrent transactions don't interfere (sheet 69)
Durabilitycommitted data survives a crash

Statements

StatementDoes
BEGIN · START TRANSACTIONstart a transaction
COMMITsave and end
ROLLBACKundo and end
SAVEPOINT smark a point
ROLLBACK TO SAVEPOINT sundo back to the mark
RELEASE SAVEPOINT sforget the mark

⚠ Common Mistakes

  • Leaving a transaction open (idle in transaction) and blocking others
  • Calling an external API inside a transaction
  • Assuming MySQL can roll back a CREATE TABLE

✓ Tips & Best Practices

  • Do slow work before BEGIN; keep the transaction tight
  • Retry on serialization or deadlock errors (sheet 69, sheet 70)
  • Set idle_in_transaction_session_timeout in PostgreSQL

Quick Summary

  • BEGIN → statements → COMMIT / ROLLBACK
  • SAVEPOINT for partial undo
  • ACID
