Relationships & ER Modeling

one-to-one · one-to-many · many-to-many · junction table · cardinality · ERD

Connecting Entities

Entities relate in three ways. One-to-many is the workhorse: the foreign key goes on the "many" side (orders.customer_id). One-to-one puts a unique foreign key (often the primary key itself) on the optional side. Many-to-many needs a junction table holding two foreign keys, like order_items or product_tags. An ER diagram shows entities as boxes and cardinality with crow's-foot marks on the lines.

Modeling Facts

  • The FK lives on the "many" side
  • Junction tables can carry data (quantity)
  • NOT NULL FK = mandatory; nullable = optional
  • Self-relationships: employees.manager_id (sheet 34)

NoSQL Comparison

  • One-to-many: embed (few, owned) or reference (many, shared)
  • Many-to-many: arrays of ids, e.g. tags: ['sale', 'new']
  • No junction collection unless the link has its own data

Relationship Tables

-- One-to-many: a customer has many orders
CREATE TABLE orders (
  order_id    INT PRIMARY KEY,
  customer_id INT NOT NULL REFERENCES customers
);
-- One-to-one: optional profile per customer
CREATE TABLE customer_profiles (
  customer_id INT PRIMARY KEY REFERENCES customers,
  birthday    DATE,
  newsletter  BOOLEAN NOT NULL DEFAULT false
);
-- Many-to-many: products ↔ tags
CREATE TABLE tags (tag_id INT PRIMARY KEY, name TEXT);
CREATE TABLE product_tags (
  product_id INT REFERENCES products ON DELETE CASCADE,
  tag_id     INT REFERENCES tags     ON DELETE CASCADE,
  PRIMARY KEY (product_id, tag_id)
);

-- Querying many-to-many: two joins
SELECT p.name, t.name AS tag
FROM   products p
JOIN   product_tags pt USING (product_id)
JOIN   tags t          USING (tag_id);

Code Explained

customer_id NOT NULL — every order must have a customer
Profile PK = FK, so at most one profile per customer
Composite PK stops tagging a product twice
CASCADE removes links when either side is deleted

Dialect Notes

Same in all four. Only the key syntax differs (identity columns, AUTO_INCREMENT); relationships are always foreign keys.

In an ORM

model Product {
  id   Int   @id
  tags Tag[]       // implicit many-to-many
}
model Tag {
  id       Int       @id
  products Product[] // Prisma creates _ProductToTag
}

⚠ Common Mistakes

  • Putting the FK on the "one" side (customers.order_id)
  • Modeling many-to-many with a comma list
  • One-to-one tables without a unique constraint

✓ Tips & Best Practices

  • Name junction tables after both sides: product_tags
  • Sketch the ERD before writing DDL
  • Generate diagrams from the live schema with tools like DBeaver

Quick Summary

  • 1:N — FK on the many side
  • 1:1 — unique FK
  • M:N — junction table
