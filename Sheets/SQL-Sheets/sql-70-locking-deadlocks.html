Locking & Deadlocks

FOR UPDATE · FOR SHARE · SKIP LOCKED · NOWAIT · LOCK TABLE · deadlock · advisory lock

Coordinating Writers

Writers lock the rows they change until COMMIT. When you read a row and then update it based on what you saw, take the lock up front with SELECT … FOR UPDATE so no one changes it in between. NOWAIT errors instead of waiting; SKIP LOCKED skips rows others hold, which turns a table into a safe job queue. A deadlock happens when two transactions each wait for the other's lock; the database aborts one of them.

Lock Facts

  • Plain SELECT takes no row locks (MVCC)
  • Locks are held until the transaction ends
  • Lock rows in a consistent order to avoid deadlocks
  • Advisory locks are app-defined, named by a number

NoSQL Comparison

  • MongoDB: single-document atomic updates avoid read-then-write locks:
  • findOneAndUpdate({ _id, stock: { $gte: 1 } }, { $inc: { stock: -1 } })
  • SQL can do the same: UPDATE … WHERE stock >= 1

Row Locks

-- Read-then-write: lock the row first
BEGIN;
SELECT stock FROM products
WHERE  product_id = 7
FOR UPDATE;                    -- others wait here
UPDATE products SET stock = stock - 1
WHERE  product_id = 7;
COMMIT;                        -- lock released

-- Fail fast instead of waiting
SELECT * FROM orders
WHERE  order_id = 101 FOR UPDATE NOWAIT;

-- Workers each claim a different paid order
UPDATE orders SET status = 'shipped'
WHERE  order_id = (SELECT order_id FROM orders
                   WHERE  status = 'paid'
                   ORDER  BY order_date
                   LIMIT  1
                   FOR UPDATE SKIP LOCKED)
RETURNING order_id;

-- Deadlock: A locks 1 then 2, B locks 2 then 1
-- → ERROR: deadlock detected (one is aborted)

LOCK TABLE products IN SHARE MODE;  -- whole table
SELECT pg_advisory_xact_lock(42);   -- app mutex

Code Explained

FOR UPDATE blocks other writers and other FOR UPDATEs
NOWAIT raises an error if the row is already locked
SKIP LOCKED hands each worker an unlocked row
pg_advisory_xact_lock is released at commit

⚠ Common Mistakes

  • Read, decide in the app, write: two buyers get the last item
  • Locking rows in different orders in different code paths
  • LOCK TABLE on a busy table during peak hours

✓ Tips & Best Practices

  • Prefer one atomic UPDATE … WHERE over read-then-write
  • Use SKIP LOCKED for queues instead of polling flags
  • Watch pg_locks / pg_stat_activity when things hang

Quick Summary

  • FOR UPDATE · FOR SHARE
  • NOWAIT · SKIP LOCKED
  • Deadlock → one aborts; retry
