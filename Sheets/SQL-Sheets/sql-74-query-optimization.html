Query Optimization

SARGable predicates · SELECT * · N+1 · ANALYZE · VACUUM · statistics

Making Queries Fast

Most slow queries come from a few causes. Non-SARGable predicates wrap the column in a function or arithmetic, so its index can't be used; rewrite them as ranges on the bare column. SELECT * drags unneeded columns and blocks index-only scans. The N+1 pattern runs one query per row from app code instead of one set-based query. The planner relies on statistics, refreshed by ANALYZE; PostgreSQL's VACUUM clears dead row versions so tables and indexes stay lean.

Optimization Facts

  • Measure first: EXPLAIN ANALYZE (sheet 73)
  • SARGable = Search ARGument able: usable by an index
  • Autovacuum normally runs VACUUM and ANALYZE for you
  • Fewer round trips beat faster single queries

NoSQL Comparison

  • Same rules in MongoDB: index the filter fields
  • Project only needed fields: find(q, { name: 1 })
  • Avoid unanchored $regex and $where on big collections

Common Fixes

-- ✗ function on the column: index unusable
SELECT order_id FROM orders
WHERE  extract(YEAR FROM order_date) = 2026;
-- ✓ range on the bare column
SELECT order_id FROM orders
WHERE  order_date >= '2026-01-01'
  AND  order_date <  '2027-01-01';

-- ✗ math on the column    ✓ math on the constant
WHERE  price * 1.08 > 100   -- →  WHERE price > 100 / 1.08

-- ✗ every column           ✓ only what's needed
SELECT * FROM orders WHERE customer_id = 42;
SELECT order_id, total FROM orders WHERE customer_id = 42;

-- ✗ N+1 from app code: one query per customer
SELECT * FROM orders WHERE customer_id = $1;  -- × 500
-- ✓ one query for all of them
SELECT * FROM orders WHERE customer_id = ANY ($1);

-- Fresh statistics; clean up dead rows (PG)
ANALYZE orders;
VACUUM (ANALYZE) orders;

Code Explained

extract(…) hides order_date from its index
Moving the math to the constant side keeps the index usable
= ANY ($1) takes an array of ids in one round trip
VACUUM (ANALYZE) — reclaim space and refresh stats

In an ORM

// ✗ N+1: one query per customer
for (const c of customers)
  c.orders = await prisma.order.findMany(
    { where: { customerId: c.id } });
// ✓ one batched query for all customers
await prisma.customer.findMany({ include: { orders: true } });

⚠ Common Mistakes

  • Adding indexes before reading the plan
  • Fixing N+1 with caching instead of a better query
  • Turning off autovacuum to "save resources"

✓ Tips & Best Practices

  • Enable pg_stat_statements to find the costliest queries
  • Batch writes; paginate reads (sheet 16)
  • Re-run ANALYZE after big loads or deletes

Quick Summary

  • Keep predicates SARGable
  • Select only needed columns
  • Kill N+1; keep stats fresh
