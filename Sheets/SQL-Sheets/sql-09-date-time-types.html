Date & Time Types

DATE · TIME · TIMESTAMP · TIMESTAMPTZ · INTERVAL · DATETIME2 · time zones

Dates, Times & Zones

DATE is a calendar day, TIME a time of day, TIMESTAMP a date plus time with no zone, and TIMESTAMPTZ an instant: PostgreSQL converts it to UTC on the way in and back to the session's zone on the way out. INTERVAL is a duration. Store moments that happened (orders, logins) as TIMESTAMPTZ; store wall-clock plans ("9:00 in Chicago") as TIMESTAMP plus a zone name.

Time Facts

  • Write literals as ISO 8601: '2026-10-18 14:30'
  • TIMESTAMPTZ doesn't store the zone; it converts
  • SET TIME ZONE changes display, not data
  • PG precision is microseconds

NoSQL Comparison

  • MongoDB Date is UTC milliseconds since 1970; no zone kept
  • Write ISODate("2026-10-18T14:00:00Z")
  • DynamoDB has no date type: ISO strings or epoch numbers

Date & Time Types

CREATE TABLE events (
  event_day DATE,          -- 2026-10-18
  starts    TIME,          -- 09:30:00
  local_ts  TIMESTAMP,     -- wall clock, no zone
  happened  TIMESTAMPTZ,   -- an instant
  length    INTERVAL       -- 01:30:00
);

SET TIME ZONE 'America/Chicago';
SELECT TIMESTAMPTZ '2026-10-18 14:00:00+00';
-- 2026-10-18 09:00:00-05

SELECT TIMESTAMP '2026-10-18 14:00' AT TIME ZONE 'UTC';
-- read the wall time as UTC → timestamptz

SELECT DATE '2026-03-31' + 1;          -- 2026-04-01
SELECT DATE '2026-01-31' + INTERVAL '1 month';
-- 2026-02-28 00:00:00 (clamped to month end)
SELECT INTERVAL '90 minutes';          -- 01:30:00
SELECT now()::date, now()::time(0);

Code Explained

+00 in the literal fixes the instant; display follows the session
AT TIME ZONE on a TIMESTAMP returns a TIMESTAMPTZ
date + 1 adds days; + INTERVAL returns a timestamp
Month math clamps: Jan 31 + 1 month = Feb 28

⚠ Common Mistakes

  • Using TIMESTAMP for instants, then servers in other zones disagree
  • WHERE ts <= '2026-10-18' misses everything after midnight
  • Storing dates as text like '10/18/2026'

✓ Tips & Best Practices

  • Run servers in UTC; convert only for display
  • Use half-open ranges: >= day AND < day + 1
  • Store IANA zone names ('Europe/Oslo'), not fixed offsets
