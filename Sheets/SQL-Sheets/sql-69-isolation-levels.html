Isolation Levels

READ COMMITTED · REPEATABLE READ · SERIALIZABLE · dirty read · phantom read · MVCC

What Concurrent Transactions See

The isolation level decides how much of other transactions' work you can see while yours runs. Weaker levels allow anomalies: a dirty read sees uncommitted data, a non-repeatable read sees a row change between two reads, a phantom is a new row appearing in a repeated query. READ COMMITTED (the PostgreSQL and SQL Server default) re-reads fresh data per statement; REPEATABLE READ reads one snapshot; SERIALIZABLE behaves as if transactions ran one at a time, and may abort yours with a retryable error.

Isolation Facts

  • MVCC: readers see a snapshot; they don't block writers
  • PostgreSQL never allows dirty reads
  • Higher levels → more retries, not more locks (PG)
  • Set the level before the first query in the transaction

NoSQL Comparison

  • MongoDB transactions use snapshot isolation
  • readConcern: 'snapshot', writeConcern: 'majority'
  • Conflicts abort with TransientTransactionError: retry

Isolation in Action

-- A: one snapshot for the whole transaction
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT stock FROM products WHERE product_id = 7;  -- 10
--   B (autocommit): UPDATE products SET stock = 4
--                   WHERE product_id = 7;
SELECT stock FROM products WHERE product_id = 7;  -- 10
COMMIT;
SELECT stock FROM products WHERE product_id = 7;  -- 4
-- Under READ COMMITTED the 2nd read would show 4

-- A: update a row B changed after A's snapshot
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT stock FROM products WHERE product_id = 7;
--   B: UPDATE … stock = stock - 1 … ; COMMIT
UPDATE products SET stock = stock - 1
WHERE  product_id = 7;
-- ERROR: could not serialize access due to
--        concurrent update → ROLLBACK and retry

-- Make it the default for a session
SET SESSION CHARACTERISTICS AS TRANSACTION
  ISOLATION LEVEL SERIALIZABLE;
SHOW transaction_isolation;

Code Explained

REPEATABLE READ keeps showing the snapshot value
The final read, after COMMIT, sees B's change
PG stops the lost update with a serialization error
Apps must catch SQLSTATE 40001 and retry the transaction

Pick a Level

typical web requestREAD COMMITTED

invariants across rows (no double-booking)SERIALIZABLE + retry

⚠ Common Mistakes

  • Using SERIALIZABLE without retry logic
  • Assuming every engine's REPEATABLE READ behaves the same
  • Reading, computing in the app, then writing back blindly

✓ Tips & Best Practices

  • Prefer atomic updates: SET stock = stock - 1 WHERE stock > 0
  • Wrap transactions in a retry loop for 40001 / 40P01
  • Keep long reports on a replica or snapshot
