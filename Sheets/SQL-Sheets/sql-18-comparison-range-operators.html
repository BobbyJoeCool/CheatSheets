Sheet 18

Comparison & Range Operators

= · <> · != · < > <= >= · BETWEEN · IN · NOT IN

Comparing Values

=, <> (standard) or !=, and < > <= >= compare numbers, text (in collation order) and dates. BETWEEN a AND b is shorthand for >= a AND <= b, so both ends are included. IN (…) tests membership in a list or subquery, and NOT IN the reverse. Any comparison with NULL yields UNKNOWN, so those rows are filtered out (sheet 11).

Comparison Facts

  • <> and != are identical
  • BETWEEN 20 AND 10 matches nothing: low bound first
  • IN () with an empty list is a syntax error
  • NOT IN (…, NULL) never matches (sheet 36)

NoSQL Comparison

  • MongoDB: $eq $ne $gt $gte $lt $lte $in $nin
  • { price: { $gte: 10, $lte: 20 } } = BETWEEN 10 AND 20
  • $ne and $nin also match documents missing the field

Comparisons

SELECT * FROM products WHERE price = 19.99;
SELECT * FROM orders   WHERE status <> 'cancelled';
SELECT * FROM orders   WHERE status != 'cancelled';

SELECT * FROM products
WHERE  price BETWEEN 10 AND 20;       -- 10 ≤ price ≤ 20
SELECT * FROM products
WHERE  price NOT BETWEEN 10 AND 20;

-- DATE column: BETWEEN includes Sept 30
SELECT * FROM orders
WHERE  order_date BETWEEN '2026-09-01' AND '2026-09-30';

-- TIMESTAMP column: half-open range instead
SELECT * FROM customers
WHERE  created_at >= '2026-09-01'
  AND  created_at <  '2026-10-01';

SELECT * FROM orders
WHERE  status IN ('paid', 'shipped');
SELECT * FROM customers
WHERE  country NOT IN ('US', 'CA');

Code Explained

BETWEEN is inclusive on both ends
On timestamps, BETWEEN … '2026-09-30' stops at midnight
>= start AND < next_start never misses or double-counts
IN (a, b) = x = a OR x = b

In an ORM

await prisma.order.findMany({
  where: {
    total: { gte: 10, lte: 20 },          // BETWEEN
    status: { in: ['paid', 'shipped'] },  // IN
    customerId: { notIn: [7, 9] },        // NOT IN
  },
});

⚠ Common Mistakes

  • Reversed BETWEEN bounds returning nothing
  • BETWEEN on timestamps losing the final day
  • Comparing numbers stored as text

✓ Tips & Best Practices

  • Prefer half-open ranges for dates and times
  • Use IN instead of a chain of ORs
  • Use NOT EXISTS over NOT IN with subqueries

Quick Summary

  • = <> < > <= >=
  • BETWEEN — inclusive range
  • IN / NOT IN — list membership
