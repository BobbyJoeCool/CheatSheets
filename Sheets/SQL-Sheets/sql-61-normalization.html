Normalization

1NF · 2NF · 3NF · BCNF · functional dependency · denormalization

One Fact, One Place

Normalization arranges columns so each fact is stored once, which prevents anomalies: a city changed in one order row but not the others. It's built on functional dependency: A → B means knowing A determines B (a customer_id determines the customer's city). Each normal form removes one kind of misplaced dependency. Denormalization later copies data back on purpose for speed, as orders.total does in the shop schema.

Design Facts

  • Aim for 3NF; it's the practical default
  • order_items.unit_price is a price snapshot, not a 3NF breach
  • Each denormalized copy needs a way to stay in sync
  • Normalize first, denormalize with evidence

NoSQL Comparison

  • Document databases denormalize by design
  • Embed what's read together; copy names into orders
  • The cost moves to updates: change a name in many documents

Normalizing an Order Table

-- Unnormalized: repeats and lists
CREATE TABLE orders_flat (
  order_id      INT,
  customer_name TEXT,   -- repeated on every order
  customer_city TEXT,   -- depends on the customer
  products      TEXT,   -- 'Lamp, Desk': not atomic
  prices        TEXT    -- '39.99, 129.00'
);

-- 1NF: one value per cell → one row per item
-- 2NF: product name depends on product_id alone,
--      not the whole (order_id, product_id) key
--      → move to products
-- 3NF: customer_city depends on the customer,
--      not the order → move to customers

-- Result: the shop schema (sheet 04)
--   customers(customer_id, name, city)
--   orders(order_id, customer_id → customers)
--   products(product_id, name, price)
--   order_items(order_id, product_id, qty, price)

-- Deliberate denormalization: cached total
UPDATE orders o
SET    total = (SELECT sum(quantity * unit_price)
                FROM   order_items i
                WHERE  i.order_id = o.order_id);

Code Explained

A list in one cell breaks 1NF: you can't join or index it
Partial dependency on part of a composite key breaks 2NF
Non-key → non-key (order → customer → city) breaks 3NF
total duplicates the items; keep it in sync (sheet 67)

Dialect Notes

Same in all four: normalization is a design discipline, not syntax. Enforce the result with keys and constraints (sheet 56, sheet 57).

In an ORM

model Order {
  id    Int         @id
  items OrderItem[]   // 1NF: items in their own table
}
model OrderItem {
  orderId   Int
  productId Int       // name and price live in Product
  @@id([orderId, productId])
}

Anomalies Prevented

AnomalyExample

denormalize whenreads dominate and the copy is maintained

⚠ Common Mistakes

  • Comma-separated lists in a column
  • Copying customer details into every order "for convenience"
  • Denormalizing before measuring a real problem

✓ Tips & Best Practices

  • Ask "what does this column depend on?" for every column
  • Snapshot values that must not change later (prices, addresses)
  • Use materialized views for read-heavy rollups (sheet 64)

Quick Summary

  • 1NF atomic · 2NF whole key · 3NF nothing but the key
  • Prevents update anomalies
  • Denormalize deliberately
