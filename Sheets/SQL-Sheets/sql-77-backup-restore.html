Sheet 77

Backup & Restore

pg_dump · pg_restore · mysqldump · .backup · BACKUP DATABASE · point-in-time recovery

Getting Data Back

A logical backup (pg_dump, mysqldump) writes SQL or an archive you can restore anywhere, even into a newer version. A physical backup copies the data files and, together with the transaction log (PostgreSQL WAL, MySQL binlog, SQL Server log backups), allows point-in-time recovery: restore to the second before a bad DELETE. A backup only counts once you've restored it successfully.

Backup Facts

  • Logical dumps are consistent snapshots
  • Roles and settings need separate dumps (pg_dumpall -g)
  • Big databases: physical backups restore faster
  • Store copies off the database server

NoSQL Comparison

  • MongoDB: mongodump / mongorestore (BSON)
  • Atlas: continuous backups with point-in-time restore
  • mongoexport isn't a backup: JSON loses types

Backup & Restore

# PostgreSQL: one database, compressed custom format
pg_dump -Fc -d shop -f shop.dump
pg_restore -d shop_restored --clean --if-exists shop.dump
pg_dump -d shop --schema-only > schema.sql
pg_dump -d shop -t orders --data-only > orders.sql
pg_dumpall --globals-only > roles.sql

# MySQL
mysqldump --single-transaction --routines shop > shop.sql
mysql shop_restored < shop.sql

# SQLite: safe copy of a live database
sqlite3 shop.db ".backup 'shop-2026-10-18.db'"
sqlite3 shop.db "VACUUM INTO 'shop-compact.db'"

# PostgreSQL point-in-time recovery (config)
#   archive_mode = on
#   archive_command = 'cp %p /archive/%f'
#   restore: recovery_target_time = '2026-10-18 09:59'

# SQL Server (T-SQL, run in sqlcmd)
# BACKUP DATABASE shop TO DISK = '/backup/shop.bak';
# RESTORE DATABASE shop FROM DISK = '/backup/shop.bak'
#   WITH REPLACE;

Code Explained

-Fc — custom format: compressed, selective restore
--clean --if-exists drops objects before recreating
--single-transaction — consistent InnoDB dump, no locks
.backup copies safely while the database is in use

⚠ Common Mistakes

  • Never trying a restore until the outage
  • Treating a replica as a backup
  • Dumping data but not roles, extensions or settings

✓ Tips & Best Practices

  • Restore into a scratch database on a schedule
  • Keep dumps from the version you'll restore with
  • Use managed PITR in the cloud when you can

Quick Summary

  • Logical: pg_dump · mysqldump · .backup
  • Physical + logs → point in time
  • Test the restore
