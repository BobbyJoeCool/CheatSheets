Index Basics

CREATE INDEX · UNIQUE INDEX · composite index · B-tree · INCLUDE · DROP INDEX

Finding Rows Without Scanning

An index is a separate, sorted structure (usually a B-tree) that maps column values to rows, so the database can jump to matches instead of reading the whole table. It speeds up WHERE, joins, ORDER BY and MIN/MAX, at the cost of slower writes and extra disk. A composite index sorts by several columns in order; INCLUDE adds payload columns so a query can be answered from the index alone. Primary keys and unique constraints create indexes automatically.

Index Facts

  • Every INSERT/UPDATE maintains every index
  • Foreign keys are not indexed automatically (PG)
  • Small tables don't need indexes; scans are fine
  • Confirm use with EXPLAIN (sheet 73)

NoSQL Comparison

  • MongoDB: createIndex({ customerId: 1, orderDate: -1 })
  • Same compound-prefix rule and the same write cost
  • _id is indexed automatically

Creating Indexes

CREATE INDEX orders_customer_id_idx
  ON orders (customer_id);

-- Composite: equality column first, then sort column
CREATE INDEX orders_cust_date_idx
  ON orders (customer_id, order_date DESC);

SELECT order_id, order_date
FROM   orders
WHERE  customer_id = 42
ORDER  BY order_date DESC
LIMIT  10;                     -- index finds + sorts

-- Unique index (like a UNIQUE constraint)
CREATE UNIQUE INDEX products_name_uq
  ON products (lower(name));

-- Covering: extra columns for index-only scans
CREATE INDEX orders_status_idx
  ON orders (status) INCLUDE (total);

-- Build without blocking writes (PostgreSQL)
CREATE INDEX CONCURRENTLY customers_city_idx
  ON customers (city);

DROP INDEX IF EXISTS customers_city_idx;

Code Explained

customer_id = 42 narrows to one customer's entries
order_date DESC in the index means no sort step
INCLUDE (total) lets SELECT total … WHERE status = … skip the table
CONCURRENTLY is slower but doesn't lock out writes

In an ORM

model Order {
  customerId Int
  orderDate  DateTime
  @@index([customerId, orderDate(sort: Desc)])
}

What Indexes Cost

CostEffect
writesevery index updated per row
spaceoften 10–50% of the table each
memoryhot indexes compete for cache
unused onespure cost: find and drop them

⚠ Common Mistakes

  • Indexing every column "just in case"
  • Composite index in the wrong column order
  • Forgetting FK indexes, making joins and deletes slow

✓ Tips & Best Practices

  • Index what your WHERE, JOIN and ORDER BY use
  • PG: pg_stat_user_indexes.idx_scan = 0 finds unused indexes
  • Use CONCURRENTLY on production tables

Quick Summary

  • CREATE [UNIQUE] INDEX name ON t (cols)
  • Faster reads, slower writes
  • Composite order matters
