Sheet 18

Auto Scaling

launch templates · Auto Scaling groups · desired / min / max · target tracking · scheduled scaling · instance refresh

Groups That Heal and Scale

An Auto Scaling group (ASG) keeps a number of instances running from a launch template, across AZs, replacing unhealthy ones. Target tracking policies keep a metric (CPU, requests per target) near a value; scheduled actions scale for known peaks; predictive scaling forecasts. Instance refresh rolls out a new template gradually.

Key Points

  • Desired capacity floats between min and max
  • Use ELB health checks so failed apps (not just failed VMs) are replaced
  • Mixed instances policies combine On-Demand and Spot across types
  • Warm pools cut scale-out time

Limits & Quotas

  • 500 Auto Scaling groups per Region by default
  • 50 scaling policies per group
  • 5,000 launch templates per Region

Launch Template, ASG, Policies

aws ec2 create-launch-template --launch-template-name web \
    --launch-template-data file://lt.json
aws autoscaling create-auto-scaling-group --auto-scaling-group-name web \
    --launch-template LaunchTemplateName=web,Version='$Latest' \
    --min-size 2 --max-size 10 --desired-capacity 2 \
    --vpc-zone-identifier "$APP_A,$APP_B,$APP_C" \
    --target-group-arns $TG --health-check-type ELB \
    --health-check-grace-period 120

aws autoscaling put-scaling-policy --auto-scaling-group-name web \
    --policy-name cpu50 --policy-type TargetTrackingScaling \
    --target-tracking-configuration '{"PredefinedMetricSpecification":
      {"PredefinedMetricType":"ASGAverageCPUUtilization"},"TargetValue":50}'
aws autoscaling put-scheduled-update-group-action \
    --auto-scaling-group-name web --scheduled-action-name morning \
    --recurrence "0 12 * * MON-FRI" --min-size 4

aws autoscaling start-instance-refresh --auto-scaling-group-name web \
    --preferences '{"MinHealthyPercentage":90,"InstanceWarmup":120}'

Code Explained

The ASG spans three private subnets (three AZs)
ELB health checks replace instances whose app fails
Target tracking adds or removes instances to keep CPU near 50%
Instance refresh replaces instances in batches with the new template

Azure / GCP Equivalent

  • Azure VM Scale Sets + autoscale rules (az-18)
  • GCP Managed instance groups + autoscaler (gcp-18)

Cost Check

  • Auto Scaling itself is free; you pay for instances
  • Mixed On-Demand + Spot cuts cost for stateless fleets
  • Scheduled scale-in overnight saves on predictable load

Scaling Policies

PolicyUse
Target trackingKeep a metric at a target
Step scalingBigger jumps for bigger breaches
ScheduledKnown daily / weekly peaks
PredictiveForecast from history
ManualSet desired capacity

Capacity Settings

SettingMeaning
minNever fewer
maxNever more (cost cap)
desiredCurrent target
warm poolPre-initialized instances

Do & Don't

  • Do Use ELB health checks and a realistic grace period
  • Do Scale on requests per target for web tiers
  • Don’t Set min = max and lose self-healing benefits of scaling
  • Don’t Store state on instances that may be terminated

Local Testing

  • Load-test with k6 / Locust against a staging ASG
  • Test launch template user data locally first
  • Review scaling activity with aws autoscaling describe-scaling-activities

Production Checklist

  • Min 2+ across 3 AZs, ELB health checks
  • Instance refresh for deployments
  • Alarms on failed launches and max capacity reached
