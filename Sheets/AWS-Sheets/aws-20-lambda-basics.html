Functions on AWS

AWS Lambda runs a handler when an event arrives: an API request, S3 upload, queue message, schedule or direct invoke. You choose a runtime (Python, Node.js, Java, .NET, Ruby, or custom / container), memory (CPU scales with it) and timeout. The function runs with an execution role. Function URLs give a dedicated HTTPS endpoint without API Gateway.

Key Points

  • Code outside the handler runs once per execution environment: put clients there
  • Environment variables configure the function (encrypted at rest)
  • Synchronous, asynchronous and poll-based (event source mapping) invocations
  • Arm64 (Graviton) is cheaper per GB-second

Security Check

  • Least-privilege execution role per function
  • Function URLs: use AWS_IAM auth unless the endpoint must be public
  • Keep secrets in Secrets Manager, not environment variables

Limits & Quotas

  • Timeout up to 15 minutes; memory 128 MB–10,240 MB
  • Payload 6 MB synchronous; 1 MB asynchronous (raised from 256 KB in 2025)
  • Zip package 50 MB direct upload / 250 MB unzipped; images up to 10 GB

handler.py

import json, os, boto3
s3 = boto3.client("s3")                  # created once per environment
BUCKET = os.environ["BUCKET"]

def handler(event, context):
    body = json.loads(event.get("body") or "{}")
    key = f"orders/{body['id']}.json"
    s3.put_object(Bucket=BUCKET, Key=key, Body=json.dumps(body))
    return {"statusCode": 201, "body": json.dumps({"key": key})}

Create, Invoke, Expose

zip fn.zip handler.py
aws lambda create-function --function-name orders --runtime python3.13 \
    --architectures arm64 --handler handler.handler --zip-file fileb://fn.zip \
    --role $LAMBDA_ROLE --memory-size 512 --timeout 10 \
    --environment Variables={BUCKET=acme-orders}
aws lambda invoke --function-name orders --cli-binary-format raw-in-base64-out \
    --payload '{"body": "{\"id\": 42}"}' out.json && cat out.json
aws lambda update-function-code --function-name orders --zip-file fileb://fn.zip
aws lambda create-function-url-config --function-name orders --auth-type AWS_IAM
aws logs tail /aws/lambda/orders --follow

Code Explained

The S3 client is reused across warm invocations
Arm64 and 512 MB keep cost low while giving enough CPU
raw-in-base64-out lets the CLI take a plain JSON payload
Logs go to the /aws/lambda/<name> log group

  • Arm64 is about 20% cheaper per GB-second
  • More memory can be cheaper if it shortens run time

Do & Don't

  • Do Initialize clients outside the handler
  • Do Configure DLQs or on-failure destinations for async invokes
  • Don’t Use Lambda for long-running or always-busy workloads
  • Don’t Open function URLs with NONE auth for internal APIs

Local Testing

  • sam local invoke and sam local start-api run functions in Docker
  • Unit-test the handler as a plain function with fake events
  • LocalStack runs Lambda with other emulated services

Production Checklist

  • Alarms on errors, throttles and duration
  • Reserved concurrency to protect downstream systems
  • Execution role least privilege; secrets from Secrets Manager
