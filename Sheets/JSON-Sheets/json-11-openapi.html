OpenAPI & JSON Bodies

openapi: 3.1 · requestBody · responses · components/schemas · $ref · readOnly · examples

Describing JSON APIs

OpenAPI is a YAML or JSON document that describes an HTTP API: paths, parameters, and the JSON request and response bodies. Bodies are written in JSON Schema, usually defined once under components/schemas and reused with $ref. From one spec you get interactive docs, generated client SDKs and server stubs, mock servers, and request validation. OpenAPI 3.1 uses standard JSON Schema 2020-12; 3.0 used its own subset, which is why nullable: true still appears everywhere.

Key Ideas

  • One spec per API, usually openapi.yaml in the repo
  • Bodies are keyed by media type: content: application/json: schema:
  • Each response is keyed by status code; default catches the rest
  • readOnly fields (like id) appear in responses only; writeOnly (like password) in requests only
  • Errors: reuse one Problem schema (RFC 9457 problem details, application/problem+json)

Notes

openapi: 3.1.0 — spec version (not your API version, which goes in info.version)
requestBody.required: true — body must be present; separate from the schema’s own required list
"201" — quote status codes in YAML so they stay strings
$ref: "#/components/schemas/User" — a JSON Pointer into this same document
readOnly: true — clients should not send id; servers return it
type: [string, "null"] — 3.1 way to allow null; 3.0 wrote type: string + nullable: true

POST /users with JSON Bodies (3.1)

openapi: 3.1.0
info: { title: Users API, version: 1.0.0 }
paths:
  /users:
    post:
      summary: Create a user
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: "#/components/schemas/User" }
            example: { email: ada@example.com, role: admin }
      responses:
        "201":
          description: Created
          content:
            application/json:
              schema: { $ref: "#/components/schemas/User" }
components:
  schemas:
    User:
      type: object
      required: [email]
      properties:
        id:       { type: integer, readOnly: true }
        email:    { type: string, format: email }
        role:     { type: string, enum: [admin, viewer], default: viewer }
        nickname: { type: [string, "null"] }      # 3.1 nullable

Common Mistakes

  • Mixing 3.0 and 3.1 syntax — nullable: true is ignored by strict 3.1 tools; pick one version per spec
  • Leaving status codes unquoted — 201: becomes an integer key, which some parsers and linters reject
  • Copying the same object into every endpoint — changes drift; define it once in components/schemas and $ref it
  • Marking id as required on the create request — use readOnly: true so it is required only in responses

Tips

  • Lint in CI with spectral lint — catches missing descriptions, bad $refs and inconsistent naming
  • Add realistic example values — docs, mock servers and generated tests all use them
  • Generate client types (openapi-typescript, openapi-generator) rather than hand-writing request shapes
  • Validate real requests against the spec in tests so docs and code can’t drift apart

Summary

  • requestBody / responses — bodies keyed by media type and status
  • components/schemas + $ref — define once, reuse everywhere
  • readOnly / writeOnly — one schema for request and response
  • openapi: 3.1 — real JSON Schema 2020-12; type: [x, "null"]
  • application/problem+json — standard error body
