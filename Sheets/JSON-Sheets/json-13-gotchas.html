Number.MAX_SAFE_INTEGER · BigInt · dates · NaN · undefined · duplicate keys · BOM · key order

Where JSON Bites

JSON is tiny — six types and no options — so every language has to map its own types onto it, and they don’t all agree. Large integers lose precision in JavaScript, there is no date type, NaN and Infinity are not valid JSON, and the spec leaves duplicate keys and key order undefined. Most production JSON bugs come from these gaps, not from syntax errors.

The Rules to Remember

  • JSON numbers have no size limit, but JavaScript stores them as 64-bit floats: integers above 2^53 − 1 lose precision
  • Dates travel as strings — use ISO 8601 / RFC 3339 with an offset: "2026-10-23T14:05:00Z"
  • Valid JSON must be UTF-8 (RFC 8259) and must not start with a BOM
  • Objects are unordered — never rely on key order for meaning or signatures
  • Duplicate keys “SHOULD” be unique; most parsers silently keep the last one

JavaScript

JSON.parse('{"id": 9007199254740993}').id  // 9007199254740992  (precision lost)
JSON.stringify({ n: 10n })                 // TypeError: Do not know how to serialize a BigInt
JSON.stringify({ d: new Date(0) })         // '{"d":"1970-01-01T00:00:00.000Z"}'
JSON.parse('{"d":"1970-01-01T00:00:00.000Z"}').d   // a string, not a Date
JSON.stringify({ x: NaN, y: Infinity })    // '{"x":null,"y":null}'
JSON.stringify({ u: undefined, f() {} })   // '{}'   (keys dropped)
JSON.stringify([undefined, () => 1])       // '[null,null]'
JSON.parse('{"a": 1, "a": 2}')             // { a: 2 }  (last wins)
JSON.parse('\uFEFF{}')                     // SyntaxError (BOM)
JSON.stringify({ b: 1, a: 2, 10: "x" })    // '{"10":"x","b":1,"a":2}'  (integer keys first)

Python

json.loads("9007199254740993")       # 9007199254740993  (int is exact)
json.loads('{"x": NaN}')             # {'x': nan}   — accepts non-standard JSON
json.dumps(float("nan"))             # 'NaN'        — emits invalid JSON!
json.dumps(float("nan"), allow_nan=False)  # ValueError
json.dumps({1: "a", None: "b"})      # '{"1": "a", "null": "b"}'  (keys → strings)
json.dumps(datetime.now())           # TypeError: not JSON serializable
json.dumps(obj, default=str)         # fallback: str() anything unknown
json.loads("0.1", parse_float=Decimal)   # Decimal('0.1')  (exact money)

Notes

9007199254740993 — Number.MAX_SAFE_INTEGER + 2; JS rounds to the nearest representable float
10n — BigInt has no JSON form; convert with .toString() or add a toJSON method
Date — serialized through its toJSON() (ISO string); parsing never revives it
NaN / Infinity — become null in JS; Python writes them raw unless allow_nan=False
undefined / functions — dropped from objects, null inside arrays
\uFEFF — byte-order mark; strip it before parsing files saved by some Windows editors
Integer-like keys — JS objects list them first in ascending order, whatever order you wrote
default=str — handles dates, UUIDs, Decimals on the way out

Common Mistakes

  • Returning database IDs as JSON numbers — a JS client silently rounds 9007199254740993 and fetches the wrong record
  • Storing prices as floats — 0.1 + 0.2 problems reach invoices; use integer cents or decimal strings
  • Assuming JSON.parse revives dates — it returns strings; compare or sort them as dates only after converting
  • Signing or hashing JSON.stringify(obj) — different key order or whitespace on another system breaks the signature

Tips

  • Add "id_str"-style string IDs (as Twitter/X did) when clients include JavaScript
  • Use a reviver to revive dates: JSON.parse(s, (k, v) => k.endsWith("At") ? new Date(v) : v)
  • Python: json.loads(s, object_pairs_hook=...) can raise on duplicate keys
  • Document units and time zones in the field name or schema: durationMs, createdAt (UTC)

Summary

  • 2^53 − 1 — largest safe integer in JS; send bigger IDs as strings
  • Date — no JSON type; ISO 8601 strings both ways
  • NaN / undefined — not JSON; become null or vanish
  • duplicate keys / order — undefined; never depend on them
