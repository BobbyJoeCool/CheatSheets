Typed Validation in Code

z.object · safeParse · z.infer · BaseModel · model_validate_json · ValidationError

Parse, Don’t Just Cast

JSON.parse() returns any and json.loads() returns a plain dict — the type annotations you put on them are promises, not checks. A schema library defines the shape once and gives you both a runtime check at the boundary (HTTP body, file, queue message) and a static type for the rest of the code. Zod is the common choice in TypeScript; Pydantic (v2) in Python. Both coerce, apply defaults, and return readable, path-based errors.

Where to Validate

  • At every trust boundary: request bodies, third-party API responses, config files, queue messages
  • Unknown keys: Zod strips them, Pydantic ignores them — both can be made strict
  • Coercion: Pydantic converts "1" → 1 by default (lax mode); Zod never coerces unless you use z.coerce

Notes

z.object({...}) — schema object; z.infer<typeof X> turns it into a TypeScript type
.safeParse() — returns { success, data | error }; never throws
.parse() — returns the typed value or throws ZodError
BaseModel — field annotations are the schema; instantiation validates
model_validate_json() — parses bytes/str directly; faster than json.loads then validate
e.errors() — list of dicts with loc, msg, type, input

TypeScript — Zod

import { z } from "zod";

const User = z.object({
  id:    z.number().int().positive(),
  email: z.string().email(),
  role:  z.enum(["admin", "viewer"]).default("viewer"),
  tags:  z.array(z.string()).optional(),
});
type User = z.infer<typeof User>;  // { id: number; email: string; ... }

const res = User.safeParse(JSON.parse(body));
if (!res.success) {
  res.error.issues;   // [{ path: ["email"], message: "Invalid email", ... }]
} else {
  res.data.role;      // "viewer"  (default applied)
}
User.parse(data);     // returns User or throws ZodError

Python — Pydantic v2

from typing import Literal
from pydantic import BaseModel, ConfigDict, EmailStr, Field, ValidationError

class User(BaseModel):
    model_config = ConfigDict(extra="forbid")      # reject unknown keys
    id: int = Field(gt=0)
    email: EmailStr                                # pip install "pydantic[email]"
    role: Literal["admin", "viewer"] = "viewer"
    tags: list[str] | None = None

u = User.model_validate_json(body)    # parse + validate in one step
u.model_dump_json()                   # back to a JSON string
User.model_json_schema()              # dict in JSON Schema format

try:
    User.model_validate({"id": "x", "email": "a@b.io"})
except ValidationError as e:
    e.errors()[0]["loc"]              # ('id',)

Common Mistakes

  • const user = JSON.parse(body) as User — a cast checks nothing; a missing field crashes later, far from the cause
  • Validating deep inside business logic instead of at the boundary — bad data has already spread
  • Forgetting Pydantic’s lax mode — "42" silently becomes 42; use strict=True (model or field) when type matters
  • Expecting Zod to keep unknown keys — z.object strips them by default; use .passthrough() (v3) / z.looseObject() (v4) to keep

Tips

  • Use safeParse in request handlers and turn issues into a 400/422 response
  • Keep the schema as the single source of truth and derive types (z.infer) — never maintain both by hand
  • Pydantic’s model_validate_json() skips building an intermediate dict — use it for large bodies
  • Use z.coerce.number() for query strings and form fields, which always arrive as text

Summary

  • z.object + z.infer — one definition, runtime check + TS type
  • safeParse / parse — result object vs. throw
  • BaseModel — Python class that validates on creation
  • model_validate_json / model_dump_json — JSON in and out
  • extra="forbid" / .strict() — reject unknown keys
