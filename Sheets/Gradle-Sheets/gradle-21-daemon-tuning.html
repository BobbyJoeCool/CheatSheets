Daemon & Build Tuning

org.gradle.daemon · org.gradle.jvmargs · org.gradle.parallel · --stop / --status · offline mode · build scans (--scan) · --profile

Making Builds Fast

The daemon is a background JVM that keeps classes, caches and the file-system state warm between builds; it is on by default. Most speed comes from a few switches in gradle.properties: enough heap, parallel project execution, and the two caches. Measure before tuning: a build scan (--scan) or --profile shows where time goes.

Notes

  • A new daemon starts if JVM args or Java version differ
  • Daemons stop after 3 hours idle by default
  • ~/.gradle/gradle.properties overrides the project file per machine
  • File-system watching is on by default on all major OSes

gradle.properties for a Fast Build

# Commit the settings the whole team should share
org.gradle.jvmargs=-Xmx4g -XX:MaxMetaspaceSize=1g -Dfile.encoding=UTF-8
org.gradle.parallel=true
org.gradle.caching=true
org.gradle.configuration-cache=true
org.gradle.workers.max=8
org.gradle.daemon.idletimeout=3600000
org.gradle.vfs.watch=true
kotlin.daemon.jvmargs=-Xmx2g

Code Explained

jvmargs — heap for the daemon; the most common fix for slow builds
parallel — build independent projects at the same time
caching / configuration-cache — sheet 20
workers.max — cap parallel work (default: CPU cores)
idletimeout — ms before an idle daemon exits
kotlin.daemon.jvmargs — heap for the Kotlin compiler

⚠ Common Mistakes

  • Setting org.gradle.jvmargs without -Xmx — the default heap is small and builds thrash in GC
  • Using --no-daemon locally — every build pays JVM startup and cold caches
  • Killing daemons with kill -9 — use ./gradlew --stop so locks are released

✓ Tips & Best Practices

  • Put machine-specific heap sizes in ~/.gradle/gradle.properties
  • Exclude the project and ~/.gradle from antivirus scans on Windows
  • Compare two scans side by side to find what slowed a build

Quick Summary

  • org.gradle.jvmargs — daemon heap
  • org.gradle.parallel — parallel projects
