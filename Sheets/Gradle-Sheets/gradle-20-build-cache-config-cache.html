Sheet 20

Build Cache & Configuration Cache

--build-cache · org.gradle.caching · --configuration-cache · org.gradle.configuration-cache · problems report · UP-TO-DATE vs FROM-CACHE

Two Different Caches

The build cache stores task outputs keyed by their inputs, so a task whose inputs were seen before (on any branch, or on another machine with a remote cache) is restored FROM-CACHE instead of run. The configuration cache stores the task graph after configuration, so the next run with the same tasks skips running build scripts entirely. Gradle 9 treats the configuration cache as the preferred mode; turn both on in gradle.properties.

Notes

  • UP-TO-DATE — outputs already in build/; FROM-CACHE — restored
  • Cached tasks need declared inputs/outputs (sheet 22)
  • Config-cache problems are listed in an HTML report under build/reports/configuration-cache/
  • Local cache: ~/.gradle/caches/build-cache-1

Turning Them On + a Remote Cache

// gradle.properties
//   org.gradle.caching=true
//   org.gradle.configuration-cache=true
//   org.gradle.configuration-cache.problems=warn   # while migrating

// settings.gradle.kts — share outputs between CI and developers
buildCache {
    local { isEnabled = true }
    remote<HttpBuildCache> {
        url = uri("https://cache.example.com/cache/")
        isPush = providers.environmentVariable("CI").isPresent  // CI writes
        credentials { username = "ci"; password = providers
            .environmentVariable("CACHE_PASSWORD").orNull }
    }
}

Code Explained

org.gradle.caching=true — same as --build-cache every run
configuration-cache=true — same as --configuration-cache
problems=warn — report problems without failing
remote<HttpBuildCache> — a shared HTTP cache node
isPush only on CI — developers read, CI writes

In Groovy DSL

local { isEnabled = true } → local { enabled = true }
remote<HttpBuildCache> { } → remote(HttpBuildCache) { }
isPush = ….isPresent → push = ….present

Java vs Kotlin Projects

compileJava and compileKotlin are both cacheable
Kotlin — compiles in its own Kotlin daemon; tune with kotlin.daemon.jvmargs
Kotlin plugin supports the configuration cache — keep it current

⚠ Common Mistakes

  • Confusing the two caches — the build cache saves task work; the configuration cache saves script evaluation
  • Letting every developer push to the remote cache — one bad machine can poison it
  • Using absolute paths as task inputs — cache keys differ per machine; use @PathSensitive(RELATIVE)

✓ Tips & Best Practices

  • Try ./gradlew build --configuration-cache before enabling it in properties
  • Run ./gradlew clean build twice: the second should be mostly FROM-CACHE
  • A build scan's Performance tab shows cache hits and misses

Quick Summary

  • Build cache — reuse task outputs
  • Configuration cache — reuse the task graph
  • org.gradle.caching=true — enable the build cache
  • org.gradle.configuration-cache=true — enable the config cache
