Applying Plugins

plugins { } block · id("java") · core vs community plugins · version · apply false · alias(libs.plugins.x) · pluginManagement

Plugins

Almost everything a build does comes from plugins: they add tasks, conventions (like src/main/java) and configuration blocks (extensions). Core plugins ship with Gradle and need no version. Community plugins come from the Gradle Plugin Portal or a Maven repository and need a version. Declare them in the plugins { } block at the top of a build script so Gradle can resolve them early and generate type-safe accessors.

Notes

  • plugins { } must come first; only buildscript { } may precede it
  • plugins { } cannot use variables; use alias(libs.plugins…) for versions
  • Declare a version once (root, apply false), then apply by id in subprojects
  • Legacy forms to replace: apply(plugin = …) and buildscript { classpath(…) }

Declaring Plugins

// settings.gradle.kts — where plugins come from
pluginManagement {
    repositories { gradlePluginPortal(); mavenCentral() }
}
// root build.gradle.kts — declare versions, apply nowhere
plugins {
    id("com.gradleup.shadow") version "9.0.0" apply false
}
// app/build.gradle.kts
plugins {
    `java-library`                     // core id with a dash → backticks
    application                        // core plugin, no version
    id("com.gradleup.shadow")          // version comes from the root
    alias(libs.plugins.spring.boot)    // id + version from the catalog
}

Code Explained

pluginManagement — plugin repositories for the whole build
apply false — put the plugin on the classpath without applying it
Backticks — Kotlin accessor form of a core id with a dash
alias(libs.plugins.x) — id and version from libs.versions.toml

In Groovy DSL

`java-library` → id 'java-library' — no backticks needed
id("x") version "9.0.0" apply false → id 'x' version '9.0.0' apply false
alias(libs.plugins.x) — same in both DSLs

Java vs Kotlin Projects

Java — core plugins java, java-library, application; no version
Kotlin — kotlin("jvm") = id("org.jetbrains.kotlin.jvm"); not core, needs a version
`kotlin-dsl` is for writing build logic, not for Kotlin apps

⚠ Common Mistakes

  • Giving the same plugin a version in two subprojects — Gradle fails with a conflict; declare it once in the root with apply false
  • Adding a version to a core plugin (id("java") version …) — core plugins are versioned with Gradle and reject a version
  • Using com.github.johnrengelman.shadow — that id is abandoned; the plugin moved to com.gradleup.shadow

✓ Tips & Best Practices

  • Keep plugin versions in [plugins] of the version catalog (sheet 11)
  • Run ./gradlew buildEnvironment to see which plugin versions resolved
  • Prefer plugins { } over buildscript { }: faster and gives accessors

Quick Summary

  • plugins { id("x") version "v" } — apply a community plugin
  • plugins { java } — apply a core plugin
  • apply false — declare once, apply later
  • pluginManagement — where plugins come from
