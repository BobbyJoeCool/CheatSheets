Sheet 09

Declaring Dependencies & Configurations

implementation · api (java-library) · compileOnly · runtimeOnly · testImplementation · project(":lib") · group:name:version

Dependencies

Dependencies are declared into configurations, named buckets that decide where a library is visible: at compile time, at runtime, in tests, or to consumers of your library. Use implementation by default. Use api (from java-library) only when a type from the dependency appears in your public API. Coordinates follow Maven's group:name:version format.

Notes

  • api exists only with the java-library plugin
  • Gradle 9 needs junit-platform-launcher declared explicitly
  • Prefer catalog entries (libs.x) over inline strings
  • Inspect: ./gradlew :app:dependencies --configuration runtimeClasspath

A dependencies { } Block

plugins { `java-library` }

dependencies {
    api("com.fasterxml.jackson.core:jackson-databind:2.19.0") // public API
    implementation("com.google.guava:guava:33.4.0-jre")       // internal
    implementation(project(":core"))                         // subproject
    implementation(libs.okhttp)                               // catalog
    compileOnly("org.projectlombok:lombok:1.18.38")          // no runtime
    annotationProcessor("org.projectlombok:lombok:1.18.38")
    runtimeOnly("org.postgresql:postgresql:42.7.7")          // runtime only
    testImplementation("org.junit.jupiter:junit-jupiter:5.13.4")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
    implementation(files("libs/legacy.jar"))                 // local JAR
}

Code Explained

api — consumers also get Jackson on their compile classpath
implementation — hidden from consumers; faster recompiles
project(":core") — depend on a subproject in the same build
compileOnly — provided at runtime by something else
annotationProcessor — processors run by javac
files(…) — a local JAR; prefer a repository when possible

In Groovy DSL

implementation("g:a:v") → implementation 'g:a:v'
project(":core") → project(':core'); libs.okhttp unchanged
`java-library` → id 'java-library'

Java vs Kotlin Projects

Java — annotationProcessor(…) runs processors in javac
Kotlin — use kapt(…) (kotlin("kapt")) or ksp(…) instead
Kotlin — stdlib is added automatically; testImplementation(kotlin("test"))

⚠ Common Mistakes

  • Using compile / testCompile from old tutorials — long removed; use implementation
  • Making everything api — every change recompiles all downstream projects
  • Leaving out the JUnit junit-platform-launcher — Gradle 9 test runs fail to start

✓ Tips & Best Practices

  • Ask Gradle why a library is present: ./gradlew dependencyInsight --dependency guava
  • Use the JUnit BOM (platform(...)) so all JUnit modules share one version
  • Keep annotationProcessor in step with compileOnly for Lombok-style tools

Quick Summary

  • implementation — the default choice
  • api — only for types in your public API
  • compileOnly / runtimeOnly — one side of the classpath
  • testImplementation — test-only dependencies
