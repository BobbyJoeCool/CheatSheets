Composite Builds

includeBuild · substituting a library with local source · pluginManagement includeBuild · --include-build · composite vs multi-project

Combining Separate Builds

A composite build joins complete, independent builds, each with its own settings file, so they act as one. The common case: you are fixing a library and an app that uses it. includeBuild("../json-lib") makes Gradle build the library from source and substitute it for the published com.example:json-lib dependency, with no version bump or publishToMavenLocal. Included builds are also how build-logic (sheet 18) delivers plugins.

Notes

  • Substitution is automatic when group:name match the included project
  • Included builds run on the including build's Gradle version
  • Run a task in an included build: ./gradlew :json-lib:test
  • Remove the includeBuild line to go back to the published JAR

Developing an App and a Library Together

// app/settings.gradle.kts
pluginManagement {
    includeBuild("../my-plugins")             // plugins built from source
}
rootProject.name = "app"
includeBuild("../json-lib")                   // swap in a local checkout

// Explicit form, when coordinates don't match automatically:
// includeBuild("../json-lib") {
//     dependencySubstitution {
//         substitute(module("com.example:json-lib")).using(project(":"))
//     }
// }

// app/build.gradle.kts — unchanged
dependencies { implementation("com.example:json-lib:2.3.0") }

Code Explained

pluginManagement { includeBuild } — plugins from a local build
includeBuild("../json-lib") — library built from source
substitute(…).using(project(":")) — manual mapping
The app's dependency line does not change
One-off without editing settings: --include-build ../json-lib

In Groovy DSL

settings.gradle — same calls: includeBuild '../json-lib'
substitute(module('…')).using(project(':')) — same, single quotes
implementation("g:a:v") → implementation 'g:a:v'

Java vs Kotlin Projects

Language doesn't matter — any JVM build can be included
A Kotlin app can include a Java library, and the reverse
Substitution swaps the JAR for the included build's jar output

Commands

⚠ Common Mistakes

  • Including a build whose group differs from the coordinates you use — nothing is substituted; add dependencySubstitution
  • Committing a developer-only includeBuild — CI then needs the sibling checkout; use --include-build instead
  • Expecting allprojects { } to reach included builds — they are separate builds

✓ Tips & Best Practices

  • Guard optional includes: if (file("../json-lib").exists()) includeBuild("../json-lib")
  • IntelliJ imports included builds, so you can debug into library source
  • Use composites instead of mavenLocal() for cross-repo work

Quick Summary

  • includeBuild(path) — join another build
  • Automatic substitution — by group:name
  • --include-build — composite for one run
  • pluginManagement { includeBuild } — plugins from source
