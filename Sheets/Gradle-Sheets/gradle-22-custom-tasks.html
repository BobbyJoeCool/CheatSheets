Writing Custom Tasks

abstract class : DefaultTask() · @TaskAction · @Input / @InputFile / @OutputDirectory · @get: annotations · @CacheableTask · registering

Task Classes

For anything beyond a few lines, write a task class: an abstract class extending DefaultTask with annotated lazy properties and one @TaskAction method. The annotations tell Gradle what the inputs and outputs are, which makes the task incremental (UP-TO-DATE) and, with @CacheableTask, cacheable. Keep the class in build-logic so it can be tested and reused.

Notes

  • Gradle generates the property implementations for abstract getters
  • In Kotlin, annotate with @get:Input (the getter), not @Input
  • Inject services (ExecOperations, FileSystemOperations) instead of using project

A Cacheable Task

@CacheableTask
abstract class GenerateVersionFile : DefaultTask() {
    @get:Input abstract val version: Property<String>
    @get:InputFile @get:PathSensitive(PathSensitivity.RELATIVE)
    abstract val template: RegularFileProperty
    @get:OutputFile abstract val outputFile: RegularFileProperty

    @TaskAction fun generate() {
        val text = template.get().asFile.readText()
        val out = text.replace("@VERSION@", version.get())
        outputFile.get().asFile.writeText(out)
    }
}
tasks.register<GenerateVersionFile>("generateVersionFile") {
    version = project.version.toString()
    template = layout.projectDirectory.file("src/version.tmpl")
    outputFile = layout.buildDirectory.file("generated/version.txt")
}

Code Explained

@CacheableTask — outputs may be stored in the build cache
abstract val … : Property<String> — Gradle implements it
@PathSensitive(RELATIVE) — cache key ignores absolute paths
@OutputFile — Gradle creates parent folders and tracks the file
@TaskAction — the method that does the work
register<T> — wire values in at configuration time

In Groovy DSL

abstract class X : DefaultTask() → abstract class X extends DefaultTask
@get:Input abstract val v: Property<String> → @Input abstract Property<String> getV()
register<X>("x") → register('x', X)

Java vs Kotlin Projects

Java — public abstract class X extends DefaultTask, abstract getters
Kotlin — @get: puts the annotation on the getter Gradle reads
In build-logic: src/main/java or src/main/kotlin

⚠ Common Mistakes

  • Writing @Input instead of @get:Input in Kotlin — it lands on the property, where Gradle never sees it
  • Forgetting abstract on the class — Gradle 9 requires it when properties are abstract or @Inject is used
  • Not declaring outputs — the task can never be UP-TO-DATE and always runs

✓ Tips & Best Practices

  • Inject a service: @get:Inject abstract val exec: ExecOperations
  • Use @get:Incremental + InputChanges to process only changed files
  • Test task classes with Gradle TestKit (GradleRunner)

Quick Summary

  • abstract class X : DefaultTask() — a task type
  • @get:Input / @get:OutputFile — declare I/O
  • @TaskAction — the work
  • @CacheableTask — opt into the build cache
