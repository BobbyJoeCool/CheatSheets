Builds on CI

On CI, run the wrapper with the same tasks developers use, and cache ~/.gradle between runs. On GitHub Actions, gradle/actions/setup-gradle handles caching, wrapper validation and build-scan links. When a build fails, add logging and a stack trace first, then inspect the dependency graph; clear caches only as a last resort.

CI Defaults

  • Gradle detects CI and uses plain console output
  • Use --no-daemon only if agents are thrown away anyway
  • Run ./gradlew build — not separate compile, test steps
  • Publish test reports from build/reports/tests/

GitHub Actions Workflow

# .github/workflows/build.yml
name: build
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 21 }
      - uses: gradle/actions/setup-gradle@v4   # cache + wrapper check
      - run: ./gradlew build --scan

Code Explained

setup-java — JDK that runs Gradle (17+)
setup-gradle — caches ~/.gradle, validates the wrapper
--scan — link to a build scan in the job log
Only main writes the cache by default; PRs read it

⚠ Common Mistakes

  • Deleting ~/.gradle at the first error — it rarely helps and costs a full re-download
  • Caching ~/.gradle by hand and with setup-gradle — double caches, slower restores
  • Running CI on a different JDK than developers without a toolchain — "works on my machine"

✓ Tips & Best Practices

  • Remove just one corrupted entry: rm -rf ~/.gradle/caches/modules-2/files-2.1/<group>
  • Read the first error in the output; later ones are often follow-ons
  • Add --continue in CI to see failures from every module

Quick Summary

  • setup-gradle — CI caching done right
  • --stacktrace --info — first debugging step
  • dependencyInsight — version questions
  • Clear caches — last resort
