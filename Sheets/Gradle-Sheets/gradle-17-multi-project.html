Sheet 17

Multi-Project Builds

include(":app", ":lib") · rootProject.name · project(":lib") dependency · subproject layout · :app:build · avoid allprojects

Many Projects, One Build

A multi-project build has one settings.gradle.kts that includes several subprojects, each with its own build script. Projects depend on each other with project(":core"), and Gradle builds them in the right order, in parallel when allowed. Share configuration with convention plugins (sheet 18) rather than allprojects { } / subprojects { } blocks.

Notes

  • include("lib:payments") maps to folder lib/payments
  • The root project often has no code, only settings
  • TYPESAFE_PROJECT_ACCESSORS enables projects.core
  • org.gradle.parallel=true builds independent projects at once

Settings + Two Subprojects

// settings.gradle.kts
rootProject.name = "shop"
include("app", "core", "lib:payments")       // lib/payments → :lib:payments
enableFeaturePreview("TYPESAFE_PROJECT_ACCESSORS")

// core/build.gradle.kts
plugins { `java-library` }
dependencies { api(libs.jackson.databind) }

// app/build.gradle.kts
plugins { application }
dependencies {
    implementation(project(":core"))
    implementation(projects.lib.payments)     // type-safe accessor
}
application { mainClass = "shop.App" }

Code Explained

rootProject.name — the build's name; set it explicitly
include(…) — each path becomes a subproject
api(...) in core — app also sees Jackson
project(":core") — string path to a sibling project
projects.lib.payments — the same, checked at compile time

In Groovy DSL

settings.gradle: include 'app', 'core', 'lib:payments'
api(libs.jackson.databind) → api libs.jackson.databind
projects.lib.payments — works in Groovy too

Java vs Kotlin Projects

Java — each subproject applies java-library or application
Kotlin — declare kotlin("jvm") version "…" apply false once in the root
Kotlin — subprojects then apply kotlin("jvm") with no version

Sharing Config

ApproachVerdict
Convention plugin✔ Preferred — opt-in per project
Version catalog✔ For versions only
gradle.properties✔ For flags shared by all
subprojects { }✖ Couples projects, breaks isolation
allprojects { }✖ Same, plus applies to root

⚠ Common Mistakes

  • Reaching into another project (project(":core").tasks…) — couples configuration and blocks Isolated Projects
  • Creating a folder but not include-ing it — Gradle ignores it without warning
  • Putting code in the root project of a multi-project build — tasks then run twice in confusing ways

✓ Tips & Best Practices

  • Group libraries under libs/ or modules/ and keep app thin
  • Run the narrowest task path (:app:test) for fast feedback
  • Use --configure-on-demand or Isolated Projects (incubating in 9.7+) for huge builds

Quick Summary

  • include("a", "b") — add subprojects
  • project(":a") — depend on a sibling
  • :a:task — run in one project
  • Convention plugins — share config safely
