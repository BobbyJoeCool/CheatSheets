Resolving Versions

When two paths in the graph ask for different versions of one module, Gradle picks the highest version by default (Maven picks the nearest). Constraints and platforms (BOMs) let you steer that choice without adding dependencies, and rich versions say how firm a version is. Use dependencyInsight to see which version won and why.

Notes

  • A BOM is a POM of versions; platform() imports it as constraints
  • enforcedPlatform overrides even higher transitive versions
  • Constraints apply only if something else pulls the module in
  • Locking (--write-locks) freezes dynamic versions for repeatable builds

Steering Resolution

dependencies {
    implementation(platform(libs.spring.boot.bom))       // import a BOM
    implementation("com.fasterxml.jackson.core:jackson-databind")  // no version
    constraints {
        implementation("org.yaml:snakeyaml:2.4") { because("CVE fix") }
    }
    implementation("com.example:client:1.2") {
        exclude(group = "commons-logging", module = "commons-logging")
    }
    implementation("org.slf4j:slf4j-api") {
        version { strictly("[2.0, 3.0[") }               // any 2.x, never 3
    }
}
configurations.all { resolutionStrategy.failOnVersionConflict() }
dependencyLocking { lockAllConfigurations() }

Code Explained

platform(...) — versions from the BOM become constraints
constraints { } — minimum version if the module appears at all
because("…") — shows up in dependencyInsight output
exclude(...) — drop one transitive dependency
strictly("[2.0, 3.0[") — a range nothing can override
failOnVersionConflict() — make every conflict a build error

In Groovy DSL

implementation(platform(x)) → implementation platform(x)
exclude(group = "a", module = "b") → exclude group: 'a', module: 'b'
version { strictly("…") } → version { strictly '…' }

Java vs Kotlin Projects

Same conflict rules for Java and Kotlin dependencies
Kotlin — align Kotlin modules with platform("org.jetbrains.kotlin:kotlin-bom:…")
Kotlin — coroutines: platform("org.jetbrains.kotlinx:kotlinx-coroutines-bom:…")

Rich Versions

KeywordMeaning
require("1.2")At least 1.2 (same as a plain version)
prefer("1.4")Use 1.4 if nothing asks for more
strictly("1.3")Exactly 1.3 — fails if impossible
reject("1.3.1")Never pick this version
"1.+" / "[1.0,2.0)"Dynamic / range — lock these

⚠ Common Mistakes

  • Using enforcedPlatform in a published library — it forces versions on every consumer; keep it to applications
  • Using exclude to fix a version clash — it removes the module entirely; use a constraint instead
  • Leaving 1.+ versions unlocked — builds change silently when a new release appears

✓ Tips & Best Practices

  • Add because("…") to every constraint so the reason survives review
  • Spring Boot: use SpringBootPlugin.BOM_COORDINATES instead of hard-coding the BOM
  • Fix CVEs in transitive libs with a constraint, not a direct dependency

Quick Summary

  • Highest version wins — Gradle's default
  • platform(bom) — import aligned versions
  • constraints { } — set a version without a dependency
  • dependencyInsight — explain a resolution
