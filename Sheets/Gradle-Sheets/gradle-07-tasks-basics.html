Sheet 07

Tasks: Registering & Configuring

tasks.register · tasks.named · doFirst / doLast · dependsOn · finalizedBy · mustRunAfter · group & description · lazy vs eager

Tasks

A task has inputs, outputs and one or more actions (doFirst, doLast). Register tasks with tasks.register, which is lazy: the configuration block runs only if the task ends up in the graph. Change existing tasks with tasks.named or tasks.withType<T>().configureEach. Wiring an output to another task's input, or using dependsOn, tells Gradle the order.

Notes

  • Typed tasks: tasks.register<Copy>("x") gives from, into…
  • Declare inputs / outputs so the task can be UP-TO-DATE
  • Inside actions, don't touch project — capture values first (config cache)

Register, Configure, Order

val generateInfo = tasks.register("generateInfo") {
    group = "build"
    description = "Writes build-info.txt"
    val out = layout.buildDirectory.file("build-info.txt")
    val ver = project.version.toString()      // captured at config time
    inputs.property("version", ver)
    outputs.file(out)
    doLast { out.get().asFile.writeText("version=$ver\n") }
}
tasks.named("processResources") { dependsOn(generateInfo) }
tasks.register<Copy>("copyDocs") {             // typed task
    from("docs"); into(layout.buildDirectory.dir("site"))
}
tasks.withType<JavaCompile>().configureEach { options.encoding = "UTF-8" }
tasks.named<Test>("test") { finalizedBy("jacocoTestReport") }

Code Explained

tasks.register — returns a TaskProvider; configured lazily
inputs / outputs — enable up-to-date checks and caching
doLast — the action that runs at execution time
dependsOn(generateInfo) — run it before processResources
register<Copy> — a built-in task type with its own DSL
withType<T>().configureEach — lazily configure every task of a type

In Groovy DSL

register<Copy>("x") → register('x', Copy)
withType<JavaCompile>() → withType(JavaCompile)
val ver = … → def ver = …; "$ver" interpolates, '…' doesn't

Java vs Kotlin Projects

Java — withType<JavaCompile>: options.encoding, options.compilerArgs
Kotlin — withType<KotlinCompile>: compilerOptions { }; sources are always UTF-8
processResources, test, jar — same tasks in both

Ordering & Conditions

APIMeaning
dependsOn(t)t must run first (and is pulled in)
mustRunAfter(t)If both run, this runs after t
shouldRunAfter(t)Soft version of mustRunAfter
finalizedBy(t)Run t after this, even on failure
onlyIf { … }Skip unless the condition is true

Lazy vs Eager APIs

APILazy?
tasks.register(…)✔
tasks.named(…)✔
withType<T>().configureEach✔
tasks.create(…)✖ eager
tasks.getByName(…)✖ eager
withType<T> { … }✖ eager

Built-in Task Types

TypeUse
Copy / SyncCopy files (Sync deletes extras)
DeleteRemove files
Zip / JarCreate archives
Exec / JavaExecRun a program / main class

⚠ Common Mistakes

  • Using tasks.create or withType<T> { } — eager APIs configure every task on every build and slow configuration
  • Reading project.something inside doLast — breaks the configuration cache; capture values in a val outside the action
  • Using dependsOn when you only need ordering — use mustRunAfter so you don't force the other task to run

✓ Tips & Best Practices

  • Pass a TaskProvider (not a name string) to dependsOn for safer wiring
  • Give every custom task a group so it shows in ./gradlew tasks
  • Wire outputs to inputs (from(otherTask)) — dependencies are then inferred

Quick Summary

  • tasks.register — create a task lazily
  • tasks.named — configure an existing task
  • doLast { } — task action
  • dependsOn / mustRunAfter — ordering
