Pagination, Filtering & Versioning

?page=&limit= · cursor pagination · ?sort= · filter params · /api/v1 routers · etag · swagger-ui-express

Description

List endpoints need limits: offset pagination (?page=2&limit=20) is simple, while cursor pagination (?after=<id>) stays fast and stable as data changes. Filtering and sorting come from validated query params, never raw ones. Version the API with path prefixes so breaking changes ship as /api/v2 while /api/v1 keeps working, and describe it all with an OpenAPI document.

Notes

  • Always cap limit (e.g. max 100)
  • Return paging metadata or Link headers so clients know there's more
  • Allowlist sortable fields; never pass ?sort= straight to SQL
  • Express sends weak ETags for res.json: conditional GETs get 304 for free

Cursor Pagination + Versions

// GET /api/v1/todos?limit=20&after=120&sort=-created&status=open
const SORTS = { created: "created_at", title: "title" };

v1.get("/todos", async (req, res) => {
  const limit = Math.min(Number(req.query.limit) || 20, 100);
  const after = req.query.after ? Number(req.query.after) : null;
  const raw = String(req.query.sort ?? "-created");
  const column = SORTS[raw.replace(/^-/, "")] ?? "created_at";
  const dir = raw.startsWith("-") ? "desc" : "asc";

  const rows = await repo.list({ limit: limit + 1, after, column, dir });
  const hasMore = rows.length > limit;
  const items = rows.slice(0, limit);
  const next = hasMore
    ? `${req.baseUrl}/todos?limit=${limit}&after=${items.at(-1).id}` : null;
  if (next) res.links({ next });
  res.json({ items, next });
});

app.use("/api/v1", v1);
app.use("/api/v2", v2);                      // breaking changes live here

import swaggerUi from "swagger-ui-express";
app.use("/docs", swaggerUi.serve, swaggerUi.setup(openapiSpec));

Code Explained

limit + 1 rows — cheap way to know if another page exists
SORTS map — allowlist; unknown values fall back
res.links({ next }) — standard Link header
swagger-ui-express — serves interactive docs from a spec

Prefer / Avoid

  • Unbounded SELECT * for lists → a default and maximum limit
  • OFFSET 100000 on big tables → cursor (WHERE id > ?) pagination
  • Changing v1 responses in place → ship breaking changes under /api/v2

Pagination Styles

StyleQueryTrade-off
offset?page=3&limit=20simple; slow + shifts on inserts
cursor?after=120&limit=20fast, stable; no page jumps
keyset (multi-col)?after=2026-01-01,120stable sort on non-unique

⚠ Common Mistakes

  • Letting ?limit=100000 through: one request dumps the table
  • Building ORDER BY ${req.query.sort}: SQL injection
  • Offset paging a feed that changes: users see duplicates or miss rows

✓ Tips & Best Practices

  • Generate the OpenAPI spec from zod schemas (zod-openapi) to keep docs honest
  • Return total only when cheap; counts on big tables are slow
  • Turn ETag off (app.set("etag", false)) only if a proxy handles it

Quick Summary

  • cap limit — always
  • cursor pagination — ?after=id
  • allowlist sort/filter fields
  • /api/v1, /api/v2 — versions
