Caching with Redis

redis / ioredis client · cache-aside middleware · EX TTL · cache keys · invalidation · Cache-Control

Description

Caching saves repeated work: store a computed result in Redis with a time-to-live and serve it until it expires or you invalidate it. The usual pattern is cache-aside: look in the cache, and on a miss load from the database and write the result back. Pair server caching with HTTP Cache-Control headers so browsers and CDNs avoid the request entirely.

Notes

  • client.set(key, value, { EX: 60 }) — expire after 60 s
  • Cache JSON strings; parse on the way out
  • Invalidate on writes (del) or use short TTLs
  • Include everything that changes the result in the key (user, query)

Cache-Aside Middleware

import { createClient } from "redis";
export const redis = createClient({ url: process.env.REDIS_URL });
redis.on("error", (err) => console.error("redis", err));
await redis.connect();

const cache = (ttl = 60) => async (req, res, next) => {
  if (req.method !== "GET") return next();
  const key = `cache:${req.user?.id ?? "anon"}:${req.originalUrl}`;
  const hit = await redis.get(key);
  if (hit) return res.set("X-Cache", "HIT").type("json").send(hit);

  const json = res.json.bind(res);
  res.json = (body) => {                         // store what we send
    if (res.statusCode === 200)
      redis.set(key, JSON.stringify(body), { EX: ttl });
    return json(body);
  };
  res.set("X-Cache", "MISS");
  next();
};

app.get("/stats", cache(300), async (req, res) =>
  res.json(await expensiveStats()));

app.post("/todos", async (req, res) => {
  const todo = await repo.create(req.valid.body);
  await redis.del(`cache:${req.user.id}:/todos`);  // invalidate
  res.status(201).json(todo);
});

app.get("/public/countries", (req, res) => {
  res.set("Cache-Control", "public, max-age=86400");  // browsers + CDN
  res.json(countries);
});

Code Explained

Key includes user + URL: no data leaks between users
Wrapping res.json — captures the body on a miss
Only cache 200s; errors shouldn't stick
Cache-Control: public — lets CDNs cache shared data

Prefer / Avoid

  • Caching per-user data under a shared key → user id in the key
  • No TTL (set without EX) → always expire
  • Redis for data that never changes → Cache-Control + CDN, or in-memory

Redis Client Calls

CallDoes
get(k)read (string or null)
set(k, v, { EX: s })write with TTL
del(k)invalidate
incr(k)counters / rate limits
expire(k, s)set TTL
scanIterator({ MATCH })find keys (not KEYS)

Cache-Control Values

ValueMeaning
no-storenever cache

⚠ Common Mistakes

  • Leaving user id out of the key: one user's data is served to others
  • Calling KEYS cache:* in production: blocks Redis; use SCAN
  • App crashes when Redis is down: catch cache errors and fall through to the DB

✓ Tips & Best Practices

  • Reuse the Redis client for sessions (37) and rate limits (42)
  • Start with Cache-Control headers; add Redis when the DB is the bottleneck
  • Log hit rate (X-Cache) to see whether caching helps

Quick Summary

  • cache-aside — check, load, store
  • EX — always a TTL
  • key = user + URL
  • Cache-Control — browser / CDN caching
