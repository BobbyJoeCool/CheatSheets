Sheet 23

Error-Handling Middleware

(err, req, res, next) · next(err) · placed last · default error handler · NODE_ENV · headersSent

Description

Express recognizes error middleware by its four parameters: (err, req, res, next). When anything calls next(err), throws in a sync handler, or rejects in an async one, Express skips normal middleware and runs the error handlers in order. Mount yours after all routes. Without one, Express's default handler sends the stack trace in development and a bare status page in production.

Notes

  • All four params are required, even if you don't use next
  • The default handler uses err.status / err.statusCode, else 500
  • If headers are already sent, delegate with next(err) so Express closes the connection
  • You can chain several: logger → JSON responder → fallback

Logging + JSON Error Handlers

// routes …
app.use("/api", api);

// 404 for anything unmatched (normal middleware, not error)
app.use((req, res) => res.status(404).json({ error: "Not Found" }));

// error logger
app.use((err, req, res, next) => {
  req.log?.error({ err }, "request failed") ?? console.error(err);
  next(err);                                  // pass to the responder
});

// error responder: always last
app.use((err, req, res, next) => {
  if (res.headersSent) return next(err);      // let Express close it
  const status = err.status ?? err.statusCode ?? 500;
  res.status(status).json({
    error: status < 500 ? err.message : "Internal Server Error",
    ...(app.get("env") === "development" && { stack: err.stack }),
  });
});

Code Explained

Four params — that's how Express tells it's an error handler
Hide 5xx messages from clients; log the details
res.headersSent — streaming responses can fail midway
Stack traces only in development

Prefer / Avoid

  • (err, req, res) => … (three params) → (err, req, res, next) even if next unused
  • Error handler mounted before routes → after routes and the 404 handler
  • Sending err.message for 500s → a generic message; log the real one

Express 4 → 5

  • 4.x rejected promises in handlers never reached it → 5.x rejections go to error middleware automatically

⚠ Common Mistakes

  • Leaving off next from the signature: Express treats it as normal middleware and skips it for errors
  • Putting the 404 handler after the error handler: unmatched routes never get your JSON 404
  • Calling res.json when res.headersSent is true: throws a second error inside the handler

✓ Tips & Best Practices

  • Return a consistent error envelope: { error: { code, message } } (sheet 25)
  • Include req.id in error responses so users can quote it to support
  • Map known error types (validation, DB unique) to 4xx in the handler

Quick Summary

  • (err, req, res, next) — four params
  • mount after routes and 404
  • err.status — becomes the status
  • check res.headersSent
