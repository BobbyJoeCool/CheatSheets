Testing APIs Directly

The request fixture is an APIRequestContext: an HTTP client that uses baseURL, extraHTTPHeaders and proxy settings from config. Use it for pure API tests, or inside UI tests to seed data and verify the backend. page.request shares cookies with the browser context, so API calls are authenticated like the user.

Notes

  • request fixture has its own cookie jar; page.request shares the page's
  • data objects are sent as JSON; use form or multipart otherwise
  • failOnStatusCode: true throws on non-2xx
  • response.timing() (1.62) and cookie methods (1.64) available

API Tests

// playwright.config.ts → use: { baseURL: 'https://api.example.com',
//   extraHTTPHeaders: { Authorization: `Bearer ${process.env.API_TOKEN}` } }

test('create and fetch an issue', async ({ request }) => {
  const created = await request.post('/repos/acme/app/issues', {
    data: { title: 'Bug: cart total', labels: ['bug'] },
  });
  expect(created.status()).toBe(201);
  const { number } = await created.json();

  const got = await request.get(`/repos/acme/app/issues/${number}`);
  await expect(got).toBeOK();
  expect(await got.json()).toMatchObject({ state: 'open' });
});

test('UI shows API-created item', async ({ page }) => {
  await page.request.post('/api/todos', { data: { text: 'from API' } });
  await page.goto('/todos');
  await expect(page.getByText('from API')).toBeVisible();
});

Code Explained

request.post(url, { data }) — JSON body
toBeOK() — 2xx check with good errors
toMatchObject — partial body match
page.request — authenticated as the page

⚠ Common Mistakes

  • Using the request fixture expecting the UI's login cookies; use page.request
  • Forgetting await on res.json(); you compare a Promise
  • Leaking contexts from request.newContext(); call dispose()

✓ Tips & Best Practices

  • Seed data with API calls and verify through the UI for faster e2e tests
  • Keep API tests in a separate project with no browser (request only)
  • Log in via API, then storageState() for UI tests
