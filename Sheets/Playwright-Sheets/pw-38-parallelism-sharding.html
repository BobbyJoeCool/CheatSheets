Parallelism & Sharding

workers · fullyParallel · --shard=1/4 · merge-reports · mergeFiles · describe.configure({ mode: 'serial' })

Running Tests in Parallel

Playwright runs test files in parallel across worker processes (default: half the CPU cores). With fullyParallel: true, individual tests in the same file are spread across workers too. Sharding splits the suite across machines with --shard=x/n; each shard writes a blob report that merge-reports combines into one HTML report.

Notes

  • Each worker is a separate Node process with its own browser
  • Workers are restarted after a test failure
  • test.info().workerIndex / parallelIndex identify workers
  • mode: 'serial' skips remaining tests after a failure

Configuration and Commands

export default defineConfig({
  fullyParallel: true,
  workers: process.env.CI ? '50%' : undefined,     // number or % of cores
  reporter: process.env.CI ? 'blob' : 'html',
});

// per file
test.describe.configure({ mode: 'parallel' });     // tests in this file in parallel
test.describe.configure({ mode: 'serial' });       // dependent steps, in order

// shard across 4 CI machines
// npx playwright test --shard=1/4    (…2/4, 3/4, 4/4)
// → each writes blob-report/report-*.zip

// combine on one machine
// npx playwright merge-reports --reporter html ./all-blob-reports
// html reporter option (1.62): [['html', { mergeFiles: true }]]

Code Explained

fullyParallel — parallelize inside files
workers — count or percentage
mode: 'serial' — ordered, shared failure
--shard=i/n — split run across machines
merge-reports — one report from all shards

describe.configure modes

ModeBehaviour
defaultSequential in file, independent retries
parallelTests in file run concurrently
serialIn order; on failure skip the rest; retry group

⚠ Common Mistakes

  • Tests sharing a user account or DB rows; they pass alone and fail in parallel
  • Using mode: 'serial' to fix shared state; it hides the coupling and slows the suite
  • Forgetting fullyParallel and wondering why shards are unbalanced (sharding splits by file otherwise)

✓ Tips & Best Practices

  • Use unique data per test (Date.now(), worker index) to stay parallel-safe
  • Enable fullyParallel before sharding for even shard sizes
  • Upload blob-report as a CI artifact from every shard, then merge

Quick Summary

  • workers — processes per machine
  • fullyParallel — per-test distribution
  • --shard=i/n — split across machines
  • merge-reports — combine blob reports
