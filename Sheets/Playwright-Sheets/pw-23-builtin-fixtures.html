What Fixtures Are

Fixtures are the values a test destructures from its first argument. Playwright creates only the fixtures a test asks for, sets them up before the test and tears them down after, even on failure. Test-scoped fixtures (page, context) are fresh per test; worker-scoped ones (browser) are shared by all tests in one worker process.

Notes

  • Fixtures are lazy: unused fixtures cost nothing
  • context options come from use in config or test.use()
  • mount is built in since 1.62 (component testing)
  • testInfo is the second argument, not a fixture

Using Built-ins

test('two users chat', async ({ browser, browserName, request }) => {
  test.skip(browserName === 'webkit', 'WS issue on WebKit');

  const alice = await browser.newContext();          // extra isolated users
  const bob = await browser.newContext({ storageState: 'playwright/.auth/bob.json' });
  const a = await alice.newPage();
  const b = await bob.newPage();

  const res = await request.post('/api/rooms', { data: { name: 'qa' } });
  const { id } = await res.json();
  await a.goto(`/rooms/${id}`);
  await b.goto(`/rooms/${id}`);
  await a.getByRole('textbox').fill('hi bob');
  await a.keyboard.press('Enter');
  await expect(b.getByText('hi bob')).toBeVisible();
  await alice.close(); await bob.close();
});

Code Explained

browser — create extra contexts per user
browserName — 'chromium' \| 'firefox' \| 'webkit'
request — API client sharing baseURL
manual contexts — you must close them

⚠ Common Mistakes

  • Creating contexts with browser.newContext() and never closing them; memory leaks across the worker
  • Asking for page in a pure API test; it launches a browser for nothing, use request
  • Mutating browser state (e.g. closing it) inside a test

✓ Tips & Best Practices

  • Destructure only what you need; it keeps tests fast
  • Use browser.newContext() for multi-user scenarios
  • Use request for setup data instead of clicking through the UI

Quick Summary

  • browser — shared per worker
  • request — API calls in tests
