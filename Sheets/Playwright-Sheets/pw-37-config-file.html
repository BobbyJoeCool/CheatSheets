The Config File

playwright.config.ts exports defineConfig({...}). Top-level keys control the runner (where tests are, workers, retries, reporters); use sets browser/context options inherited by every test; projects define named variants (browsers, devices, environments) that each run the matching tests with their own use. Project values override top-level ones.

Notes

  • testProject.default: false (1.64) keeps a project out of plain runs
  • Use process.env for environment switches
  • --config other.config.ts picks another file
  • dotenv is not built in; import it yourself

Typical Config

import { defineConfig, devices } from '@playwright/test';
import 'dotenv/config';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 4 : undefined,
  reporter: process.env.CI ? [['blob'], ['github']] : 'html',
  use: {
    baseURL: process.env.BASE_URL ?? 'http://localhost:3000',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },
  projects: [
    { name: 'setup', testMatch: /.*\.setup\.ts/ },
    { name: 'chromium', use: { ...devices['Desktop Chrome'] }, dependencies: ['setup'] },
    { name: 'visual', testMatch: /visual\/.*/, default: false },   // only via --project
  ],
  webServer: { command: 'npm start', url: 'http://localhost:3000' },
});

Code Explained

fullyParallel — tests within files run in parallel
forbidOnly — fail CI on stray test.only
reporter — different locally vs CI
use — defaults for every project
default: false — opt-in project (1.64)
webServer — start the app first

⚠ Common Mistakes

  • Putting baseURL at the top level instead of inside use; it's ignored
  • Defining use on a project and losing top-level use values you expected to merge deeply
  • Hard-coding CI-only values (workers: 1) for local runs too

✓ Tips & Best Practices

  • Branch on process.env.CI for retries, workers and reporters
  • Keep one config; use projects instead of several config files where possible
  • Type-check config with defineConfig for autocompletion

Quick Summary

  • defineConfig — typed config
  • use — context/browser defaults
  • projects — named variants
  • webServer — boot the app under test
