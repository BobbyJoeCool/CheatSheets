Same Patterns, Different Hosts

Each block shows the same five moves: compile, test, find, extract a group, and replace. The pattern syntax carries over from sheets 01–15; what changes is the API, the string escaping, the replacement tokens, and which features the engine supports. Go and Rust use linear-time engines without lookaround or backreferences; the rest are backtracking engines close to PCRE.

Biggest Differences

  • Go/Rust: no lookaround or backrefs; Go $1x means group 1x, so write ${1}x
  • Ruby: ^ $ match at every line; validate with \A…\z
  • PHP: patterns need delimiters /…/; add u for UTF-8

Go — regexp (RE2 syntax)

re := regexp.MustCompile(`(\w+)@(\w+)\.com`)
re.MatchString("me@site.com")              // true
re.FindAllString("a@b.com c@d.com", -1)    // [a@b.com c@d.com]
re.FindStringSubmatch("me@site.com")[2]    // "site"
re.ReplaceAllString("me@site.com", "${2}:$1")  // "site:me"
regexp.Compile(`(?<=a)b`)                  // error: no lookbehind

Ruby — built-in Regexp

"me@site.com" =~ /@(\w+)/            # 2  ($1 == "site")
"me@site.com".match?(/@/)            # true, sets no globals
"a1 b22".scan(/\d+/)                 # ["1", "22"]
"a1 b22".gsub(/\d+/) { |d| d.to_i * 2 }  # "a2 b44"
/(?<user>\w+)@/ =~ "me@x.io"; user   # "me" (named → local var)
"ok\nbad" =~ /\A\w+\z/               # nil (/^\w+$/ would match)

Rust — regex crate

let re = Regex::new(r"(?<user>\w+)@(\w+)").unwrap();
re.is_match("me@site")                       // true
&re.captures("me@site").unwrap()["user"]     // "me"
re.find_iter("a@b c@d").map(|m| m.as_str())  // "a@b", "c@d"
re.replace_all("me@site", "$2:$user")        // "site:me"
Regex::new(r"(?<=a)b").is_err()              // true

PHP — PCRE (preg_*)

preg_match('/(\w+)@(\w+)/', 'me@site', $m);   // 1; $m[2]: 'site'
preg_match_all('/\d+/', 'a1 b22', $m);        // 2; $m[0]: ['1','22']
preg_replace('/(\w+)@/', '$1 at ', 'me@site') // 'me at site'
preg_replace_callback('/\d+/', fn($m) => $m[0]*2, 'a1')  // 'a2'
preg_split('/\s*,\s*/', 'a, b ,c')            // ['a','b','c']
preg_match('/^\p{Lu}/u', 'Élan')              // 1  (u = UTF-8)

C++ — <regex>

std::regex re(R"((\w+)@(\w+))");      // raw string R"(...)"
std::smatch m;
std::regex_search(s, m, re);          // true; m[2] == "site"
std::regex_match(s, re);              // whole string
std::regex_replace(s, re, "$2:$1");   // "site:me"

C — POSIX <regex.h>

regex_t re;  regmatch_t m[3];
regcomp(&re, "([a-z]+)@([a-z]+)", REG_EXTENDED);
if (regexec(&re, s, 3, m, 0) == 0)          /* 0 = match */
    printf("%.*s\n", (int)(m[2].rm_eo - m[2].rm_so),
           s + m[2].rm_so);                 /* site */
regfree(&re);              /* ERE: no \d, no lazy */

⚠ Common Mistakes

  • Porting a JS or Python pattern with lookbehind to Go or Rust: it fails to compile
  • Validating with /^…$/ in Ruby; multi-line input slips through
  • Using std::regex in a hot path in C++; it's often 10× slower than RE2, PCRE2 or CTRE

✓ Tips & Best Practices

  • Go: use backticks for patterns and ${1} in replacements
  • C#: [GeneratedRegex] compiles at build time; RegexOptions.NonBacktracking guarantees linear time
  • Ruby: prefer match? for yes/no checks; it skips setting $~

Quick Summary

  • Go / Rust — RE2-style, linear, no lookaround
  • C# / Ruby / PHP / Perl — PCRE-like
  • C++ — ECMAScript grammar, slow
  • C — POSIX ERE via regcomp
