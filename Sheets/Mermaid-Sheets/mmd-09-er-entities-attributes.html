ER — Entities & Attributes

erDiagram · ENTITY { type name } · PK / FK / UK · "comment" · alias · direction

Entities and Their Columns

An erDiagram models data: entities (usually tables) and the relationships between them. Give an entity a block { } of attributes, one per line as type name, optionally followed by keys (PK, FK, UK) and a quoted comment. Mermaid doesn't check types, so write whatever your database uses. Since v12, ER diagrams default to the redux-color theme and neo look.

Rules

  • Entity names: letters, digits, - and _; quote others
  • Types start with a letter; may hold ( ) [ ], e.g. varchar(255)
  • End a type with ? for nullable (v11.16): string? nickname
  • Several keys: separate with commas — PK, FK
  • Comments can't contain double quotes

Shop Schema

erDiagram
  direction LR
  CUSTOMER {
    int id PK
    string email UK "login name"
    string? phone
  }
  ORDER {
    int id PK
    int customer_id FK
    date placed_on
    decimal(10_2) total
  }
  CUSTOMER ||--o{ ORDER : places

Common Type Words

Type Typical use
int / bigint Ids, counts

boolean Flags

⚠ Common Mistakes

  • Writing decimal(10,2). The comma ends the type; use decimal(10_2) or a comment for precision.
  • Using spaces in an entity name (ORDER LINE). Use ORDER-LINE, or an alias: ol["Order Line"].
  • Putting the key before the name (int PK id). The order is always type name keys "comment".

✓ Tips & Best Practices

  • Mirror your real schema names so the diagram doubles as documentation; generate it from migrations if you can.
  • Show only key columns on big diagrams; full column lists make every box huge.
  • Use direction LR for wide schemas so boxes line up as a chain.

Quick Summary

  • erDiagram — entities and relationships
  • ENTITY { type name } — attributes, one per line
  • PK / FK / UK — keys after the name
  • "comment" / type? — notes and nullable types
