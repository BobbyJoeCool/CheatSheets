Information Flow Over Time

An eventmodeling diagram follows the Event Modeling method: a timeline of time frames, each holding one entity — a UI screen, a processor, a command, an event or a read model. Each line is tf <number> <type> <Name>; Mermaid infers the arrow from each frame to the next and puts entities in swimlanes by type. Use rf (reset frame) to break the inferred chain and ->> to link frames explicitly.

Notes

  • Frame numbers must be unique; their order doesn't matter
  • tf / timeframe (compact / relaxed) are interchangeable
  • Namespace.Name puts an entity in its own swimlane
  • Inline data: { description: string } after the name
  • See eventmodeling.org for the method

⚠ Common Mistakes

  • Reusing a frame number. Every tf and rf needs its own number, or the diagram errors.
  • Expecting an arrow into a reset frame. rf deliberately stops the inferred link; add ->> if one is needed.
  • Mixing up commands and events: commands are requests (AddItem), events are facts in past tense (ItemAdded).

✓ Tips & Best Practices

  • Number frames in steps of 10 (10, 20) so you can insert frames later without renumbering.
  • Name events in past tense and commands as imperatives — the diagram then reads as a story.
  • Start with the happy path using tf only, then add rf branches and data.
