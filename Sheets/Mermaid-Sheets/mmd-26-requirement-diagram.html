Tracing Requirements

A requirementDiagram (based on SysML v1.6) shows requirements, the elements that implement or test them, and the relationships between them. A requirement block has a type keyword, a name, and fields: id, text, risk and verifymethod. An element block has a type and a docref. Relationship lines read source - type -> destination. v12 defaults: redux-color, neo, ELK.

Notes

  • Quote text that contains - or keywords: text: "Sign-in…"
  • Quoted text supports markdown: text: "must be fast"
  • Reverse form: dest <- type - source
  • direction LR changes the layout

Login Requirements

requirementDiagram
  requirement login {
    id: 1
    text: Users can sign in.
    risk: high
    verifymethod: test
  }
  performanceRequirement speed {
    id: 1.1
    text: "Sign-in under 2 s"
    risk: medium
    verifymethod: demonstration
  }
  element auth_svc {
    type: service
  }
  login - contains -> speed
  auth_svc - satisfies -> login

Fields

Field Values
id: Any text, e.g. 1.2

risk: low · medium · high
verifymethod: analysis · inspection · test · demonstration
type: Element type (free text)
docref: Element doc reference

Relationships

Type Meaning

⚠ Common Mistakes

  • Using unquoted text that contains a keyword (text: element must load). The parser sees element; quote the text.
  • Writing arrows like flowcharts (a --> b). Requirement relationships are a - satisfies -> b.
  • Inventing risk or verification values. Only the listed values are accepted.

✓ Tips & Best Practices

  • Use the same ids as your requirements tracker so the diagram links back to it.
  • Add element blocks for tests (type: test suite) and connect them with verifies to show coverage.
  • Split big specs into one diagram per feature area.

Quick Summary

  • requirementDiagram — declaration
  • requirement name { id text risk verifymethod } — a requirement
  • element name { type docref } — implementing / testing thing
  • a - satisfies -> b — relationship
