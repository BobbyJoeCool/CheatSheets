Causes of a Problem

An ishikawa-beta diagram (fishbone, cause-and-effect) puts a problem at the head and its causes on bones along the spine. The syntax is pure indentation: the first line after the declaration is the problem, the next indent level holds cause categories, and deeper levels hold causes and sub-causes. It's a structured way to run a root-cause discussion.

Notes

  • First line = the problem (fish head)
  • Indent level 1 = categories (bones)
  • Deeper levels = causes, sub-causes
  • Added in v11.12.3; syntax may change

⚠ Common Mistakes

  • Writing the problem as a cause ("Because of no CDN"). The head should state the effect: "Slow page loads".
  • Mixing indentation widths. A cause can jump to the wrong bone; indent two spaces per level.
  • Listing solutions instead of causes; fixes belong in follow-up actions, not on the bones.

✓ Tips & Best Practices

  • Start from a standard category set (6M or the software list) so the team doesn't miss an area.
  • Ask "why?" again for each cause and add the answer as a sub-cause.
  • Keep each cause to a few words so the bones stay readable.
