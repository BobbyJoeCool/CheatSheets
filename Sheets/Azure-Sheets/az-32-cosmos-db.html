Globally Distributed NoSQL

Azure Cosmos DB stores JSON items in containers spread across physical partitions by a partition key. Every operation costs request units (RUs); you buy throughput as provisioned, autoscale or serverless. Five consistency levels trade latency for freshness, and the change feed streams every write. Multiple APIs exist: NoSQL (native), MongoDB, Cassandra, Gremlin and Table.

Key Points

  • Pick a partition key with high cardinality that appears in most queries
  • A point read of a 1 KB item by id + partition key costs 1 RU
  • Cross-partition queries cost more and scale worse
  • Session consistency is the default and fits most apps

Account, Container, Data Role

az cosmosdb create -g rg-data -n cosmos-shop \
    --default-consistency-level Session \
    --locations regionName=eastus2 failoverPriority=0 isZoneRedundant=True
COSMOS=$(az cosmosdb show -g rg-data -n cosmos-shop --query id -o tsv)
az resource update --ids $COSMOS \
    --set properties.disableLocalAuth=true
az cosmosdb sql database create -g rg-data -a cosmos-shop -n shop
az cosmosdb sql container create -g rg-data -a cosmos-shop -d shop \
    -n orders --partition-key-path /customerId --max-throughput 4000

# Built-in Data Contributor role for the app identity
az cosmosdb sql role assignment create -g rg-data -a cosmos-shop \
    --role-definition-id 00000000-0000-0000-0000-000000000002 \
    --principal-id $MI --scope "/"

Python SDK

from azure.cosmos import CosmosClient
from azure.identity import DefaultAzureCredential
db = CosmosClient("https://cosmos-shop.documents.azure.com",
                  DefaultAzureCredential()).get_database_client("shop")
orders = db.get_container_client("orders")
orders.upsert_item({"id": "o-42", "customerId": "c-7", "total": 59.0})
item = orders.read_item("o-42", partition_key="c-7")       # ~1 RU
for o in orders.query_items("SELECT * FROM o WHERE o.total > @t",
        parameters=[{"name": "@t", "value": 50}], partition_key="c-7"):
    print(o["id"])

Code Explained

Zone redundancy is set per region location
disableLocalAuth turns off account keys
Autoscale scales between 10% and 100% of 4,000 RU/s
Passing partition_key keeps queries to one partition

AWS / GCP Equivalent

  • AWS DynamoDB (partition / sort keys, RCU / WCU) (aws-32)
  • GCP Firestore, Spanner, Bigtable (gcp-32)
  • RUs ≈ DynamoDB capacity units; partition key choice matters the same way

Cost Check

  • Provisioned: per 100 RU/s per hour; autoscale bills the hourly peak
  • Serverless: per million RUs consumed, best for spiky low traffic
  • Storage per GB per region; every extra region multiplies cost

Security Check

  • Disable key-based (local) auth; use Entra data-plane RBAC
  • Private endpoints with public network access off
  • Least-privilege data roles (Reader vs Contributor)

Limits & Quotas

  • Item size up to 2 MB
  • Logical partition up to 20 GB
  • Physical partition up to 10,000 RU/s

Do & Don't

  • Do Model around access patterns and the partition key first
  • Do Use point reads (id + partition key) whenever possible
  • Don’t Choose a low-cardinality partition key like country
  • Don’t Run unbounded cross-partition queries on hot paths

Local Testing

  • The Cosmos DB emulator runs on Windows or as a Linux Docker image
  • Point the SDK at the emulator endpoint with its well-known key
  • Check RU charge per query in the response headers while testing

Production Checklist

  • Local auth disabled; Entra data roles only
  • Zone redundancy and, if needed, multi-region with failover
  • Alerts on 429 throttling and RU consumption
