Sheet 36

You Might Not Need an Effect

derive during render · logic in handlers · reset with key · chained effects · notifying parents · caching with useMemo

Effects Are an Escape Hatch

Effects are for synchronizing with external systems. If no external system is involved, you probably don't need one. Compute derived values during render, handle user actions in event handlers, reset state with a key, and cache expensive calculations with useMemo. Unnecessary effects cause extra renders, flicker and bugs from chained updates.

Notes

  • Rule of thumb: code that runs because the component was shown → effect; because the user did something → handler
  • Setting state in an effect based on other state causes an extra render pass
  • Chains of effects that set state for each other are hard to follow
  • Notifying a parent should happen in the same handler that changed the state

♿ Accessibility

  • Fewer render passes mean less flicker in live regions and focus targets

Version Notes

  • From react.dev's You Might Not Need an Effect; unchanged in React 19
  • The React Compiler makes useMemo mostly automatic (sheet 60)

Code Explained

fullName needs no state at all
useMemo recomputes the filter only when inputs change
A new key remounts Profile, clearing every piece of its state
The POST belongs to the click, not to a submitted flag
Calling onChange in the handler avoids a second render cycle

Effect → No Effect

// ✗ Derived state in an effect
const [fullName, setFullName] = useState('');
useEffect(() => setFullName(`${first} ${last}`), [first, last]);
// ✓ Compute during render
const fullName = `${first} ${last}`;

// ✗ Expensive filter in an effect
useEffect(() => setVisible(filter(todos, tab)), [todos, tab]);
// ✓ Cache it
const visible = useMemo(() => filter(todos, tab), [todos, tab]);

// ✗ Reset on prop change
useEffect(() => setComment(''), [userId]);
// ✓ Reset with a key
<Profile key={userId} userId={userId} />

// ✗ Event logic in an effect
useEffect(() => {
  if (submitted) post('/api/register', data);
}, [submitted]);
// ✓ In the handler
function handleSubmit() { post('/api/register', data); }

// ✗ Notify parent after state changes
useEffect(() => onChange(isOn), [isOn]);
// ✓ Update both in the handler
function toggle() {
  setIsOn(!isOn);
  onChange(!isOn);
}

// ✓ Legit effect: external system
useEffect(() => {
  const unsub = store.subscribe(sync);
  return unsub;
}, []);

⚠ Common Mistakes

  • useEffect + setState to mirror props
  • Effect chains: A sets B, B's effect sets C
  • Triggering POST requests from state flags

✓ Tips & Best Practices

  • Before writing an effect, name the external system it syncs with
  • If you can't, look for a render-time or handler solution
  • Move data fetching to a library or framework loader

Quick Summary

  • Derive in render
  • Act in handlers
  • Reset with key
  • Effects only for external systems
