State Is a Snapshot

Within one render, a state variable is a fixed snapshot: calling the setter doesn't change the variable you're reading, it queues a new value for the next render. React batches every update from the same event into one re-render. When the next value depends on the previous one, pass an updater function (n => n + 1) so each queued update sees the latest value.

Notes

  • Automatic batching covers handlers, timeouts, promises and native events
  • Updater functions run during the next render, in the order they were queued
  • If the new value is Object.is-equal to the old one, React may skip the re-render
  • flushSync forces an update to apply immediately (rarely needed)

♿ Accessibility

  • Use flushSync before moving focus to an element that a state update just rendered, or focus it in an effect

Version Notes

  • React 18 extended automatic batching beyond React event handlers
  • In React 17 and earlier, updates in timeouts and promises were not batched

Code Explained

n is 0 for the whole handler, so three setN(n + 1) calls produce 1
Each updater receives the result of the previous one, producing 3
console.log(n) prints the snapshot, not the queued value
After await, the two setters still batch into one render
flushSync commits the update so the new DOM node exists on the next line

Snapshots and Updaters

function Counter() {
  const [n, setN] = useState(0);

  function addThreeWrong() {
    setN(n + 1);   // 0 + 1
    setN(n + 1);   // 0 + 1
    setN(n + 1);   // 0 + 1  -> 1
  }

  function addThree() {
    setN((prev) => prev + 1);   // 0 -> 1
    setN((prev) => prev + 1);   // 1 -> 2
    setN((prev) => prev + 1);   // 2 -> 3
  }

  function logAfterSet() {
    setN(n + 5);
    console.log(n);    // still the old value
  }

  return <button onClick={addThree}>{n}</button>;
}

// One re-render for both updates (batched)
function Form() {
  const [name, setName] = useState('');
  const [saved, setSaved] = useState(false);
  async function save() {
    await api.save(name);
    setSaved(true);
    setName('');
  }
}

⚠ Common Mistakes

  • Expecting the state variable to change right after calling the setter
  • Using setN(n + 1) in loops or repeated calls
  • Reaching for flushSync to fix logic that should use updaters

✓ Tips & Best Practices

  • Name updater params after the state: setCount(c => c + 1)
  • Compute the next value once, store it in a variable, then use it for both the setter and any logging
  • Read the DOM after updates in an effect, not right after the setter

Quick Summary

  • State = snapshot per render
  • Setters queue, React batches
  • Updater fn for previous-based updates
  • flushSync = rare escape hatch
