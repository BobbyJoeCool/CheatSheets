Sheet 16

Choosing Compute

VMs vs containers vs functions vs PaaS · control vs convenience · cost shape · decision table across the three providers

Matching the Workload to the Service

Every cloud offers a ladder from full control to full convenience: VMs, managed Kubernetes, serverless containers, app platforms and functions. Climb as high as the workload allows: each step up removes servers to patch and scaling to tune, at the cost of limits and some lock-in. Cost shape differs too: VMs bill while running, serverless bills per request.

Key Points

  • Steady 24/7 load is often cheapest on VMs or containers with commitments
  • Spiky or idle-heavy load is cheapest on scale-to-zero services
  • Kubernetes pays off with many services and a team to run it
  • Batch jobs fit spot VMs or job services

One Container, Three Platforms

IMAGE=registry.example.com/shop/api:1.4.0

# Serverless container: the default choice for HTTP services
gcloud run deploy api --image=$IMAGE --region=us-central1 \
    --min-instances=0 --max-instances=20
az containerapp create -n api -g rg-app --environment cae-app \
    --image $IMAGE --min-replicas 0 --max-replicas 20 \
    --ingress external --target-port 8080
aws apprunner create-service --service-name api \
    --source-configuration file://apprunner.json

# Kubernetes: when you already run a cluster
kubectl create deployment api --image=$IMAGE --replicas=3
kubectl expose deployment api --port=80 --target-port=8080

# VM: when you need the OS (agents, GPUs, licensing)
gcloud compute instances create api-vm --zone=us-central1-a \
    --metadata-from-file=startup-script=run-container.sh

Code Explained

The same image runs on every rung of the ladder
Min 0 lets serverless containers scale to zero when idle
App Runner takes its settings from a JSON source configuration
VMs make sense when the workload needs the operating system

Rule of Thumb

  • Default: serverless containers for web services, functions for events
  • Pick Kubernetes for a platform, not for one app
  • Pick VMs for legacy apps, GPUs, special licensing or OS-level agents

Do & Don't

  • Do Containerize even if you start on a PaaS: it keeps options open
  • Do Compare monthly cost at expected load, not list prices
  • Don’t Choose Kubernetes because it is popular
  • Don’t Pick functions for long-running, CPU-heavy work

Local Testing

  • Docker Compose runs the same images as any platform above
  • kind / minikube for Kubernetes; Functions emulators for functions (sheet 15)
  • Load-test locally with k6 to estimate instance counts

Production Checklist

  • Autoscaling limits set on every platform
  • Health checks and graceful shutdown handled (SIGTERM)
  • Choice documented with the expected cost at normal and peak load
