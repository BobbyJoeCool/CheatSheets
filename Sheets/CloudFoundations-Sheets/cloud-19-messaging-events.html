Messaging & Events

Decoupling Services

Messaging lets one service hand work to another without waiting. A queue holds messages for one consumer group to process. A topic fans each message out to many subscribers. An event bus routes events by content to targets. Almost every cloud messaging service delivers at least once, so consumers must be idempotent: processing the same message twice must be safe.

Key Points

  • Messages that keep failing go to a dead-letter queue for inspection
  • Visibility timeout / lock duration: how long a consumer has before redelivery
  • FIFO / sessions / ordering keys give ordering, at lower throughput
  • Events describe what happened; commands ask for work

Send and Receive

# AWS SQS queue
aws sqs create-queue --queue-name orders
aws sqs send-message --queue-url $Q --message-body '{"id": 42}'
aws sqs receive-message --queue-url $Q --wait-time-seconds 20

# Azure Service Bus queue
az servicebus queue create -g rg-msg --namespace-name sb-shop -n orders
# (send / receive go through the SDK; the CLI manages entities)

# Google Cloud Pub/Sub topic + subscription
gcloud pubsub topics create orders
gcloud pubsub subscriptions create orders-worker --topic=orders \
    --ack-deadline=60
gcloud pubsub topics publish orders --message='{"id": 42}'
gcloud pubsub subscriptions pull orders-worker --auto-ack --limit=5

Idempotent Consumer (pseudocode)

def handle(msg):
    if store.seen(msg.id):        # already processed: just ack
        return ack(msg)
    with db.transaction():
        apply_order(msg.body)
        store.mark_seen(msg.id)   # same transaction as the change
    ack(msg)

Code Explained

SQS long polling (--wait-time-seconds 20) cuts empty receives
The Azure CLI creates Service Bus entities; apps send and receive with the SDK
Pub/Sub separates topics (publish) from subscriptions (receive)
Recording the message ID with the change makes retries harmless

Across the Clouds

  • AWS SQS, SNS, EventBridge (aws-23, aws-24)
  • Azure Service Bus, Event Grid, Event Hubs (az-23, az-24)
  • Google Cloud Pub/Sub, Eventarc, Cloud Tasks (gcp-23, gcp-24)

Rule of Thumb

  • Queue for work distribution, topic for fan-out, event bus for routing by content
  • Always configure a dead-letter queue and alert on it
  • Assume duplicates and out-of-order delivery unless you pay for ordering

Do & Don't

  • Do Put a message ID in every message and dedupe on it
  • Do Keep messages small; store large payloads in object storage and send a link
  • Don’t Process a message, crash before acking, and assume it will not come back
  • Don’t Use a queue as a database to query later

Local Testing

  • LocalStack emulates SQS, SNS and EventBridge
  • The Pub/Sub emulator: gcloud beta emulators pubsub start
  • The Service Bus emulator runs in Docker for local development

Production Checklist

  • Dead-letter queues with alerts on depth
  • Alarms on queue age / backlog
  • Consumers idempotent and scaled on queue depth
