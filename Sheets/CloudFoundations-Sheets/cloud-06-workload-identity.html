Sheet 06

Workload Identity & Federation

IAM roles · managed identities · service accounts · short-lived credentials · OIDC federation from CI · why long-lived keys are risky

Credentials for Code, Without Secrets

Applications need identities too. Instead of pasting an access key into config, attach an identity to the compute resource: an IAM role on AWS, a managed identity on Azure, a service account on Google Cloud. The platform hands out short-lived tokens automatically. Outside the cloud (CI pipelines, other clouds) use OIDC federation: the provider trusts tokens from GitHub or another identity provider.

Key Points

  • Tokens expire in about an hour and refresh themselves
  • SDKs find these credentials automatically (default credential chains)
  • Federation means no stored secret in GitHub at all
  • A leaked long-lived key works until someone notices and revokes it

Same Code, No Keys (SDK default chains)

# AWS: boto3 picks up the role from the environment / instance profile
import boto3
s3 = boto3.client("s3")

# Azure: DefaultAzureCredential uses the managed identity in Azure
from azure.identity import DefaultAzureCredential
from azure.storage.blob import BlobServiceClient
blobs = BlobServiceClient("https://demostore.blob.core.windows.net",
                          credential=DefaultAzureCredential())

# Google Cloud: Application Default Credentials use the service account
from google.cloud import storage
gcs = storage.Client()

GitHub Actions OIDC Logins

permissions: { id-token: write, contents: read }
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with: { role-to-assume: "arn:aws:iam::111122223333:role/gh-deploy",
            aws-region: us-east-1 }
  - uses: azure/login@v2
    with: { client-id: ..., tenant-id: ..., subscription-id: ... }
  - uses: google-github-actions/auth@v2
    with: { workload_identity_provider: "projects/123/locations/global/...",
            service_account: "deploy@app-prod.iam.gserviceaccount.com" }

Code Explained

No credentials appear in the code: the default chain finds them
On a laptop the same code uses your CLI login instead
id-token: write lets the GitHub job request an OIDC token
Each cloud trusts that token through a role, app registration or pool

Across the Clouds

  • AWS IAM roles, instance profiles, OIDC providers (aws-07)
  • Azure managed identities, federated credentials (az-07)
  • Google Cloud service accounts, Workload Identity Federation (gcp-07)

Rule of Thumb

  • If you are about to create an access key, look for the identity-based option first
  • One identity per workload, with only the roles that workload needs
  • Federate CI; never store cloud keys as repository secrets

Do & Don't

  • Do Use the SDK default credential chain in all code
  • Do Scope federation trust to one repo and branch / environment
  • Don’t Commit a key file or .env with cloud secrets
  • Don’t Reuse one powerful identity for every service

Local Testing

  • Laptop: aws sso login, az login, gcloud auth application-default login feed the same default chains
  • LocalStack and Azurite accept dummy credentials, so no real keys are needed
  • Use act to dry-run GitHub workflows (OIDC steps need the real runner)

Production Checklist

  • Zero long-lived access keys for workloads (alert on any that appear)
  • Federation trust conditions pinned to repo, branch and environment
  • Key creation blocked by policy where the cloud supports it
