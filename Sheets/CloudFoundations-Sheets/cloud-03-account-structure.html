Sheet 03

Accounts, Projects & Hierarchy

AWS Organizations & accounts · Azure tenants, management groups, subscriptions & resource groups · Google Cloud organization, folders & projects · billing boundaries · blast radius

How Resources Are Grouped

Every cloud has a container that owns resources, bills them and limits who can touch them: an AWS account, an Azure subscription (with resource groups inside) or a Google Cloud project. Above that sits an organization tree for policy and billing. Separate containers per environment and team keep a mistake in dev from reaching production.

Key Points

  • AWS: Organization → OUs → accounts; the account is the security boundary
  • Azure: Entra tenant → management groups → subscriptions → resource groups
  • Google Cloud: organization → folders → projects
  • Policies set high in the tree are inherited below

Creating the Container

# AWS: a new member account in your organization
aws organizations create-account \
    --email dev-team@example.com --account-name "app-dev"
aws organizations list-accounts --query "Accounts[].[Name,Id]" \
    --output table

# Azure: pick the subscription, then make a resource group in it
az account list -o table
az account set --subscription "app-dev"
az group create --name rg-app-dev --location eastus2 \
    --tags owner=team-a env=dev

# Google Cloud: a project under a folder, linked to billing
gcloud projects create app-dev-4821 --folder=123456789012
gcloud billing projects link app-dev-4821 \
    --billing-account=0X0X0X-0X0X0X-0X0X0X
gcloud config set project app-dev-4821

Code Explained

AWS accounts are created from the management account of an Organization
An Azure resource group is a folder for resources with a shared lifecycle
Google Cloud project IDs are global and permanent; pick them carefully
All three need a billing link before resources can be created

Across the Clouds

  • AWS Organizations, OUs, accounts (aws-02)
  • Azure management groups, subscriptions, resource groups (az-01, az-02)
  • Google Cloud organization, folders, projects, billing accounts (gcp-01, gcp-02)

Rule of Thumb

  • One account / subscription / project per environment per app is a good default
  • Delete a whole resource group or project to clean up everything at once
  • Apply guardrail policies at the top of the tree, not resource by resource

Do & Don't

  • Do Keep production in its own account / subscription / project
  • Do Use a naming scheme: app-env-region (rg-shop-prod-eus2)
  • Don’t Run everything in one shared account where any mistake hits all
  • Don’t Use the AWS root user or a Global Administrator for daily work

Local Testing

  • Create a sandbox account / subscription / project you can delete whole
  • Google Cloud: gcloud projects delete cleans up everything in a test project
  • Azure: az group delete -n rg-test --yes --no-wait removes a test environment

Production Checklist

  • Organization-level guardrails (SCPs, Azure Policy, Organization Policy) in place
  • Break-glass admin accounts with MFA, stored offline
  • Billing alerts per account / subscription / project
