Renting Servers by the Second

A virtual machine is a slice of a physical server with your choice of CPU, memory, disk and image. Families target workloads (general purpose, compute, memory, GPU), and Arm families (Graviton, Cobalt, Axion) are usually cheaper per unit of work. Put identical VMs in a scale group (Auto Scaling group, VM Scale Set, managed instance group) to add and remove machines with load.

Key Points

  • Billing is per second (AWS Linux, Google Cloud) or per minute (Azure) while running
  • Stopped VMs still pay for disks and reserved IPs
  • Startup scripts / cloud-init configure a VM on first boot
  • Treat VMs as cattle: rebuild from an image instead of fixing in place

Launch a Small Linux VM

# AWS
P=/aws/service/ami-amazon-linux-latest
aws ec2 run-instances \
    --image-id resolve:ssm:$P/al2023-ami-kernel-default-arm64 \
    --instance-type t4g.small --subnet-id subnet-a \
    --user-data file://init.sh --metadata-options HttpTokens=required

# Azure
az vm create -g rg-app -n vm-web-1 --image Ubuntu2404 \
    --size Standard_B2s --custom-data init.sh \
    --generate-ssh-keys --public-ip-address ""

# Google Cloud
gcloud compute instances create web-1 --zone=us-central1-a \
    --machine-type=e2-small --image-family=debian-12 \
    --image-project=debian-cloud --no-address \
    --metadata-from-file=startup-script=init.sh

Code Explained

Each command picks a small size, an image and a first-boot script
AWS resolves the latest Amazon Linux image from a public SSM parameter
HttpTokens=required enforces IMDSv2 on AWS
Empty public IP / --no-address keeps the VM private

Across the Clouds

  • AWS EC2, AMIs, Auto Scaling groups (aws-15, aws-16, aws-18)
  • Azure VMs, managed disks, VM Scale Sets (az-15, az-16, az-18)
  • Google Cloud Compute Engine, managed instance groups (gcp-15, gcp-16, gcp-18)

Rule of Thumb

  • Choose the smallest size that passes load tests, then scale out
  • Try Arm first for Linux workloads: often 20–40% better price-performance
  • Bake images with Packer for faster, repeatable boots

Do & Don't

  • Do Keep VMs stateless; store data in managed disks, databases or object storage
  • Do Use scale groups even for one instance (self-healing)
  • Don’t SSH in to patch production servers by hand
  • Don’t Leave dev VMs running 24/7

Local Testing

  • Multipass, Vagrant or a local VM runs the same cloud-init script
  • Test startup scripts in a container first (docker run -it ubuntu)
  • Packer builds images locally before pushing to a cloud

Production Checklist

  • Images patched and rebuilt on a schedule
  • Instances spread across zones in a scale group with health checks
  • No public IPs; admin access through Session Manager, Bastion or IAP
