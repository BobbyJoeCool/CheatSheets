Infrastructure in Version Control

Infrastructure as code describes the resources you want in files, reviews changes in pull requests and applies them with a tool. Declarative tools compare the desired state with what exists and make the difference. Terraform (and its open-source fork OpenTofu) works with all three clouds; each provider also has native tools: CloudFormation and CDK, Bicep, and Infrastructure Manager (managed Terraform).

Key Points

  • Plan before apply: review what will be created, changed or destroyed
  • State tracks what the tool manages; keep it remote and locked
  • Drift: someone changed a resource by hand outside the code
  • Modules / constructs package reusable patterns

One Bucket in Terraform per Cloud

resource "aws_s3_bucket" "logs" {
  bucket = "acme-logs-prod"
  tags   = { owner = "platform", env = "prod" }
}

resource "azurerm_storage_account" "logs" {
  name                     = "acmelogsprod"
  resource_group_name      = "rg-logs-prod"
  location                 = "eastus2"
  account_tier             = "Standard"
  account_replication_type = "ZRS"
}

resource "google_storage_bucket" "logs" {
  name                        = "acme-logs-prod"
  location                    = "US-CENTRAL1"
  uniform_bucket_level_access = true
  labels                      = { owner = "platform", env = "prod" }
}

Workflow

terraform init          # download providers, connect remote state
terraform plan -out=tf.plan
terraform apply tf.plan

Code Explained

Each resource block names a type from that cloud's provider
Arguments differ per cloud, but the workflow is identical
plan -out saves exactly what apply will do
Native tools: CloudFormation / CDK, Bicep, Infrastructure Manager

Across the Clouds

  • AWS CloudFormation, CDK, SAM, Terraform (aws-34, aws-35, aws-36)
  • Azure Bicep, Azure Developer CLI, Terraform (az-34, az-35, az-36)
  • Google Cloud Terraform, Infrastructure Manager, Config Connector (gcp-34, gcp-35, gcp-36)

Rule of Thumb

  • Terraform / OpenTofu if you use more than one cloud; native tools are fine for one
  • Every change through a pull request with the plan output attached
  • Never edit managed resources by hand; fix the code instead

Do & Don't

  • Do Keep state in a remote, encrypted, locked backend
  • Do Pin provider versions in required_providers
  • Don’t Commit terraform.tfstate to git (it can contain secrets)
  • Don’t Apply from a laptop to production

Local Testing

  • terraform validate and terraform fmt -check run with no cloud access
  • LocalStack works as an AWS endpoint for Terraform tests
  • terraform test and Terratest test modules; Checkov / Trivy scan for misconfigurations

Production Checklist

  • Apply only from CI with OIDC credentials (sheet 22)
  • Plans reviewed in pull requests; destroy actions highlighted
  • Drift detection on a schedule
