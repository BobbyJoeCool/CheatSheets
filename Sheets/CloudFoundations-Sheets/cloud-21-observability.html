Knowing What Your System Is Doing

Observability rests on three signals: metrics (numbers over time), logs (event records) and traces (one request's path through services). Each cloud collects platform metrics and logs automatically; your app adds its own through OpenTelemetry, the vendor-neutral standard that every provider now accepts. Alerts on user-facing symptoms and SLOs turn data into action.

Key Points

  • Platform metrics come free; custom metrics and log ingestion are billed
  • Structured (JSON) logs are far easier to query
  • Trace IDs in logs link a log line to its request
  • Alert on symptoms (errors, latency) before causes (CPU)

Query Recent Errors

# AWS CloudWatch Logs Insights
aws logs start-query --log-group-name /app/api \
    --start-time $(date -d '-1 hour' +%s) --end-time $(date +%s) \
    --query-string 'fields @timestamp, @message
      | filter level = "error" | sort @timestamp desc | limit 20'

# Azure Log Analytics (KQL)
az monitor log-analytics query -w <workspace-id> --analytics-query \
  "AppTraces | where SeverityLevel >= 3 | top 20 by TimeGenerated"

# Google Cloud Logging
gcloud logging read 'resource.type="cloud_run_revision" AND
  severity>=ERROR' --freshness=1h --limit=20

OpenTelemetry in Python (any cloud)

from opentelemetry import trace
tracer = trace.get_tracer("checkout")

def checkout(cart):
    with tracer.start_as_current_span("checkout") as span:
        span.set_attribute("cart.items", len(cart))
        return charge(cart)

Code Explained

Each provider has its own query language: Logs Insights, KQL, Logging query language
All three accept OpenTelemetry traces and metrics through exporters or collectors
Span attributes become searchable fields
The same instrumented code works on every cloud

Across the Clouds

  • AWS CloudWatch metrics, logs, X-Ray / ADOT (aws-37, aws-38)
  • Azure Azure Monitor, Log Analytics, Application Insights (az-37, az-38)
  • Google Cloud Cloud Monitoring, Cloud Logging, Cloud Trace (gcp-37, gcp-38)

Rule of Thumb

  • Instrument with OpenTelemetry, not a vendor SDK, to stay portable
  • Set log retention on day one: default retention can be forever and costly
  • Every alert should have a runbook link

Do & Don't

  • Do Log in JSON with a request / trace ID on every line
  • Do Define SLOs for the few user journeys that matter
  • Don’t Log full request bodies with personal data or secrets
  • Don’t Page someone for a CPU spike that users never noticed

Local Testing

  • Run an OpenTelemetry Collector plus Jaeger or Grafana LGTM in Docker
  • docker run -p 4317:4317 otel/opentelemetry-collector receives local traces
  • Use the console exporter during development to print spans

Production Checklist

  • Alerts on error rate and latency with runbooks
  • Log retention and sampling set to control cost
  • Dashboards for each service's golden signals
