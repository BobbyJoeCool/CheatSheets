Sheet 02

Regions, Zones & the Edge

regions · availability zones · edge / points of presence · latency & data residency · zonal vs regional vs global resources · choosing a region

Where Your Resources Live

Each provider splits the world into regions (a metro area such as Northern Virginia or Iowa), and each region into availability zones: separate data centers with their own power and cooling, close enough for fast links. Spreading an app across zones survives a data-center failure; spreading across regions survives a regional outage. Edge locations cache content and terminate connections close to users.

Key Points

  • Region names differ: us-east-1 (AWS), eastus2 (Azure), us-central1 (Google Cloud)
  • Zones: us-east-1a, Azure zones 1/2/3, us-central1-a
  • Not every service or instance type exists in every region
  • Data moving between regions is billed; within a zone it is usually free

Listing Regions and Zones

# AWS: regions enabled for the account, then zones in one region
aws ec2 describe-regions --query "Regions[].RegionName" --output text
aws ec2 describe-availability-zones --region us-east-1 \
    --query "AvailabilityZones[].ZoneName"

# Azure: locations (regions) and which have availability zones
az account list-locations --query "[].name" -o tsv
az vm list-skus -l eastus2 --zone --size Standard_D2s_v5 -o table

# Google Cloud: regions and the zones inside one
gcloud compute regions list --format="value(name)"
gcloud compute zones list --filter="region:us-central1"

# Set a default so you stop typing it
aws configure set region us-east-1
az config set defaults.location=eastus2
gcloud config set compute/region us-central1

Code Explained

--query (AWS, Azure) and --format / --filter (gcloud) trim output
Azure lists zone support per VM size, because zones vary by size
Defaults keep commands short; scripts should still pass the region explicitly
Each provider has 30+ regions; pick close to users and data rules

Across the Clouds

  • AWS regions, AZs, Local Zones, edge locations (aws-01)
  • Azure regions, availability zones, region pairs (az-01)
  • Google Cloud regions, zones, global network tiers (gcp-01)

Rule of Thumb

  • Pick the region closest to most users that offers every service you need
  • Run production across at least two zones
  • Go multi-region only when the business needs it: it doubles cost and complexity

Choosing a Region

FactorQuestion
LatencyWhere are the users?
Data residencyMust data stay in a country?

PricePrices vary by region (10–30%)
CarbonSome regions run on cleaner energy

Do & Don't

  • Do Put the region in resource names or tags so you can find strays
  • Do Check service availability per region before designing
  • Don’t Assume zone a in your account is the same building as zone a in another (AWS maps names per account)
  • Don’t Send traffic between regions without budgeting for it

Local Testing

  • Region and zone choices cannot be emulated; test failover in a cheap dev deployment
  • Use the providers' latency test pages to compare regions from your location
  • Chaos tools (AWS Fault Injection Service, Azure Chaos Studio) simulate zone loss

Production Checklist

  • Spread instances and databases across 2–3 zones
  • Document the backup region and how to fail over to it
  • Keep data in regions allowed by your compliance rules
