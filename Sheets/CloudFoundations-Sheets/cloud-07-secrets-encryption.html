Sheet 07

Secrets & Encryption

secret stores · key management services · envelope encryption · encryption at rest vs in transit · customer-managed keys · rotation

Protecting Passwords, Keys and Data

Store passwords, API tokens and connection strings in a secret store (AWS Secrets Manager, Azure Key Vault, Google Secret Manager) and read them at runtime with the workload's identity. Encryption keys live in a key management service (AWS KMS, Key Vault keys, Cloud KMS), which never reveals the master key. Data is encrypted at rest by default on all three; you choose who manages the key.

Key Points

  • Secrets are versioned: rotate by adding a new version
  • Envelope encryption: a data key encrypts the data, the master key encrypts the data key
  • Provider-managed keys are the default; customer-managed keys (CMK / CMEK) add control and audit
  • TLS protects data in transit; enforce HTTPS-only on storage and APIs

Store and Read a Secret

# AWS Secrets Manager
aws secretsmanager create-secret --name prod/db-password \
    --secret-string 'S3cure!pass'
aws secretsmanager get-secret-value --secret-id prod/db-password \
    --query SecretString --output text

# Azure Key Vault
az keyvault secret set --vault-name kv-shop-prod \
    --name db-password --value 'S3cure!pass'
az keyvault secret show --vault-name kv-shop-prod \
    --name db-password --query value -o tsv

# Google Secret Manager
printf 'S3cure!pass' | gcloud secrets create db-password --data-file=-
gcloud secrets versions access latest --secret=db-password

# Encrypt a small value with each KMS
aws kms encrypt --key-id alias/app --plaintext fileb://token.txt
az keyvault key encrypt --vault-name kv-shop-prod -n app-key \
    --algorithm RSA-OAEP-256 --value <base64>
gcloud kms encrypt --key=app --keyring=main --location=global \
    --plaintext-file=token.txt --ciphertext-file=token.enc

Code Explained

All three keep secret history as versions
Reading a secret is an authorized, logged API call
Shell history can capture secrets; real scripts read from files or stdin
KMS encrypt calls are for small payloads (keys, tokens), not files

Across the Clouds

  • AWS Secrets Manager, Parameter Store, KMS (aws-08)
  • Azure Key Vault secrets, keys and certificates (az-08)
  • Google Cloud Secret Manager, Cloud KMS (gcp-08)

Rule of Thumb

  • Secrets in a secret store, read at startup or through platform references
  • Default encryption is fine for most data; use customer-managed keys when compliance asks
  • Automate rotation for database passwords

Do & Don't

  • Do Inject secrets at runtime through platform integrations
  • Do Turn on soft delete / deletion protection for vaults and keys
  • Don’t Put secrets in environment variables baked into images or IaC files
  • Don’t Log request bodies that may contain tokens

Local Testing

  • Use a local .env that is gitignored, loaded only on your machine
  • LocalStack emulates Secrets Manager and KMS; Azurite does not cover Key Vault (use a dev vault)
  • Scan commits with gitleaks or GitHub secret scanning before pushing

Production Checklist

  • Secrets read by managed identity, never stored in code or pipelines
  • Rotation scheduled and tested
  • Deletion protection on vaults, keys and secrets
