Identity & Access Concepts

principals (users, groups, workloads) · roles & permissions · policies & scopes · least privilege · MFA · human vs machine identity

Who Can Do What, Where

Every request to a cloud API is made by a principal (a person, group or workload) and checked against policies that grant permissions on a scope (an account, subscription, project or single resource). AWS writes policies as JSON documents attached to identities or resources; Azure assigns roles at a scope with RBAC; Google Cloud binds roles to principals in allow policies.

Key Points

  • Deny by default: nothing is allowed until a policy grants it
  • An explicit deny beats any allow (AWS, Azure deny assignments, Google deny policies)
  • Grant roles to groups, not individual users
  • Humans sign in with SSO + MFA; workloads use roles or managed identities (sheet 06)

Granting Read Access on Each Cloud

# AWS: attach a managed read-only policy to a role
aws iam attach-role-policy --role-name analytics-reader \
    --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess

# Azure: assign a built-in role to a group at resource-group scope
az role assignment create --assignee-object-id <group-object-id> \
    --assignee-principal-type Group \
    --role "Storage Blob Data Reader" \
    --scope /subscriptions/<sub-id>/resourceGroups/rg-data

# Google Cloud: bind a predefined role to a group on a project
gcloud projects add-iam-policy-binding app-prod-4821 \
    --member="group:analysts@example.com" \
    --role="roles/storage.objectViewer"

An AWS Policy Document

{ "Version": "2012-10-17",
  "Statement": [{ "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": ["arn:aws:s3:::reports", "arn:aws:s3:::reports/*"] }] }

Code Explained

All three express "this principal may read storage on this scope"
Azure scope is a resource ID path; narrower scope = less access
Google Cloud role names read like roles/service.permissionLevel
The JSON shows AWS's Effect / Action / Resource structure

Across the Clouds

  • AWS IAM users, roles, policies (aws-05, aws-06)
  • Azure Entra ID + Azure RBAC role assignments (az-05, az-06)
  • Google Cloud IAM principals, roles, allow policies (gcp-05, gcp-06)

Rule of Thumb

  • Start with built-in / predefined roles; write custom ones only for gaps
  • Grant at the narrowest scope that works
  • Review who has Owner / Administrator monthly

Do & Don't

  • Do Use SSO with MFA for every human
  • Do Grant to groups and review group membership
  • Don’t Hand out Owner / Administrator to unblock someone quickly
  • Don’t Share one login among a team

Local Testing

  • AWS IAM Policy Simulator tests a policy before you attach it
  • Azure: az role assignment list --assignee <id> --all shows what someone can do
  • Google Cloud Policy Troubleshooter explains why access was allowed or denied

Production Checklist

  • MFA enforced for every human identity
  • No standing admin access; use just-in-time elevation (PIM, temporary roles)
  • Access reviews on a schedule
