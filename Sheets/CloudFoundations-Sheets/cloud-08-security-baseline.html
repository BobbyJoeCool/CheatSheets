Sheet 08

Security Baseline & Guardrails

audit logging · org-level policies · public-access blocks · threat detection services · tagging & ownership · the first-day checklist

The Settings to Turn On First

A few controls prevent most cloud incidents: audit logs of every API call, organization policies that forbid risky configurations, public-access blocks on storage, threat detection that flags odd behavior, and tags so every resource has an owner. All three providers offer each piece; turning them on is cheap compared with cleaning up a breach.

Key Points

  • Audit logs: CloudTrail, Azure Activity Log, Cloud Audit Logs
  • Guardrails: Service Control Policies, Azure Policy, Organization Policy constraints
  • Posture and threats: Security Hub + GuardDuty, Defender for Cloud, Security Command Center
  • Most breaches start with an exposed key or a public bucket

Turning On Guardrails

# AWS: block public S3 access for the whole account
aws s3control put-public-access-block --account-id 111122223333 \
    --public-access-block-configuration \
    BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,\
RestrictPublicBuckets=true
aws guardduty create-detector --enable

# Azure: assign a built-in policy that denies public blob access
DEF=$(az policy definition list --query \
  "[?displayName=='Storage account public access should be disallowed'].name" \
  -o tsv)
az policy assignment create --name deny-public-blob --policy $DEF \
    --scope /subscriptions/<sub-id>

# Google Cloud: enforce public access prevention org-wide
gcloud resource-manager org-policies enable-enforce \
    storage.publicAccessPrevention --organization=123456789012
gcloud resource-manager org-policies enable-enforce \
    iam.disableServiceAccountKeyCreation --organization=123456789012

Code Explained

The AWS account-level block overrides any bucket that tries to go public
Azure looks up the built-in policy by display name, then assigns it
Google org policies apply to every project under the organization
Blocking service account key creation forces identity-based access

Across the Clouds

  • AWS CloudTrail, GuardDuty, Security Hub, Config, SCPs (aws-09)
  • Azure Activity Log, Defender for Cloud, Azure Policy (az-09)
  • Google Cloud Cloud Audit Logs, Security Command Center, Organization Policy (gcp-06, gcp-09)

Rule of Thumb

  • Turn guardrails on before teams start building, not after
  • Prefer deny policies at the organization over review checklists
  • Every resource needs an owner tag; untagged resources get questions

Do & Don't

  • Do Send audit logs to a separate, locked-down account or project
  • Do Review the security posture score weekly
  • Don’t Disable a guardrail to make a deploy pass and forget to turn it back on
  • Don’t Ignore findings until an audit forces you to look

Local Testing

  • Scan IaC before deploy with Checkov, tfsec / Trivy or KICS
  • Prowler (AWS, Azure, Google Cloud) audits a live account against benchmarks
  • Use a sandbox to test that a policy blocks what you expect

Production Checklist

  • CIS benchmark checks enabled in the posture tool
  • Audit logs retained per compliance rules and immutable
  • Alerts for root / Global Administrator sign-ins and policy changes
