Databases Without the Database Server

Managed databases handle patching, backups, replication and failover so you only manage schemas, queries and access. Relational services run PostgreSQL, MySQL or SQL Server. NoSQL services trade joins for massive scale and predictable latency. Caches (Redis-compatible) cut read load. You still choose sizes, high availability, backups and network access.

Key Points

  • High availability = a standby in another zone with automatic failover
  • Read replicas scale reads; writes still go to the primary
  • Point-in-time restore rewinds to any second within the retention window
  • See the SQL and NoSQL sets for query languages and data modeling

A Small PostgreSQL Database

# AWS RDS
aws rds create-db-instance --db-instance-identifier shop-db \
    --engine postgres --db-instance-class db.t4g.micro \
    --allocated-storage 20 --master-username app \
    --manage-master-user-password --multi-az --no-publicly-accessible

# Azure Database for PostgreSQL Flexible Server
az postgres flexible-server create -g rg-data -n shop-db \
    --tier GeneralPurpose --sku-name Standard_D2ds_v5 --storage-size 32 \
    --high-availability ZoneRedundant --public-access None

# Google Cloud SQL
gcloud sql instances create shop-db --database-version=POSTGRES_17 \
    --edition=ENTERPRISE --tier=db-custom-1-3840 --region=us-central1 \
    --availability-type=REGIONAL --no-assign-ip --network=vpc-app

Code Explained

Each command creates PostgreSQL with high availability across zones
--manage-master-user-password keeps the password in Secrets Manager
Public access is off in all three; reach them from the private network
HA roughly doubles the instance cost

Across the Clouds

  • AWS RDS / Aurora, DynamoDB, ElastiCache (aws-31, aws-32, aws-33)
  • Azure Azure SQL, PostgreSQL Flexible Server, Cosmos DB, Managed Redis (az-31, az-32, az-33)
  • Google Cloud Cloud SQL / AlloyDB, Firestore / Spanner, Memorystore (gcp-31, gcp-32, gcp-33)

Rule of Thumb

  • Default to managed PostgreSQL unless you have a reason not to
  • Pick NoSQL for known access patterns at very large scale, not to avoid schemas
  • Test restores, not just backups

Do & Don't

  • Do Keep databases on private networking only
  • Do Use IAM / Entra authentication where supported
  • Don’t Run the database on a VM to save money without counting your time
  • Don’t Leave backups at the default retention without checking compliance

Local Testing

  • Run the same engine in Docker: docker run -e POSTGRES_PASSWORD=pw postgres:17
  • DynamoDB Local, the Cosmos DB emulator and the Firestore emulator for NoSQL
  • Testcontainers starts real databases inside integration tests

Production Checklist

  • Multi-zone high availability and automated backups with point-in-time restore
  • Deletion protection on
  • Connection pooling (RDS Proxy, PgBouncer) and slow-query monitoring
