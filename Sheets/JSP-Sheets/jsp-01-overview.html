JSP Overview & Request Lifecycle

_jspService · translation phase · servlet container · JSP vs Servlet · first-request latency

What JSP Is

A JavaServer Page is a text file (.jsp) that mixes static HTML/XML template text with JSP syntax — directives, scripting elements, and action tags. The servlet container translates it into a Java servlet class, compiles that class, and then executes it on every request. You write the template; the container writes the servlet.

Key Facts

  • File extension is .jsp; fragment includes use .jspf
  • Translation happens once per change — subsequent requests hit compiled bytecode
  • JSP 3.1 is part of Jakarta EE 10; package prefix changed from javax.* to jakarta.*
  • JSP's job is the view — generating response output, not business logic
  • Every JSP compiles to a class that extends HttpJspBase, which extends HttpServlet

Lifecycle — What the Container Does

// ── PHASE 1: Translation (once, on first request or redeploy)
//   Container reads hello.jsp
//   → generates hello_jsp.java (a servlet class)

// ── PHASE 2: Compilation (once)
//   hello_jsp.java → hello_jsp.class

// ── PHASE 3: Initialization (once per class load)
void jspInit() { /* override in <%! %> declaration */ }

// ── PHASE 4: Request handling (every request)
void _jspService(HttpServletRequest  request,
                 HttpServletResponse response)
    throws ServletException, IOException {
    // Your JSP template becomes code here.
    // You CANNOT override _jspService directly.
}

// ── PHASE 5: Destruction (on undeploy / shutdown)
void jspDestroy() { /* override in <%! %> declaration */ }

Lifecycle Notes

Translation — only reruns when the .jsp file changes (or server restarts)
Compilation — produces a .class in the container's work directory
jspInit() — declare in <%! %>; called once after class load
_jspService() — called per request; template output goes here; cannot be overridden
jspDestroy() — declare in <%! %>; clean up resources here
First request is slow (translate + compile); all subsequent requests are fast

⚠ Common Mistakes

  • Putting business logic in JSP — the container translates it into servlet code, but it still belongs in the servlet or service layer
  • Expecting jspInit() / jspDestroy() to work without declaring them in <%! %> — they must be declarations, not scriptlets
  • Trying to override _jspService() — this is generated by the container; any attempt is silently ignored or causes a compile error
  • Mixing javax.servlet and jakarta.servlet imports — pick one based on your Jakarta EE version and stick to it

✓ Tips

  • Pre-compile JSPs at build time with the Maven tomcat7-maven-plugin or jetty-jspc-maven-plugin to catch errors before deployment
  • The container's work directory (e.g. Tomcat/work/) holds the generated .java files — read them when debugging unexpected output
  • Use <%@ page trimDirectiveWhitespaces="true" %> to strip whitespace-only lines introduced by directives from the response
  • Tag the JSP version explicitly: <%@ page language="java" %> is the only valid language value — makes intent clear

Quick Summary

  • .jsp — text file translated into a servlet by the container
  • translation + compile — happens once; requests hit bytecode after
  • _jspService() — generated method that handles every request; not overridable
  • jspInit() / jspDestroy() — lifecycle hooks; declare in <%! %>
  • JSP = view — servlet handles logic, JSP renders output
