Project Structure & Deployment

WAR layout · WEB-INF · URL mapping · webapps dir · precompilation · hot reload

WAR Structure

A JSP web application is packaged as a WAR (Web Application Archive). The WAR has a mandatory layout: anything under WEB-INF/ is never directly accessible by the browser — only the server can read those files. JSPs placed at the webapp root or in subdirectories outside WEB-INF/ are URL-accessible. JSPs inside WEB-INF/jsp/ can only be reached via a RequestDispatcher forward from a servlet.

Key Facts

  • WEB-INF/ contents are never served directly — protected by the container
  • Best practice: store all JSPs under WEB-INF/jsp/ and dispatch to them from servlets
  • Tomcat's work directory holds generated .java and .class files — inspect when debugging
  • Dropping a WAR into tomcat/webapps/ auto-deploys it; the context path equals the WAR filename
  • ROOT.war deploys to the root context /

Standard WAR Layout

myapp.war
├── index.jsp                  # URL: /myapp/
├── css/
│   └── style.css
├── js/
│   └── app.js
└── WEB-INF/
    ├── web.xml                # Deployment descriptor
    ├── classes/               # Compiled .class files
    │   └── com/example/
    │       └── MyServlet.class
    ├── lib/                   # JAR dependencies (JSTL, etc.)
    │   ├── jakarta.servlet.jsp.jstl-3.0.1.jar
    │   └── jakarta.servlet.jsp.jstl-api-3.0.0.jar
    └── jsp/                   # Protected JSPs (recommended)
        ├── home.jsp
        ├── login.jsp
        └── error.jsp

# Maven project source layout mirrors this:
src/main/webapp/               # = WAR root
src/main/webapp/WEB-INF/
src/main/webapp/WEB-INF/web.xml

Layout Notes

WEB-INF/web.xml — deployment descriptor; servlet mappings, error pages, session config
WEB-INF/classes/ — servlet and bean .class files; added to container classpath automatically
WEB-INF/lib/ — JAR files; scanned for TLD files; on classpath automatically
WEB-INF/jsp/ — convention, not required; keeps JSPs browser-inaccessible
index.jsp at root — served as welcome file if listed in web.xml

⚠ Common Mistakes

  • Placing JSPs at the WAR root when they should be protected — a user can request /myapp/checkout.jsp directly and bypass the servlet controller
  • Adding jakarta.servlet.jsp-api as compile scope — the container provides it; use provided or the JAR conflicts at runtime
  • Forgetting to include JSTL JARs in WEB-INF/lib/ — the container doesn't bundle JSTL; a missing taglib URI causes a translation error
  • Editing files inside the expanded WAR in webapps/ — changes are lost on next redeploy; always edit source and rebuild

✓ Tips

  • Always store view JSPs under WEB-INF/jsp/ — forces every request through a servlet, preventing direct URL access to templates
  • Use the Tomcat Manager app (/manager/html) to redeploy individual WARs without restarting the server
  • Inspect the generated servlet in work/Catalina/localhost/<app>/org/apache/jsp/ when tracking down output or compilation bugs
  • Set <reloadable>true</reloadable> in context.xml during development for automatic class reload — disable in production

Quick Summary

  • WEB-INF/ — container-protected; never browser-accessible
  • WEB-INF/lib/ — JARs auto-added to classpath; put JSTL here
  • WEB-INF/jsp/ — recommended home for all view JSPs
  • ROOT.war — deploys to root context /
  • work/ dir — holds generated .java; inspect when debugging
