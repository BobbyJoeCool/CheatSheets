Servlet-to-JSP Data Flow

RequestDispatcher · forward · setAttribute · MVC pattern · @WebServlet · Post/Redirect/Get

The MVC Pattern with Servlets & JSP

In the standard JSP/Servlet MVC pattern, the servlet is the controller: it receives requests, invokes service/DAO classes, and places results into request (or session) attributes. It then forward()s to a JSP view, which reads the attributes via EL and renders HTML. The JSP never talks to services or databases. This clean separation makes the application testable and maintainable.

Key Facts

  • RequestDispatcher.forward() — same request/response; attributes survive; URL in browser does not change
  • response.sendRedirect() — new request; attributes lost; URL changes; use for Post/Redirect/Get
  • Put all data the JSP needs into request.setAttribute() before forwarding
  • Post/Redirect/Get (PRG): on successful POST, redirect to a GET — prevents double-submission on refresh
  • @WebServlet("/path") annotation replaces <servlet> / <servlet-mapping> in web.xml

Servlet Controller + JSP View Pattern

// ── Servlet controller ────────────────────────────────────
@WebServlet("/products")
public class ProductServlet extends HttpServlet {

    @Override
    protected void doGet(HttpServletRequest req,
                         HttpServletResponse res)
            throws ServletException, IOException {

        // 1. Parse / validate input
        String cat = req.getParameter("category");

        // 2. Call service layer
        List<Product> products = productService.findByCategory(cat);

        // 3. Place data into request scope
        req.setAttribute("products", products);
        req.setAttribute("category", cat);
        req.setAttribute("pageTitle", cat + " Products");

        // 4. Forward to JSP view
        req.getRequestDispatcher("/WEB-INF/jsp/products.jsp")
           .forward(req, res);
    }

    @Override
    protected void doPost(HttpServletRequest req,
                          HttpServletResponse res)
            throws ServletException, IOException {
        // Process POST (form submit)
        productService.save(buildFromRequest(req));

        // Post/Redirect/Get — prevent double-submit
        res.sendRedirect(req.getContextPath() + "/products");
    }
}
<%-- ── JSP view: /WEB-INF/jsp/products.jsp ──────────────── --%>
<%@ taglib prefix="c"   uri="jakarta.tags.core"      %>
<%@ taglib prefix="fn"  uri="jakarta.tags.functions" %>
<%@ page pageEncoding="UTF-8" %>
<!doctype html>
<html><head><title>${pageTitle}</title></head>
<body>
<h1>${fn:escapeXml(category)} Products</h1>
<p>${fn:length(products)} items found</p>
<ul>
<c:forEach items="${products}" var="p">
  <li><c:out value="${p.name}"/> — ${p.price}</li>
</c:forEach>
</ul>
</body></html>

Pattern Notes

req.setAttribute("key", val) — store any Java object; JSP reads via EL ${key}
getRequestDispatcher("/WEB-INF/jsp/x.jsp").forward(req,res) — delegate to JSP; URL stays the same
Forward vs redirect — forward shares request attributes; redirect loses them (use session for flash messages)
PRG — POST saves data, redirect to GET page; refresh re-issues safe GET, not the POST
@WebServlet("/path") — annotation-based URL mapping; no web.xml entry needed
JSP view responsibility — only EL reads, JSTL tags, zero business logic

⚠ Common Mistakes

  • Forwarding after a POST without a redirect — user hitting refresh re-submits the POST form, duplicating the action (duplicate order, duplicate record)
  • Calling forward() after any output has been written to the response — once the buffer is flushed, forward throws IllegalStateException
  • Accessing the database or calling services from inside the JSP using scriptlets — puts business logic in the view, making it untestable and hard to maintain

✓ Tips

  • Always forward to JSPs under WEB-INF/jsp/ — they cannot be requested directly; every access goes through the servlet controller
  • For flash messages after a PRG redirect, store the message in session, read and remove it in the next GET request — prevents the message showing again on refresh
  • Use a Front Controller servlet (or a framework like Spring MVC) to centralize routing rather than one servlet per URL — reduces duplication of auth checks and error handling

Quick Summary

  • Servlet = controller: call services, setAttribute(), then forward()
  • JSP = view: read ${attrs}, render HTML, zero business logic
  • forward() — same request; attrs survive; URL unchanged
  • sendRedirect() — new request; use after POST (PRG pattern)
  • Store JSPs in WEB-INF/jsp/ — controller-only access
