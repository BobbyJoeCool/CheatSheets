Health Probes & Pod Lifecycle

livenessProbe · readinessProbe · startupProbe · httpGet / tcpSocket / exec / grpc · preStop · terminationGracePeriodSeconds

Telling Kubernetes What Healthy Means

The kubelet runs probes against each container. A failing readiness probe removes the pod from Service endpoints (no traffic) without restarting it. A failing liveness probe restarts the container. A startup probe holds off the other two until a slow app has booted. On shutdown, pods get SIGTERM, a grace period, then SIGKILL.

Notes

  • No probes: the pod is Ready as soon as the process starts
  • Liveness should check the process only, never databases or other services
  • Readiness can (carefully) check dependencies the pod truly needs
  • Probe traffic comes from the kubelet on the node, not from the Service

Probes & Shutdown

spec:
  terminationGracePeriodSeconds: 30  # SIGTERM → wait → SIGKILL
  containers:
    - name: api
      image: ghcr.io/acme/api:1.4.2
      ports: [{ name: http, containerPort: 8080 }]
      startupProbe:                  # protects slow starters
        httpGet: { path: /healthz, port: http }
        periodSeconds: 5
        failureThreshold: 30         # up to 150s to boot
      livenessProbe:                 # fail → restart container
        httpGet: { path: /healthz, port: http }
        periodSeconds: 10
        timeoutSeconds: 2
      readinessProbe:                # fail → no Service traffic
        httpGet: { path: /ready, port: http }
        periodSeconds: 5
      lifecycle:
        preStop: { exec: { command: ["sleep", "5"] } }   # let LBs drain

Code Explained

startupProbe — liveness/readiness start only after it passes
failureThreshold × periodSeconds — time before giving up
port: http — named container port
timeoutSeconds — default is just 1s
preStop — runs before SIGTERM; counts against the grace period
sleep 5 — endpoints update before the app stops accepting

⚠ Common Mistakes

  • Liveness probe that checks the database — a DB blip restarts every pod
  • Same endpoint and timing for liveness and readiness — restarts when you only wanted to shed load
  • Liveness with no startup probe on a slow app — restart loop before it ever boots

✓ Tips & Best Practices

  • Liveness: cheap "is the process alive"; readiness: "can I serve now"
  • Raise timeoutSeconds to 2–5s for real-world endpoints
  • Use exec-form ENTRYPOINT so your app is PID 1 and gets SIGTERM

Quick Summary

  • readiness — gates traffic
  • liveness — restarts the container
  • startup — delays the others for slow boots
  • preStop + grace period — clean shutdown
