Sheet 08

Deployments & Rollouts

ReplicaSet · replicas · RollingUpdate · maxSurge / maxUnavailable · Recreate · rollout undo · scale

Stateless Apps, Updated Safely

A Deployment owns ReplicaSets, which keep N identical Pods running. Changing the pod template creates a new ReplicaSet and rolls pods over gradually; the old one is kept at 0 replicas so you can undo. Changing only replicas scales without a rollout.

Notes

  • Pod names: web-<template-hash>-<id>
  • Rollouts advance only as new pods turn Ready
  • Stuck after progressDeadlineSeconds (600) = failed, not rolled back
  • Need stable names or per-pod disks? Use a StatefulSet (Sheet 09)

Deployment

apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 3
  revisionHistoryLimit: 5        # old ReplicaSets kept for undo
  selector:
    matchLabels: { app: web }    # = template labels; immutable
  strategy:
    type: RollingUpdate          # or Recreate
    rollingUpdate:
      maxSurge: 25%              # extra pods during update
      maxUnavailable: 0          # never below 3 ready
  template:
    metadata: { labels: { app: web } }
    spec:
      containers: [{ name: web, image: nginx:1.27 }]

Code Explained

replicas — leave out if an HPA scales it
revisionHistoryLimit — default 10
maxUnavailable: 0 — zero downtime, needs spare room
template — any change triggers a rollout
selector — must match template labels exactly
maxSurge: 25% — of 3 replicas rounds up to 1 extra pod

Rollout Commands (kubectl rollout …)

CommandDoes
status deploy/webWait; non-zero exit on failure
history deploy/webList revisions
undo deploy/webPrevious revision
undo deploy/web --to-revision=2Specific revision
restart deploy/webNew pods, same spec
pause / resume deploy/webBatch edits into one rollout

Strategies

TypeBehavior
RollingUpdateGradual; versions overlap

Scale & Update

kubectl …Does
scale deploy/web --replicas=5Scale
set image deploy/web web=nginx:1.28Roll out

⚠ Common Mistakes

  • Editing a ConfigMap and expecting a restart — rollout restart
  • No readiness probe — rollout "succeeds" before pods work
  • maxUnavailable: 0 on a full cluster — surge pods stay Pending
  • Treating rollout undo as a fix — Git still has the bad version

✓ Tips & Best Practices

  • Gate CI on rollout status --timeout=5m
  • Recreate when two versions can't coexist
  • After undo, fix the manifest in Git too
  • Pair with a PodDisruptionBudget for node drains (Sheet 19)

Quick Summary

  • Deployment → ReplicaSet → Pods
  • maxSurge / maxUnavailable — speed vs capacity
  • rollout status / undo / restart
  • template change — rollout; replicas — scale only
