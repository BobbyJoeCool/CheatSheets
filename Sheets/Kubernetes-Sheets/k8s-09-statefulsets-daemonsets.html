Sheet 09

StatefulSets & DaemonSets

stable pod names · headless Service · volumeClaimTemplates · podManagementPolicy · DaemonSet · partition

Identity and Per-Node Workloads

A StatefulSet gives each pod a stable name (db-0, db-1), a stable DNS entry via a headless Service, and its own PVC that follows it across reschedules. Pods start in order and stop in reverse. A DaemonSet runs exactly one pod per node (or per matching node): log shippers, metrics agents, CNI and storage drivers.

Notes

  • StatefulSets don't make an app clustered; the app must handle its own replication
  • PVCs from volumeClaimTemplates survive scale-down and deletion by default
  • DaemonSets ignore replicas; new nodes get a pod automatically

StatefulSet

apiVersion: apps/v1
kind: StatefulSet
metadata: { name: db }
spec:
  serviceName: db                  # headless Service (clusterIP: None)
  replicas: 3                      # db-0, db-1, db-2, created in order
  podManagementPolicy: OrderedReady    # or Parallel
  updateStrategy: { rollingUpdate: { partition: 0 } }
  selector: { matchLabels: { app: db } }
  template: { ... }                # container mounts volume "data"
  volumeClaimTemplates:            # one PVC per pod: data-db-0 …
    - metadata: { name: data }
      spec:
        accessModes: [ReadWriteOnce]
        resources: { requests: { storage: 10Gi } }

DaemonSet

apiVersion: apps/v1
kind: DaemonSet
metadata: { name: node-exporter, namespace: monitoring }
spec:
  selector: { matchLabels: { app: node-exporter } }
  template: { ... }                # + nodeSelector / tolerations

Code Explained

serviceName — gives pods DNS like db-0.db.shop.svc.cluster.local
OrderedReady — db-1 waits for db-0 to be Ready; Parallel doesn't
partition: 2 — only pods with ordinal ≥ 2 update (canary)
volumeClaimTemplates — PVC named <tmpl>-<pod>
maxUnavailable — DaemonSet pods replaced per step
nodeSelector — limit a DaemonSet to some nodes

⚠ Common Mistakes

  • Forgetting the headless Service — stable pod DNS names don't resolve
  • Expecting PVCs to vanish on scale-down — they stay (and keep billing)
  • Scaling a database StatefulSet and assuming data replicates by itself

✓ Tips & Best Practices

  • Use an operator (CloudNativePG, Strimzi) for serious databases
  • Set persistentVolumeClaimRetentionPolicy to control PVC cleanup
  • Parallel speeds up apps that don't need ordering

Quick Summary

  • StatefulSet — stable names, ordered, PVC per pod
  • serviceName — headless Service for pod DNS
  • partition — staged rollouts
  • DaemonSet — one pod per node
