Writing Markdown Well

Good Markdown reads cleanly as plain text and renders correctly everywhere. Use a predictable structure: one H1, headings that never skip levels, blank lines around every block, and fenced code with a language. Write for accessibility: meaningful alt text, descriptive link text and real table headers. Most rendering bugs come from a small set of pitfalls, listed below.

House Style

  • One sentence per line → small, readable diffs
  • - for bullets, */** for emphasis, --- for rules
  • Lowercase, hyphenated file names: getting-started.md

A Clean Document

# Deploy Guide

What this covers and who it's for, in one or two lines.

## Prerequisites

- Node.js 20 or later
- Access to the `prod` cluster

## Steps

1. Build the image.
2. Push it to the registry.
3. Run the deploy script:

   ```bash
   ./deploy.sh --env prod
   ```

See [Rollback](#rollback) if anything fails.

⚠ Common Mistakes

  • Writing for one renderer and publishing to another — extensions show up as raw text
  • Skipping blank lines "because it worked in preview" — stricter parsers break
  • Images without alt text and links reading "here"
  • Hard-wrapping lines at 80 characters — every edit rewraps and bloats diffs

✓ Tips & Best Practices

  • Add markdownlint + a link checker to CI
  • Keep a short style guide in CONTRIBUTING.md
  • Prefer plain Markdown; use HTML only where Markdown has no syntax
  • Re-read the raw file — if it's hard to read, simplify
