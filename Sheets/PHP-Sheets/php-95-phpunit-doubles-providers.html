PHPUnit — Data Providers & Test Doubles

#[DataProvider] · createMock() · createStub() · expects() · willReturn() · code coverage

Many Inputs, Fake Collaborators

A data provider feeds many input/expected pairs into one test method, so you write the logic once. Providers are public static methods referenced with #[DataProvider('name')]. Test doubles replace real dependencies: a stub returns canned values (createStub()), a mock also verifies how it was called (createMock() + expects()). Mock interfaces, not concrete classes.

Notes

  • Name provider rows with string keys for readable failures
  • final classes can't be doubled — depend on interfaces
  • Don't mock what you don't own; wrap third-party APIs
  • Coverage needs Xdebug or PCOV
  • #[CoversClass(Cart::class)] scopes coverage

Providers and Doubles

<?php
use PHPUnit\Framework\Attributes\DataProvider;
use PHPUnit\Framework\TestCase;

final class SlugTest extends TestCase
{
    public static function slugs(): array
    {
        return [
            'spaces'  => ['Hello World', 'hello-world'],
            'symbols' => ['PHP & You!', 'php-you'],
            'trim'    => ['  x  ', 'x'],
        ];
    }

    #[DataProvider('slugs')]
    public function testSlugify(string $in, string $out): void
    {
        $this->assertSame($out, slugify($in));
    }

    public function testSendsWelcomeMail(): void
    {
        $mailer = $this->createMock(Mailer::class);    // interface
        $mailer->expects($this->once())
               ->method('send')
               ->with('ana@x.io', $this->stringContains('Welcome'))
               ->willReturn(true);

        (new Signup($mailer))->register('ana@x.io');
    }
}

Code Explained

Provider is public static and returns rows of arguments
Row keys appear in failure messages
Each row runs as a separate test
createMock + expects(once()) verifies the call
with() constrains arguments; willReturn() sets the result

⚠ Common Mistakes

  • Non-static data providers (PHPUnit 10+ requires static)
  • Mocking value objects or the class under test
  • Over-specifying calls so refactors break tests

✓ Tips & Best Practices

  • Prefer simple fakes over complex mock setups
  • Use providers for edge-case tables
  • Mock interfaces at architectural boundaries

Quick Summary

  • #[DataProvider] + static method
  • Stubs return, mocks verify
  • Mock interfaces
  • Coverage via Xdebug/PCOV
