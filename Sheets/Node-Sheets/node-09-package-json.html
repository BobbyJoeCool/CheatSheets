The Project Manifest

package.json describes a project: its name and version, its dependencies, the scripts you run, and how other code may import it. Node itself reads only a few fields ("type", "exports", "imports", "main"); npm and other tools read the rest. Create one with npm init -y.

Notes

  • Must be valid JSON: no comments, no trailing commas
  • "exports" wins over "main" and blocks unlisted paths
  • "private": true prevents accidental npm publish
  • Set fields from the CLI: npm pkg set type=module

A Typical package.json

{
  "name": "@acme/notes-api",
  "version": "1.4.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./src/index.js", "./client": "./src/client.js" },
  "imports": { "#db/*": "./src/db/*.js" },
  "bin": { "notes": "./bin/cli.js" },
  "scripts": {
    "dev": "node --watch --env-file=.env src/server.js",
    "start": "node src/server.js",
    "test": "node --test"
  },
  "engines": { "node": ">=24" },
  "dependencies": { "fastify": "^5.2.0" },
  "devDependencies": { "typescript": "~5.9.0" }
}

Code Explained

@acme/ — a scoped package name
exports — public entry points; import '@acme/notes-api/client'
imports — private aliases: import db from '#db/users'
bin — commands installed on PATH
engines — supported Node range
devDependencies — not installed with --omit=dev

Common Mistakes

  • Adding "exports" without listing subpaths users import; they get ERR_PACKAGE_PATH_NOT_EXPORTED
  • Putting runtime packages in devDependencies; production installs omit them
  • Editing versions by hand and not updating the lockfile; run npm install after

Tips

  • Use "imports" #aliases instead of long ../../ paths
  • Read fields from code with import pkg from './package.json' with { type: 'json' }
  • Expose "./package.json" in "exports" for tools that read it

Summary

  • type — ESM or CJS for .js
  • exports — public entry points
  • imports — internal # aliases
  • scripts — named project commands
