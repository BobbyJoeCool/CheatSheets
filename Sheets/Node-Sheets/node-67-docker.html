Containerizing a Node App

A good Node image installs only production dependencies from the lockfile, runs as the non-root node user, and starts node directly so signals reach your shutdown handler. A multi-stage build keeps build tools and dev dependencies out of the final image, and copying package*.json before the source lets Docker cache the install layer.

Notes

  • Official images include a node user (uid 1000)
  • -slim is Debian with fewer packages; good default
  • Alpine uses musl libc; some native modules misbehave

Multi-Stage Dockerfile

FROM node:26-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

FROM node:26-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:26-slim
ENV NODE_ENV=production
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY package.json ./
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]

Code Explained

deps stage — production-only node_modules
build stage — dev deps for TS / bundling, then discarded
COPY package*.json first — install layer is cached
USER node — don't run as root
Exec-form CMD [...] — node is PID 1 and gets SIGTERM

Common Mistakes

  • CMD npm start; npm may not forward SIGTERM, so shutdown hangs then gets killed
  • COPY . . before npm ci; every code change reinstalls dependencies
  • Copying a local node_modules built for macOS into a Linux image

Tips

  • Add HEALTHCHECK or rely on your orchestrator's probes
  • Scan images with docker scout or Trivy
  • Set memory limits and size --max-old-space-size to match (Sheet 54)

Summary

  • multi-stage — small final image
  • npm ci --omit=dev — production deps only
  • USER node — non-root
  • CMD ["node", …] — signals work
