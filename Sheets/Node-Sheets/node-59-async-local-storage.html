Request Context Without Parameters

AsyncLocalStorage stores a value that follows one logical operation through every await, callback, and timer it triggers, like thread-local storage for async code. Start a context with run(store, fn); anything that runs inside, however deep, reads it with getStore(). The classic use is a request ID in every log line without passing it through every function.

Notes

  • Each concurrent request gets its own store
  • getStore() returns undefined outside a run()
  • Many tracing and logging libraries use it internally

A Request ID in Every Log

import { AsyncLocalStorage } from 'node:async_hooks';
import { randomUUID } from 'node:crypto';
import { createServer } from 'node:http';

const ctx = new AsyncLocalStorage();

function log(msg) {
  const id = ctx.getStore()?.requestId ?? '-';
  console.log(`[${id}] ${msg}`);
}

async function loadUser(id) {
  log(`loading user ${id}`);                    // no requestId parameter
  await new Promise((r) => setTimeout(r, 10));
  log('loaded');                                // still the same request
}

createServer((req, res) => {
  const requestId = req.headers['x-request-id'] ?? randomUUID();
  ctx.run({ requestId }, async () => {
    await loadUser(7);                          // [3f2c…] loading user 7
    res.end('ok');
  });
}).listen(3000);

Code Explained

One instance — create at module level, share it
run(store, fn) — store is visible inside fn and its async work
?. — handles code that runs outside a request
x-request-id — reuse the ID from a proxy if present

Common Mistakes

  • Creating a new AsyncLocalStorage per request; nothing else can see it
  • Storing a primitive and expecting to update it; store an object and mutate its fields
  • Using enterWith in shared code; context leaks into unrelated work

Tips

  • Wrap it in a tiny module: getRequestId(), withContext()
  • Add the store to logger child bindings automatically (Sheet 65)
  • Keep stores small; they live as long as the async work
