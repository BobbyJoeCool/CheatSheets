Uncaught Errors & Rejections

uncaughtException · unhandledRejection · --unhandled-rejections · crash-and-restart design · error in streams / emitters

When Errors Escape

An error nobody catches emits 'uncaughtException'; a rejected promise nobody handles emits 'unhandledRejection'. Both crash the process by default, which is correct: after an unknown error, the app's state can't be trusted. Use these handlers only to log and exit, and let a supervisor (Docker, systemd, Kubernetes, PM2) start a fresh process.

Notes

  • Without a handler: stack trace to stderr, exit code 1
  • origin tells you whether it came from a rejection
  • Errors thrown inside callbacks can't be caught by an outer try

Last-Resort Handlers

process.on('uncaughtException', (err, origin) => {
  logger.fatal({ err, origin }, 'uncaught exception');
  process.exitCode = 1;
  setTimeout(() => process.exit(1), 1000).unref();   // let logs flush
});

process.on('unhandledRejection', (reason) => {
  throw reason;                     // turn it into an uncaughtException
});

// Where escaped errors come from:
setTimeout(() => { throw new Error('boom'); });     // no caller to catch it
emitter.emit('error', new Error('x'));              // no 'error' listener
async function save() { throw new Error('db down'); }
save();                                             // no await, no .catch()
stream.pipe(dest);                           // pipe errors aren't forwarded

try {
  setTimeout(() => { throw new Error('nope'); });   // ✖ try can't catch this
} catch {}

Code Explained

logger.fatal — log with full stack before dying
exit after a delay — gives async log transports time
throw reason — one code path for both kinds
save() without await — a floating promise
try only catches errors on the current call stack

Common Mistakes

  • Logging in uncaughtException and continuing to serve requests; resources may be half-open or corrupted
  • process.on('unhandledRejection', () => {}) to hide warnings; real failures go silent
  • Relying on the handler instead of fixing the floating promise it reported

Tips

  • Turn on no-floating-promises in typescript-eslint
  • Send fatal errors to your error tracker (Sentry, etc.) before exit
  • Test crash behavior: make sure your container actually restarts

Summary

  • uncaughtException — last chance to log
  • unhandledRejection — floating promise failed
  • log + exit — the only safe response
  • supervisor — restarts the process
