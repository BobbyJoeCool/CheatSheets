Handling Query Errors

Prisma throws typed error classes from the Prisma namespace. Database-level failures arrive as PrismaClientKnownRequestError with a stable code (e.g. P2002) and a meta object. Check the class with instanceof, branch on code, and translate it into a domain error or HTTP status at one boundary.

Notes

  • Import Prisma from your generated client
  • meta shape can vary by driver adapter
  • …OrThrow → P2025 when not found
  • Validation errors = bug in your query shape

Catching & Mapping Errors

import { Prisma } from "../generated/prisma/client";

export async function createUser(email: string) {
  try {
    return await prisma.user.create({ data: { email } });
  } catch (e) {
    if (e instanceof Prisma.PrismaClientKnownRequestError) {
      switch (e.code) {
        case "P2002": throw new ConflictError(`Duplicate: ${e.meta?.target}`);
        case "P2003": throw new BadRequestError("Related record missing");
        case "P2025": throw new NotFoundError();
      }
    }
    if (e instanceof Prisma.PrismaClientValidationError) {
      throw new BadRequestError("Invalid query input");
    }
    throw e;                                       // unknown → 500
  }
}

⚠ Common Mistakes

  • e.code without instanceof — e is unknown
  • Leaking raw Prisma messages to clients — exposes schema
  • Swallowing errors with an empty catch
  • Retrying P2002 — it will keep failing

✓ Tips & Best Practices

  • Map errors once in middleware, not in every handler
  • Retry only transient codes: P2034, P1001
  • Validate input (Zod) before querying — Sheet 29
  • Log code, meta, and the model with each error

Quick Summary

  • KnownRequestError + code — branch
  • P2002 409 · P2025 404 · P2003 400
  • …OrThrow — explicit not-found
  • retry transient errors only
