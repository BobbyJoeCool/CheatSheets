Indexes & Constraints

Indexes speed up where, orderBy, and joins but slow writes. Use @@index for plain indexes, @@unique for unique constraints, and @@id for composite keys. Composite indexes follow the leftmost-prefix rule: [tenantId, createdAt] serves tenantId alone or both, not createdAt alone.

Notes

  • Unique fields become findUnique keys
  • Compound key name: tenantId_slug
  • name: renames key · map: DB name
  • Ship index changes via migrations

schema.prisma

model Article {
  id        Int      @id @default(autoincrement())
  tenantId  Int
  slug      String   @db.VarChar(120)
  body      String   @db.Text
  status    Status   @default(DRAFT)
  meta      Json     @db.JsonB
  createdAt DateTime @default(now()) @db.Timestamptz(6)

  @@unique([tenantId, slug])
  @@index([tenantId, status, createdAt(sort: Desc)])
  @@index([meta], type: Gin)
}
model Enrollment {
  studentId Int
  courseId  Int
  @@id([studentId, courseId])
}

Code Explained

@db.VarChar(120) — DB length limit
@@unique([...]) — unique per tenant
sort: Desc — matches newest-first sorts
type: Gin — JSON/array containment
@@id — composite PK
tenantId_slug — compound key input

⚠ Common Mistakes

  • Indexing every column — slower writes, wasted disk
  • Wrong composite order — [createdAt, tenantId] won't serve tenantId
  • Shrinking VarChar(n) — fails if data is longer
  • Missing FK indexes — cascades scan whole tables

✓ Tips & Best Practices

  • Confirm usage with EXPLAIN ANALYZE via $queryRaw
  • Use map: to keep index names stable
  • Match index sort order to your hot orderBy
  • @@unique on join models blocks duplicate links

Quick Summary

  • @@index — faster filters and sorts
  • @@unique — uniqueness + a_b key
  • @@id — composite primary key
  • @db.* — exact native type
