Migration Strategies

expand-contract · --create-only · backfill · CONCURRENTLY · rollback · backups

Zero-Downtime Schema Changes

During a rolling deploy, old and new app versions run against the same database. Every migration must therefore be backward compatible with the running code. Use expand → migrate → contract: add new structures, backfill and dual-write, switch reads, and only then remove the old structures in a later deploy.

Notes

  • Prisma has no down migrations
  • Rollback = new forward migration
  • Back up before migrate deploy
  • Renames look like drop + add — edit SQL

Rename a Column Safely (expand → contract)

-- Deploy 1 · expand: add nullable column
ALTER TABLE "User" ADD COLUMN "fullName" TEXT;
-- app writes BOTH name and fullName, reads name

-- Deploy 2 · backfill in batches (script or SQL)
UPDATE "User" SET "fullName" = "name"
WHERE "fullName" IS NULL AND id BETWEEN 1 AND 10000;
-- app reads fullName, still writes both

-- Deploy 3 · contract: enforce + drop old column
ALTER TABLE "User" ALTER COLUMN "fullName" SET NOT NULL;
ALTER TABLE "User" DROP COLUMN "name";

-- Simple rename (needs code + DB in one step):
-- prisma migrate dev --create-only, then replace DROP/ADD with:
ALTER TABLE "User" RENAME COLUMN "name" TO "fullName";

-- Large Postgres table: build index without blocking writes
CREATE INDEX CONCURRENTLY "User_email_idx" ON "User"("email");

Code Explained

expand — additive, old code unaffected
dual-write — both columns stay in sync
batched backfill — avoid long locks
contract — only after no code uses name
--create-only — edit SQL before apply
RENAME — keeps data (Prisma would drop)
CONCURRENTLY — keep in its own migration

⚠ Common Mistakes

  • Renaming a field in the schema — Prisma drops and re-adds the column
  • Dropping a column in the same deploy that stops using it
  • One huge UPDATE backfill — long locks, replication lag
  • Editing applied migrations to "fix" production

✓ Tips & Best Practices

  • Practice the deploy on a copy of production data
  • Set a lock_timeout in risky migration SQL
  • Keep contract steps in a separate, later release
  • Automate migrate deploy in CI before app rollout

Quick Summary

  • expand → migrate → contract — zero downtime
  • --create-only — hand-edit SQL
  • backups + migrate status — before deploy
  • rollback — forward-fix migration
