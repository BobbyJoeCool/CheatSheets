Securing Data Access

Prisma's query API and tagged-template raw queries are parameterized, so injection risk comes from …Unsafe methods and Prisma.raw. The bigger risks are authorization (users reading other users' rows) and over-exposure (returning secrets). Scope every query by owner or tenant, strip sensitive fields, encrypt connections, and give the app a least-privilege database user.

Notes

  • Prisma has no built-in authorization
  • Postgres RLS needs per-tx set_config
  • Encryption at rest = DB/provider setting
  • Field-level crypto via an extension

Scoping, Masking & RLS

// tenant/owner scoping for every query
export const forTenant = (tenantId: number) =>
  prisma.$extends({ query: { $allModels: {
    async $allOperations({ args, query }) {
      if ("where" in args) args.where = { ...args.where, tenantId };
      return query(args);
    },
  } } });

// never return secrets
const prisma = new PrismaClient({
  adapter, omit: { user: { password: true, totpSecret: true } },
});

// Postgres row-level security: set the session user inside the tx
await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SELECT set_config('app.user_id', ${String(userId)}, true)`;
  return tx.invoice.findMany();           // RLS policy filters rows
});

// ✖ injectable           ✔ parameterized
prisma.$queryRawUnsafe(`SELECT * FROM users WHERE email = '${email}'`);
prisma.$queryRaw`SELECT * FROM users WHERE email = ${email}`;

Code Explained

$allOperations — inject tenantId
"where" in args — skip creates
omit — secrets hidden by default
set_config(…, true) — tx-local setting
RLS policy reads current_setting
…Unsafe + interpolation — injectable
tagged template — always bound

⚠ Common Mistakes

  • findUnique({ where: { id } }) with no owner check — IDOR
  • Passing req.body straight into data — mass assignment
  • Logging query params in production — leaks PII
  • Using the migration (DDL) user at runtime

✓ Tips & Best Practices

  • Add tenantId to compound uniques: @@unique([tenantId, id])
  • Hash passwords (argon2/bcrypt) before create
  • Allow-list sortable/filterable fields from query strings
  • Run npm audit and keep Prisma updated

Quick Summary

  • parameterized queries — no string SQL
  • scope by owner/tenant — authorization
  • omit / select — minimal exposure
  • TLS + least-privilege DB users
