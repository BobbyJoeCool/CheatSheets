Production-Ready Prisma

Keep Prisma behind a thin data-access layer: one client instance, query shapes defined once, errors mapped once, and services that never leak Prisma types to HTTP responses. Split large schemas into multiple .prisma files by domain, and keep naming consistent so the generated API reads naturally.

Naming

  • Model: PascalCase singular · field: camelCase
  • FK: authorId next to author
  • Booleans: isActive, hasPaid
  • Enums: PascalCase; values UPPER_CASE

Repository Pattern

// user.repo.ts
export const publicUser = {
  select: { id: true, email: true, name: true, createdAt: true },
} satisfies Prisma.UserDefaultArgs;
export type PublicUser = Prisma.UserGetPayload<typeof publicUser>;

export const userRepo = {
  byId: (id: number) =>
    db.user.findUnique({ where: { id }, ...publicUser }),
  list: (cursor?: number, take = 20) =>
    db.user.findMany({
      ...publicUser, take,
      ...(cursor && { skip: 1, cursor: { id: cursor } }),
      orderBy: { id: "desc" },
    }),
  create: (data: Prisma.UserCreateInput) =>
    db.user.create({ data, ...publicUser }),
};

⚠ Common Mistakes

  • Prisma calls scattered through controllers — hard to change
  • Returning Prisma models directly — leaks new columns
  • One giant schema.prisma in big apps — merge conflicts
  • Inconsistent names (user_id vs authorId) — confusing API

✓ Tips & Best Practices

  • Keep transactions in services, queries in repos
  • Export typeof db as the app's DB type
  • Use @@map to keep DB snake_case with camelCase code
  • Review generated SQL for hot paths before launch

Quick Summary

  • one client + $extends — single entry point
  • shapes + GetPayload — consistent responses
  • multi-file schema — organize by domain
  • repo → service → route — clear layers
