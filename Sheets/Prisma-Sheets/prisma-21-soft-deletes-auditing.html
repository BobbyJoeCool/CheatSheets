Recoverable Deletes & Change History

A soft delete marks a row with a deletedAt timestamp instead of removing it, so it can be restored and audited. An audit log records who changed what and when. A query extension ($extends) can apply both automatically so individual queries don't have to remember.

Notes

  • Unique columns still collide with soft-deleted rows
  • Cascades don't run on soft delete
  • Extensions don't cover $queryRaw
  • Audit inside the same transaction

Soft-Delete Extension + Audit Write

export const db = prisma.$extends({
  query: {
    user: {
      async findMany({ args, query }) {
        args.where = { deletedAt: null, ...args.where };   // hide deleted
        return query(args);
      },
      async delete({ args }) {                             // delete → update
        return prisma.user.update({ where: args.where, data: { deletedAt: new Date() } });
      },
    },
  },
});
await db.user.delete({ where: { id: 5 } });                // soft delete
await prisma.user.update({ where: { id: 5 }, data: { deletedAt: null } }); // restore
await prisma.$transaction(async (tx) => {                  // change + audit
  const after = await tx.post.update({ where: { id: 9 }, data: { title: "New" } });
  await tx.auditLog.create({
    data: { model: "Post", recordId: 9, action: "UPDATE", actorId: me.id, after } });
});

Code Explained

$extends({ query }) — intercept queries
spread args.where — caller can override
delete → update — sets deletedAt
deletedAt: null — restore the row
$transaction — change + log together
after (and before) — Json snapshots
actorId — who made the change

Schema

model User {
  id        Int       @id @default(autoincrement())
  deletedAt DateTime?           // null = active
  updatedAt DateTime  @updatedAt
  @@index([deletedAt])
}
model AuditLog {
  id       Int      @id @default(autoincrement())
  model    String   // "Post"
  recordId Int
  action   String          // CREATE | UPDATE | DELETE
  actorId  Int?                 // who
  before   Json?
  after    Json?
  at       DateTime @default(now())
}

⚠ Common Mistakes

  • @unique email blocks re-signup after soft delete
  • Filtering only findMany — count still sees deleted rows
  • Writing audit rows outside the transaction — logs can lie

✓ Tips & Best Practices

  • Use a partial unique index (raw SQL migration) for active rows
  • Keep a base client for admin/purge paths
  • Index deletedAt or put it first in composite indexes
  • Strip secrets before saving audit snapshots

Quick Summary

  • deletedAt — soft delete marker
  • $extends query — automatic filtering
  • restore — set deletedAt: null
  • AuditLog — model, recordId, action, before/after
