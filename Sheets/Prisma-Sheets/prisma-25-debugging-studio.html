Debugging & Studio

prisma studio · log · $on('query') · DEBUG · prisma validate · prisma debug

Seeing What Prisma Does

Prisma Studio is a local GUI for browsing and editing data (npx prisma studio, port 5555). For code, enable query logging to see the SQL, parameters, and duration of each query, and use the DEBUG environment variable for internal client/CLI logs. CLI commands like validate and debug catch configuration problems before runtime.

Notes

  • Studio edits real data — careful on prod
  • log: ['query'] prints to stdout
  • emit: 'event' → handle with $on
  • Params are logged separately from SQL

Logging & Inspection

const prisma = new PrismaClient({
  adapter,
  log: [
    { emit: "event", level: "query" },
    { emit: "stdout", level: "warn" },
    { emit: "stdout", level: "error" },
  ],
});

prisma.$on("query", (e) => {
  console.log(`${e.duration}ms ${e.query}`);   // SELECT … WHERE "id" = $1
  console.log("params:", e.params);             // ["42"]
});

// time + label every operation (extension)
const traced = prisma.$extends({ query: {
  async $allOperations({ model, operation, args, query }) {
    console.time(`${model}.${operation}`);
    try { return await query(args); }
    finally { console.timeEnd(`${model}.${operation}`); }
  },
} });

Code Explained

emit: 'event' — route logs to $on
emit: 'stdout' — print directly
e.query — generated SQL
e.params — bound values
e.duration — milliseconds
$allOperations — per-op timing

⚠ Common Mistakes

  • Logging query events in production — noisy, may leak data
  • Reading e.query without e.params — values look missing
  • Running Studio against production casually
  • Debugging stale types — rerun prisma generate first

✓ Tips & Best Practices

  • Log only queries slower than a threshold in production
  • Add tracing with @prisma/instrumentation + OpenTelemetry
  • Use Studio to verify seeds and migrations locally
  • Paste slow SQL into EXPLAIN ANALYZE
