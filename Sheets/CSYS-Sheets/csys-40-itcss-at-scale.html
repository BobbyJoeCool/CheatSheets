ITCSS at Scale

At scale, ITCSS needs additional conventions to remain maintainable. Key concerns are: design token management (keeping settings in sync with design tools), team conventions (naming, where new things go), linting (enforcing layer rules automatically), and documentation (keeping a living style guide). These practices prevent the architecture from degrading over time as teams grow and codebases expand.

Scaling Concerns

  • Design tokens should live in settings and never be duplicated in components
  • Use Stylelint to enforce import order and naming conventions
  • Document each object and component with usage examples
  • Define a decision tree: "Where does this new CSS go?"
  • Use CSS @layer to make layer boundaries explicit and browser-enforced
  • Design token pipeline: Figma tokens → Style Dictionary → settings layer

⚠ Common Mistakes

  • Hardcoding values in Components that duplicate Settings — creates drift between design tokens and actual usage
  • Allowing ad-hoc utility classes to be added to components layer — utilities must stay in their own layer or specificity order breaks
  • Not documenting the architecture — new team members default to wherever seems convenient without a decision tree or ADR

✓ Tips

  • Write an Architecture Decision Record (ADR) for CSS layer rules — formalize what goes where so decisions are documented
  • Use a living style guide (Storybook, Fractal) tied to the components layer — keeps documentation and implementation in sync
  • Add a CI step that lints CSS naming conventions — enforces o-/c-/u- prefixes automatically

Summary

  • Decision tree — tells every team member where new CSS belongs
  • Stylelint rules — automate naming and specificity conventions
  • Token pipeline — Figma → Style Dictionary → Settings layer
  • ADR + living style guide — prevent architectural decay as team grows
