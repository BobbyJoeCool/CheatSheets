Framework Integration Patterns

Every major build tool and framework handles CSS systems slightly differently. Understanding the integration points — where config goes, what gets auto-detected, and what needs explicit configuration — saves significant setup time. This sheet is a quick reference for the most common framework/tool combinations across the CSS systems covered in this binder.

Integration Rules of Thumb

  • PostCSS config is auto-detected from project root in Vite, Next.js, and Parcel
  • Sass requires npm install -D sass — the runtime; no additional loader config in Vite
  • CSS Modules work by naming files *.module.css in all major tools
  • Tailwind requires postcss.config.js with the Tailwind plugin
  • Component frameworks (Bootstrap/Bulma) can use CDN or npm + Sass override

⚠ Common Mistakes

  • Adding PostCSS config after installing Tailwind but forgetting to restart the dev server — config changes require a restart
  • In Next.js: importing global CSS in non-_app.js files — only _app.js or layout.js can import global stylesheets
  • Styled-components SSR in Next.js without the Babel/SWC plugin — causes hydration mismatches and FOUC

✓ Tips

  • Check the official integration docs for each framework — they update frequently and often have one-command setup
  • Vite's CSS preprocessing is synchronous and fast — prefer Vite for CSS-heavy projects where build speed matters
  • Use CSS Modules as the default in server-component-heavy apps (Next.js App Router) — they have zero runtime overhead

Summary

  • Vite: sass + CSS Modules auto-detected; PostCSS via postcss.config.js
  • Next.js: Sass + CSS Modules built-in; Tailwind via postcss.config.js
  • CSS Modules work everywhere with *.module.css naming convention
  • styled-components SSR requires explicit plugin/config in every framework
