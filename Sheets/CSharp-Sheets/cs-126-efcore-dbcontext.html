EF Core — DbContext & Setup

DbContext · DbSet<T> · AddDbContext · providers (SQL Server, PostgreSQL, SQLite) · connection strings · dotnet ef

Getting Started with EF Core

Entity Framework Core is .NET's object-relational mapper: you work with C# classes and LINQ, and EF Core translates to SQL for SQL Server, PostgreSQL, SQLite, MySQL and more. A DbContext represents a session with the database and exposes a DbSet<T> per table. Register it with DI and configure the provider and connection string.

Key Facts

  • EF Core 10 ships with .NET 10 (LTS)
  • One provider package per database
  • DbContext is not thread-safe; register it scoped
  • dotnet-ef CLI tool manages migrations

DbContext & Registration

// packages: Microsoft.EntityFrameworkCore.Sqlite (+ .Design); tool: dotnet-ef

public class Blog
{
    public int Id { get; set; }                     // primary key by convention
    public required string Title { get; set; }
    public List<Post> Posts { get; } = [];              // navigation
}
public class Post
{ public int Id { get; set; } public int BlogId { get; set; } }

public class AppDb(DbContextOptions<AppDb> options) : DbContext(options)
{
    public DbSet<Blog> Blogs => Set<Blog>();
    public DbSet<Post> Posts => Set<Post>();
}

// appsettings.json: "ConnectionStrings": { "Default": "Data Source=app.db" }
builder.Services.AddDbContext<AppDb>(o =>
    o.UseSqlite(builder.Configuration.GetConnectionString("Default")));

⚠ Common Mistakes

  • Registering DbContext as a singleton — not thread-safe and grows its change tracker forever
  • Hard-coding connection strings — keep them in configuration / secrets
  • Using the in-memory provider to test SQL behavior — it isn't relational; use SQLite or Testcontainers

✓ Tips & Best Practices

  • Use IDbContextFactory<T> in background services and Blazor
  • Log SQL in development to learn what EF generates
  • Keep entities simple; put rules in services or the domain
