Handling Exceptions

Code that might fail goes in a try block. If an exception is thrown, the runtime looks for the first matching catch (checked top to bottom), and a finally block runs no matter what — success, exception or return. Unhandled exceptions bubble up the call stack and terminate the program.

Key Facts

  • All exceptions derive from System.Exception
  • Order catches from most specific to most general
  • finally runs even after return inside try
  • catch without a type catches everything

try / catch / finally

try
{
    string text = File.ReadAllText("config.json");
    int port = int.Parse(text);
    Console.WriteLine($"Port {port}");
}
catch (FileNotFoundException ex)              // most specific first
{
    Console.WriteLine($"Missing file: {ex.FileName}");
}
catch (FormatException)                       // no variable needed
{
    Console.WriteLine("Config is not a number");
}
catch (Exception ex)                          // everything else
{
    Console.WriteLine($"{ex.GetType().Name}: {ex.Message}");
    throw;                                    // rethrow, keep stack
}
finally
{
    Console.WriteLine("Done");                // always runs
}

Code Explained

try — code that may throw
catch (T ex) — handles T and subclasses
Omit the variable when you don't use it
catch (Exception) — last-resort handler
throw; — rethrow after logging
finally — cleanup that must always happen

What Runs When

ScenarioBlocks Executed

⚠ Common Mistakes

  • Catching Exception first — later specific catches are unreachable (CS0160)
  • Empty catch { } blocks — failures vanish silently; at least log
  • Using exceptions for normal control flow — use TryParse / TryGetValue patterns

✓ Tips & Best Practices

  • Catch only what you can handle; let the rest bubble up
  • Log ex.ToString(), not just ex.Message
  • Prefer using over finally for disposing resources

Quick Summary

  • try — guarded code
  • catch (T ex) — handle specific types
  • finally — always runs
  • throw; — rethrow preserving the stack
