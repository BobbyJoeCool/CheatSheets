Closures & Captured Variables

captured variables · lifetime extension · loop capture gotcha · static lambda prevents capture · closure allocations

Capturing Variables

When a lambda or local function uses a variable from its surrounding method, it captures the variable itself, not a copy of its value. The compiler moves captured variables into a hidden class so they outlive the method. Later changes are visible to the lambda, which is powerful — and the source of the classic for-loop bug.

Key Facts

  • Captured = shared variable, not a snapshot
  • foreach creates a fresh variable each iteration (C# 5+)
  • for uses one variable for all iterations
  • Captures allocate a closure object

Closures

int counter = 0;
Action increment = () => counter++;       // captures counter
increment(); increment();
Console.WriteLine(counter);               // 2

Func<int> MakeCounter()
{
    int count = 0;                        // lives on after return
    return () => ++count;
}
var next = MakeCounter();
Console.WriteLine($"{next()} {next()}");   // 1 2
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
    actions.Add(() => Console.Write(i));  // all share one i
actions.ForEach(a => a());                // 333  ✗
for (int i = 0; i < 3; i++)
{
    int copy = i;                         // new variable each pass
    actions.Add(() => Console.Write(copy));
}                                         // 012  ✓

Func<int, int> sq = static x => x * x;    // static: can't capture

Code Explained

Capture — lambda shares counter with the method
MakeCounter — local outlives the call
for capture — every lambda sees the final i (3)
int copy = i — fresh variable per iteration
static lambda — compile error if it captures

Costs & Risks

IssueEffect
Closure allocationHeap object per capture scope
Lifetime extensionObjects kept alive by long-lived lambdas
Event handlers capturing thisMemory leaks if not removed
Shared mutable stateRace conditions across threads

⚠ Common Mistakes

  • Capturing a for loop counter and running the lambdas later — they all see the last value
  • Capturing large objects in long-lived callbacks — they can't be garbage-collected
  • Mutating captured variables from parallel tasks — data races; use Interlocked or locks

✓ Tips & Best Practices

  • Use static lambdas to guarantee no hidden captures
  • Copy to a local inside the loop when deferring work
  • Pass state explicitly (e.g. Task.Factory.StartNew(state => …, state)) in hot code

Quick Summary

  • Closures capture variables, not values
  • Captured locals outlive the method
  • for counter is shared; copy it
  • static — forbid captures
