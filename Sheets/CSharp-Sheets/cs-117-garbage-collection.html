Garbage Collection & Finalizers

generations 0/1/2 · Large Object Heap · finalizers ~T() · GC.SuppressFinalize · WeakReference · event-handler leaks

Automatic Memory Management

The garbage collector reclaims objects that are no longer reachable. It's generational: new objects start in Gen 0, survivors move to Gen 1 and Gen 2, and objects ≥ 85 KB go to the Large Object Heap. Most apps never call the GC directly; your job is to avoid leaks (unexpected references) and dispose unmanaged resources.

Key Facts

  • Gen 0 collections are frequent and cheap
  • Finalizers delay collection and run on a separate thread
  • Static references and event subscriptions keep objects alive
  • Server GC is the default for ASP.NET Core

GC in Practice

var data = new byte[100];
Console.WriteLine(GC.GetGeneration(data));        // 0
GC.Collect();                                     // don't do this in real apps
Console.WriteLine(GC.GetGeneration(data));        // 1 (survived)

Console.WriteLine(GC.CollectionCount(0));         // # of Gen 0 GCs
public class NativeBuffer : IDisposable
{
    private IntPtr _ptr = Marshal.AllocHGlobal(1024);
    public void Dispose() { Free(); GC.SuppressFinalize(this); }
    ~NativeBuffer() => Free();                    // finalizer: last resort
    private void Free()
    {
        if (_ptr == IntPtr.Zero) return;
        Marshal.FreeHGlobal(_ptr); _ptr = IntPtr.Zero;
    }
}

var cache = new ConditionalWeakTable<object, Metadata>();   // no leak
var weak = new WeakReference<BigThing>(new BigThing());
if (weak.TryGetTarget(out var thing)) Use(thing);           // may be collected

Code Explained

GetGeneration — which generation an object is in
GC.Collect — forces a collection (diagnostics only)
Finalizer ~T() — safety net for unmanaged memory
SuppressFinalize — skip finalizer after Dispose
ConditionalWeakTable — attach data without keeping keys alive
WeakReference<T> — reference that allows collection

⚠ Common Mistakes

  • Calling GC.Collect() to "fix" memory — usually hurts performance and hides the real leak
  • Writing finalizers for classes without unmanaged resources — adds overhead for nothing
  • Allocating large temporary arrays repeatedly — fills the LOH; use ArrayPool

✓ Tips & Best Practices

  • Investigate memory with dotnet-counters and dotnet-gcdump
  • Prefer SafeHandle over hand-written finalizers
  • Reduce allocations in hot paths (spans, pooling, structs)

Quick Summary

  • Generational GC — Gen 0/1/2 + LOH
  • Leaks = unwanted references
  • Finalizers — last resort; use SafeHandle
  • Diagnose with dotnet-counters / gcdump
