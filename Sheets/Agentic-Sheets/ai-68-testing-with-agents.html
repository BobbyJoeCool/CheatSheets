Testing with Agents

Tests turn an agent from "looks right" into "is right." The strongest workflow is test-first: have the agent write failing tests for the behavior you want, confirm they fail, lock them, then implement until green. Guard against the agent editing tests to pass, keep test commands fast and documented, and let CI be the final gate.

Test Commands in AGENTS.md

  • Full suite command
  • Single-file / single-test command
  • How to run e2e and what they need (DB, browser)
  • Coverage command and target

Lock Tests, Then Implement

// .claude/settings.json: tests are read-only during implementation
{
  "permissions": {
    "allow": ["Bash(npm test *)", "Bash(npx vitest run *)"],
    "deny":  ["Edit(tests/**)", "Write(tests/**)"]
  },
  "hooks": {
    "Stop": [{ "hooks": [{ "type": "command",
      "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/tests-must-pass.sh" }] }]
  }
}

Code Explained

allow test runs — fast loops without prompts
deny Edit(tests/**) — agent can't weaken tests
Stop hook — block "done" until tests pass
toggle — remove the deny while writing tests

⚠ Common Mistakes

  • Letting the same session write the code and then "verify" it with tests it writes afterwards
  • Accepting tests that mock the very function under test
  • No single-test command, so every check runs the slow full suite
  • Trusting "all tests pass" without seeing the command output

✓ Tips & Best Practices

  • Write and commit failing tests first; then implement in a separate step
  • Ask "what bug would these tests miss?" to find gaps
  • Add characterization tests before letting an agent touch legacy code
  • Make CI required on agent PRs; never bypass it

Quick Summary

  • test-first — failing tests → commit → implement
  • lock tests — deny edits during implementation
  • Stop hook — no "done" while red
  • CI — the final, non-negotiable gate
