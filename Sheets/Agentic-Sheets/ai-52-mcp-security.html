MCP Security

An MCP server is code running with your permissions, and its tool output goes straight into the model's context. That makes two risks: a malicious or compromised server can steal data or act badly, and prompt injection hidden in tool results (an issue body, a web page, a DB row) can try to steer the agent. Treat servers like dependencies and their output like untrusted input.

Threats

  • Tool poisoning: hidden instructions in tool descriptions
  • Prompt injection via fetched content
  • Rug pulls: server changes behavior after approval
  • Over-scoped tokens: one leak, wide damage
  • Data exfiltration through write-capable tools

Dangerous Combinations ("lethal trifecta")

IngredientExampleMitigation
Access to private dataDB, email, private reposScope tokens narrowly
Exposure to untrusted contentWeb pages, public issues, emailsSeparate sessions for untrusted input
Ability to communicate outHTTP, Slack post, PR commentsKeep outbound tools on ask / deny

⚠ Common Mistakes

  • Installing an MCP server from a random repo without reading what its tools do
  • Giving one session private-data tools, untrusted web content, and outbound posting at once
  • Using @latest for local servers, so behavior can change under you
  • Granting a server your personal admin token instead of a scoped service token

✓ Tips & Best Practices

  • Review new or changed tool descriptions; that's where poisoning hides
  • Keep write and outbound tools on ask even in auto modes
  • Use separate sessions for untrusted input (public issues, web research)
  • Centrally manage approved servers in managed settings

Quick Summary

  • server = code — runs with your permissions
  • tool output = untrusted — may contain injection
  • least privilege — scoped tokens, read-only first
  • trifecta — never combine all three freely
