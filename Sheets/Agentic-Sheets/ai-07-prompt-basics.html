Prompt Basics for Coding

A good coding prompt reads like a ticket a senior engineer would be happy to pick up. State the goal, the constraints, where to look, and how you will judge the result. Agents are literal: if you don't say "don't touch the public API" or "add a test", assume they won't. Specific beats long; one clear paragraph usually beats a page of vague hopes.

Prompt Checklist

  • Goal: what should be true when it's done
  • Where: files, functions, or folders involved
  • Constraints: libraries, style, what not to change
  • Verify: the test or command that proves it
  • Pattern: an existing file to copy from

Weak vs Strong Prompt

<!-- Weak -->
fix the login bug

<!-- Strong -->
Users with a + in their email can't log in (see issue #482).
The check is in src/auth/validate.ts, validateEmail().
- Fix the regex so RFC 5322 plus-addressing passes
- Don't change the function signature; it's used in 6 places
- Add cases to src/auth/validate.test.ts for "a+b@x.com"
- Run `npm test -- validate` and make sure it passes
Follow the style of the existing tests in that file.

Why It Works

symptom + issue — tells the agent what "broken" means
file + function — skips a slow repo-wide search
don't change signature — a constraint it would not guess
add test cases — makes the fix verifiable
run command — the agent checks its own work
follow the style — points to a pattern to copy

Useful Phrases

PhraseEffect
"Don't write code yet"Forces investigation or planning first
"Ask me if anything is unclear"Invites clarifying questions
"Keep the change minimal"Reduces drive-by refactors
"Explain your approach first"Lets you veto before edits
"Match the pattern in X"Consistent code style
"Stop and report if tests fail twice"Prevents thrash loops

Avoid

PatternProblem
"Make it better"No definition of done
"Fix all the bugs"Unbounded scope
Ten tasks in one promptSteps get skipped
Only saying what not to doNo positive target
Emotional pressureDoesn't improve output

⚠ Common Mistakes

  • Describing the solution you imagine instead of the problem; the agent can't improve on a bad idea
  • Omitting constraints that live only in your head (perf budgets, API stability, browser support)
  • Asking for a fix with no way to verify it, then discovering it never worked
  • Re-prompting with the same vague words when the first answer misses

✓ Tips & Best Practices

  • Write the prompt as acceptance criteria: bullets the reviewer can tick off
  • Name the test command; agents run it far more reliably when told
  • Reference an existing file as the pattern to follow
  • Put recurring constraints in CLAUDE.md so prompts stay short

Quick Summary

  • goal — what should be true when done
  • where — files and functions to look at
  • constraints — what must not change
  • verify — the command that proves it works
